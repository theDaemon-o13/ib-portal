# Раздел «Уязвимости»: группы, сканы, сроки

Спецификация для реализации. Визуальный и сценарный эталон — `docs/prototype/vulnerabilities-demo.html` (данные в нём демонстрационные, в продукт не переносятся). Правила оценки и сроков из CLAUDE.md, раздел 7 (п. 7.1–7.4), остаются в силе и здесь не повторяются, кроме мест, где они уточняются.

## 1. Зачем

Сейчас уязвимости — один реестр конструктора. Нужна группировка по сервисам и подразделениям: у сервиса есть БД, серверы, веб-приложения, у подразделения — рабочие станции. Отчёт сканера всегда относится к одному такому узлу. Импорт со сравнением и выбором по строкам сохраняется полностью.

Поля реестра и автоматизации в этом этапе не меняются: структура полей одна на весь раздел (по отчёту сканера), в узлах нет кнопок создания реестров и правки полей.

## 2. Структура

```
Уязвимости
├─ Группа (вид: Сервис | Подразделение)      например «Хумо Онлайн», «Отдел платёжных карт»
│  └─ Тип систем (из справочника)            БД, Серверы, Рабочие станции, Сетевое оборудование, Веб-приложения
│     ├─ Реестр       — текущее состояние: одна запись на «Пакет + Идентификатор»
│     └─ Сканы        — итоги сканирования: снимок файла, сравнение с предыдущим, охват
└─ «Без группы» (системная, вид «Временная») — записи прежнего реестра после обновления
```

- **Группа**: название (уникально без учёта регистра), вид, список типов. Создаётся кнопкой «Создать группу»: название, вид, галочки типов (минимум один). Тип добавляется позже кнопкой «Добавить тип». Группу можно переименовать (уникальность та же, запись в журнал); «Без группы» не переименовывается.
- **Узел** = группа × тип систем. Реестр и сканы принадлежат узлу. Один тип в группе — один узел.
- **Справочник «Типы систем»** — новый справочник в существующем механизме справочников (ссылка по id, переименование ничего не ломает).
- **«Без группы»** — системная группа с одним узлом «Из прежнего реестра». Создаётся миграцией/seed, вручную не создаётся и не удаляется, импорт сканов в неё запрещён. Записи переносятся из неё в узлы кнопкой «Перенести» или «Перенести выбранные».
- Удаление групп и узлов в этом этапе не делается.

## 2а. Профили сканирования VM (релиз 1.6.0)

Система VM сканирует по профилям: Scan_Windows, Scan_Linux, Scan_PostgreSQL, Scan_Website, Scan_Docker. Один отчёт — один профиль. Сравнение скана с реестром узла корректно только внутри одного профиля: скан другого профиля не совпадёт по находкам, и всё открытое окажется в «Пропали».

- **Справочник.** Seed один раз добавляет в «Типы систем» Windows, Linux, PostgreSQL, Website, Docker, если их нет (без регистра). Существующие значения не меняются, узлы никуда не переносятся, неиспользуемые старые значения владелец архивирует сам.
- **Профиль из имени файла** (`backend/src/modules/vulns/profiles.ts`, `detectProfile`). Действующее значение справочника или его синоним как отдельное слово, без регистра, можно с префиксом Scan: `Scan_Linux`, `scan-linux`, `…_Linux_2026_10_15.xlsx`. Не нашли или подошли два типа — профиля нет, без угадывания.
- **Несовпадение.** Профиль найден и это не тип узла: в предпросмотре предупреждение, применение только с галочкой «Я проверил, файл относится к этому узлу» (`profileConfirmed`, иначе 409 `PROFILE_NOT_CONFIRMED`). Факт пишется в `comparison.profileMismatch` скана и в запись журнала `vuln.scan.applied`. Профиля нет — импорт как раньше.
- **Импорт с группы.** Кнопка «Импорт скана» на странице группы: портал предлагает узел по профилю, выбрать можно любой узел группы. Профиля нет или его узла нет — узел выбирает пользователь. Типа нет в группе: «Добавить тип X в группу и импортировать», право то же, что у «Добавить тип» (`registers.manage`); без права — сообщение и выбор существующего узла. Предпросмотр сравнивает с пустым реестром (все находки «Новые», «Пропали» нет), узел создаётся в транзакции применения. Отмена или ошибка чтения узла не оставляют. Право проверяется и при предпросмотре, и при применении.
- **«Сменить тип узла»** (`registers.manage`). Только на действующий тип, которого нет в группе; у «Без группы» нельзя. Реестр, сканы и продления остаются у узла, снимки старых сканов не меняются. Запись в журнал (`vuln.node.type_changed`), вкладка «История» у узла — по `history.view`. После смены старое значение справочника свободно, его можно архивировать.
- **Регулярность.** Дерево и карточки узлов: «Последний скан N дн. назад», выше порога — предупреждающий цвет. «Все группы»: «Узлов без скана дольше порога» со списком. Сверка активов: проверка `vuln_nodes.without_recent_scan` (раздел 5.2). Узел без единого скана считается превысившим порог, ровно порог — ещё нет. «Без группы» не считается.
- **Настройки** — `app_settings`, ключ `vulns`: `{ "scanMaxAgeDays": 90, "profileAliases": { "<id типа>": ["postgres", "pg"] } }`. Строки нет или значение негодное — порог 90 дней, без синонимов. Меняется в «Настройки → Параметры портала», только супер-администратор.
- **Один хост в нескольких профилях.** Находки ведутся отдельно в каждом узле: ключ «Пакет + Идентификатор» действует внутри узла. Одна и та же уязвимость хоста в сканах Windows и PostgreSQL — две записи с отдельными сроками.

## 3. Импорт скана (в узел)

Импорт запускается только из узла. Файл — .xlsx отчёта сканера. Образец: `backend/test/fixtures/vuln-windows-2026-10-15.xlsx` (файл владельца).

**Разбор по содержимому, не по названиям листов:**
- Лист хостов — лист, где в первых 12 строках есть заголовок «Имя хоста». Строка-название над заголовком (например, «Отдел платёжных карт») — это **охват скана**. Колонки «IP-адрес» (или начинается с «IP»), «ОС». Хосты ни к чему не привязываются, это только охват.
- Листы находок — все листы с заголовками «Пакет» и «CVE» (или «Идентификатор»). Колонки по названию: Уровень, CVSS, Эксплойт, Сетевой вектор, Обновить до версии, Краткое описание, Обнаружений. Несколько листов объединяются.
- **Синонимы колонок** — в одном месте, `HEADER_MATCH` в `backend/src/modules/vulns/scan-parser.ts`. «Вектор» — это «Сетевой вектор»; заголовок, начинающийся с «Описание» («Описание (из CVE, англ.)» отчёта Linux), — «Краткое описание»; начинающийся с «Идентификатор» — CVE; с «Обновить до» — «Обновить до версии» (1.13.9).
- **Известные колонки, которые портал не читает** (`IGNORED_HEADERS`): «Задача №» — в предпросмотре серой строкой «Колонка „Задача №“ не используется» (`summary.info`), без жёлтого предупреждения. Колонки, которых в файле нет («Обнаружений» у отчёта Linux), — по-прежнему предупреждение.
- **Значения вектора** приводятся к списку «Сетевой вектор» (`OPTION_ALIASES`): «Удалённо (сеть)» и «Сеть» → «Удалённо (сеть)», «Локально» → «Локально». «Смежная сеть» и «Физический» в списке не было — добавляются новыми значениями, как любое новое значение списка.
- Колонка «Оценка» из файла **не используется**: Оценка и Критичность считаются порталом по п. 7.1 (в файле там формула с плавающей погрешностью).
- Идентификатор — не только CVE (в образце есть `BDU:2025-01793`).
- **Ключ записи — «Пакет + Идентификатор».** Одна CVE бывает у разных пакетов (в образце CVE-2023-44487).
- Повтор ключа в файле — объединение, число обнаружений берётся большее, в предпросмотре счётчик повторов.
- Строка без пакета или идентификатора пропускается с сообщением в предпросмотре; CVSS не число — пустой с сообщением.
- «Обнаружений» — не число хостов (в образце 22 обнаружения на 12 хостов), так и подписывать.
- **Дата скана** берётся из имени файла (`ГГГГ_ММ_ДД`, `ГГГГ-ММ-ДД`, `ГГГГ.ММ.ДД`), редактируется в предпросмотре.

**Предпросмотр сравнения** с реестром узла, ничего не пишется до подтверждения:

| Группа | Условие | По умолчанию | При подтверждении |
|---|---|---|---|
| Новые | ключа нет в узле | выбраны | создаётся запись |
| Повторно обнаружены | запись была «Устранена» | выбраны | та же запись открывается заново, `reopened`, срок пойдёт от передачи ИКТ этого скана |
| Изменились | отличаются Уровень, CVSS, Эксплойт, Сетевой вектор, Обновить до версии или Обнаружений | выбраны | поля обновляются, в истории «было → стало» |
| Без изменений | всё совпадает | — | отмечаются как найденные в этом скане |
| Пропали | открытая запись узла, которой нет в файле | **не выбраны** | выбранные — «Устранена» со ссылкой на скан; невыбранные остаются открытыми |

Плюс сравнение охвата с предыдущим сканом узла: новые и выбывшие хосты. Выбор по строкам и «выбрать все» по группе. Используй существующий механизм сравнения и выбора импорта, расширив его.

**Ожидаемо на образце** (тест): 12 хостов, охват «Отдел платёжных карт», 90 находок с одного листа, 1 идентификатор не CVE, 1 строка без CVSS (Оценка пустая, Критичность «Высокая»), Оценка Adobe Acrobat DC CVE-2026-34621 = 8,2, 7-Zip CVE-2025-0411 = 6,7.

**Применение большого скана** (1.13.9, `docs/plans/release-1.13.9.md`). Отчёт сервера Linux — тысячи находок, и это норма.
- Одна транзакция, всё или ничего, как раньше. Внутри — пачки: значения списков, записи, связи с узлом, «встречалась в скане» и строки журнала — `createMany` (до 1000 строк, не больше 65 535 параметров), изменённые записи — `UPDATE … FROM jsonb_to_recordset` (`backend/src/lib/bulk.ts`). Число запросов растёт с числом пачек: 3390 новых находок — 47 запросов вместо 7 659. Строки журнала и история записей те же: по строке на запись, те же поля и порядок.
- Один импорт в узел за раз: advisory-блокировка по id узла (импорт с группы — по «группа + тип») в начале транзакции; занято — 409 `IMPORT_IN_PROGRESS` «В этот узел уже идёт импорт».
- Предел транзакции массовых операций — 120 с (`BULK_TX` в `lib/db.ts`, совпадает с `proxy_read_timeout` nginx); обычные транзакции — 15 с.
- Сбой применения (не 409/400, в том числе таймаут транзакции) — 500 `IMPORT_FAILED` «Импорт не завершён, ничего не записано. Сообщите администратору номер запроса <id>». В логе backend — строка `error` «импорт не выполнен»: узел, строк, шаг, длительность, номер запроса (`reqId`, 8 шестнадцатеричных символов).
- Уведомлений в транзакции импорта нет. Прогон автоматизаций — после фиксации, своей транзакцией; новые записи срока не имеют, поэтому правила п. 7.4 на импорт не срабатывают.
- Так же пачками пишут передача ИКТ, продление и его отмена, «Пропали → Устранена», «Перенести выбранные», обратный импорт по ID (общий импорт Excel) и задачи из событий автоматизаций.

## 4. Скан (итог сканирования)

Хранится: узел, дата скана, файл (в `files`, sha256), кто загрузил, охват (название, список хостов), снимок строк файла, результат сравнения (ключи по группам и какие «пропавшие» отмечены устранёнными), предыдущий скан, данные передачи ИКТ.

Экран скана: факты (охват, хостов, находок, загрузил, новых по критичности), блок передачи ИКТ, вкладки «Сравнение» (пять карточек-счётчиков и список выбранной группы), «Находки» (снимок файла с посчитанной Оценкой), «Охват» (хосты, отметки «новый в охвате», «выбыл из охвата»). Скан не удаляется и не редактируется.

**Аннулирование скана** (1.13.12, ADR-0052). Скан аннулируется при условиях:
- он не передан ИКТ;
- в том же узле есть более поздний неаннулированный скан (порядок — дата скана, затем время загрузки);
- у пользователя есть право «Удаление данных» (`data.delete`);
- указана причина: «Повторная загрузка», «Ошибочный файл» или «Другое» с текстом.

Иначе кнопки нет, backend отвечает 409 `SCAN_HANDED_OVER`, `SCAN_LAST` или `SCAN_ANNULLED`, без права — 403.

- **Как хранится.** Аннулирование — событие корзины (`deletions`, `entity = 'vuln_scan'`). Сам скан не меняется (триггер `vuln_scans_guard`): файл, снимок находок и сравнение остаются. Журнал — `vuln.scan.annulled`.
- **Изменения, которые скан внёс в реестр, не откатываются.** Об этом прямо говорит окно подтверждения.
- **Где аннулированный скан не учитывается:**
    - дерево узла и список «Итоги сканирования» (там — по переключателю «Показать аннулированные», с отметкой);
    - «Сканы ждут передачи ИКТ», возраст последнего скана, число сканов узла;
    - хосты сканов для сверки активов;
    - «прошлый скан» предпросмотра импорта и сравнение охвата.
- **Передача ИКТ** аннулированного скана — 409 `SCAN_ANNULLED`.
- **Открытый по прямой ссылке** — с плашкой «Аннулирован <дата>, <кто>, причина», без «Передать ИКТ».
- **Карточка записи.** В списке сканов — с отметкой «аннулирован». «Впервые» и «последний раз» считаются по неаннулированным сканам на лету; строки записи (`first_scan_id`, `last_scan_id`) не меняются.
- **Срок не затрагивается.** `deadline_scan_id` ставит только передача ИКТ, а аннулировать можно только непереданный скан, и аннулированный передать нельзя.
- **Сканы, загруженные позже,** сохраняют своё сравнение и «прошлый скан» — это история.
- **Корзина.** Строка «Скан уязвимостей» с причиной. Восстанавливает супер-администратор, тем же механизмом; условие одно — узел и группа не удалены (409 `PARENT_DELETED`). Восстановленный скан снова «ждёт передачи ИКТ». Поздняя передача более раннего скана срок записей не сдвигает (ADR-0030).
- **`check-integrity`:** аннулированные сканы не переданы ИКТ; в их узлах есть неаннулированный скан.

## 5. Передача ИКТ и сроки

**Передача ИКТ — отдельное действие у скана**, импорт срок не запускает:
- поля: дата передачи (не раньше даты скана, не позже сегодня), кому (по умолчанию «ОИКТ»), файл письма или служебки (необязательно);
- после передачи у записей, чей срок ведётся от этого скана, начинается срок; до этого статус «Не передано ИКТ»;
- повторная передача и правка даты не предусмотрены (запись в журнал).

**Итоговый срок записи:**
1. Базовый срок = дата передачи ИКТ скана, от которого ведётся срок записи + дни по Критичности (п. 7.2: 14/30/90/180). Дни календарные; окончание на выходном переносится на ближайший рабочий день по производственному календарю. Ручная Критичность пересчитывает базовый срок.
2. \+ сумма действующих (не отменённых) продлений.
3. Если есть решение ИБ по п. 7.3 (компенсирующие меры + срок после пересмотра ИБ), берётся его дата — оно главнее продлений.

Срок ведётся от первого переданного ИКТ скана, в котором запись встречалась после последнего открытия (первого по времени передачи); повторные сканы и поздняя передача более раннего скана его не сдвигают. При повторном обнаружении устранённой записи срок ведётся от нового скана, решение по п. 7.3 снимается с записью в истории. Запись со статусом «Риск принят» при новом скане не открывается. Просрочка, уведомления и эскалации п. 7.4 считаются по итоговому сроку. В карточке записи всегда видны базовый срок по процедуре, каждое продление и итог.

## 6. Продление сроков по обоснованию ОИКТ

Процедуру не меняет: продление делается по обоснованию ОИКТ и фиксируется порталом.

- Кнопка «Обновить сроки» на странице узла (область — узел) и группы (область — все узлы группы).
- **Дни задаются по Уровню из отчёта сканера** («Важная» +30 и т. д.), 0–365, только продление. Список уровней строится из значений, которые есть в области.
- Участвуют открытые записи с идущим сроком. Не участвуют (показывается сколько): с решением по п. 7.3; из сканов, не переданных ИКТ.
- Фильтры: «Только просроченные», «Только со сроком до <дата>».
- **Обоснование ОИКТ обязательно:** номер обращения, дата, файл; комментарий — по желанию. Без них кнопка неактивна.
- Предпросмотр «было → станет» по каждой записи, применение после подтверждения.
- Продление — событие: область, дни по уровням, фильтры, обоснование, кто, когда, список (запись, дни, было, стало). В истории каждой записи строка «Срок продлён на N дн. (было → стало) по обоснованию ОИКТ № … от …».
- Отмена — целиком, с подтверждением на странице; сроки возвращаются, событие остаётся с отметкой «Отменено <дата>».
- Вкладка «Продления сроков» у узла и список у группы.
- **Новое право «Уязвимости: изменение сроков»** (код предложи, например `vuln.deadlines`): продление и его отмена. Никому автоматически не выдаётся, назначается в матрице.

## 7. Экраны (по прототипу)

- В разделе слева — дерево: «Все группы», группы (сначала обычные, «Без группы» последней), узлы, под узлом сканы по дате с точкой «передан / ждёт передачи ИКТ». Счётчики: открыто и просрочено. Под деревом легенда.
- **Все группы:** показатели (открыто, критических, просрочено, сканов ждут передачи ИКТ), таблица групп (вид, типы, счётчики, последний скан), список сканов, ждущих передачи.
- **Группа:** показатели, карточки узлов (счётчики, последний скан и статус передачи), «Добавить тип», «Обновить сроки», продления группы.
- **Узел:** «Импорт скана», «Обновить сроки», вкладки «Реестр», «Итоги сканирования», «Продления сроков». Реестр: поиск, фильтры Критичности и статуса (Открытые, Просроченные, Не передано ИКТ, Устранённые, Все), сортировка: просроченные, не переданные, в работе, устранённые; внутри по Критичности и Оценке.
- **Карточка записи** (боковая панель): поля, формула Оценки, Критичность (авто или вручную), блок срока, решение по п. 7.3, сканы (впервые, последний раз, список), история. В «Без группы» — «Перенести в узел».
- Статусы записи: «В работе», «Просрочена», «Не передано ИКТ», «Устранена», отметка «повторно».
- Светлая и чёрная темы, стиль портала.

## 8. Перенос существующих данных

- Все записи текущего реестра уязвимостей переносятся в «Без группы / Из прежнего реестра» без потери значений и истории. Их текущий срок фиксируется как «срок из прежнего реестра» (дата) и остаётся базовым после переноса в узел.
- Существующие `scan_reports` / `scan_hosts` и файлы сохраняются; как их отобразить (привязать к узлу «Без группы» как сканы или оставить архивом) — предложить в плане.
- При переносе записи в узел, где уже есть такой ключ, перенос отклоняется с сообщением.
- Ничего не удаляется. Число перенесённых записей — в выводе seed и в журнале.

## 8а. Задачи по группе (релиз 1.14.0, ADR-0053)

- Задачи автоматизаций реестра «Уязвимости» (напоминания, уведомления и эскалации п. 7.4, свои правила) при создании попадают в системную цепочку группы, в которой находится узел записи: «Уязвимости · <группа>». Записи «Без группы» — «Уязвимости · Без группы». Сводная задача правила по реестру «Уязвимости» группы не имеет и остаётся без цепочки.
- «Перенести» и «Перенести выбранные» из «Без группы»: незавершённые задачи записи переходят в цепочку новой группы, выполненные остаются в прежней; переход — в журнале от того, кто перенёс.
- Переименование группы меняет название её цепочки. Удалённая группа (корзина) цепочку не удаляет.
- На странице группы — «Задачи: N активных», открывает панель цепочки.
- Фаза 2: цепочки по узлу вместо группы, автоматическое завершение напоминания при устранении записи, одно сводное напоминание на группу.

## 9. Не делаем сейчас (этап 2)

- Привязка находок к хостам (нужна выгрузка «хост × уязвимость» от сканера).
- Пометка скана ошибочным с откатом его изменений.
- Поля и автоматизации на уровне узла или группы.
- Отдельный счётчик «просрочено по процедуре» без учёта продлений.
- Удаление групп, удаление узлов.
- Ручное создание записи в узле (записи появляются из сканов и переносом из «Без группы»).
- Критичность системы у группы.

## 10. Решения владельца

- Структура «Группа (сервис/подразделение) → Тип систем → Реестр + Сканы»; хосты — только охват скана.
- Скан — история и сравнение, реестр — текущее состояние.
- Срок идёт от передачи отчёта ИКТ, а не от импорта.
- Продление — по обоснованию ОИКТ, по Уровню сканера, только увеличение, отдельное право; процедура не меняется.
- Данные прежнего реестра — во временную группу «Без группы».

Решения по плану 1.5.0 (30.10.2026, `docs/plans/release-1.5.0.md`):
- Seed пишет «Срок из прежнего реестра» только в новое поле, идемпотентно; число записей — в выводе seed и в предпроверке `deploy/prechecks/1.5.0.md`.
- «Срок из прежнего реестра» и «Продлено, дн.» — служебные поля: вручную не правятся ни в карточке, ни обратным импортом Excel; `check-integrity` сверяет «Продлено, дн.» с суммой действующих продлений.
- Код права — `vulns.deadlines`; создание группы, «Добавить тип» и переименование группы — `registers.manage`.
- На странице «Реестры» у реестра уязвимостей отключены создание записей, импорт отчёта сканера и сравнение; выгрузка и обратный импорт Excel по ID остаются.
- «Система» в окне импорта необязательна и предзаполняется системой из предыдущего импорта узла.

## Удаление (релиз 1.6.1, ADR-0033)

- «Удалить группу», «Удалить тип из группы», удаление записей — право «Удаление данных» (`data.delete`), мягко, в корзину.
- Группа и тип — только без открытых записей (не закрытый статус, не архив); иначе 409 `OPEN_RECORDS` со списком типов и числом открытых. Скрываются тип(ы), записи (устранённые и архивные) и сканы; продления остаются. Группа подтверждается вводом названия; название свободно для новой группы.
- Запись — причина: «Ошибочный импорт», «Ложное срабатывание», «Дубль», «Другое» (с текстом); массово — одна причина, одно событие. В событии — статус, «открыта ли», итоговый срок, узел каждой записи. Удалённая не участвует в показателях, сроках, эскалациях и сверке; ключ в узле освобождается.
- Ключ удалённой записи снова в скане узла — группа предпросмотра `deleted` «Были удалены (причина)», по умолчанию не выбрана; выбранная заводится новой записью (удалённая остаётся в корзине, восстановить её тогда нельзя — ключ занят).
- «Без группы» не удаляется; без неархивных записей API отдаёт её с `hidden: true` — в дереве и на «Все группы» не показывается; «Архив сканов прежнего реестра» открывает её узел на вкладке сканов.
- Прозрачность: `GET /vulns/deletions/stats?nodeId|groupId&from&to` — «Удалено записей» за период по причинам (восстановленные не считаются); сверка `vulns.deleted_open` (5.3) — удалённые открытые за 12 месяцев со ссылками на события корзины.
