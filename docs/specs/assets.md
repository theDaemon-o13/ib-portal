# Реестр активов и сверка (релиз 1.6.0)

**Статус: согласовано 02.11.2026, реализовано** (ветка `feature/assets`). Решения владельца по вопросам «Решить до кода» — в плане `docs/plans/release-1.6.0.md`.

Источники владельца: процедура классификации ИТ-активов, реестр сервисов Excel (v3), отчёты Kaspersky Security Center. ADR: 0031 «Три реестра активов и сверка», 0032 «Адаптеры импорта: отчёты KSC и реестр сервисов».

## 0. Данные банка

В seed, тестах, фикстурах и документации нет реальных сервисов, хостов, IP, ФИО, телефонов, доменов и имён команд. Seed создаёт пустые реестры, справочные значения и автоматизацию. Тестовые файлы импорта генерируются кодом теста с вымышленными именами (`TEST-PC01NB`, `10.0.0.x`, «Иванов И.»).

Таблица «команды → продукты» по умолчанию **пустая**: её начальное наполнение содержит имена команд банка, поэтому владелец вносит его на проде в «Параметры портала». Нормализация ОС и правила типа хоста — общие, они в значении по умолчанию.

## 1. Категории критичности

Список, в этом порядке: **Mission Critical, Business Critical, Operational, Non-Critical**. Значимые для сверки и самооценки — первые два; набор хранится в `app_settings.assets` и меняется в «Параметрах портала».

В первой редакции значения были «Operational Critical» и «Non-critical». На прод они не выкладывались, поэтому seed просто создаёт новый список; на dev — см. раздел 8.

| Категория | RTO по умолчанию | RPO по умолчанию |
|---|---|---|
| Mission Critical | 2 ч | до 4 ч |
| Business Critical | 12 ч | 4–24 ч |
| Operational | 72 ч | 1–7 дн. |
| Non-Critical | не задано | не задано |

**RTO и RPO** — обычные текстовые поля. Значений по умолчанию у конструктора нет. Таблица выше показана в подсказке поля в карточке записи: это новая настройка поля «Подсказка» (`register_fields.settings.hint`, любой тип поля, правится в конструкторе). Значимый продукт без RTO или RPO — проверка сверки `products.rto_rpo`.

**Перевод старой шкалы при импорте:** «Business Operatinal» и «Business Operational» → Operational; «Office Productivity» → Non-Critical; Mission Critical и Business Critical — как есть; пусто → пусто; другое — предупреждение в предпросмотре, поле пустое.

**Пересмотр:** раз в 6 месяцев. «Пересмотр до» — существующий вычисляемый срок: «Дата классификации» + 183 дня при каждой категории (правило «дата + дни по значению списка», по списку категорий). Без категории или даты классификации срока нет: сверка показывает это нарушением `products.review`. За 30 дней — задача получателям метки «Активы».

**Условная обязательность** («Работает» только с категорией, уровень 4 раздела 2.3) конструктор не умеет и ради этого не меняется. Получилось проверкой сверки `products.working_without_category`.

**Ключ «Компонент + Продукт».** Ключ импорта у конструктора — одно поле, поэтому ключ — служебное поле «Ключ компонента». Его вычисляет адаптер реестра сервисов. Вручную оно не правится ни в форме, ни обратным импортом: ответ 409, как у служебных полей уязвимостей. Компонент, заведённый вручную, ключа не получает и при импорте не сопоставляется.

**Исходное написание ОС** хранится в отдельном служебном поле, а не только в истории: оно нужно, чтобы дополнить таблицу нормализации и найти, что изменилось.

В карточке продукта — обратный список компонентов, в карточке хоста — тоже (механизм обратных связей ADR-0017).

## 3. Импорт реестра сервисов (адаптер)

Готовый импорт конструктора файл владельца не загрузит. Нужно:
- заголовки найти в строке 6, а не в первой;
- поделить «IP:порт» на два поля;
- перевести шкалу и «Класификацию»;
- нормализовать ОС;
- найти продукт по команде;
- создать недостающие продукты и хосты.

Поэтому это **адаптер**, как у KSC: он превращает файл в строки «Компонентов» и отдаёт их существующему конвейеру. Конвейер — предпросмотр, применение одной транзакцией, проверка версий. Правило «пустая ячейка не меняет значение» сохраняется. Строки 1–5 удалять не нужно. В реестре «Компоненты» — кнопка «Импорт реестра сервисов».

**Файл.** `.xlsx` или XML Spreadsheet. Лист «Список активов» (по названию; нет — первый лист, где в первых 12 строках есть «Наименование актива»). Заголовки там, где найдены, данные — ниже. Листы «Справочник» и «контакты» не читаются.

| Колонка файла | Куда |
|---|---|
| Наименование актива | Компонент |
| Тип актива | Тип актива (незнакомое значение — ошибка строки) |
| Важность/Критичность | Категория критичности, по переводу раздела 1 |
| Местоположение | Местоположение |
| Описание/назначение | Описание |
| Операционная система/ПО | ОС / ПО (нормализованное) и «ОС / ПО в источнике» |
| IP-адрес | IP-адрес и Порт |
| Владелец | Владелец |
| Класификация | «В эксплуатации» → Среда Prod, Статус «Работает»; «Тест/внедрение», «Тест» → Среда Test, Статус «Работает» |
| Команда | Команда и Продукт по таблице `assets.teamProducts` |

Правила:
- **IP:порт.** Неполный адрес (меньше четырёх октетов) сохраняется как есть, с предупреждением в предпросмотре.
- **Продукт.** По таблице `assets.teamProducts`. Команды нет в таблице — продукт с её именем. Продукта нет в «Сервисах» — блок «Будут созданы продукты: …» с подсказкой «чтобы объединить команды в один продукт, заполните «Параметры портала → Активы: команды → продукты» до импорта». Статус нового продукта «Работает», категории нет. Импорт не блокируется. Пустая команда — компонент без продукта, с предупреждением.
- **Хосты.** Для каждого полного IP, которого нет в «Хостах» (по имени и по полю IP), — блок «Будут созданы хосты: N». У такого хоста Тип «Сервер», Источник «Реестр сервисов», имя = IP. Компонент связывается с хостом. Блок можно снять — компоненты останутся без хоста. Неполный IP хоста не создаёт.
- **Местоположение.** Незнакомое значение добавляется в список при применении, в предпросмотре — предупреждение.
- **ОС.** Написания нет в таблице нормализации — сохраняется как есть.
- **Статус** ставится только у нового компонента: если владелец перевёл компонент в «Выводится», повторный импорт этого не отменит. Среда обновляется.
- **Пустая категория** импорт не блокирует, компонент попадает в сверку.

**Создание продуктов и хостов.** Они создаются в транзакции применения, до компонентов (ADR-0032). Предпросмотр ничего не создаёт: запланированные записи и значения списков хранятся в `register_imports.payload`, ссылки на них — токенами. Если после предпросмотра кто-то завёл продукт или хост с тем же ключом, не применяется ничего.

## 4. Импорт отчётов Kaspersky Security Center (адаптер)

### 4.1 Формат

Определяется по содержимому, а не по расширению:
- **XML Spreadsheet 2003** (SpreadsheetML, `.xls` из KSC): начало `<?xml`, `<?mso-application progid="Excel.Sheet"?>`, корень `Workbook` пространства `urn:schemas-microsoft-com:office:spreadsheet`;
- **`.xlsx`**, если владелец пересохранил файл в Excel.

Разбор XML:
- `<!DOCTYPE` и сущности отклоняются до разбора;
- лимиты как у остального импорта: 25 МБ, 20 000 строк;
- ячейки `ss:Data` типов String, DateTime и Number; учитываются `ss:Index` и `ss:MergeAcross`.

Парсер — `saxes` 5.0.1, прямая зависимость (решение владельца 02.11.2026). В реестре «Хосты» — кнопка «Импорт отчёта KSC».

Листы: **Summary** (строка 2 — название отчёта) и **Details** (строка 1 — заголовки).

### 4.2 Обрезанный отчёт

KSC по умолчанию ограничивает детальную часть 1000 строками.
- **Отчёт о развёртывании и статус баз:** итог сводки — сумма «Количество устройств». Если он не совпал с числом строк Details, импорт блокируется: «Отчёт обрезан: в сводке N устройств, в таблице M. Увеличьте в KSC лимит записей в свойствах шаблона отчёта и выгрузите заново».
- **Отчёт о версиях программ:** итог однозначно не посчитать. При ровно 1000 строк (или 5000, 10000, 100000 — известные лимиты) — предупреждение и запрет «Нет в файле».

### 4.3 Принимаемые отчёты

Каждый обновляет только свои поля. Остальные колонки адаптер не передаёт, а пустая ячейка значение не меняет.

| Отчёт (строка 2 Summary) | Поля хоста | «Нет в файле» |
|---|---|---|
| «Отчет о развертывании защиты» | Группа KSC, Версия агента, Продукт защиты, Версия защиты, В KSC = Да | да, область «В KSC = Да» |
| «Отчет о статусе антивирусных баз», «… об используемых антивирусных базах» | Статус баз, Дата баз, IP-адрес, Домен | нет |
| «Отчет о версиях программ "Лаборатории Касперского"» | Последняя связь, Последнее появление в сети, Защита установлена, Версия агента | нет |

- «Неизвестно» — пустое значение.
- Незнакомый статус баз сохраняется: в список добавляется значение, в предпросмотре предупреждение.
- **Версии программ:** берутся строки программы защиты (Kaspersky Endpoint Security для Windows / for Mac, Kaspersky Security для Windows Server), строки «Агент администрирования…» — только для версии агента, «Сервер администрирования…» пропускаются.
- «Отчет о владельцах устройств» и «Отчет о реестре оборудования» отклоняются с подсказкой, что они не нужны. Любой другой — «Неизвестный отчёт KSC».

**Почему область «В KSC = Да».** Отчёт о развёртывании видит всю сеть, но хосты из реестра сервисов и сканера в KSC могут не попасть. Иначе они оказались бы в «Нет в файле».

### 4.4 Ключ, дубли, тип

- **Ключ** — «Устройство»: нижний регистр, без пробелов по краям, без суффикса после первой точки. «NetBIOS-имя», где есть, — подтверждение: не совпало — предупреждение.
- **Дубли внутри отчёта** после нормализации: в хост идёт строка с самой свежей датой («Созданы» или «Последнее подключение…»). Остальные показываются блоком «Дубли в KSC — удалить устаревшие записи в консоли». Для источника Kaspersky это заменяет правило «не склеивать».
- **Совпадение с хостом другого источника.** Ключ импорта у реестра один, поэтому второй хост с тем же именем не создаётся: поля Kaspersky записываются в найденный хост. В предпросмотре — предупреждение со списком таких хостов. Имя, тип и источник у найденного хоста не меняются.
- **Тип нового хоста** — по `assets.hostTypeRules`: Сервер — продукт «…для Windows Server», группа «Servers», имя с SRV / SERVER / `^DC\d`; Рабочая станция — имя на NB, PC, MAC (с цифрами или без); иначе «Другое». У существующего хоста тип не перезаписывается.
- **Группа KSC** — текстом, в «Подразделение» не переносится.
- **ОС** в KSC нет. Если у хоста ОС пуста, а в последнем скане VM есть — сверка показывает «Можно взять из скана», сама ОС не подставляется.

### 4.5 Сведения об импорте без миграции

Тип отчёта, итог сводки, число строк, дубли — в `register_imports.summary.source` (jsonb). Проверка «последний отчёт о развёртывании старше 35 дней» читает применённые импорты с этим типом.

## 5. Сверка

Форма факта и правило «Нет данных» — как сейчас (сделано): `code`, `section`, `relatedSections`, `title`, `status`, `numerator`, `denominator`, `percent` (вниз до 0,1), `records` со ссылками, `calculatedAt`, `message`, `warnings`. Пустой источник — «Нет данных: <реестр> не заполнен» без чисел и списка; выведенные и закрытые записи не считаются.

| Код | Раздел | Условие нарушения |
|---|---|---|
| `products.without_category` | 2.3 | продукт или компонент без категории |
| `products.working_without_category` | 2.3 | статус «Работает» без категории (вместо условной обязательности) |
| `products.ownership` | 2.2 | значимый продукт без владельца, назначения |
| `products.risk_link` | 2.3 | значимый продукт без «Связи с ключевыми рисками» |
| `products.rto_rpo` | 2.3 | значимый продукт без RTO или RPO |
| `products.review` | 2.3 | пересмотр не задан (нет даты классификации или категории) или просрочен |
| `products.documented` | 2.2, 2.3 | нет даты классификации или согласования |
| `components.above_product` | 2.3 | компонент критичнее своего продукта |
| `products.without_components` | 2.2 | значимый продукт без компонентов |
| `products.without_hosts` | 2.2 | значимый продукт без хостов (через компоненты или напрямую) |
| `systems.without_product`, `products.without_system` | 2.2 | как сейчас |
| `assets.unsupported_os` | 8.2 | компонент или хост с ОС из `assets.unsupportedOs` у продукта без плана |

## 8. Данные и откат

- **Миграций нет.** Seed (`system.register.assets.v2`) создаёт три реестра, метку «Активы», напоминание о пересмотре, поле «Сервис» у инцидентов. Существующие записи не меняются.
- **На dev есть реестры первой редакции.** Seed доводит их до v2 на месте:
    - переименовывает поля («Уровень системы» → «Категория критичности», «Основание уровня» → «Связь с ключевыми рисками»);
    - переименовывает значения шкалы (Operational Critical → Operational, Non-critical → Non-Critical), поэтому записи сохраняют выбор;
    - добавляет недостающие поля, значения и реестр «Компоненты»;
    - прежнее поле-дату «Пересмотр до» и «Состояние защиты» отправляет в архив вместе с данными.

  Проверено на dev: `check:integrity` в порядке. На проде первой редакции не было.
- **Откат на 1.5.0:** реестры и поля остаются обычными данными. Подсказку поля и служебные поля активов старый backend не знает: подсказка не видна, служебные поля редактируются как обычные.
