## 0. Данные банка

Репозиторий публичный. ФИО, табельных номеров, e-mail, подразделений, должностей и результатов тестов нет:
- в seed;
- в тестах и фикстурах;
- в документации и примерах.

Seed создаёт только пустые реестры «Сотрудники» и «Результаты INDIGO», их поля и параметр порогов в `app_settings`.

Тестовые файлы (выгрузку HR и отчёт INDIGO) генерирует код теста по форматам из разделов 2 и 4. В них вымышленные люди («Иванов Иван Иванович») и подразделения («Отдел тестирования»). Файлов `.xlsx` с данными в git нет: генератор пишет их во временный каталог теста.

## 1. Что получает пользователь

- **«Реестры → Сотрудники».** Загрузка выгрузки HR обычным импортом конструктора. Повторный импорт обновляет записи по табельному номеру. Тех, кого нет в новом файле, можно отметить «Уволен» через «Сравнение» (ADR-0017).
- **«Реестры → Результаты INDIGO».** Загрузка отчёта «Статистика по баллам» кнопкой «Импорт отчёта INDIGO». В предпросмотре:
    - проверка полноты;
    - средний процент по сводке и по строкам;
    - разбор строк, которые требуют ручного сопоставления с сотрудником.
- **Дашборд.** Средний результат, распределение по оценкам, системный виджет «На пересдачу» (без уволенных) со ссылкой на список, результаты и средний результат по подразделениям.

Отдельной страницы «Осведомлённость» в 1.8.0 нет: всё делают экраны конструктора. Каких расширений конструктора это требует — раздел 7.

### 2.1. Импорт выгрузки HR

Точный формат выгрузки владелец пришлёт отдельно. До этого используется обычное сопоставление колонок конструктора: колонки файла по названиям полей, ключ — «Табельный номер». Отдельного адаптера HR в 1.8.0 нет.

- **Повторный импорт** обновляет записи по табельному номеру. Пустая ячейка значение не меняет, как во всём конвейере.
- **Новая запись без «Статуса»** получает «Работает». Это производное значение реестра, как «Экземпляр» у компонентов (раздел 7.4).
- **Повторное появление уволенного в файле.** Если в файле есть колонка «Статус», значение берётся из неё. Если колонки нет, статус «Уволен» не меняется. Предпросмотр показывает предупреждение «В файле есть уволенные: N — проверьте статус» со списком (решение 4).
- **Деление ФИО** (раздел 2.2).
- **Журнал.** Предпросмотр и применение пишутся в `audit_log` (`register.import.previewed`, `register.import.applied` и запись на каждую изменённую запись). Это уже делает конвейер.

### 2.2. ФИО одной колонкой

Заполнены «ФИО», а «Фамилия», «Имя» и «Отчество» пустые — поле делится по пробелам:
- **Ровно три части** — фамилия, имя, отчество.
- **Четыре части, последняя — «оглы», «кызы», «угли», «кизи» или «зода»** (без регистра) — фамилия, имя, отчество из двух последних частей. Сейчас список зашит в код. Если владелец решит, что он должен меняться без релиза, его перенесут в «Параметры портала».
- **Иначе** (меньше трёх частей, составная фамилия из двух слов, лишние слова) — ФИО сохраняется целиком, части остаются пустыми. В предпросмотре предупреждение «ФИО не разделено на фамилию, имя и отчество: N строк» со списком строк.

Двойная фамилия через дефис («Петрова-Сидорова») — одна часть, она делится как обычно.

Обратный случай: «ФИО» пустое, части заполнены — ФИО собирается «Фамилия Имя Отчество» через пробел.

Деление выполняется при каждой записи (импорт, форма), но только если части пустые. Заполненные вручную части не перетираются.

### 2.3. «Нет в файле» → «Уволен»

Используется существующее «Сравнение» (ADR-0017): кнопка в окне предпросмотра импорта.
- Ключ сравнения — «Табельный номер». Seed записывает его в настройку реестра.
- Область — «Весь реестр» (с предупреждением, как сейчас).
- Действие — статус «Уволен» у отмеченных. Применение идёт по правилам массовых действий (ADR-0016): `expected`, пакеты, история карточки `via: compare`, сводная запись журнала.

Записи не удаляются: на них ссылаются результаты тестов. «Уволен» — закрывающий статус, поэтому уволенные не попадают в «Нет в файле» повторно и не участвуют в автоматическом сопоставлении (раздел 4.5).

### 2.4. Права

Права — как у любого реестра, новых кодов нет:
- просмотр — `ib.work`;
- импорт и правка записей — `records.edit`;
- поля и настройки реестра — `registers.manage`.

| `retake` | На пересдачу | список: Да, Нет | роль аналитики «измерение» | адаптер |
| `match` | Сопоставление | список: Точно, Вручную, Не сопоставлен | роль аналитики «измерение» | адаптер, карточка, пересчёт |

**Служебные поля.** Все поля, кроме «Сотрудника», служебные (как «Ключ компонента» в 1.6.0). Их ставят только адаптер и пересчёт (раздел 5). Форма и обратный импорт Excel их не меняют: 409 `AWARENESS_SERVICE_FIELD`, как у активов. Результат — это запись отчёта; исправлять его надо загрузкой исправленного отчёта.

**«Сотрудник» правится в карточке** (`records.edit`). Тогда «Сопоставление» становится «Вручную», а очищенная связь — «Не сопоставлен». «Подразделение» при правке в карточке не меняется: его пересчитывает только кнопка (раздел 5).

### 3.1. Ключ попытки

Ключ: «Тест + нормализованное ФИО + Дата теста». Значение — `<тест> | <фамилия имя отчество> | <ГГГГ-ММ-ДД>` после нормализации раздела 4.5. Конвейер сравнивает ключ через `register_import_key()`: без регистра, лишние пробелы схлопываются.

- Повторная загрузка того же отчёта ничего не меняет: все строки «без изменений».
- Пересдача в другой день — новая запись.
- Две попытки одного человека в одном тесте в один день (решение 3): загружается попытка с большим «Результатом, %», при равном — первая по порядку в файле. Остальные показываются блоком «Повторы в один день». Ключ остаётся «Тест + ФИО + Дата».

### 3.2. Оценка и «На пересдачу»

Пороги лежат в `app_settings`, ключ `awareness.grades`, параметр «Параметры портала → Осведомлённость: пороги оценки»:

```json
{ "excellent": 90, "good": 70, "satisfactory": 50, "retakeBelow": 50 }
```

- **Оценка:**
    - «Результат, %» ≥ `excellent` — «Отлично»;
    - ≥ `good` — «Хорошо»;
    - ≥ `satisfactory` — «Удовлетворительно»;
    - иначе — «Провал».
- **На пересдачу:** «Да», если «Результат, %» < `retakeBelow`, иначе «Нет».
- **Порог пересдачи хранится отдельно** от порогов оценки и с ними не связан.
- **Проверка значения:** `100 ≥ excellent > good > satisfactory ≥ 0`, `0 ≤ retakeBelow ≤ 100`. Числа целые или с одним знаком после запятой. Процент сравнивается как есть, без округления: 89,9 — «Хорошо».
- **Seed** один раз (`seed_markers`) пишет строку со значениями по умолчанию. Если строка испорчена, код берёт те же значения по умолчанию, как у остальных параметров портала.
- **Кто меняет:** параметры портала меняет только «Супер-администратор» (CLAUDE.md, раздел 5).

**Когда считается.** Оценка фиксируется при создании записи по порогам на момент импорта. Если в повторно загруженном отчёте у существующей записи «Результат, %» тот же, оценка не пересчитывается, даже если пороги изменились. Так повторная загрузка ничего не меняет. Если процент изменился (исправленный отчёт), оценка считается по текущим порогам. Пересчёт старых оценок по новым порогам в 1.8.0 не делается («Запланировано»).

Нет «Результата, %» (пустая ячейка) — оценки и «На пересдачу» нет, в предпросмотре ошибка строки.

## 4. Адаптер отчёта INDIGO

Как отчёты KSC в 1.6.0 (ADR-0032), отчёт превращается в лист с колонками по названиям полей и передаётся в общий конвейер: предпросмотр, применение одной транзакцией, проверка версий. Второго конвейера нет.

- **Маршрут:** `POST /registers/:id/imports?adapter=indigo`. Права — `records.edit`, как у остальных адаптеров. Только для реестра `awareness_results`, иначе 409 `WRONG_ADAPTER`.
- **«Нет в файле» не считается** (`missing: false`). Каждый отчёт — это попытки за свой период: если человека нет в новом отчёте, это ничего не значит.

### 4.1. Формат файла

INDIGO выгружает отчёт как `.xls` в формате BIFF8 (двоичный Excel в контейнере OLE). Файл часто приходит с повреждённым хвостом.

- **Тип определяется по содержимому**, не по расширению:
    - **ZIP** (`50 4B`) — `.xlsx`, читается exceljs, как сейчас (`lib/spreadsheetml.ts`, `readSheets`).
    - **OLE** (`D0 CF 11 E0 A1 B1 1A E1`) — отказ 400 `OLD_EXCEL_FORMAT`: «Это файл старого формата Excel. Откройте его в Excel и сохраните как .xlsx, затем загрузите снова».
    - **SpreadsheetML** — читается (общий код), но отчёт INDIGO в этом формате не ожидается. Если листа «Статистика по баллам» в нём нет — ошибка раздела 4.2.
    - **Остальное** — 400 `BAD_FILE`.
- **Прямое чтение `.xls`** не делается (решение 2): своего разбора BIFF8 нет, SheetJS не подключаем.
- **Лимиты** — как у импорта: 25 МБ, 20 000 строк.

### 4.2. Поиск листа, заголовков и сводки

- **Лист** — «Статистика по баллам» (без регистра и лишних пробелов). Если такого нет и лист в книге один — берётся он. Иначе ошибка «В книге нет листа «Статистика по баллам»».
- **Название теста** — первая непустая ячейка строки 1 (A1 бывает объединённой). Сохраняется как есть, в том числе двуязычное через « | ». Пусто — ошибка «В первой строке нет названия теста».
- **Строка заголовков** — первая строка, где есть ячейки с текстом «№» и «Фамилия» (без регистра, пробелы по краям не важны). Номера колонок берутся из этой строки:
    - «Фамилия», «Имя», «Отчество», «Группа», «Дата», «Затрачено» — по тексту;
    - тройки «Б», «М», «%» — слева направо по порядку появления: первая — обычные вопросы, вторая — мультивыбор, третья — итог. Тройка — это «Б», за ним ближайшее «М», за ним ближайшее «%». Пустые колонки между ними пропускаются.
    - Не нашлось трёх полных троек или одной из обязательных колонок (Фамилия, Имя, Дата, итоговая тройка) — ошибка с названием того, чего нет.
- **Сводка** ищется над строкой заголовков, по меткам строк, а не по номерам:
    - метки — «Всего», «Верно», «Частично», «Неверно», «Пропущено», «СреднийБалл», «МаксБалл», «Процент»;
    - сравниваются без регистра, пробелов и знака «:»;
    - числа строки — ячейки правее метки, слева направо: первое — обычные вопросы, второе — мультивыбор, третье — итог.
    - Если над сводкой есть строка с текстами «Обычные вопросы» и «Мультивыбор вопросы», числа относятся к группам по колонкам этих заголовков. Итог — третья группа, правее мультивыбора.
    - Для проверки полноты нужны «Всего», «МаксБалл» и «Процент» итога. Если их нет, предупреждение «Сводка не найдена — полнота не проверена». Импорт не блокируется.
- **Данные** — строки ниже заголовков до первой полностью пустой строки. Строки после неё не читаются. Если ниже есть непустые строки, предупреждение «После пустой строки N есть ещё данные — они не загружены».

### 4.3. Разбор строки

| Колонка отчёта | Поле | Правило |
|---|---|---|
| Фамилия, Имя, Отчество | ФИО | склеиваются через пробел, лишние пробелы убираются; отчество может быть пустым |
| Группа | Группа INDIGO | как есть |
| Дата | Дата теста | текст ДД.ММ.ГГГГ; ячейка-дата Excel тоже принимается (при пересохранении в `.xlsx` Excel может превратить текст в дату). Не разобралась или не существует (31.02) — ошибка строки, остальные строки загружаются |
| Затрачено | Затраченное время | текст ЧЧ:ММ:СС как есть; время Excel (доля суток) — переводится в ЧЧ:ММ:СС; другое — значение сохраняется как текст с предупреждением |
| итог Б, М, % | Балл, Макс. балл, Результат, % | числа; запятая или точка; знак «%» отбрасывается |
| обычные % | Обычные вопросы, % | число |
| мультивыбор % | Мультивыбор, % | число |
| № | — | не загружается, только номер строки в сообщениях |

Строка без фамилии и имени — ошибка строки «Нет ФИО». Если «Результат, %» не число — ошибка строки.

### 4.4. Проверка полноты

- **Сверка:** число строк данных × «МаксБалл» итога = «Всего» итога. В отчёте из 420 строк с «МаксБаллом» 10 «Всего» = 4200.
- **При расхождении** предупреждение «Отчёт может быть неполным: по сводке N ответов (это K попыток), в таблице M строк». Импорт не блокируется: лимит выгрузки INDIGO неизвестен, в отличие от KSC. Если «МаксБалл» равен 0 или сводки нет, сверка не выполняется и об этом есть предупреждение.
- **Средний процент:** «Процент» итога из сводки показывается рядом со средним «Результатом, %» по строкам таблицы. Строки с ошибками в среднее не входят, их число указано рядом. Расхождение больше 0,5 п. п. выделяется.

Числа сверки сохраняются в `register_imports.summary.source` (раздел 4.8).

### 4.5. Сопоставление с «Сотрудниками»

В отчёте нет табельного номера, только ФИО (ADR-0038).

- **Нормализация ФИО:** без регистра, лишние пробелы схлопываются, пробелы по краям убираются, «ё» → «е». Одна функция для адаптера, ключа попытки и пересчёта (`modules/awareness/logic.ts`).
- **У сотрудника** сравнивается поле «ФИО» (заголовок), а не части. Поэтому сопоставляются и сотрудники, у которых ФИО не разделилось.
- **Точно:** полное ФИО из отчёта (фамилия, имя и отчество; отчество непустое) совпало ровно с одним сотрудником со статусом «Работает». Связь ставится, «Сопоставление» = «Точно».
- **Не сопоставлен** — связь пустая, если:
    - совпадений несколько (однофамильцы с одинаковым ФИО);
    - совпадений нет;
    - в отчёте нет отчества;
    - совпал только уволенный.
- **«Сотрудники» пусты** — импорт работает, все записи «Не сопоставлен». В предпросмотре подсказка «Реестр «Сотрудники» пуст — сначала загрузите выгрузку HR, иначе все результаты будут без связи».
- **Подразделение:** из связанного сотрудника (его «Подразделение» на момент импорта). Если связи нет или у сотрудника подразделение пустое — из «Группы INDIGO». «Группа INDIGO» сохраняется всегда как есть: в ней вперемешку подразделения и должности.
- **Фиксация.** Подразделение фиксируется при создании записи. Повторный импорт не меняет «Сотрудника», «Сопоставление» и «Подразделение» у существующих записей (поля «только у новой записи», ADR-0032). Иначе повторная загрузка снимала бы ручное сопоставление. Связь у несопоставленных — кнопкой (раздел 5); подразделение у уже связанных в 1.8.0 не обновляется (решение 8).

### 4.6. Предпросмотр

Окно обычного импорта, и к нему блоки адаптера:

1. **Сведения:**
    - тест;
    - строк в таблице;
    - средний процент по сводке и по строкам;
    - сверка полноты (раздел 4.4).
2. **«Требуют ручного сопоставления: N».** Только новые записи без связи. На каждую строку: ФИО и группа из отчёта, причина («однофамильцы: 2», «не найден», «нет отчества», «найден только уволенный») и выбор сотрудника.
    - Однофамильцы предложены первыми, остальные находятся поиском по реестру «Сотрудники» (только «Работает»).
    - Выбранный — «Вручную», подразделение берётся из выбранного сотрудника.
    - Можно не выбирать: строка остаётся «Не сопоставлен».
    - Механизм выбора — расширение конвейера (раздел 7.2).
3. **«Повторы в один день: N»** — если есть (раздел 3.1).
4. **Обычные блоки конвейера:** добавится, без изменений, ошибки строк.

### 4.7. Применение

Как в конвейере: одна транзакция с проверкой версий. Если после предпросмотра изменились поля реестра или записи с теми же ключами, не применяется ничего (`IMPORT_STALE`).

Ручной выбор проверяется заново. Выбранный сотрудник не удалён и в статусе «Работает», иначе `IMPORT_STALE`. Подразделение берётся из сотрудника в момент применения.

Журнал — как у конвейера. В diff каждой созданной записи есть `importId` и способ сопоставления.

### 4.8. Сведения об импорте

Хранятся без миграции, в `register_imports.summary.source` (как у KSC):

```json
{ "adapter": "indigo", "test": "…", "rows": 420, "summaryTotal": 4200, "summaryMax": 10,
  "summaryPercent": 74.3, "rowsPercent": 74.1, "complete": true,
  "matchedExact": 400, "matchedManual": 12, "unmatched": 8, "sameDayRepeats": 0 }
```

Число несопоставленных после ручного выбора дописывается при применении (сводная запись журнала `register.import.applied` и `summary.source`).

## 5. Пересчёт по сотрудникам

Кнопка «Обновить по сотрудникам…» на экране записей реестра «Результаты INDIGO», в панели действий рядом с импортом. Право — `records.edit`. Окно — предпросмотр, затем применение (порядок массовых действий, ADR-0016). Решение 8.

- **Обрабатываются только записи «Не сопоставлен».** «Точно» и «Вручную» не трогаются.
- **Предпросмотр** — строки, которые теперь сопоставляются «Точно» по правилам раздела 4.5 (например, после загрузки «Сотрудников»). На каждую: ФИО, тест, дата, найденный сотрудник, «Подразделение» «было → станет» (из «Группы INDIGO» → из сотрудника). Любую строку можно снять.
- **Применение:** отмеченные получают связь, «Сопоставление» = «Точно» и подразделение сотрудника. Проверка `expected` (409 `BULK_CHANGED`), обычная правка записи (`via: awareness_refresh`), сводная запись журнала.
- **Подразделение у уже связанных** (сотрудник перешёл в другой отдел) в 1.8.0 не обновляется: оно фиксируется при импорте. Если понадобится — следующий шаг.

Автоматического пересчёта нет: смена подразделения у сотрудника старые результаты не меняет.

## 6. Отображение

Экраны записей, карточка, фильтры, выгрузка Excel — обычные экраны конструктора.

- **Уволенные.** В «Результатах» связь показывает ФИО сотрудника. Результаты уволенного сохраняются и видны, как любые другие. Связь на запись в закрывающем статусе показывается с меткой этого статуса: «Иванов Иван Иванович (уволен)» (решение 7, общее правило — раздел 7.6).
- **Виджеты дашборда** (по ролям аналитики, без настройки):

| Виджет | Откуда | Что есть сейчас |
|---|---|---|
| Средний результат | «Результат, %» — показатель | работает: среднее, максимум, записей |
| Распределение по оценкам | «Оценка» — измерение | работает |
| На пересдачу | системный виджет: число записей «На пересдачу = Да», у которых сотрудник не уволен (несопоставленные считаются), до 6 последних попыток со ссылками, ссылка на полный список с фильтром `lopen=` (раздел 7.5) | **новый**; плитку seed не создаёт |
| Сопоставление | «Сопоставление» — измерение | работает: сколько не сопоставлено |
| Попытки по неделям | «Дата теста» — дата | работает |
| По подразделениям | «Подразделение» — текстовое измерение | **нужно расширение 7.1** |
| Средний результат по подразделениям | среднее «Результата, %» по «Подразделению» | **нужно расширение 7.3** |

Плитка дашборда условие по связанной записи не умеет: её определение — строка `dashboard_tiles` «поле-список ∈ значения», и новое условие потребовало бы схемы. Поэтому «На пересдачу» без уволенных — системный виджет, а не плитка (решение 7). Число виджета и `total` списка по его ссылке совпадают.

Все виджеты считают по всем записям реестра, за всё время и по всем тестам. Отбор по тесту и периоду — следующий шаг после 1.8.0 (решение 6).

## 7. Расширения конструктора

Общие, не только для этого раздела. Схема БД не меняется.

### 7.1. Текстовое поле с ролью «измерение»

Сейчас роль аналитики у текста недоступна (`ALLOWED_ROLES.text = []`). Подразделение в обоих реестрах — текст (так в задании; список не подходит, потому что обычный импорт HR не создаёт новых значений списка).

- `ALLOWED_ROLES.text = ['dimension']`.
- **Виджет распределения по тексту:**
    - группировка по нормализованному значению (без регистра, пробелов и «ё»/«е»);
    - подпись — самое частое написание;
    - 12 самых частых значений, затем «Остальные: N» и «Не заполнено».
- **Фильтр** `f=<поле>:<значение>` для текстового поля — точное совпадение после той же нормализации, в SQL. Ссылка из полосы виджета открывает список с этим фильтром.
- **Многострочный текст** роль не получает.

### 7.2. Выбор связи в предпросмотре импорта

Адаптер может отдать блок выбора: по строкам новых записей — поле связи, кандидаты и подсказка поиска. Применение принимает `choices: { [номер строки]: id записи | null }` вместе с `skip`.

Сервер проверяет:
- строка есть в блоке;
- запись — из реестра связи;
- запись не удалена;
- запись попадает в область адаптера (для INDIGO — «Работает»).

Выбор адаптер переводит в значения строки. Для INDIGO это «Сотрудник», «Сопоставление» = «Вручную» и «Подразделение» из выбранного сотрудника.

Без `choices` применение работает как раньше.

### 7.3. Виджет «Среднее по измерению»

Системный виджет «Средний результат по подразделениям» для реестра `awareness_results` («Результат, %» по «Подразделению»), как постоянные виджеты разделов: полосы «подразделение → среднее» по всем подразделениям, от худшего среднего к лучшему, без обрезки (решение 9). Полоса ведёт в список с фильтром по подразделению (`f=`, раздел 7.1). Общая настройка «показатель по измерению» в конструкторе — позже, если понадобится.

### 7.4. Производные значения и предпросмотр по реестру

Хуки по `systemKey`, как `deriveComponentInstance` в 1.6.1:
- **«Сотрудники»:** деление и сборка ФИО (раздел 2.2), «Работает» у новой записи без статуса; предупреждения предпросмотра (неразделённые ФИО, уволенные в файле).
- **«Результаты INDIGO»:** «Сопоставление» при правке «Сотрудника» в карточке.

### 7.5. Фильтр «связь пустая или открыта» (`lopen=`)

Общий параметр фильтра записей `lopen=<id поля связи>`: связь пустая или связанная запись не в закрывающем статусе. Исключается только запись, у которой связанная запись жива и закрыта; удалённая связанная запись закрытой не считается — неизвестно, что человек уволен (как у несопоставленных). Работает в SQL — в списке записей, в счётчике `total` и в массовых действиях «все по фильтру» (выгрузка Excel фильтров не принимает — выгружается весь реестр). На этом фильтре строится ссылка виджета «На пересдачу». Поле не связь — 400.

### 7.6. Метка закрывающего статуса у связи

Общее правило вывода полей связи (решение 7): если связанная запись в закрывающем статусе, после её заголовка — метка этого статуса в нижнем регистре в скобках: «Иванов Иван Иванович (уволен)». В списке, карточке и выгрузке Excel; ссылка на запись остаётся. У записей без статуса и с открытым статусом вывод не меняется. При обратном импорте Excel метка не мешает: связь ищется по номеру записи, как сейчас.

## 8. Схема и права

- **Миграций нет.** Реестры, поля и параметр — данные seed, сведения об импорте — `register_imports.summary.source`. Плитку и автоматизации seed не создаёт (решения 5 и 7).
- **Коды прав не меняются:** просмотр — `ib.work`, импорт и правка — `records.edit`, структура — `registers.manage`, пороги — супер-администратор («Параметры портала»).
- **Seed однократный** (`seed_markers`, `awareness.v1`). Удалённое или изменённое администратором seed не восстанавливает. Если уже есть реестр с тем же названием, системному реестру даётся название с «(системный)», как у активов.
- **`check-integrity`:**
    - у реестров есть системные поля;
    - ключи попыток уникальны;
    - параметр порогов проходит проверку;
    - «Сопоставление» согласовано со связью: «Точно» и «Вручную» — со связью, «Не сопоставлен» — без.

## 9. Тестовые файлы

Генератор (`backend/src/test/awareness-files.ts`, рядом с остальными генераторами тестовых файлов — так он проходит typecheck) строит листы и `.xlsx` в памяти:

- **Отчёт INDIGO** на 450 строк вымышленных людей:
    - название теста в объединённой A1 через « | »;
    - сводка в строках 2–10 с метками в отдельной колонке левее чисел, три группы колонок;
    - строка заголовков с объединёнными ячейками и пустыми колонками между ними;
    - три тройки «Б/М/%».
  В отчёте есть:
    - однофамильцы (два «Иванов Иван Иванович» в «Сотрудниках»);
    - человек без отчества;
    - «Семёнов» и «Семенов»;
    - строка с неразбираемой датой;
    - строка после пустой.
  Варианты: сдвинутые колонки; неполный отчёт (сводка на 460 строк); без сводки.
- **Выгрузка HR** на 500 вымышленных сотрудников в «Отдел тестирования», «Отдел проверки» и т. п. Варианты:
    - ФИО одной колонкой с неделимыми ФИО;
    - тремя колонками;
    - файл без части сотрудников (для «Нет в файле»).
- **Двоичный файл с сигнатурой OLE** для отказа (только заголовок, содержимого нет).

# Часть 2. Учебные письма и расписание (релиз 1.9.0)

**Статус: согласовано 05.11.2026.** Ссылки «ответ N» — на раздел «Ответы владельца» плана `docs/plans/release-1.9.0.md`.

## 11. Данные банка

Репозиторий публичный. Текстов реальных писем, имён, адресов и подписи с контактами нет в seed, тестах, фикстурах и документации.

## 12. Что получает пользователь

Новый пункт меню «Осведомлённость» (право `ib.work`):
- **«Письма»** — список с фильтрами (статус, тип, архив), карточка справа (`DetailPanel`, `?letter=`). В карточке:
    - редактор с вкладками RU и TJ;
    - версии и их сравнение;
    - согласование;
    - «Отметить отправленным»;
    - экспорт;
    - события.
- **«Шаблоны»** — шаблоны писем с переменными и кнопка «Письмо из шаблона».
- **«Расписание»** — правила рассылок, ближайшие плановые даты, «Проверить сейчас».
- Кнопка **«Срочная рассылка»** на экране «Письма».

Ещё:
- **«Настройки → Подпись ИБ»** — по `settings.manage` и `ib.work`;
- **«Реестры → Рассылки»** — журнал отправок;
- **дашборд и монитор** — «Ближайшая рассылка» и счётчики.

Писем портал не отправляет. Письмо копируется в почтовый клиент или открывается там как файл `.eml`.

| Отметить отправленным без согласования | Черновик, На согласовании | Отправлено | `ib.work` | только срочное; нет `{{…}}` (400 `UNFILLED_VARIABLES`); комментарий «Отправлено без согласования: причина» обязателен; пометка в карточке и в журнале |
| Отметить отправленным ещё раз | Отправлено | Отправлено | `ib.work` | новая дата и аудитория; новая запись в «Рассылках»; текст не меняется |
| Создать копию | любой | новый Черновик | `ib.work` | содержимое последней версии, тип и повод; без задачи и событий. У отправленного — версия перед `sent`: тот же текст, но «Подпись ИБ» остаётся блоком и показывает текущую подпись, а не текст на дату отправки (решение владельца 05.11.2026) |
| В архив / из архива | любой | тот же | `ib.work` | архивное письмо не правится и не отправляется на согласование |

Остальные переходы — 409 `LETTER_STATE` с понятным текстом.

**Переменные в письме.** `{{подпись}}` — служебная, незаполненной не считается: при каждом сохранении письма она становится блоком «Подпись ИБ» (как в письме из шаблона), в теме — 400 `SIGNATURE_IN_SUBJECT`. Любая другая `{{…}}` в темах или текстах блокирует «На согласование» и первую отметку «Отправлено» (решение владельца 05.11.2026).

### 13.4. Языки (ответ 9)

- **Плановое письмо** — тема и текст обязательны на обоих языках: при отправке на согласование и при отметке «Отправлено». Иначе 400 `LANG_REQUIRED` «Заполните тему и текст на русском и таджикском».
- **Срочное письмо** — достаточно одного языка (тема и текст). Язык считается заполненным, если заполнены и тема, и текст; половина языка — 400 `LANG_REQUIRED`.
    - В карточке и в списке писем — пометка «только RU» или «только TJ».
    - В записи «Рассылок» пометка дописывается к значению «Письмо»: «№ 12, версия 3, только RU».
    - Экспорт предлагает только заполненный язык.

**Аудитория** — текст: «Все сотрудники» или перечень подразделений через запятую. Подсказки — из значений «Подразделения» реестра «Сотрудники» и прежних аудиторий.

### 13.3. События

Каждое действие из 13.2, кроме «Сохранить», — строка `awareness_letter_events`: кто, когда, версия, комментарий, признаки `self_approved` и `without_approval`, дата отправки и аудитория, запись «Рассылок», задача. Таблица только пополняется (триггер). Каждое действие и сохранение пишется ещё и в `audit_log` (`entity = 'awareness_letter'`).

## 14. Версии и заморозка (ADR-0039)

- **Каждое сохранение — новая версия:** номер, кто, когда, тема и текст на обоих языках, причина.
    - Причины: `edit` — правка; `restore` — восстановление; `template` — создано из шаблона; `copy` — копия; `sent` — отправка.
    - Сохранение без изменений версию не создаёт.
- **Просмотр версии** — только чтение. **Сравнение** двух любых версий выводит изменения темы и текста по строкам, отдельно для RU и TJ.
- **«Восстановить версию N»** создаёт новую версию с содержимым N (`restore`, «восстановлена из версии N»). Только в «Черновике» или в «Утверждено» (тогда утверждение снимается, как при правке). Старые версии не меняются.
- **Заморозка.** При первой отметке «Отправлено» создаётся версия `sent`: подпись (раздел 17.3) подставляется текстом на момент отправки. Письмо получает `frozen`.
    - Дальше любая правка темы, текста, типа, повода, статуса и версий — 409 `LETTER_FROZEN` «Письмо отправлено — его нельзя изменить. Создайте копию».
    - То же правило в БД: триггер не даёт менять у замороженного письма статус, ссылки на версии, название, тип, повод, шаблон и задачу, а также добавлять ему версии. Версии и так не меняются.
    - Заморозка не мешает архиву: `archived_at` у замороженного письма меняется — в архив и из архива (условие владельца, DB-тест).
    - Разрешены архив, повторная отметка «Отправлено», «Создать копию» и экспорт.
- **Версии и события не удаляются и не меняются** (триггер).

## 15. Редактор и содержимое

- **Возможности редактора:** заголовки (три уровня), жирный, курсив, подчёркнутый, зачёркнутый, маркированный и нумерованный списки, ссылка, таблица (строки, столбцы, заголовок, объединение), изображение, цитата, горизонтальная линия, «Подпись ИБ».
- **Вставка из Word и Outlook** — через тот же белый список: лишнее оформление отбрасывается.
- **Санитизация — на backend при каждом сохранении** письма, шаблона и подписи. Белый список:
    - **теги:** `h2 h3 h4 p br strong b em i u s ul ol li a table thead tbody tr th td img hr blockquote div span`;
    - **`a`:** `href` с `http:`, `https:` или `mailto:`; относительные и прочие — вырезаются;
    - **`img`:** `src` только `data:image/png`, `data:image/jpeg` или `data:image/gif` в base64, тип подтверждается сигнатурой; `alt`, `width`, `height`;
    - **`td`, `th`:** `colspan`, `rowspan`;
    - **`div`:** `data-ib-fragment="signature"`.
- **Всё остальное вырезается:** `script`, `iframe`, `object`, `embed`, `form`, `input`, `style`, `link`, `meta`, `svg`, `math`; атрибуты `on*`, `style`, `class`, `id`; `javascript:`, `vbscript:` и `data:` в ссылках; внешние и относительные `src`. Сохраняется результат санитизации.
- **Ссылок на портал в письме нет.** `href` на хост `PORTAL_URL` — 400 `PORTAL_LINK` «В письме ссылка на портал — сотрудники его не видят».
- **Изображения хранятся внутри письма** (`data:` в версии). Файлов в хранилище нет.
- **Лимиты** — «Параметры портала → Осведомлённость: размер писем» (`awareness.letters`, меняет супер-администратор):
    - `{ "maxImageKb": 1024, "maxLetterKb": 2048, "warnLetterKb": 1024 }` (ответ 10): письмо уходит на 1500+ ящиков, и каждая копия лежит на почтовом сервере;
    - лимит письма — HTML обоих языков вместе с изображениями;
    - от `warnLetterKb` редактор показывает предупреждение «Письмо N КБ — каждая из 1500+ копий ляжет на почтовый сервер», сохранение не блокируется;
    - проверка параметра: `maxImageKb ≤ maxLetterKb`, `warnLetterKb ≤ maxLetterKb`;
    - превышение — 413 `IMAGE_TOO_LARGE` или `LETTER_TOO_LARGE` с размерами;
    - редактор проверяет размер изображения до вставки, но решает backend.
- **Показ** — только HTML, который санитизировал backend. CSP страниц запрещает встроенные скрипты.

## 16. Экспорт

Язык на выбор: **RU**, **TJ** или **RU+TJ** (у срочного письма с одним языком — только он, раздел 13.4). В RU+TJ сначала русский, затем разделитель (горизонтальная линия) и таджикский; тема — «тема RU / тема TJ». Экспортируется последняя версия, у отправленного — версия `sent`. Можно выбрать любую версию.

- **«Скопировать с оформлением»** — в буфер `text/html` и `text/plain` (Clipboard API). Изображения — `data:`. Если браузер не дал доступа к буферу — подсказка «Выделите текст в предпросмотре и нажмите Ctrl+C».
- **`.eml`:**
    - `MIME-Version: 1.0`, `X-Unsent: 1`, `Subject` по RFC 2047 (`=?UTF-8?B?…?=`, кодированные слова не длиннее 75 символов). `From`, `To` и `Date` не ставятся: их ставит почтовый клиент;
    - тело: `multipart/alternative` → `text/plain` и `multipart/related` → `text/html` и изображения;
    - каждое изображение — часть с `Content-ID`, `Content-Disposition: inline`, в HTML `src="cid:…"`; одинаковые — одна часть;
    - части — base64 в UTF-8, строки по 76 символов, переводы строк CRLF;
    - имя файла — из названия письма.
- **Оформление для почты** добавляется только при экспорте: встроенные стили таблиц, заголовков и шрифта. В БД их нет.
- **Текстовая часть:** заголовки и абзацы, списки «•» и «1.», ссылки «текст (адрес)», таблицы — ячейки через табуляцию.
- **PDF** — через печать браузера: страница печати письма со своим стилем, без интерфейса портала.
- **Журнал:** `awareness_letter.exported` — формат, язык, версия.

Чек-лист проверки в Outlook и WorldClient (веб-почта MDaemon) и известные ограничения клиентов — в руководстве пользователя. Их подтверждает владелец на своих клиентах.

## 17. Шаблоны и «Подпись ИБ»

### 17.1. Шаблон
- Название, тема и текст RU и TJ — тот же редактор и та же санитизация.
- Правка — `ib.work`, с проверкой `version`. Архив вместо удаления. История — из `audit_log`.
- Шаблон в архиве нельзя выбрать в новом правиле и для «Письма из шаблона». Правила, где он уже выбран, создают задачи без черновика (раздел 19.5).

### 17.2. Переменные
- Вид — `{{описание}}`, где описание — любой текст без фигурных скобок, до 60 символов.
- Список извлекается из обеих тем и обоих текстов автоматически и показывается под редактором.
- Сравнение имён — без регистра, пробелы схлопываются. Одинаковое имя в RU и TJ — одна переменная. Для разных значений по языкам нужны разные имена («{{тема RU}}», «{{тема TJ}}»).
- Не больше 30 переменных.
- `{{подпись}}` — служебная: в форму не попадает, становится блоком «Подпись ИБ».
- **«Письмо из шаблона»:** форма — по полю на переменную, плюс название, тип и повод письма. Значения — простой текст, в HTML экранируются. Пустая переменная — 400 `UNFILLED_VARIABLES` со списком, черновик не создаётся. Создаётся черновик (версия `template`).
- **Черновик из расписания** создаётся без формы: переменные остаются в тексте и подсвечиваются. «На согласование» с ними — 400 `UNFILLED_VARIABLES`.

### 17.3. «Подпись ИБ»
- Одна на портал: HTML RU и TJ — подпись и контакт для сообщений о подозрительных письмах.
- Правка — `settings.manage` и `ib.work`, вкладка «Настройки → Подпись ИБ». Служебный администратор её не видит: это содержимое ИБ, а не настройка портала.
- В черновиках, на согласовании и в утверждённых письмах блок «Подпись ИБ» показывает текущую подпись нужного языка — в редакторе, предпросмотре и экспорте.
- В замороженном письме — текст подписи на момент отправки (версия `sent`). Правка подписи его не меняет.

## 18. Реестр «Рассылки»

Системный реестр конструктора `awareness_mailings`. Поля системные: переименовать можно, удалить и архивировать нельзя. Поля не служебные: ручной ввод и импорт Excel разрешены (история прошлых рассылок).

| Ключ | Поле | Тип | Признаки |
|---|---|---|---|
| `sentOn` | Дата отправки | дата | роль аналитики «дата» |
| `letter` | Письмо | текст | «№ 12, версия 3», у одноязычного срочного — «№ 12, версия 3, только RU»; ссылка на карточку письма (ответ 6) |
| `subject` | Тема | текст | заголовок |
| `kind` | Тип | список: Плановое, Срочное | роль аналитики «измерение» |
| `reason` | Повод | текст | |
| `audience` | Аудитория | текст | роль аналитики «измерение» |
| `preparedBy` | Подготовил | сотрудник | варианты — `workUsersWhere()` |
| `task` | Задача | текст | «Задача #123» |

- **Запись создаётся при «Отметить отправленным»** в той же транзакции, обычным созданием записи (`via: awareness_letter`). Повторная отметка — новая запись.
    - Тема — тема отправленного языка, для RU+TJ — «RU / TJ».
    - «Подготовил» — автор письма, если он среди участвующих в работе, иначе пусто.
- **Ссылка.** Значение «Письмо» вида «№ N, версия V» существующего письма показывается ссылкой на его карточку. Другие значения (ручной ввод, история) — просто текст.
- **Права** — как у любого реестра: просмотр — `ib.work`, правка и импорт — `records.edit`, структура — `registers.manage`.
- Сам «Отправлено без согласования» в реестр не пишется. Он виден в карточке письма и в журнале.

## 19. Расписание и автозадачи (ADR-0040)

### 19.1. Правило
| Поле | Правило |
|---|---|
| Название | обязательно, входит в название задачи |
| Периодичность | раздел 19.2 |
| Дата начала | плановые даты не раньше неё; отсчёт для «каждую N-ю неделю» |
| Опережение | 7–90 дней, по умолчанию 10. Меньше 7 нельзя: этап «черновик» — за 7 дней, задача рождалась бы с просроченным этапом (400 в API, CHECK в БД, ограничение в форме) |
| Роль-исполнитель | только роли, держатели которых участвуют в работе (раздел 19.4) |
| Шаблон | необязательно |
| Активно | да / нет |

Правка — `ib.work`, с проверкой `version`. Архив вместо удаления. Предпросмотр «Ближайшие 6 дат» показывает номинальную и плановую дату, перенос и причину.

### 19.2. Периодичность и плановая дата
- **Ежемесячно** в день N (1–31).
- **Дважды в месяц** в дни N и M (N ≠ M).
- **Ежеквартально** в день N K-го месяца квартала (K = 1–3, по умолчанию 1; ответ 11).
- **Ежегодно** D.M.
- **Каждую N-ю неделю** (1–12) в выбранный день недели. Первая дата — первый такой день недели не раньше даты начала.

Даты:
- **Номинальная дата** — по периодичности. День 29–31, которого нет в месяце, — последний день месяца; 29.02 в невисокосный год — 28.02.
- **Плановая дата** — номинальная, перенесённая на предыдущий рабочий день, если она выпала на выходной (`app_settings.work_week`) или праздник (производственный календарь РТ). Перенос может уйти в предыдущий месяц.
- Две номинальные даты одного правила перенеслись на один день — задача одна.
- Все даты — по местному времени портала (`APP_TZ`, по умолчанию Asia/Dushanbe, +05), не по UTC.

### 19.3. Прогон, идемпотентность, догон
- Прогон — шаг ежечасного фонового прогона backend (`plugins/jobs.ts`), после автоматизаций. Своя транзакция и advisory-блокировка: второй экземпляр backend пропускает шаг. «Проверить сейчас» на правиле — тот же прогон для одного правила.
- **Окно:** создаются запуски с плановой датой от сегодня до сегодня + опережение включительно.
- **Идемпотентность.** Запуск — строка «правило + номинальная дата» (уникально). В ней же хранятся плановая дата, даты этапов и задача. Повторный прогон и перезапуск дублей не создают, даже если календарь сдвинул плановую дату.
- **Догон.** После простоя сервера создаются все запуски, чья плановая дата ещё в окне. Даты раньше сегодня не создаются никогда.
- **Отключённое или архивное правило** задач не создаёт. Включённое снова — догоняет только окно.
- **Правка и отключение правила** не трогают созданные запуски и задачи.

### 19.4. Роль-исполнитель и «назначено на роль»
- Выбрать можно только роль с правом `ib.work`, кроме служебной «Администратор портала» (`workRolesWhere()` в `lib/work-users.ts`). То же проверяет API: 400 `BAD_ROLE`.
- Задача создаётся **без исполнителя**, со списком кандидатов: держатели роли, отобранные `workUsersWhere()`. Это общая задача (1.6.4, ADR-0034).
    - Видят её все сотрудники ИБ.
    - «Взять себе» — только кандидаты (403 `NOT_CANDIDATE`), назначить другого — `tasks.assign`. Дальше — обычный процесс задач (ответ 4).
- Пока задачу никто не взял, каждый прогон обновляет кандидатов: добавляет новых держателей роли и убирает тех, кто роль потерял или отключён.
- У роли нет держателей — задача без кандидатов (взять может любой сотрудник ИБ), эскалация сразу.

### 19.5. Задача рассылки
| Свойство | Значение |
|---|---|
| Название | «Рассылка: <название правила> — ДД.ММ.ГГГГ» (плановая дата) |
| Категория | «Осведомлённость» (системная) |
| Приоритет | «Обычный» |
| Срок | плановая дата |
| Источник | `manual`, автор пустой (ответ 3, вариант A); связь — в таблицах модуля. В подсказки цепочек и «Найти среди старых» не попадает (отсекается по связи). Карточка и доска показывают «Создана расписанием: <правило>» |
| Описание | этапы с датами текстом; шаблон в архиве — пометка |

- **Этапы** (даты — в запуске, перенос на предыдущий рабочий день, не раньше дня создания задачи):
    - **черновик** — за 7 дней; выполнен, когда письмо задачи отправлено на согласование;
    - **согласование** — за 3 дня; выполнен, когда письмо утверждено;
    - **отправка** — в плановую дату; выполнен, когда письмо отмечено отправленным.
- Отметить этап вручную нельзя. Просроченный невыполненный этап — красным в карточке задачи и на дашборде.
- **Шаблон в правиле** — черновик письма создаётся сразу и привязывается к задаче (раздел 17.2). Автор черновика — создатель правила (у письма всегда есть автор); в журнале создание — действие системы. Шаблон в архиве или больше лимитов размера — задача без черновика, с пометкой в описании. Без шаблона письмо создаётся из карточки задачи: «Создать письмо» или «Письмо из шаблона». Оно привязывается к задаче.
- **Отметка «Отправлено» задачу не закрывает** (ответ 8): её проходят по обычным правилам проверки (ADR-0022, ADR-0028).
    - В историю задачи пишется запись «Письмо № N отмечено отправленным ДД.ММ.ГГГГ» (`audit_log`, `entity = 'task'`, в транзакции отметки).
    - Пока задача открыта, в карточке — подсказка «Письмо отправлено — завершите задачу» рядом с кнопкой процесса.
    - Так же — у срочной задачи (раздел 19.6).

### 19.6. Другие задачи модуля
- **Срочная рассылка** — кнопка на экране «Письма»: название, повод (обязательно), шаблон (необязательно). Создаётся:
    - письмо «Срочное» с этим поводом;
    - задача «Срочная рассылка: <название>»: исполнитель — нажавший, срок — 1 рабочий день, приоритет «Высокий», категория «Осведомлённость», источник `manual` без автора; карточка и доска показывают «Учебное письмо № N».
- **Доработка после возврата** — задача «Доработать письмо: <название>»: исполнителю задачи письма (рассылки или срочной), если он есть и участвует в работе, иначе автору письма, иначе без исполнителя с меткой «Автор письма». У черновика из расписания автор — создатель правила, а над письмом работает исполнитель задачи. Срок — дата этапа «отправка» запуска, если письмо из расписания, иначе 3 рабочих дня. Категория «Осведомлённость», в описании — комментарий начальника ИБ.

### 19.7. Эскалация
- За 3 рабочих дня до срока (и позже) задачу рассылки никто не взял → уведомление в портале `awareness_unclaimed` «Рассылку «…» никто не взял, срок ДД.ММ».
- Получатель — пользователь с отметкой «Является начальником ИБ». Если отметки нет или её держатель отключён — держатели системной роли «Начальник ИБ» (ответ 2). Получатели — через `workUsersWhere()`: служебных и отключённых среди них нет.
- Один раз на задачу (`dedupe_key`). Писем портал не отправляет.

## 20. Дашборд и монитор

- **Системный виджет «Ближайшая рассылка»:**
    - «<название>, через N дн.» (сегодня — «сегодня», просрочено — «просрочено на N дн.») и три этапа с датами;
    - просроченный этап — красным;
    - ссылка — на задачу;
    - открытых запусков нет — «Запланированных рассылок нет».
- **Счётчики:**
    - «Отправлено писем за <год>: плановых N, срочных M» — отметки «Отправлено» по дате отправки за текущий календарный год;
    - «Рассылки с просрочкой» — открытые запуски, у которых наступила дата этапа, а этап не выполнен.
- **Монитор** — показатели «Ближайшая рассылка» (`awareness_next`: число — дней до отправки, подпись — название, красным при просроченном этапе) и «Рассылки с просрочкой» (`awareness_overdue`) в слайде «Ключевые показатели». Нового вида слайда нет (расхождение 8).

## 21. Схема, права, проверки

- **Таблицы** (одна миграция, только добавляет):
    - `awareness_letters`, `awareness_letter_versions`, `awareness_letter_events`;
    - `awareness_templates`, `awareness_fragments`;
    - `awareness_schedule_rules`, `awareness_schedule_runs`.

   Версии и события только пополняются (триггер). Замороженное письмо меняется только в части архива (триггер).
- **Влияние на данные:** добавляются новые таблицы, существующие данные не меняются. Задачи модуля — обычные строки `tasks` и `task_candidates`, запись «Рассылок» — обычная запись реестра.
- **Права** — коды не меняются:

| Действие | Право |
|---|---|
| Письма, шаблоны, правила, срочная рассылка, экспорт | `ib.work` |
| Утвердить и вернуть | отметка «Является начальником ИБ» (ответ 1) |
| «Подпись ИБ» — правка | `settings.manage` и `ib.work` |
| Лимиты `awareness.letters` | «Супер-администратор» («Параметры портала») |
| «Рассылки» | как у реестров: `ib.work`, `records.edit`, `registers.manage` |

Служебная учётная запись: все маршруты модуля — 403 `SERVICE_ACCOUNT`. Модуль в белый список не входит.

- **Журнал:**
    - `awareness_letter.*` — создание, сохранение (номер версии), переходы, экспорт, копия, архив;
    - `awareness_template.*`, `awareness_fragment.updated`;
    - `awareness_rule.*`, `awareness_schedule.run` — сводная строка прогона, если что-то создано.
- **`check-integrity`:**
    - текущая, утверждённая и отправленная версии принадлежат письму;
    - номера версий без пропусков;
    - у замороженного письма есть версия `sent` и событие `sent`;
    - запись «Рассылок» из события существует;
    - роль правила участвует в работе;
    - у каждого запуска есть задача;
    - системные поля реестра «Рассылки» и фрагмент `signature` на месте.

### 21.1. Запланировано (не в 1.9.0)
- Проверка перехода по ссылке (фишинг-симуляция) — не планируется в этапе 1.
- Отправка писем из портала — нет (внешних интеграций нет).
- Сводка по сотруднику «какие письма получал» — аудитория хранится текстом, связи с «Сотрудниками» нет.
- Свой `source` для задач модуля и перенос задач по таблицам модуля («расширить → перенести → сузить»). В 1.9.0 — только терпимость API и доски к неизвестному `source` («Другое», без 500).
