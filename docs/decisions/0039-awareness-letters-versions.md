# ADR-0039. Учебные письма: версии, согласование и заморозка

Дата: 05.11.2026. Статус: принято (релиз 1.9.0; спецификация — `docs/specs/awareness.md`, разделы 13–17; план — `docs/plans/release-1.9.0.md`).

## Контекст

Отдел ИБ рассылает сотрудникам учебные письма о фишинге и мошенничестве — на русском и таджикском, на 1500+ ящиков. Портал писем не отправляет (внешних интеграций нет, CLAUDE.md, раздел 1): письмо готовится, согласуется и выгружается в почтовый клиент. Нужно:

- видеть, кто и что поменял в тексте, и сравнивать редакции;
- согласовывать у начальника ИБ и не дать отправить не то, что согласовано;
- после отправки письмо не должно меняться — оно уже ушло людям;
- срочное письмо (инцидент) иногда уходит без согласования — это должно быть видно.

## Решение

**Письмо и версии.**
- Письмо — `awareness_letters` (номер, название, тип «плановое» / «срочное», повод, статус, `frozen`, ссылки на текущую, утверждённую и отправленную версии, задача, шаблон, архив). Содержимое — только в версиях.
- Версия — `awareness_letter_versions`: тема и HTML на двух языках, кто, когда, причина (`created`, `edit`, `restore`, `template`, `copy`, `sent`). Каждое сохранение с изменённым содержимым — новая версия; без изменений версии нет. Версии только пополняются (триггер).
- «Восстановить версию N» — новая версия с содержимым N (`restore`, `restored_from`). Сравнение двух любых версий — построчно, на frontend, своя функция без зависимости.

**Статусы.** Черновик → На согласовании → Утверждено → Отправлено (`flow.ts`, без БД, с тестами).
- Утверждает пользователь с отметкой «Является начальником ИБ» (ADR-0027), а не право `docs.approve.head` — оно не используется с 1.4.0. Новых кодов прав нет.
- **Самосогласование** (`self_approved`, «без независимого согласования») — по фактическому участию: утверждающий — автор хотя бы одной версии, написанной человеком (`created`, `edit`, `restore`), или исполнитель задачи письма. Автор по полю `created_by` не годится: у черновика из расписания это создатель правила. Создание расписанием и из шаблона участием не считается.
- Правка утверждённого письма — только с подтверждением «Утверждение будет снято» (409 `APPROVAL_DROP_CONFIRM`); утверждение снимается событием `approval_dropped`. Название в письмо не входит и утверждение не снимает.
- «Отметить отправленным» — если последняя версия утверждена; срочное — и без согласования, с причиной «Отправлено без согласования: …». Незаполненные `{{…}}` блокируют и согласование, и первую отметку.
- События — `awareness_letter_events` (кто, когда, версия, комментарий, признаки, дата отправки и аудитория, запись «Рассылок», задача); только пополняются. Каждое действие — ещё и `audit_log` (`entity = 'awareness_letter'`).

**Заморозка.** Первая отметка «Отправлено» создаёт версию `sent`: блок «Подпись ИБ» подставляется текстом подписи на момент отправки. Письмо получает `frozen`.
- Дальше — только архив, повторная отметка (новая дата и аудитория, новая запись «Рассылок»), копия и экспорт. Остальное — 409 `LETTER_FROZEN`.
- Триггер БД — вторая линия: у замороженного письма меняются только `archived_at`, `version`, `updated_at`; новых версий нет (условие владельца — архив не мешает заморозке, DB-тест).
- «Создать копию» отправленного берёт версию **перед** `sent`: текст тот же, а блок «Подпись ИБ» остаётся живым и показывает текущую подпись.

**Содержимое.**
- Санитизация — на backend при каждом сохранении письма, шаблона и подписи (`sanitize-html`, белый список; `sanitize.ts`). Сохраняется результат. Ссылка на портал — 400 `PORTAL_LINK`.
- Изображения — данными (`data:` PNG, JPEG, GIF с проверкой сигнатуры) внутри версии, без файлового хранилища. Картинки по ссылке (`cid:`, `file://`, внешний адрес) вырезаются, их число возвращается предупреждением «Не вставлено изображений: N…»; редактор при вставке подставляет картинки из буфера вместо ссылок, если они там есть.
- Лимиты — `app_settings.awareness.letters` («Параметры портала»): изображение 1 МБ, письмо 2 МБ, предупреждение от 1 МБ. Превышение — 413.
- `{{подпись}}` в тексте письма при сохранении становится блоком «Подпись ИБ» (как в письме из шаблона); в теме — 400.
- «Подпись ИБ» — одна строка `awareness_fragments`, правка — `settings.manage` и `ib.work`.

**Экспорт** — `.eml` (`X-Unsent`, тема по RFC 2047, `multipart/alternative` с `text/plain` и `multipart/related`, изображения по `Content-ID`), HTML для буфера обмена, страница печати. Встроенные стили для почтовых клиентов добавляются только при экспорте. Каждый экспорт — в журнале.

**Редактор** — TipTap 3.32.0 (MIT), отдельный ленивый чанк ~150 КБ gzip: остальные страницы его не грузят.

## Последствия

- История текста полная и неизменная; отправленное нельзя «тихо» поправить ни через интерфейс, ни через API, ни запросом к БД под ролью приложения.
- Повтор изображений в версиях увеличивает объём таблицы — его ограничивает лимит письма. Десятки писем в год — порядок мегабайт.
- Отправку портал только отмечает: пользователь сам вставляет письмо в Outlook или WorldClient. Чек-лист проверки экспорта — в руководстве пользователя.
- `check-integrity` проверяет версии (принадлежат письму, номера без пропусков), заморозку (версия и событие `sent`), записи «Рассылок».
