# ADR-0030. Срок от передачи ИКТ и продления по обоснованию ОИКТ

Дата: 30.10.2026. Статус: принято (релиз 1.5.0, `docs/specs/vulnerabilities.md`, разделы 5–6).

## Контекст
До 1.5.0 срок устранения шёл от даты «Уведомлено ДИКТ», которую ставил импорт отчёта (по умолчанию = дата отчёта). По процедуре срок идёт от передачи отчёта ИКТ, а ОИКТ может обосновать продление. Все потребители срока (дашборд, монитор, фильтр, Excel, правила п. 7.4, задачи из событий) считают его одной функцией `calcValue` по `values` записи — менять их по отдельности не нужно, если итоговый срок тоже выражается через `values`.

## Решение
- **Формула** (`DueDateRule` получает необязательные `baseFieldId` и `addDaysFieldId`):
  `итог = (меры и «Срок после пересмотра ИБ» заполнены) ? срок ИБ : перенос_на_рабочий( (срок из прежнего реестра ?? передача ИКТ + дни[Критичность]) + продлено_дней )`.
  Дни — календарные (14/30/90/180), окончание на выходном или празднике переносится на ближайший рабочий день по производственному календарю. Ручная Критичность пересчитывает базу.
- **Служебные поля** реестра (seed): «Уведомлено ДИКТ» (`notified`) — дата передачи ИКТ, «Срок из прежнего реестра» (`legacyDue`), «Продлено, дн.» (`extDays`). Их ставит только портал: форма, обратный импорт Excel и массовые действия их не меняют (409 `VULN_SERVICE_FIELD`, в выгрузке — серые колонки).
- **Передача ИКТ** — действие у скана (`records.edit`), один раз: дата (от даты скана до сегодня), кому (по умолчанию «ОИКТ»), файл по желанию. Записи, которые встречались в этом скане после последнего открытия и у которых срок ещё не начался, получают `notified` = дата передачи и скан срока. Срок идёт от первого переданного скана (по времени передачи); поздняя передача более раннего скана его не сдвигает.
- **Повторное обнаружение** устранённой записи: статус «Открыта», новый цикл, `notified`, `legacyDue`, `extDays` и решение п. 7.3 снимаются (в истории — было), срок — от передачи этого или следующего скана. «Риск принят» при новом скане не открывается.
- **Срок из прежнего реестра** — у записей 1.1.0–1.4.0: срок по процедуре на момент обновления (без п. 7.3), пишется seed один раз и только в новое поле; остаётся базой после переноса в узел, снимается при повторном обнаружении.
- **Продление** — право `vulns.deadlines` «Уязвимости: изменение сроков» (никому не выдаётся автоматически, в том числе «Супер-администратору»). Область — узел или все узлы группы. Дни 0–365 по Уровню сканера (и «Без уровня»), только увеличение; участвуют открытые записи с идущим сроком, без решения п. 7.3; фильтры «Только просроченные», «Только со сроком до». Обоснование ОИКТ обязательно: номер, дата, файл; комментарий по желанию. Предпросмотр «было → станет», применение с `expected` (409 `BULK_CHANGED`) одной транзакцией: `vuln_extensions`, `vuln_extension_items` (цикл записи, дни, было, стало), `extDays += дни`, история записи, журнал.
- **Отмена** — целиком, тем же правом, с подтверждением: `extDays −= дни` только у строк текущего цикла записи; событие остаётся с «Отменено <дата>». Таблицы продлений только пополняются (триггер; отмена — один раз).
- После передачи, продления и отмены сразу запускаются автоматизации реестра: ключ события п. 7.4 — дата срока, поэтому новый срок даёт новые напоминания, а старые события не повторяются.
- `check-integrity` сверяет «Продлено, дн.» с суммой действующих продлений текущего цикла и перечисляет расхождения.

## Последствия
- Откат на 1.1.0–1.4.0: старый код игнорирует новые ключи правила — продления не учитываются, у записей из не переданных сканов срока нет, служебные поля редактируемы. Это написано в RELEASE.md.
- Отдельный счётчик «просрочено по процедуре без продлений» — этап 2; в карточке база, продления и итог видны всегда.
