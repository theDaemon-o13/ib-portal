# ADR-0043. Механизмы контроля документа и автоматизации

Дата: 06.11.2026. Статус: принято (релиз 1.11.0; план — `docs/plans/release-1.11.0-documents.md`, раздел 5; решения владельца 05.11.2026 — раздел 11).

## Контекст

У утверждённого документа есть требования, выполнение которых ИБ должна регулярно проверять («пароли — не короче 12 символов» → «раз в квартал проверить групповую политику»). Нужно хранить такие механизмы контроля у документа и ставить по ним периодические задачи ответственным, не заводя второго планировщика и не ломая откат на 1.10.0.

## Решение

**Механизм контроля** — `document_controls` у документа (не у версии: при пересмотре сохраняется): пункт или раздел, требование, механизм со стороны ИБ, способ проверки, ожидаемое доказательство, подразделение-исполнитель, порядок, «активно». Только у утверждённого документа; в архиве — только чтение. Физически не удаляется (права и триггер) — отключается. Изменения — с `version` (409) и в `audit_log` («было → стало»).

**Права без новых кодов.** Вести — владелец документа, начальник ИБ (отметка, не супер-администратор) и `docs.manage`; видеть — сотрудники ИБ (`requirePerm('ib.work')` на маршрутах, роль — в сервисе). Служебная учётная запись (ADR-0036) — 403: модуль не в группе `config.service`.

**Автоматизация** — `document_control_automations`: название и описание задачи, механизм (необязательно, того же документа), периодичность (ADR-0041), дата первого запуска, срок «в течение X дней» (1–365) календарных или рабочих, ответственный (`workUsersWhere()`), «активно». Не удаляется — отключается.

**Прогон** — шаг ежечасного `tick` (`runControlAutomations`) рядом с автоматизациями реестров и расписанием рассылок, своя транзакция и advisory-блокировка; «Проверить сейчас» — тот же прогон для одной автоматизации.
- Запуск `document_control_runs` уникален по «автоматизация + номинальная дата» — повторный прогон дублей не даёт; таблица только пополняется (триггер).
- Срок в рабочих днях: дата запуска с выходного или праздника — на предыдущий рабочий день, не раньше даты первого запуска; несколько номинальных дат с одной плановой — один запуск, по первой (как у расписания рассылок); в календарных — без переноса. Срок задачи — от фактического дня её создания (+ X рабочих по производственному календарю или + X календарных).
- Догон после простоя: номинальная дата не старше 7 дней — задача; старше — запуск «пропущен» без задачи. Задним числом (раньше дня создания автоматизации) запуски не создаются.
- Нет ответственного (отключён, без `ib.work`, служебный): запуск «не создан: нет ответственного», у автоматизации — отметка, автору документа — одно уведомление `doc_control_no_assignee` на состояние; после смены ответственного — снова задачи.
- Документ в архиве или удалён — запусков нет; на пересмотре — работают.

**Задача** — `source = 'document_control'` (`tasks_source_check` расширен), категория — системное значение «Контроль по документу» (`document_control`, seed; одноимённое значение администратора становится системным). Документ — через `document_control_runs.task_id`, **не** `tasks.document_id`: 1.10.0 читает причину задачи по документу строгим списком. В DTO задачи — `origin` вида `document_control` (документ, автоматизация, механизм, дата запуска). Задачу запуска удалить нельзя (409 `TASK_LINKED_TO_CONTROL`, и при массовом удалении), архивировать можно.

**Событие** `automation_events` с `control_automation_id` создаётся и обрабатывается в той же транзакции: CHECK требует `status = 'processed'` — прогоны событий (и 1.10.0 после отката) его не берут.

## Последствия

- Откат на 1.10.0 без отката базы: новые таблицы и колонку 1.10.0 не читает; задачи контроля для него — задачи с неизвестным `source` (API задач с 1.9.0 принимает его без ошибки).
- В реестре утверждённых и выгрузке — число активных механизмов и автоматизаций.
- Фаза 2 (не сейчас): привязка выполненной задачи к доказательной базе, отчёт по контролям, виджет дашборда и слайд монитора, шаблоны механизмов по типу документа.
