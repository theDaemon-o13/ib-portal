# ADR-0012. Дашборд, экран мониторинга, настенный монитор, ключ импорта

Дата: 27.10.2026. Статус: принято (этап 8).

## Контекст

Этап 8 (CLAUDE.md, раздел 12): дашборд с KPI и виджетами из полей реестров с ролью аналитики, экран мониторинга `/monitor` для настенного монитора. Владелец проекта согласовал (27.10.2026):
- новое право `monitor.kiosk` — исключительное, системная роль «Настенный монитор»;
- переменные `MONITOR_ALLOWED_IPS` (пусто — вход монитора запрещён) и `TRUSTED_PROXY_IPS`;
- «Реестр инцидентов» — системный;
- перед nginx портала прокси нет, `X-Forwarded-For` — `$remote_addr`;
- в этап добавлены плитки-счётчики и ключ импорта Excel (подготовка к этапу 8б, реестр «Устройства DLP»).

## Решение

1. **Одно правило на число и ссылку.** Фильтр записей реестра (`modules/registers/filter.ts`) разбирается из адреса: `state`, `deadline`, `f=<поле>:<значения>`, `date`/`from`/`to`. Тот же код считает KPI, виджеты и плитки (`countRecords`) и отдаёт `total` списка `GET /registers/:id/records`. Поэтому число на дашборде совпадает с `total` раздела по его ссылке — это проверяет тест. Задачи (`overdueTaskWhere`), документы (`needsReview`) и доказательства (`listEvidence`) считаются функциями своих списков. Сроки и вычисляемые даты фильтруются в памяти — тем же `deadlineState` и календарём РТ, что и сортировка «срочное сначала».
2. **KPI:**
   - открытые уязвимости, уязвимости с просроченным сроком, со сроком ≤ 7 дней (только на мониторинге);
   - инциденты за 30 дней: «Дата выявления» от сегодня − 29 до сегодня;
   - просроченные задачи;
   - документы к пересмотру: просрочен, идёт или дата пересмотра в ближайшие 30 дней;
   - риски ИБ без решения ОУР: открытые, последнее решение — первый вариант или решений нет;
   - доказательства на проверке и истекающие.

   «Сегодня» — в `APP_TZ`. Архивные и удалённые записи не считаются нигде.
3. **Источники KPI — системные реестры** по `system_key`: `vulns`, `risks` и с этапа 8 `incidents`. Стартовый «Реестр инцидентов» seed помечает системным один раз; «Дата выявления» становится системным полем. Если реестра нет (удалён до этапа 8), KPI показывает «—» с подписью «не настроен».
4. **Расчёт на сервере, запрос на виджет, кэш 1 минута.**
   - `GET /dashboard/kpis` — все KPI одним запросом;
   - `GET /dashboard/widgets` — состав дашборда без данных;
   - `GET /dashboard/widgets/:key` — данные одного виджета или плитки;
   - `GET /monitor` — весь экран одним ответом.

   Кэш — в памяти backend (экземпляр один), общий для дашборда и мониторинга, ключ — виджет. Одновременные запросы ждут один расчёт, ошибка не кэшируется. Права проверяются до кэша. В кэше только данные, одинаковые для всех, кому они видны: документы считаются «взглядом отдела» (`DEPARTMENT_VIEW`), без «моих» согласований. В ответе `computedAt` — «Обновлено в …». Правка плитки сбрасывает её ключ.
5. **Плитки-счётчики** — таблица `dashboard_tiles`: реестр, поле-список или справочник, набор значений, название, порядок.
   - Считаются только открытые записи без архива. Закрытый статус выбрать нельзя.
   - Меняет пользователь с `registers.manage`. Удаление мягкое: у роли приложения нет `DELETE` и `TRUNCATE`.
   - Если поле или реестр ушли в архив или у поля сменили тип, плитка «не считается» и видна только в настройке.
6. **Ключ импорта.** Текстовое поле реестра можно назначить ключом (`register_fields.is_import_key`, одно на реестр — частичный уникальный индекс).
   - Уникальность ключа держит БД: колонка `register_records.import_key` заполняется триггером из `values` по текущему полю-ключу. Нормализация — функция `register_import_key()`: регистр, крайние и повторные пробелы. Частичный уникальный индекс `(register_id, import_key)` действует среди неудалённых записей.
   - Частичный индекс прямо по `values ->> <id поля>` невозможен: id поля у каждого реестра свой, а роль приложения не выполняет DDL. Проверка только в сервисе пропускала бы гонки и пути записи мимо формы (импорт, отчёт сканера).
   - Сервис даёт понятные ошибки до записи: `IMPORT_KEY_TAKEN`, `IMPORT_KEY_DUPLICATES`.
   - Импорт без колонки ID при заданном ключе сопоставляет строки по нему: найдена запись — обновление, нет — новая.
   - Повтор ключа в файле — ошибка во всех таких строках. Пустой ключ и архивная запись — ошибка строки.
   - Предпросмотр показывает сопоставление каждой строки и «нет в файле» — действующие незакрытые записи, которых нет в файле, кандидаты на «Выведено». Портал их не меняет.
   - Перед применением ключи проверяются ещё раз: запись с тем же ключом, заведённая после предпросмотра, даёт `IMPORT_STALE`, и не применяется ничего.
7. **Настенный монитор (`monitor.kiosk`).**
   - **Исключительность:** роль с этим правом не содержит других прав, пользователь с такой ролью не получает других ролей. Проверка — `assertKioskExclusive` в транзакции изменения (как `users.manage`) и в `check:integrity`. Если правило всё же нарушено в БД, `collectPermissions` оставляет киоску только `monitor.kiosk`.
   - **API:** киоску открыты только маршруты с `config.kiosk`: `/monitor`, `/auth/me`, `/auth/logout`, `/auth/change-password`. Остальные отвечают 403 уже в `onRequest`, до разбора тела; guard в `rbac.ts` — второй слой. Тест перебирает все маршруты из OpenAPI.
   - **Вход** только с адресов `MONITOR_ALLOWED_IPS` (IP и подсети, `net.BlockList`), пусто — запрещён. Ответ с чужого адреса — как на неверный пароль, в журнал — `kiosk_ip_denied`, счётчик блокировки не растёт.
   - **Каждый запрос** сессии киоска проверяет адрес: с чужого сессия закрывается (`auth.kiosk_ip_denied`).
   - **Сессия:** не завершается по бездействию, абсолютный срок — 12 часов, после него монитор показывает вход. Политика паролей — полная: смена при первом входе, срок 90 дней. MFA (ADR-0006) на монитор не распространяется: у него нет прав на настройки и пользователей.
8. **Адрес клиента.**
   - nginx передаёт `X-Forwarded-For $remote_addr`, присланный клиентом заголовок отбрасывается.
   - Backend верит заголовку только от `TRUSTED_PROXY_IPS`. Раньше было «loopback и все частные сети»: любой ПК в 10.x подставлял свой адрес, и это касалось и журнала аудита, и блокировки входа.
   - У nginx постоянный адрес в сети `front` — последний адрес подсети `/29` (`FRONT_SUBNET`, `FRONTEND_IP`). Динамические адреса Docker раздаёт с начала подсети, гонки при старте нет.
   - За PT AF или балансировщиком: добавить их адреса в `TRUSTED_PROXY_IPS` и вернуть в `nginx.conf` передачу цепочки (`$proxy_add_x_forwarded_for`). Тогда backend возьмёт адрес, который добавил последний доверенный прокси. (27.10.2026: интеграция с PT AF не планируется — пункт остаётся на случай, если перед порталом появится обратный прокси.)
9. **Экран мониторинга** — отдельный маршрут без меню.
   - Чёрная тема, если в переключателе «Авто».
   - Страницы листаются каждые 12 с, число строк считается от высоты экрана. Панель «назад / пауза / вперёд / на весь экран / закрыть» прячется через 3,5 с без мыши. Клавиши ← → и пробел, Esc закрывает (у киоска — нет).
   - Wake Lock запрашивается снова при возврате на вкладку.
   - Данные обновляются раз в минуту. Если запрос упал или браузер офлайн, данные остаются, сверху плашка «Нет связи с сервером · данные на ЧЧ:ММ».
   - У киоска вместо «закрыть» — «Выйти» с подтверждением.

## Последствия

- Схема: миграция `20261027170000_dashboard_tiles_import_key` — новая таблица и две колонки, данные не переписываются.
- Расчёт сроков в памяти читает весь реестр при каждом пересчёте кэша. На тысячах записей это быстро; при десятках тысяч — денормализовать срок в колонку, отдельным решением.
- Переменные `.env`: `MONITOR_ALLOWED_IPS`, `TRUSTED_PROXY_IPS`, `FRONT_SUBNET`, `FRONTEND_IP`, `BACK_SUBNET` (подсеть сети `back`, по умолчанию `172.31.249.0/24`; добавлена по решению владельца проекта 27.10.2026, чтобы все подсети портала согласовывались заранее). Смена подсети `front` или `back` на уже установленном сервере требует пересоздать сеть: `docker compose down` без `-v`, затем `up -d`. Тома external — данные не затрагиваются. Портал ещё не выкладывался.
- Кэш в памяти не переживает перезапуск backend и не делится между экземплярами. Если backend когда-нибудь станет в несколько экземпляров — пересмотреть.
