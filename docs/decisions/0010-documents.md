# ADR-0010. Документы: версии, маршрут согласования, пересмотр, OnlyOffice

Дата: 27.10.2026. Статус: принято.

## Контекст

Этап 6: реестр внутренних документов ИБ с маршрутом Автор → Начальник ИБ → Юридический отдел → Утверждение правлением (CLAUDE.md, правило 8), новыми версиями после утверждения и контролем пересмотра. Файлы остаются в OnlyOffice, интеграции с его API нет. Пользователи без `ib.work` (юрист, правление) работают только в «Документах», задачи им не ставятся. Владелец проекта решил: номер версии — целое число от портала плюс необязательная «Редакция» для отображения; владелец — только пользователь с `ib.work`; супер-администратор не согласует ни через какую роль; один человек не согласует два этапа одной версии; пересмотр без изменений — тоже новая версия через полный маршрут; ссылка — только http(s); юрист и правление видят ещё документы, согласованные ими в текущем круге.

## Решение

1. **Шапка и версии.** `documents` — номер, тип (по id значения справочника, ADR-0005), владелец, цикл, `review_due`, ссылки на последнюю утверждённую (`approved_version_id`) и рабочую (`working_version_id`) версии, `version` для 409. `document_versions` — номер, редакция, название, ссылка OnlyOffice, «что изменено», этап (0–3), круг. Рабочая версия не больше одной. Статус не хранится: «пересмотр просрочен» зависит от сегодняшней даты (`modules/documents/status.ts`).
2. **Неизменность.** `document_approvals` (история согласования) только пополняется: `REVOKE UPDATE, DELETE, TRUNCATE` у `ibportal_app` и триггер, как у `register_decisions`. Версии не удаляются (`REVOKE DELETE, TRUNCATE` и триггер); UPDATE утверждённой версии (`approved_at` задан) запрещает триггер — и для владельца схемы. Двойное согласование одного этапа в одном круге невозможно и при гонке: частичный уникальный индекс `(version_id, round, stage)` для `submitted`/`approved`.
3. **Права решает сервис.** Маршруты `/documents` — `requireAuth()`, потому что «владелец или `docs.manage`» и «право этапа, но не супер-администратор и не второй этап той же версии» не выражаются одним `requirePerm`. Создание и архив — `requirePerm('docs.manage')`. Права читаются из БД в транзакции действия. Запрос несёт `version` документа и `stage`, который видел пользователь: устаревший экран получает 409 (`VERSION_CONFLICT`, `STAGE_CHANGED`) и не согласует следующий этап.
4. **Документ и версия 1** ссылаются друг на друга, а `documents_has_version_check` требует ссылку на версию уже при вставке. Внешние ключи документа на версии — `DEFERRABLE INITIALLY DEFERRED` (миграция `documents_deferred_fk`); после создания сервис проверяет ссылку сразу (`SET CONSTRAINTS … IMMEDIATE`) и возвращает отложенный режим.
5. **Задачи.** У задачи — `document_id` и `document_reason` (`review` | `returned`), источник `document`, системная категория «Документы». Одна открытая задача на (документ, причина, ответственный) — частичный уникальный индекс `NULLS NOT DISTINCT`; повтор — комментарий. Владелец без `ib.work` — задача без ответственного с меткой «Владелец документа». Отправка на согласование закрывает задачу доработки, утверждение — задачу пересмотра.
6. **Пересмотр через `automation_events`** (ADR-0008, ADR-0009): у события новая колонка `document_id`, у `register_id`, `record_id`, `automation_id` снят `NOT NULL`, CHECK `automation_events_subject_check` требует ровно один предмет. Событие уникально по `(document_id, trigger_key = дата пересмотра)`, создаётся и превращается в задачу в общем часовом прогоне автоматизаций под тем же advisory-lock. Обработчик событий реестра берёт только `document_id IS NULL`. Старый backend событий документов не видит: они обрабатываются в той же транзакции, где созданы, а его выборки идут по реестру, записи или статусу `new`.
7. **Владелец не согласует этапы 1–3 своего документа** (решение владельца проекта, 27.10.2026) — даже если документ отправил другой пользователь с `docs.manage`; в списке согласующих этапа его нет. Если у этапа нет другого согласующего (у владельца есть право этапа, других активных пользователей с этим правом, кроме супер-администраторов, нет), этап при переходе на него пропускается: в `document_approvals` пишется решение `skipped` от имени владельца с причиной «Не требуется: автор — <этап>…», в журнал аудита — `document.stage_skipped`; затем проверяется следующий этап, пропуск последнего утверждает документ. Если права этапа нет ни у кого, этап не пропускается — документ ждёт («никто не назначен»). Решение `skipped` добавлено миграцией `documents_skipped_stage`; сборка этапа 6 без неё не открыла бы карточку с пропуском, поэтому они выкладываются одним релизом.
8. **Видимость без `ib.work`**: действующая версия утверждённых документов, рабочая — если ждёт пользователя или он согласовал её в текущем круге; черновики, чужие этапы и архив — нет (404). Ответ действий — `{ document: … | null }`: после возврата на доработку юристу документ может стать невидим.
9. **OnlyOffice сейчас** — ссылка `http(s)` (проверка в сервисе и CHECK в БД), открывается в новой вкладке с `rel="noopener noreferrer"`.

## Последствия

- **Заморозка текста — этап 7, обязательно.** Ссылка не фиксирует содержимое: файл в OnlyOffice можно изменить после утверждения. На этапе 7 при утверждении версии к ней обязательно прикладывается итоговый PDF — файл в хранилище `files` с sha256 (ссылка из `document_versions`, добавляется миграцией «расширить»). Утверждённая версия без PDF (все утверждённые до этапа 7) показывается с пометкой «текст не зафиксирован».
- **Интеграция с OnlyOffice (позже)** потребует:
  1. хранить идентификатор файла и версии в OnlyOffice вместо URL (API OnlyOffice Docs / DocSpace);
  2. при утверждении забирать PDF через Conversion API — это же закрывает заморозку текста;
  3. для правки из портала — Document Server API: JWT-секрет (новая переменная `.env`), маршрут `/api/v1/onlyoffice/callback` с проверкой JWT и сетевой доступ между Document Server и backend. Сейчас сеть `back` — internal, это изменение compose и сетей, его нужно согласовать;
  4. согласование с администраторами OnlyOffice: адрес, версия, сервисная учётная запись. Ограничение ссылок адресом сервера OnlyOffice — в CHANGELOG, «Перед первой выкладкой».
- Письма согласующим — этап 9; пока число «ждёт вас» у пункта «Документы». **Пересмотрено 27.10.2026:** этап 9 не планируется, писем не будет — остаётся число «ждёт вас».
- Новых кодов прав и зависимостей не понадобилось.

## Решение 27.10.2026: OnlyOffice остаётся ссылкой

Владелец проекта: внешних интеграций нет, портал работает на закрытом хосте сам по себе. По OnlyOffice выбран вариант «оставить как есть»:
- у версии документа — ссылка на файл в OnlyOffice (`http(s)`) и обязательный итоговый PDF при отправке на согласование (этап 7): он фиксирует текст и хранится в портале с sha256;
- интеграции с API OnlyOffice (Document Server, Conversion API, JWT, callback) нет, отдельный этап под неё не нужен. Раздел «Интеграция с OnlyOffice (позже)» выше сохранён как история рассматривавшегося варианта;
- в силе пункт «Перед первой выкладкой» CHANGELOG: ограничить ссылки адресом сервера OnlyOffice банка (переменная `.env`, правка compose — по согласованию).
