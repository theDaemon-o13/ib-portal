# ADR-0022. Процесс задач по колонкам и кнопкам

Дата: 29.10.2026. Статус: принято (релиз 1.2.0, этап Б).

## Контекст
До 1.2.0 любой сотрудник ИБ двигал задачу между колонками «Новые / В работе / На проверке / Готово» в любую сторону, назначал любого исполнителя и закрывал задачу сам. Владелец ввёл процесс: кто ставит, кто берёт, кто проверяет — по правам и иерархии (ADR-0020), с комментариями на ключевых переходах и следом каждого перехода.

## Решение
- **Колонки** — системные значения справочника «Статусы задач»: `new` Backlog (без исполнителя), `assigned` Поставленные (исполнитель назначен, работа не начата), `work` В работе, `review` На проверке, `done` Выполнено. Названия меняются, порядок системных колонок — нет. Администратор добавляет свои колонки в нужное место; в них задачу переносит только `tasks.status.override`. Свою колонку можно отправить в архив, когда в ней нет задач, удалить — если через неё не проходили задачи.
- **Исполнитель определяет начало процесса**: создание с исполнителем — «Поставленные», без — Backlog; назначили — «Поставленные», сняли — Backlog; сменили исполнителя у задачи «В работе» / «На проверке» — «Поставленные» (новый исполнитель берёт задачу сам). Задачи автоматизаций, документов и доказательств — по тому же правилу; система закрывает их сама в «Выполнено», без проверки.
- **Признаки колонки** `comment_forward` и `comment_return`: комментарий обязателен при переходе в колонку из колонки левее / при возврате из колонки правее. Это настройка, не код: по умолчанию вперёд — «На проверке» и «Выполнено», возврат — «В работе». Новые колонки получают те же признаки.
- **Переходы** — `task_transitions` (кто, когда, откуда, куда, вид, комментарий), только пополняется: `REVOKE UPDATE, DELETE, TRUNCATE` у роли приложения и триггер (как у `audit_log`, ADR-0002). Виды: `process` (кнопки и создание), `override` (свободная смена), `assign` (назначение / снятие исполнителя), `system`, `migration`. Комментарий перехода — ещё и строкой `task_comments` (`transition_id`): его видят все, кто видит задачу (это не история, ADR-0021).
- **Обновление на 1.2.0** — однократный шаг seed `tasks.process.v1_2`: колонка «Поставленные», порядок, «Новые» → «Backlog» и «Готово» → «Выполнено» (только если администратор их не переименовывал), признаки, перенос задач «Новые» с исполнителем (и архивных) в «Поставленные» с переходом `migration`. Удалённые задачи не трогаются. При каждом `migrate` открытые задачи выравниваются по исполнителю — на случай отката на 1.1.0 и повторной выкладки. `check-integrity` проверяет, что открытые задачи на месте.
- **Кнопки процесса** (Б2) — `POST /tasks/:id/actions/:action`: `take` Backlog → Поставленные (исполнитель — я, любой с `ib.work`), `start` Поставленные → В работе и `submit` В работе → На проверке (только исполнитель), `accept` На проверке → Выполнено и `return` На проверке → В работе (`tasks.review`, не исполнитель, и автор задачи, или старший над исполнителем, или у исполнителя нет руководителя). Действие не из своей колонки — 409 `WRONG_STATUS`, своя задача — 409 `OWN_TASK`, нет права — 403. В ответах с задачей поле `actions` — кнопки, доступные этому пользователю: frontend показывает только их, решает всегда backend.
- **Права** — в сервисе, по правам сессии (`TaskActor`): `PATCH statusId` — только `tasks.status.override` (403 `NO_OVERRIDE`); другой исполнитель при создании и правке — `tasks.assign` (403 `NO_ASSIGN`); без права — себя на задачу без исполнителя и снять себя, пока задача в «Поставленные» (иначе 403 `TASK_TAKEN`). Супер-администратор прав процесса по умолчанию не получает (решение владельца: всё новое — «Начальник ИБ»).
- В журнале аудита шаг процесса — `task.transition` («было → стало», в истории карточки); свободная смена — `task.updated`, как раньше.
- **Отчёт** (Б4) — `GET /tasks/report` по праву `tasks.report`, Excel; фильтр периода — по дате создания, сроку или выполнению (решение владельца), в часовом поясе банка. Даты шагов — первый вход в колонку по `task_transitions` без переносов `migration`; для задач до 1.2.0 — по `task.updated` с изменением статуса в `audit_log` (название колонки → ключ, прежние названия «Новые» и «Готово» учитываются), только чтение. Больше 100 000 задач — 409 `TOO_MANY_ROWS`. Выгрузка — `tasks.report_exported` в журнале.

## Последствия
- Две миграции только расширяют схему; backend 1.1.0 после отката видит пятую колонку и работает как раньше.
- Число задач, которые перенесёт обновление, DevOps проверяет запросом из `deploy/prechecks/1.2.0.md` (раздел «Перед выкладкой» в `RELEASE.md`).
- Доска строит столько колонок, сколько в справочнике.
