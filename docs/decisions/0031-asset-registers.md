# ADR-0031. Три реестра активов и сверка

Дата: 01.11.2026, переработано 02.11.2026 по процедуре классификации ИТ-активов. Статус: принято (релиз 1.6.0, `docs/specs/assets.md`).

## Контекст
Самооценка должна опираться на данные портала, но единой базы активов нет. Сервисы инвентаризирует ИБ, серверы и рабочие станции учитывает бухгалтерия, автоматического сбора нет. Следующему этапу («Что видит портал») нужны проверяемые факты без пересчёта.

Владелец передал процедуру классификации ИТ-активов, реестр сервисов в Excel и отчёты Kaspersky Security Center. В процедуре продукт (Приложение 2) определяется через сервисы-компоненты, а реестр Excel — это компоненты с IP:порт.

## Решение
- **Три системных реестра конструктора** — «Сервисы» (уровень продукта), «Компоненты», «Хосты». Без миграций и новых прав. Компонент ссылается на продукт и хост полями «Связь с записью», хост на продукты — тоже. Продукт ссылается на значение справочника «Системы», поэтому риски и уязвимости находятся без новых связей. С учётом бухгалтерии не связываем.
- **Категории критичности по процедуре:** Mission Critical, Business Critical, Operational, Non-Critical. Значимые для сверки и самооценки — первые две. Набор хранится в `app_settings.assets`, его меняет супер-администратор в «Параметрах портала».
- **Новых видов вычисляемых полей нет** (решение владельца 02.11.2026):
    - «Пересмотр до» — существующий вычисляемый срок: «Дата классификации» + 183 дня по любой категории. Без категории срока нет: это поймает сверка.
    - RTO и RPO — текстовые поля. Таблица значений по категориям из Приложения 3 показана в подсказке поля (новая настройка поля `settings.hint`). Значимый продукт без RTO или RPO — проверка сверки.
    - «Покрытие защиты» — список, который ставит только адаптер KSC.
- **Служебные поля активов** — «Ключ компонента», «ОС / ПО в источнике», «Покрытие защиты». Их ставят адаптеры импорта; форма и обратный импорт Excel их не меняют (тот же механизм, что у служебных полей уязвимостей, 409).
- **Условная обязательность** («Работает» только с категорией, уровень 4 раздела 2.3) конструктором не поддерживается и ради этого не добавляется. Вместо неё — проверка сверки `products.working_without_category`.
- **Сверка** — только чтение, считается при запросе и не хранится. Единая структура факта: код, раздел методики, связанные разделы, числитель, знаменатель, процент, записи со ссылками, дата расчёта, сообщение, предупреждения.
- **Пустота не становится числом.** Если источник пуст или проверять нечего, факт получает `no_data`: ни процента, ни списка. Подтвердить отсутствие может только человек.
- **Выведенное не считается.** Закрытый статус, архив и удаление исключают запись из числителя, знаменателя и списка.
- **Имена хостов** сравниваются без регистра и доменного суффикса. Совпавшие записи реестра не склеиваются, в факте — предупреждение со ссылками. Для отчётов KSC действует ADR-0032.
- **Процент округляется вниз**, чтобы 84,96% не прошло порог 85% из правил методики.

## Последствия
- Уровень 4 разделов 2.2 и 2.3 моделью не обеспечивается. Серверы частично вносятся вручную. Классификация при вводе в эксплуатацию — процесс вне портала.
- Записи уязвимостей с хостами не связаны, поэтому категория не входит в формулу Оценки. Значимость учитывается ручной поправкой Критичности.
- Реестры первой редакции (только dev и тесты) seed доводит до трёх реестров на месте. Поля переименовываются, значения шкалы тоже, поэтому записи сохраняют выбор. Прежнее поле-дата «Пересмотр до» и «Состояние защиты» уходят в архив вместе с данными.

## Текст методики на экране «Активы»
Сотрудникам с `ib.work` виден текст разделов методики, на которые ссылаются проверки: без него номера разделов ничего не говорят. ADR-0026 это не меняет. Оценки, баллы и маршруты `/api/v1/assessments` остаются только у `assessment.manage`, ссылка в чек-лист показывается только этому праву.
