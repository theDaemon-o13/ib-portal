# ADR-0002. Групповая роль ibportal_app и неизменяемый журнал аудита

Дата: 2026-10-26. Статус: принято.

## Контекст
CLAUDE.md, разделы 3.5 и 3.6: у роли приложения нет `UPDATE` и `DELETE` на `audit_log`. Имя логина приложения задаётся в `.env` (`DB_APP_USER`), а миграции должны ссылаться на роль по имени. Init-скрипт выполняется до миграций, когда таблицы `audit_log` ещё нет.

## Решение
- `db/init/01-app-role.sh` создаёт групповую роль `ibportal_app` (NOLOGIN) с фиксированным именем и логин `$DB_APP_USER` — её члена. Все права выдаются группе, в том числе через `ALTER DEFAULT PRIVILEGES FOR ROLE <владелец>`.
- У группы нет `CREATE` на схему `public`, `CONNECT` к базе — только у неё и владельца.
- Первая миграция отзывает у `ibportal_app` `UPDATE`, `DELETE`, `TRUNCATE` на `audit_log` и права на `_prisma_migrations`.
- Дополнительно триггеры `BEFORE UPDATE OR DELETE` и `BEFORE TRUNCATE` запрещают правку журнала для всех ролей, включая владельца. Это защита от ошибки, а не от суперпользователя.
- `npm run check:integrity` проверяет эти права и триггеры.

## Последствия
- Новые таблицы автоматически получают права для приложения. Если какой-то новой таблице нужны более узкие права, их отзывает миграция, создающая таблицу.
- Восстановление из копии (`pg_restore --clean`) пересоздаёт таблицу вместе с триггерами: `DROP TABLE` триггеры строк не вызывает.
