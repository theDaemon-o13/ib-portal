# ADR-0009. События автоматизаций → задачи; метки получателей

Дата: 27.10.2026. Статус: принято. Дополняет ADR-0008.

## Контекст

На этапе 4 автоматизации создавали события в `automation_events` с получателями: поле-сотрудник записи или текстовая метка («Руководитель ДИКТ», «Владелец системы»). На этапе 5 появились задачи, и события должны превращаться в задачи конкретным людям. Владелец проекта решил:
- в справочнике «Системы» — поле «Владелец системы» (пользователь портала);
- новый справочник «Получатели уведомлений»: метка → пользователи портала и/или e-mail; участники метки — только пользователи с `ib.work`, люди вне портала указываются e-mail (письма — этап 9);
- если после разворачивания метки нет ни одного пользователя (или владелец системы без `ib.work` / не задан) — задача без ответственного с меткой, в карточке видны метка и e-mail;
- при смене руководителя меняется одна строка справочника, правила остаются как есть.

## Решение

1. Метки — значения справочника `notify_recipients` (вид `values`, поведение по коду справочника). Участники — таблица `catalog_item_users`, адреса — `catalog_items.emails`. Сервис отказывает в участнике без `ib.work` и подсказывает указать e-mail. Системные метки (seed): «Руководитель ДИКТ», «Начальник ИБ», «Руководство Банка» и «Владелец системы» — у последней участников нет.
2. Правила ссылаются на метку по id значения справочника (`{ kind: label, itemId, label }`, ADR-0005); `label` — название на момент сохранения, его читает backend предыдущей версии. Текстовые метки этапов 4–5 перенесены миграцией `rule_recipient_ids` (функция `link_recipient_labels()`, её же вызывает seed после создания меток); ненайденные получают `itemId: null` — «получатель не найден». Метку можно переименовывать. Новый вид получателя — сотрудник по id (`{ kind: user }`). Удаление ключа `label` — отдельным релизом («сузить»).
3. «Владелец системы» находится через новое поле конструктора «Значение справочника» (`register_fields.catalog_code`): в реестре уязвимостей — системное поле «Система» (seed v2, добавляется в конец существующего реестра). Система выбирается при загрузке отчёта сканера для всех новых записей.
4. Событие обрабатывается в той же транзакции, что и прогон автоматизаций (под тем же advisory-lock): получатели разворачиваются в пользователей с `ib.work` на момент обработки, создаются задачи категории «Реестр» (по одной на пользователя), событие становится «обработано», связь — `automation_event_tasks (created | commented)`.
5. Одна открытая задача на `(правило, запись, ответственный)` — частичный уникальный индекс `NULLS NOT DISTINCT` (и для «не назначен»). Повторное срабатывание по открытой задаче добавляет в неё комментарий; после «Готово», архива или удаления создаётся новая задача.
6. Без пользователей — одна задача без ответственного, `recipient_label` хранит метки; карточка показывает их e-mail.

## Последствия

- Кнопка «Обработано» в карточке записи больше не нужна: событие ведёт к своим задачам. Маршрут `POST /automation-events/:id/process` оставлен для совместимости.
- В записи реестра счётчик и фильтр — по открытым задачам (`openTasks`, `withTasks`); старые `openEvents` и `withEvents` остаются в API.
- E-mail меток пока только хранится и показывается; отправка — на этапе 9 через MDaemon.
  **Пересмотрено 27.10.2026:** этап 9 не планируется — внешних интеграций нет. E-mail меток хранится и показывается только для справки («для справки, письма портал не отправляет»).
