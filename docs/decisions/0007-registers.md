# ADR-0007. Конструктор реестров: хранение значений, решения другого отдела, импорт Excel

Дата: 2026-10-26. Статус: принято (этап 3).

## Контекст
Реестры собираются из полей в интерфейсе (docs/concept.md, раздел 1). Требования владельца проекта: значения хранятся по id поля; поле с данными не удаляется; вычисляемое поле и решение другого отдела не перезаписываются формой и импортом; импорт Excel — в два шага; одновременная правка — через version и 409.

## Решение
- **Значения записи** — `register_records.values jsonb`: ключ — id поля; значение списка — id варианта (`register_field_options`), сотрудника — id пользователя. Переименование поля или варианта меняет только подпись.
- **Вычисляемое поле** хранит правило `{ fromFieldId, byFieldId, days: { optionId: N }, overrideFieldId }` и вычисляется при чтении. В `values` его нет — перезаписать нечем. Поля из правила нельзя архивировать и менять у них тип, пока правило на них ссылается.
- **Решение другого отдела** — отдельная таблица `register_decisions`, только пополняется (права и триггер как у `audit_log`). Значение поля всегда читается оттуда (последнее решение), иначе показывается первый вариант («Ожидает решения»). На этапе 7: внешний ключ `file_id → files`, `NOT NULL` (таблица до того пустая) и маршрут внесения решения с файлом. Чтение и отображение уже окончательные — переделывать не придётся.
- **Удаление**: поле — только без данных (иначе архив); значение списка — только неиспользуемое; запись — мягко (`deleted_at`), по праву `records.delete`, со снимком значений в журнале; запись с решениями — только в архив.
- **Смена типа** — варианты А (поле без данных), Б (число, дата, список, сотрудник → текст), В (текст → число, дата, список, если все значения распознаются). Всегда предпросмотр «изменится N записей», затем одна транзакция с записью в журнал по полю и по каждой записи.
- **Импорт Excel**: файл приходит телом запроса (без multipart), лимит 25 МБ и 20 000 строк. Предпросмотр сохраняется в `register_imports` на 30 минут вместе с версиями записей и полей; применение проверяет, что ничего не изменилось, и выполняется одной транзакцией. Сам файл не хранится (только имя и sha256) до появления файлов на этапе 7. Применить может только загрузивший.
- **Экспорт**: лист «Реестр», скрытый лист `_поля` (колонка → id поля, id реестра) и лист «Справка» с правилами заполнения.
- **Поиск** — по `search_text` (отображаемые значения), который пересчитывается при записи, переименовании варианта и смене ФИО сотрудника. Сортировка по вычисляемому сроку — на этапе 4.
- **Право** `registers.manage` (структура реестров) выдаётся только «Супер-администратору»; на уже установленных порталах — один раз через seed.
- **exceljs 4.4.0**: последняя стабильная; `uuid` внутри переопределён на 11.1.1 (`overrides`), чтобы закрыть предупреждение npm audit.

## Последствия
- Этап 4 (уязвимости) опирается на `system_key` реестра и на правило вычисления; сортировка и контроль сроков добавляются там.
- Этап 7 добавляет файлы и маршрут внесения решения, не меняя хранение.
