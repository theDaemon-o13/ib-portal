# ADR-0005. Справочники, календарь и журнал изменений настроек

Дата: 2026-10-26. Статус: принято.

## Контекст
Этап 2: справочники с архивом и системными значениями, производственный календарь РТ, шаблоны форм, пользователи и роли, журнал изменений (CLAUDE.md, разделы 3.4, 3.5, 6, 7 п. 10; docs/concept.md, раздел 9).

## Решение
- **Общие таблицы** `catalogs` (фиксированный набор, создаёт seed) и `catalog_items`. Ссылки на значения — по `id`. Цвет — ключ тона из `tokens.css` (`accent`, `info`, `low`, `high`, `med`, `crit`, `muted`), а не hex: подстраивается под тему.
- **Системные значения** отмечены `system_key`; seed создаёт их, если их нет, и никогда не перезаписывает (статусы можно переименовывать). CHECK в БД запрещает архивировать и удалять системное значение.
- **Мягкое удаление**: `archived_at` — значение скрыто из списков выбора; `deleted_at` — удалено (только несистемное и неиспользуемое). Уникальность значения без учёта регистра — частичный индекс `(catalog_code, lower(value)) WHERE deleted_at IS NULL`. Prisma 6 такие индексы не описывает и не трогает (проверено `migrate diff`).
- **«Используется»**: реестр счётчиков `modules/settings/usage.ts`. Модули следующих этапов регистрируют в нём, сколько их записей ссылается на значение или шаблон. Мягкое удаление не срабатывает на FK, поэтому проверка явная.
- **Календарь** — отдельная таблица `work_calendar_days` (`holiday` / `workday`) и настройка `app_settings.work_week`. Расчёт — чистые функции `lib/working-days.ts`.
- **Стартовые значения** seed создаёт один раз: отметки в `seed_markers`.
- **Защита от одновременной правки**: колонка `version` и `updateMany({ where: { id, version } })`; 0 строк → 409 `VERSION_CONFLICT`.
- **Журнал изменений** — из `audit_log`, отдельной таблицы нет. Запись пишется в той же транзакции, что и изменение. В `diff`: `summary` (готовая фраза, не меняется после переименований), `actorRoles` (роли автора на момент изменения), `before`/`after`. Действия с префиксами `catalog.`, `calendar.`, `form_template.`, `user.`, `role.`.
- **Правило `users.manage`** проверяется одной функцией после изменения внутри транзакции под `pg_advisory_xact_lock`: снятие права у роли, снятие роли, отключение пользователя, удаление роли. Нарушение откатывает изменение.
- **Роли удаляются физически** (не бизнес-сущность раздела 3.4): только несистемная роль без пользователей, снимок — в журнале.
- Колонки `created_by`/`updated_by` в таблицы настроек не добавлены: автор каждого изменения есть в `audit_log`.

## Последствия
- Новые модули ссылаются на `catalog_items.id` и регистрируют счётчик использования.
- Вложенные вызовы `withTx` работают через `SAVEPOINT`, поэтому сервисы можно вызывать внутри внешней транзакции (так устроены тесты `npm run test:db`).
