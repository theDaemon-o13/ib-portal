# ADR-0041. Общая периодичность: lib/cadence.ts

Дата: 06.11.2026. Статус: принято (релиз 1.11.0; план — `docs/plans/release-1.11.0-documents.md`, раздел 1, п. 9, и раздел 5.2).

## Контекст

Периодичность и перенос с нерабочего дня уже есть у расписания рассылок (1.9.0, ADR-0040: `awareness-letters/cadence.ts`). Автоматизациям механизмов контроля документов (ADR-0043) нужна та же арифметика дат плюс виды «ежедневно» и «раз в полгода» и запуск без переноса для сроков в календарных днях. Две копии одного кода разошлись бы при первой правке; при этом API и поведение рассылок 1.9.0 менять нельзя (их тесты — без изменений).

## Решение

- **`backend/src/lib/cadence.ts`** — общая механика: `nominalDates` по всем видам (`daily`, `weekly` (каждые N недель, день недели), `monthly`, `twice_monthly`, `quarterly`, `semiannual`, `yearly`), день 29–31 в коротком месяце — последний день, 29.02 в невисокосный год — 28.02; `plannedDate(nominal, календарь, 'prev' | 'none')` — перенос на **предыдущий** рабочий день по производственному календарю или без переноса.
- **У каждого модуля — свой список видов** (zod-схема в модуле): рассылки — прежние пять (`awareness-letters/cadence.ts` сохраняет схему, окно запусков и этапы, вычисления берёт из `lib/cadence.ts`); автоматизации контроля — `daily`, `weekly` (каждую неделю), `monthly`, `quarterly`, `semiannual`, `yearly` (`documents/automations.ts`).
- Все даты — строки `YYYY-MM-DD` по `APP_TZ`.

## Последствия

- Поведение рассылок не меняется: их юнит- и db-тесты 1.9.0 проходят без изменений.
- Новый вид периодичности добавляется в `lib/cadence.ts` и разрешается схемой нужного модуля; CHECK в БД у автоматизаций контроля перечисляет допустимые виды.
