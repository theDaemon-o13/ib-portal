# ADR-0040. Расписание рассылок поверх фоновых задач

Дата: 05.11.2026. Статус: принято (релиз 1.9.0; спецификация — `docs/specs/awareness.md`, разделы 18–20; план — `docs/plans/release-1.9.0.md`).

## Контекст

Плановые учебные письма уходят по графику: раз в месяц, дважды в месяц, раз в квартал и т. д. Нужно, чтобы задача на подготовку письма появлялась заранее, доставалась тем, кто ведёт рассылки, и чтобы просрочку замечали. При этом:

- в портале уже есть ежечасный фоновый прогон (`plugins/jobs.ts`) — второго планировщика быть не должно;
- откат на 1.8.0 не должен ломать доску задач: в 1.8.0 `source` задачи — закрытое перечисление, а `tasks_automation_check` требует правило автоматизации у `source = 'automation'`;
- даты — по местному времени банка и производственному календарю РТ.

## Решение

**Правило** — `awareness_schedule_rules`: название, периодичность (`cadence.ts`, `jsonb` с проверкой zod), дата начала, опережение 7–90 дней (этап «черновик» — за 7 дней, поэтому меньше нельзя: CHECK, API и форма), роль-исполнитель, шаблон, «активно». Роль — только та, держатели которой участвуют в работе: `workRolesWhere()` (право `ib.work`, не служебная).

**Даты.** Номинальная — по периодичности (день 29–31 в коротком месяце — последний день; 29.02 — 28.02). Плановая — номинальная, перенесённая на **предыдущий** рабочий день (`onOrPrevWorkingDay`). Даты этапов — черновик за 7 дней, согласование за 3, отправка в плановую дату, с тем же переносом, но не раньше дня создания задачи. Всё — по `APP_TZ` (Asia/Dushanbe).

**Прогон** — шаг ежечасного `tick` после автоматизаций (`runAwarenessSchedule`), своя транзакция и свой ключ `pg_try_advisory_xact_lock`: второй экземпляр backend пропускает шаг, ошибка расписания не откатывает автоматизации. «Проверить сейчас» на правиле — тот же прогон для одного правила.
- Окно: плановые даты в `[сегодня; сегодня + опережение]`. Даты раньше сегодня не создаются никогда — так ограничен догон после простоя.
- Идемпотентность: запуск `awareness_schedule_runs` уникален по «правило + **номинальная** дата» — смена календаря двигает плановую дату, но не ключ. Тот же плановый день по другой номинальной дате второго запуска не даёт.
- Отключённое или архивное правило не участвует; правка правила не трогает созданные запуски.

**Задача рассылки** — обычная строка `tasks`: общая, без исполнителя, кандидаты — держатели роли (`task_candidates`, 1.6.4), категория «Осведомлённость», срок — плановая дата. Этапы — в строке запуска и текстом в описании (1.8.0 после отката покажет описание). Шаблон правила — черновик письма сразу (автор — создатель правила, создание в журнале — действие системы); шаблон в архиве или больше лимитов — задача без черновика с пометкой.
- **Источник** — `source = 'manual'` без автора (решение владельца, вариант A): `tasks_source_check` и `tasks_automation_check` не меняются, откат на 1.8.0 безопасен. Происхождение — только по таблицам модуля; в DTO задачи — `origin` («Создана расписанием: <правило>» / «Учебное письмо № N»). Из подсказок цепочек и «Найти среди старых» такие задачи отсекает проверка связи.
- **Терпимость к неизвестному `source`** — в ответах API задач `source` теперь строка, неизвестное значение отдаётся как есть («Другое» в интерфейсе). Это заготовка «расширить → перенести → сузить» (CLAUDE.md, 3.3) для своего источника в следующих релизах; DB-тест вставляет задачу с `source = 'awareness'` под владельцем в транзакции с откатом.
- Пока задачу никто не взял, каждый прогон обновляет кандидатов. Роль без участников или роль, с которой сняли `ib.work`, — задача без кандидатов («у роли нет участников»).
- **Эскалация** `awareness_unclaimed` — за 3 рабочих дня до срока и позже, если задачу никто не взял, или сразу без участников. Получатель — держатель отметки «Является начальником ИБ», иначе держатели роли «Начальник ИБ» (через `workUsersWhere()`). Один раз на задачу (`dedupe_key`, `escalated_at`).

**Другие задачи модуля** — тоже `manual` без автора, категория «Осведомлённость»: «Срочная рассылка: …» нажавшему (1 рабочий день, «Высокий»), «Доработать письмо: …» после возврата — исполнителю задачи письма, иначе автору (срок — дата отправки по запуску или 3 рабочих дня). Отметка «Отправлено» задачу не закрывает: в её историю пишется запись, в карточке — подсказка завершить.

**Реестр «Рассылки»** — системный реестр конструктора, запись при каждой отметке «Отправлено» обычным `createRecord` (`via: awareness_letter`). «Подготовил» — по участию (исполнитель задачи → автор последней написанной версии → автор письма, если он участвует в работе); «Согласование» — «Согласовано» / «Без независимого согласования» / «Без согласования». Реестр в архиве — отметка проходит, ответ API предупреждает.

**Дашборд и монитор** — без новых видов: виджет «Ближайшая рассылка» — вид `list`, показатели монитора — ключи KPI `awareness_next`, `awareness_overdue` (1.8.0 неизвестные ключи отбрасывает). В набор KPI по умолчанию не входят: слайд — один экран без прокрутки.

## Последствия

- Одна точка фоновых работ, без второго таймера; прогон идемпотентен и безопасен при нескольких экземплярах backend.
- Откат на 1.8.0 — только код: задачи модуля там «поставлены вручную», новые таблицы 1.8.0 не читает. Задачу или запись, связанную с письмом, 1.8.0 удалить может (мягко) — после возврата на 1.9.0 письмо покажет ссылку на удалённую.
- Снять `ib.work` с роли-исполнителя — законное действие администратора: «Роли и права» предупреждают, `check-integrity` показывает предупреждение, а не ошибку; задачи правила идут с эскалацией.
- Свой `source` для задач модуля и перенос — следующий релиз, после того как терпимость к неизвестному `source` уже будет на проде.
