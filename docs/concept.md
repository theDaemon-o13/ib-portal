# Портал ИБ — концепция

Самостоятельный внутренний инструмент отдела ИБ, в будущем — портал. С RISK CONSOLE не интегрируется. Работает в закрытом контуре банка.

**Принцип:** ядро — конструктор реестров. Дашборд, мониторинг, задачи, документы и доказательная база работают поверх него, поэтому новый реестр сразу получает аналитику, задачи, контроль сроков и карточку записи без доработки кода.

**Обмен данными — Excel.** Импорт и экспорт реестров идут через .xlsx: отчёт сканера загружается как есть, реестр выгружается для ДИКТ, заполненный файл импортируется обратно и обновляет записи по колонке ID.

**Оформление:** в стиле Apple Liquid Glass — стеклянные панели, синий акцент Apple (#007AFF / #0A84FF), светлая тема и чёрная (#000) тёмная; переключатель «Авто / Светлая / Чёрная».

**Доступ — RBAC внутри портала.** Интеграции с AD и FreeIPA нет. Учётные записи портала с логином и паролем; право → роль → пользователь, пользователь получает сумму прав своих ролей. Права: работа в разделах ИБ, правка и удаление записей реестров, удаление задач, постановка задач другим, проверка задач, свободная смена статуса задачи, отчёт по задачам, проверка доказательств, управление и удаление документов, согласование каждого этапа документа, справочники, пользователи и роли, история в карточках, журнал действий (релиз 1.2.0: новые права по умолчанию у роли «Начальник ИБ», история и журнал — ещё у «Супер-администратора»). Роли и их права настраиваются в матрице «Роли и права». Пользователь без права «Работа в разделах ИБ» видит только раздел «Документы». Право «Настенный монитор» (системная роль того же названия) — только экран мониторинга: оно не сочетается с другими правами и ролями, вход — только с адресов настенных мониторов (`MONITOR_ALLOWED_IPS`), сессия не завершается по бездействию, но живёт не дольше 12 часов (ADR-0012).

**Про демо-макет:** переключатель «Демо: войти как» в меню слева и примерные данные есть только в прототипе — чтобы показать, как работают роли. В продукте пользователь определяется входом в систему.

1. **Конструктор реестров** — поля (текст, список, число, дата, сотрудник, вычисляемое, решение другого отдела, значение справочника), роль поля для аналитики, автоматизации «условие → действие». Вкладка «Записи» — на всю ширину одного экрана, шапка закреплена, первые 0–4 столбца закрепляются, поиск по реестру.
   - Шапка: выбор реестра (поиск, архивные, создание), владелец, вкладки «Записи / Поля / Автоматизация» и меню реестра. Выбор хранится в адресе: обновление страницы его не сбрасывает. На вкладке «Поля» справа — «Попадёт на дашборд»; настройки поля открываются щелчком по строке в боковой панели.
   - Структуру реестров меняет роль с правом «Реестры: создание и настройка полей» (по умолчанию — супер-администратор). У поля можно назначить заголовок записи (текстовое поле) и статус (список, у значений — признак «закрывает запись»).
   - Значения хранятся по полю, а не по названию: переименование поля или значения списка ничего не ломает. Поле с данными нельзя удалить — только в архив; значение списка, которое используется, — тоже. Тип поля с данными меняется только в текст или из текста в число, дату или список (если все значения подходят), с предпросмотром «изменится N записей».
   - Вычисляемое поле: дата + срок в днях по значению списка, с переопределением другим полем-датой (по желанию — только если заполнено ещё одно поле) и переносом срока с выходного или праздника на ближайший рабочий день по календарю РТ. Только для чтения; сортируется в таблице.
   - Поле «Значение справочника» (этап 5): значения берутся из справочника («Системы», «Типы документов», категории задач и т. п., кроме статусов, правил почты и меток получателей) и правятся в настройках; запись ссылается на значение по id. Справочник выбирается при создании поля; такое поле можно перевести только в текст. Используемое значение справочника не удаляется.
   - Системные поля и значения (реестр уязвимостей): переименовать можно, удалить, архивировать и сменить тип — нет; системный реестр не уходит в архив. Свои поля в системный реестр добавлять можно.
   - **Автоматизация** (вкладка конструктора, любой реестр): правило «условие → действие». Условия: «за N дней до даты», «дата просрочена» (по желанию — не меньше N рабочих дней и пока пусто указанное поле), «поле = значение». Действие — событие «напоминание / уведомление / эскалация» получателям. С этапа 5 событие в том же прогоне превращается в задачи и отмечается «обработано» со ссылками на задачи (журнал событий реестра и карточка записи).
     - Получатели: поле-сотрудник записи («Ответственный»), сотрудник портала или метка справочника «Получатели уведомлений» — «Руководитель ДИКТ», «Владелец системы», «Начальник ИБ», «Руководство Банка» или своя. В событие пишется снимок получателей на момент срабатывания.
     - Кто стоит за меткой:
       - справочник «Получатели уведомлений»: метка → участники (только пользователи с доступом к разделам ИБ, им ставятся задачи) и/или e-mail (люди вне портала — руководство банка, ДИКТ без доступа; e-mail — для справки, письма портал не отправляет). При попытке добавить участником пользователя без доступа к ИБ редактор отказывает и предлагает записать его e-mail для справки. При смене руководителя меняется одна строка справочника, правила остаются как есть;
       - «Владелец системы» — системная метка без участников: владелец берётся из справочника «Системы» (поле «Владелец системы» — любой активный пользователь портала) по полю «Система» записи. В реестре уязвимостей «Система» — системное поле; при загрузке отчёта сканера система выбирается для всех новых записей, в карточке её можно поправить;
       - правила ссылаются на метку по id значения справочника (как везде), поэтому метку можно переименовать — правила остаются привязаны. Используемую в правилах метку нельзя удалить, только отправить в архив; системные метки не удаляются и не переименовываются. Если метки нет в справочнике (старое правило с названием, которого нет), правило работает, в «Автоматизации» у него отметка «получатель не найден», а задачи по этой метке — без ответственного.
     - Событие → задачи: по задаче каждому пользователю-получателю (дубли убираются), категория «Реестр», связь с записью и правилом, метка получателя в задаче. Напоминание — срок задачи = срок записи, обычный приоритет; уведомление — 3 рабочих дня, высокий; эскалация — 1 рабочий день, высокий.
       - Если после разворачивания метки нет ни одного пользователя (метка пустая, только e-mail; владелец системы без доступа к ИБ, не задан или у записи нет системы), создаётся одна задача без ответственного с этими метками; в её карточке видны метки и их e-mail, чтобы сотрудник ИБ написал вручную или назначил задачу.
       - Если по той же записи и правилу у этого ответственного (или «не назначен») уже есть открытая задача, новая не создаётся — в неё добавляется комментарий «Повторное срабатывание». После «Готово», архива или удаления следующее срабатывание создаёт новую задачу.
       - Повторная обработка дублей не даёт: событие отмечается обработанным в той же транзакции, где создаются задачи; одна открытая задача на (правило, запись, ответственный) закреплена уникальным индексом. Событие записи, убранной в архив или удалённой, отмечается обработанным без задач.
     - Правила проверяются раз в час внутри backend (интервал — `AUTOMATION_INTERVAL_MIN`, «сегодня» — в часовом поясе `APP_TZ`), сразу после загрузки отчёта сканера и по кнопке «Проверить сейчас»; событие одно на правило, запись и срок — повторная проверка дублей не создаёт, перенос срока даёт новое событие.
     - Журнал событий реестра показывает события действующих записей; события записи в архиве остаются в её карточке.
     - **Правило и его задачи** (релиз 1.1.0): задача автоматизации всегда знает своё правило (`tasks.automation_id`, это держит БД). «В архив» и «Удалить» у правила открывают окно «Задачи, созданные им (N): оставить / в архив / удалить» с разбивкой по статусам; по умолчанию — оставить. «Только нетронутые» — задачи без комментариев и правок сотрудников (только то, что сделала автоматизация). Удалить задачи — по праву «Задачи: удаление», мягко. Удаление правила с событиями тоже мягкое: события и задачи сохраняют ссылку на него; системные правила п. 7.4 по-прежнему не удаляются и не уходят в архив.
     - **Журнал запусков** (релиз 1.1.0): каждый прогон — по расписанию, «Проверить сейчас» или после импорта отчёта — строка с временем, автором, числом правил, проверенных записей, событий и задач, ошибкой. На вкладке реестра — его прогоны и общие часовые. «Очистить…» (право «Реестры: создание и настройка полей») — старше 30/90/180 дней или весь журнал; строки удаляются физически (технический журнал), в журнале аудита — кто и сколько. События автоматизаций при этом не удаляются: они защищают от повторных задач.
     - Задач автоматизаций «без привязки» к правилу не бывает: ограничение БД `tasks_automation_check` (с этапа 5, миграция `20261027043258_tasks`, расширено в `20261027180000_dlp_permissions`) требует `("source" = 'automation') = ("automation_id" IS NOT NULL)`. Поэтому способа «привязать уже созданные задачи» в портале нет — все задачи правила находит окно «Задачи, созданные им (N)» (вопрос 7 плана 1.1.0; блок «Задачи без привязки» убран как недостижимый).
   - Контроль сроков в таблице: колонка «Дней до срока» после заголовка — «Просрочено N дн.», «Осталось N дн.» (≤ 7), «В срок · N дн.», «Закрыто»; реестр со сроком открывается «срочное сначала». Колонка есть и в выгрузке Excel (при импорте пропускается). Номер записи с открытыми задачами из автоматизаций отмечен, фильтр «С задачами».
   - Решение другого отдела вносится только с документом-основанием: «Внести решение» в карточке записи — решение, документ, его номер и дата, файл документа (обязательно), по желанию «Пересмотр до» и номер в реестре другого отдела. Без файла решение не сохраняется. Решения только пополняются; история решений с просмотром документа — в карточке. Документ сразу попадает в доказательную базу. Запись с решениями или доказательствами удаляется только в архив.
   - Удаление записи — по праву «Записи реестров: удаление», запись пропадает из реестра, в журнале остаётся снимок. Восстановления в интерфейсе нет; архив записи — обратимый. Запись с зависимостями не удаляется, только в архив: зафиксированные поля, решения другого отдела, доказательства, открытые задачи по записи, ссылки из других записей (например, разрешение DLP → устройство) — одно правило для одной записи и для массового удаления (релиз 1.1.0).
   - **Массовые действия** (релиз 1.1.0, ADR-0016): в таблице записей — галочки, «выбрать все на странице» и «Выбрать все N по фильтру». Действия: «Архивировать выбранные» (право «Записи реестров: правка»), «Удалить выбранные» (право «Записи реестров: удаление»), в «Архиве» — «Вернуть выбранные». Сначала предпросмотр («будет удалено N, уйдёт в архив M — у них есть зависимости»), потом подтверждение; если записи успели измениться, портал показывает новые числа и просит подтвердить ещё раз. Итог: сколько удалено и сколько ушло в архив, по причинам (задачи, ссылки, …), и подсказка «Сначала закройте или удалите задачи». Каждая запись — в журнале, как при одиночном действии, плюс сводная запись.
   - Кнопка «Архив» над таблицей показывает только архивные записи реестра; там их можно вернуть по одной или выбранными.
   - «Удалить все записи…» в меню реестра (право «Записи реестров: удаление»): все записи, включая архивные; портал показывает их число и просит ввести название реестра. Записи с зависимостями уходят в архив.
   - Excel: выгрузка с колонкой ID и листом «Справка»; загрузка — предпросмотр (что добавится, изменится, ошибки по строкам), затем применение целиком. Пустой ID — новая запись, неизвестный ID — ошибка, пустая ячейка не меняет значение, сотрудник — «ФИО (логин)».
   - **Ключ импорта** (этап 8): текстовое поле можно назначить ключом в настройках поля — значения уникальны среди неудалённых записей без учёта регистра и пробелов (это держит БД); с повторами ключ не назначается — портал перечисляет повторы. Файл без колонки ID (например, выгрузка Device Monitor) сопоставляется по ключу: найдена запись — обновление, нет — новая. Повтор ключа в файле — ошибка во всех таких строках, пустой ключ и запись в архиве — ошибка строки. Предпросмотр показывает, с какой записью сопоставлена каждая строка, и список «Нет в файле» — действующие записи, которых нет в выгрузке (кандидаты на «Выведено»; портал их не меняет). Повторный импорт того же файла ничего не меняет. Поле-ключ нельзя отправить в архив и сменить его тип.
   - **Многострочный текст** (релиз 1.1.0): у текстового поля — признак «Многострочный текст» (при добавлении поля и в его настройках; хранится в `register_fields.settings.text`). В карточке такое поле от 6 строк, растёт вместе с текстом и растягивается вручную; лимит — 20 000 символов вместо 4000 (форма, API, импорт Excel проверяются одной функцией; в выгрузке Excel колонка широкая, с переносом строк). В таблице текст — в одну строку с многоточием, полный — в подсказке. Снять признак нельзя, пока есть записи длиннее 4000 символов; тип многострочного поля не меняется, пока признак не снят. В реестре уязвимостей признак включён у «Комментарий ДИКТ» и «Компенсирующие меры» (однократно при обновлении до 1.1.0, запись в журнале); в остальных реестрах его включает администратор.
   - **Сравнение с реестром** (релиз 1.1.0, ADR-0017): в окне импорта (выгрузка реестра и отчёт сканера) кнопка «Сравнение» показывает открытые записи выбранной области, которых нет в файле. Ключ сравнения и поля области задаются в конструкторе (блок «Сравнение с реестром» на вкладке «Поля»); без ключа — по колонке ID; ключ импорта по умолчанию становится ключом сравнения; у реестра уязвимостей ключ «CVE / БДУ + Пакет», поля области — «Отдел», «Система», «Отчёт сканирования». Для отчёта сканера область по умолчанию — отдел отчёта и система, выбранная в окне импорта (без системы — «все системы»), подпись «Сравнить с записями реестра: отдел …, система …»; дополнительно — «Конкретный прошлый отчёт». В окне отчёта — подсказка «N записей нет в этом отчёте — нажмите «Сравнение»» (открытые записи области по умолчанию, не совпавшие ни с одной строкой отчёта). Область обязательна, «Весь реестр» — явно и с предупреждением. Записи без ключа не сопоставляются. Для отчёта сканера — предупреждение «неполный скан», если в листе «Хосты» нет хостов прошлого отчёта; статус тогда ставится только с подтверждением. Статус — свой у каждой записи или один у отмеченных, через предпросмотр и подтверждение; в истории записи — «сравнение с файлом», в журнале — файл (хранится в портале, открывается как доказательство) и его sha256. Новые и изменившиеся строки показывает обычный предпросмотр импорта.
   - **Фильтр по ссылке** (этап 8): адрес реестра принимает фильтр — открытые / закрытые, контроль сроков, значение поля, дата в интервале; применённый фильтр виден плашкой «Фильтр: …», крестик его снимает. Так открываются реестры с дашборда.
   - **Карточка записи:** клик по строке или «Новая запись» открывает боковую панель с формой, собранной из полей реестра: список → выпадающий список, сотрудник → выбор сотрудника, дата → календарь, вычисляемое поле — только просмотр с формулой, решение ОУР — через документ. Новое поле в конструкторе сразу появляется в форме. История изменений записи; удаление — по праву «Записи реестров: удаление».
2. **Реестр уязвимостей** — системный реестр конструктора, создаётся при установке. Структура по отчёту сканера: Пакет, CVE, Уровень, CVSS, Эксплойт, Сетевой вектор, Обновить до версии, Описание, Обнаружений + лист «Хосты»; плюс «Исправление» (выпущено / не выпущено), «Отчёт сканирования», «Уведомлено ДИКТ», Оценка, Критичность, Срок устранения, Статус, Комментарий ДИКТ, Компенсирующие меры, Срок после пересмотра ИБ, Ответственный.
   - **Импорт отчёта сканера** — та же кнопка «Импорт из Excel», что и для выгрузки реестра: тип файла определяется сам. Отчёт сканера — есть лист «Хосты» и лист с колонками «CVE» и «Пакет»; выгрузка реестра — колонка ID или скрытый лист «_поля»; иначе — ошибка со списком ожидаемых и найденных листов и колонок. В предпросмотре написано, как распознан файл: «Отчёт сканера» или «Выгрузка реестра». Отчёт сканера в другой реестр не загружается. Лист уязвимостей распознаётся по колонкам «Пакет» и «CVE», лист «Хосты» — по колонке «Имя хоста», ячейка A1 — отдел. Дата отчёта — из имени файла (ГГГГ-ММ-ДД), иначе вводится в предпросмотре; там же дата передачи в ДИКТ (по умолчанию = дата отчёта). Два шага: предпросмотр (новые, дубли с «было → станет» по «Обнаружений», хосты, новые значения списков, ошибки по строкам), затем применение одной транзакцией; если после предпросмотра дубль изменили или такую же пару завели вручную — не применяется ничего. Отчёт с хостами сохраняется и виден над таблицей.
   - **Отдел** (релиз 1.1.0): из ячейки A1 листа «Хосты», сохраняется в поле записи «Отдел» (фильтр в реестре, измерение для дашборда); сравнивается без регистра, лишних пробелов и «ё»/«е», показывается как в отчёте. У записей, загруженных до 1.1.0, отдел заполнен по их отчёту (запись в истории карточки); у заведённых вручную — пусто. Отчёт без отдела в A1 не загружается как есть: в окне импорта — «В отчёте не указан отдел (ячейка A1 листа «Хосты»)» и обязательный выбор отдела из известных или ввод нового; предпросмотр пересчитывается с этим отделом, до выбора «Загрузить» и «Сравнение» недоступны (иначе каждая повторная загрузка создавала бы полный набор дублей).
   - Дубли: открытая запись того же отдела (статус не закрывает запись, не в архиве) с той же парой «CVE + пакет» (без учёта регистра и пробелов) не создаётся заново; «Обнаружений» берётся из нового отчёта (14 → 3 — обновление; пусто — прежнее значение). Дубли внутри одного файла объединяются по максимуму «Обнаружений». Отчёт одного отдела не сливается с записями другого и не меняет их «Обнаружений»; записи без отдела в дублях не участвуют. Закрытая запись дублем не считается — уязвимость заводится снова.
   - Оценка (п. 7.1) = CVSS × Кэ × Ки, округление вверх до 0,1: Кэ = 1,00 «есть, эксплуатируется», 0,94 «есть», 0,91 остальное; Ки = 0,95, если исправление выпущено. «Исправление» при импорте — «выпущено», если заполнено «Обновить до версии» (и там не «не выпущено»); дальше правится вручную. Оценка — вычисляемое поле, пересчитывается при любой правке CVSS, эксплойта или исправления.
   - Критичность: ≥ 9,0 — критическая, ≥ 7,0 — высокая, ≥ 4,0 — средняя, иначе низкая; нет CVSS — высокая. Сотрудник ИБ может выбрать её вручную (форма или импорт Excel) — тогда пересчёт её не трогает, в карточке отметка «вручную» и кнопка «Считать автоматически»; очистить поле — тоже вернуть расчёт.
   - Сроки по п. 7.2 (от передачи отчёта в ДИКТ, календарные дни): Критическая — 14; Высокая — 30; Средняя — 90; Низкая — 180. Срок, выпавший на выходной или праздник, переносится на ближайший рабочий день по календарю РТ.
   - П. 7.3: если заполнены и «Компенсирующие меры», и «Срок после пересмотра ИБ» — срок берётся из решения ИБ (без переноса). Одна дата без мер срок не меняет.
   - П. 7.4 — системные правила автоматизации (только выключаются): за 3 дня до срока — напоминание ответственному и «Руководителю ДИКТ»; срок просрочен — уведомление «Руководителю ДИКТ» и «Владельцу системы»; просрочка 10 рабочих дней (по календарю РТ) и пусто «Компенсирующие меры» — эскалация «Руководству Банка» и «Начальнику ИБ», запись попадает в отчётность.
3. **Мониторинг** (`/monitor`) — один экран для настенного монитора, без мыши и без прокрутки, крупный шрифт, чёрная тема (если в переключателе «Авто»): KPI (открытые уязвимости, просрочено, срок в ближайшие 7 дней, инциденты за 30 дней, просроченные задачи, документы к пересмотру, риски без решения ОУР, истекающие доказательства), уязвимости с днями до срока / просрочки (срочное сначала, при равенстве — выше Оценка), распределение по срокам (просрочено, 0–7, 8–14, 15–30, более 30 дней) и ближайшие даты, открытые по пакетам, задачи, документы, риски и доказательства с днями; страницы листаются сами каждые 12 с, экран не гаснет (Wake Lock). Открывается кнопкой «Экран мониторинга» на дашборде.
   - **Слайды** (релиз 1.1.0, ADR-0019): экран — набор слайдов из «Настройки → Экран мониторинга» (право «Настройки»; одна настройка на все мониторы): вид (ключевые показатели, уязвимости по срокам, задачи, документы — срок пересмотра, решения ОУР, доказательства, доступ без основания DLP), название, время показа 5–300 с (по умолчанию 12), фильтры (сроки: все / просроченные / в пределах N дней; критичность, отдел, система; категории задач; типы документов; показатели; реестр DLP), «показывать», «пропускать, если данных нет», порядок. Пустой слайд показывает понятный текст («Нет просроченных задач»). Изменения мониторы подхватывают сами — при следующем обновлении (раз в минуту), на границе слайда. «Предпросмотр» показывает слайд так, как он будет на стене. По умолчанию — 6 слайдов, повторяющих прежний экран.
   - Панель управления (появляется при движении мыши, прячется через 3,5 с): назад, пауза/продолжить, вперёд, номер страницы с полосой времени до перелистывания, на весь экран, закрыть. Клавиши: ← → листать, пробел — пауза, Esc — выход.
   - Данные обновляются раз в минуту, внизу — «Обновлено в ЧЧ:ММ:СС». Если сервер недоступен, на экране остаются последние данные и плашка «Нет связи с сервером портала · данные на ЧЧ:ММ»; связь вернулась — плашка исчезает сама.
   - Учётная запись настенного монитора видит только этот экран (любой адрес ведёт сюда); вместо «закрыть» — «Выйти» с подтверждением, Esc не закрывает.
4. **Дашборд** — KPI, плитки-счётчики и виджеты; всё считается на сервере (по запросу на виджет, кэш на 1 минуту), обновляется раз в минуту. Каждый KPI, плитка, строка графика и столбик динамики ведёт в соответствующий раздел с уже применённым фильтром, и число совпадает с количеством записей там.
   - **«Настроить»** (релиз 1.1.0, ADR-0018): скрыть и вернуть элемент, перетащить, размер S/M/L (KPI — всегда S), «Сбросить». Раскладка — в БД: своя, иначе раскладка по умолчанию для роли, иначе системная. Раскладки ролей задаёт администратор с правом «Настройки» в том же режиме (выбор «По умолчанию для роли …»); у «Начальника ИБ» по умолчанию впереди просроченное и требующее решения.
   - KPI: открытые уязвимости; уязвимости с просроченным сроком устранения; инциденты за 30 дней (системный «Реестр инцидентов», поле «Дата выявления»: сегодня и 29 дней до него); просроченные задачи; документы к пересмотру (пересмотр просрочен или идёт, либо дата пересмотра в ближайшие 30 дней); риски ИБ без решения ОУР; доказательства на проверке; доказательства, срок действия которых истекает в 30 дней.
   - Виджеты строятся сами из полей реестров с ролью аналитики: группировка — распределение по значениям; показатель — среднее, максимум, число записей; динамика — восемь недель, последняя заканчивается сегодня; контроль сроков — просрочено, ≤ 7 дней, в срок и шесть самых срочных записей. Постоянные виджеты: открытые задачи по категориям, актуальность документов, доказательная база.
   - Плитки-счётчики (этап 8): «сколько открытых записей реестра, где поле ∈ {значения}» с разбивкой по значениям — например, «Доступ к соцсетям» по реестру «Устройства DLP». Добавляет, меняет, упорядочивает и удаляет пользователь с правом «Реестры: создание и настройка полей» (кнопка «Плитки»). Закрытые записи и архив не считаются, закрытый статус в плитку не выбирается. Плитка по полю или реестру в архиве не считается и видна только в настройке.
5. **Задачи** — одна доска для почты, проектов, оперплана и автозадач из реестров. Колонки — статусы справочника (Новые / В работе / На проверке / Готово, названия можно менять); в колонке сначала ближний срок. Перетаскивание карточки мышью меняет статус (в карточке — тот же статус списком). Фильтры по категориям с числами и «Архив»; «Создано автоматизацией» — задачи одного правила (с числом у каждого). «Выбрать» — режим, в котором щелчок отмечает карточки: «Архивировать выбранные» (любой сотрудник ИБ), «Удалить выбранные» (право «Задачи: удаление»), с предпросмотром и подтверждением (релиз 1.1.0). Быстрая постановка над доской: название, категория, ответственный, срок. Срочные (высокий приоритет) отмечены «срочно», просроченные — красным «просрочено · дата»; у задач из реестров — «авто», без ответственного — «не назначен». Справа — загрузка сотрудников по открытым задачам.
   - Карточка открывается в боковой панели (и по ссылке `/tasks?task=…`): название, описание, статус, ответственный, срок, приоритет, категория; «Отметить выполненной»; комментарии; история изменений из журнала аудита (кто, когда, что поменял; с релиза 1.2.0 — только по праву «История в карточках», комментарии видят все); исходное письмо с правилом и причиной срока, если задача из почты; ссылка на запись реестра и получатели с e-mail, если задача из автоматизации. Правка сохраняет только изменённое, с версией: если задачу успели изменить, карточка предлагает перечитать.
   - Ответственный — только активный пользователь с доступом к разделам ИБ. Переход в «Готово» закрывает задачу (не просрочена), уход из «Готово» открывает снова.
   - Архив: задачу может отправить в архив и вернуть любой сотрудник ИБ; архивная задача не правится. Архив открывается кнопкой «Архив» в фильтрах. Удаление — мягкое, по праву «Задачи: удаление», с подтверждением и записью в журнале.
   - Уведомления пока только внутри портала: у пункта «Задачи» в меню — число просроченных задач отдела (в подсказке — сколько из них мои). Писем портал не отправляет: внешних интеграций нет (решение 27.10.2026).
   - **Почта → задача (без интеграции):** кнопка «Задача из письма», текст письма вставляется целиком, портал разбирает «От / Тема / Отправлено» (и английские From / Subject / Sent); название — тема без RE/FW. Срок: «до ДД.ММ(.ГГГГ)» (без года — ближайшая такая дата не раньше сегодня), «сегодня», «завтра» (выходной или праздник — ближайший рабочий день), «в течение N дней» (календарных) и «в течение N рабочих дней» по производственному календарю; по умолчанию 3 рабочих дня. «Срочно» — высокий приоритет и, если срока в письме нет, 1 рабочий день. Правило разбора почты — с наибольшим числом совпавших ключевых слов (при равенстве — первое по порядку справочника) → его ответственный (если он сотрудник ИБ). Черновик показывает, почему такой срок и ответственный; разбор ничего не сохраняет. Задача создаётся только после проверки: категория «Почта», письмо и сработавшее правило сохраняются в карточке.
   - **Интеграция с MDaemon — не планируется** (решение владельца проекта 27.10.2026: портал работает на закрытом хосте без внешних интеграций; «Почта → задача» остаётся только вставкой текста). Рассматривавшийся вариант — для истории: (1) отдельный ящик, например ib-tasks@, портал читает его по IMAP — сотрудники пересылают письма туда, или правило Content Filter копирует письма отделу ИБ в этот ящик; номер задачи в теме [ИБ-123] — ответы добавляются комментариями; (2) Content Filter → действие «Run Process» с $MESSAGEFILENAME$ — скрипт на почтовом сервере передаёт письмо в API портала; уведомления из портала — через MDaemon как SMTP-релей.
6. **Документы** — реестр внутренних документов ИБ, маршрут согласования (Автор → Начальник ИБ → Юридический отдел → Утверждение правлением), контроль пересмотра; файлы в OnlyOffice.
   - Реестр: название, тип (справочник «Типы документов»), владелец, версия, дата утверждения, цикл пересмотра (по умолчанию 12 месяцев), дата следующего пересмотра, статус — черновик, на согласовании, утверждён, на пересмотре (новая версия утверждённого документа в работе), пересмотр просрочен (важнее «на пересмотре»: пока новая версия не утверждена, срок нарушен). Справа — карточка выбранного документа: маршрут, действия, версии, история. Фильтры: «Ждут вас», статусы, «Архив»; поиск по названию.
   - Номер версии (1, 2, 3…) ставит портал; необязательная «Редакция» («3.1») — только для отображения. Владелец — активный сотрудник с доступом к разделам ИБ: ему ставятся задачи.
   - Файл остаётся в OnlyOffice: у версии хранится ссылка (только http:// или https://; если задан адрес сервера OnlyOffice банка `ONLYOFFICE_URL_PREFIX` — только на него), кнопка «Открыть в OnlyOffice». Так и остаётся (решение 27.10.2026, ADR-0010): ссылка на файл и итоговый PDF при утверждении; интеграции с API OnlyOffice и отдельного этапа под неё нет.
   - **Маршрут.** Этап «Автор» — владелец документа или право «Документы: управление» (отправка за автора). Этапы 1–3 — только пользователь с правом этапа. Разделение полномочий: владелец документа не согласует ни один этап своего документа, кроме «Автор», — даже если документ отправил на согласование другой пользователь; супер-администратор не согласует ни один этап, даже если другая его роль даёт право этапа; один человек не согласует два этапа одной версии. Если этап некому согласовать, кроме владельца (у владельца есть право этапа, других активных согласующих нет), этап отмечается «Не требуется: автор — <этап>» с записью в истории (кто владелец, почему пропущен) и документ идёт дальше; пропуск последнего этапа утверждает документ. Остальные этапы обязательны; если права этапа нет ни у кого, документ ждёт («никто не назначен»). У каждого этапа видно, кто может его согласовать; в реестре отмечено «ждёт вас». Экран, отставший от документа (документ уже на другом этапе или изменён), получает отказ и предложение обновить.
   - **Возврат на доработку** — с этапов 1–3, только с замечанием. Маршрут начинается заново (новый круг), владельцу ставится задача «Доработать документ» (категория «Документы», 3 рабочих дня) с замечанием; если такая задача ещё открыта — замечание добавляется в неё комментарием. Повторная отправка на согласование закрывает задачу сама.
   - **История согласования** только пополняется (права и триггер, как у журнала аудита): кто, когда, этап, решение (отправил, согласовал, вернул, этап не требуется, начал новую версию), комментарий, номер версии, круг. С релиза 1.2.0 подробную историю в карточке видят пользователи с правом «История в карточках»; кто согласовал этапы текущего круга (блок маршрута) и замечание последнего возврата («Возвращён на доработку…») — все, кто видит документ.
   - **Версии.** Черновик правят владелец или «Документы: управление» — только на этапе «Автор». Утверждённую версию изменить нельзя: правка утверждённого документа — это новая версия, она проходит весь маршрут; пересмотр без изменений — тоже новая версия. До утверждения новой версии действует прежняя. Утверждённые версии не меняются и не удаляются (права и триггер) и видны в списке версий карточки.
   - **Пересмотр.** Дата следующего пересмотра = дата утверждения + цикл (31-е число → последний день месяца); смена цикла пересчитывает её от даты утверждения. За 30 дней до даты владельцу ставится задача «Пересмотреть документ» (событие автоматизации → задача, проверка раз в час вместе с автоматизациями реестров; повторная проверка дублей не даёт). Если новая версия уже в работе, задача не ставится; утверждение новой версии закрывает задачу. Просроченный пересмотр виден в реестре и красным числом у пункта «Документы» (сотрудникам ИБ).
   - **Пользователи без доступа к разделам ИБ** (юрист, правление) видят только «Документы»: утверждённые документы (действующую версию), документы, которые ждут их этапа, и согласованные ими в текущем круге. Черновики, документы на чужом этапе и архив им не видны; задачи им не ставятся — вместо этого число «ждёт вас» у пункта «Документы» (синее; видят все).
   - Тип, владельца и цикл меняет «Документы: управление»; он же отправляет документ в архив (пересмотр архивного не контролируется) и возвращает из архива. Физического удаления нет.
   - **Итоговый PDF (этап 7).** Ссылка на OnlyOffice не фиксирует содержимое, поэтому автор прикладывает итоговый PDF при отправке на согласование: без него документ не отправить, и все этапы согласуют именно этот файл (sha256 — в истории каждого решения). Замена PDF во время согласования возвращает маршрут к началу (новый круг). Версия, ушедшая на согласование без PDF, не утверждается, пока автор не приложит файл (с 1.0.0 это закреплено и триггером в БД). Утверждённая до этапа 7 версия без PDF показывается с пометкой «текст не зафиксирован»; задним числом PDF не прикладывается — текст зафиксирует следующий пересмотр. PDF версии просматривается прямо в карточке; юрист и правление видят PDF тех версий, которые им видны.
   - Уведомлений по e-mail нет (внешних интеграций нет): согласующие видят число «ждёт вас» у пункта «Документы».
7. **Риски ИБ** — системный «Реестр рисков ИБ» конструктора, отдельно от рисков банка; связь с реестром ОУР по номеру. Поля: риск, актив / система (справочник «Системы»), уровень, статус ИБ, № в реестре ОУР, решение ОУР, пересмотр до, владелец риска. Решение выносит ОУР; ИБ фиксирует его только с документом ОУР — решение заполняет «№ в реестре ОУР» и «Пересмотр до». Автоматизации: за 30 дней до пересмотра решения — задача владельцу риска; пересмотр просрочен — владельцу и начальнику ИБ.
8. **Доказательная база** — доказательства по объектам, формы подтверждения со сверкой требований и проверкой ИБ.
   - Доказательство привязано к объекту: записи реестра, документу или системе. Вид: форма подтверждения по шаблону, решение другого отдела (из реестра), файл (протокол, скриншот, выгрузка). У каждого — один или несколько файлов.
   - Реестр: объект, тип, файл, загрузил, дата, действует до, результат сверки, проверка ИБ; фильтры «На проверке / Принято / Истекает / Истекло / Отклонено», архив, поиск. Справа — «Загрузить» с покрытием систем формами выбранного шаблона.
   - Форма заполняется целиком; отметка соответствия видна сразу; срок действия — дата загрузки + срок шаблона. Файл без формы — по желанию со сроком «действует до».
   - Проверка — право «Доказательства: проверка», но не своё: проверяющий не принимает доказательство, которое загрузил или к которому приложил файл. Отклонение — с комментарием, загрузившему — задача «Исправить и загрузить заново» (категория «Доказательства», 7 дней); задача закрывается, когда приложен исправленный файл или загружена новая форма. Новый файл возвращает принятое доказательство на проверку; убрать файл можно только у доказательства на проверке (не последний).
   - Срок действия: «истекает» — за 30 дней, «истекло» — после даты. За 30 дней ответственному — задача «Обновить доказательство» (раз в час, вместе с автоматизациями); принятие новой формы по тому же объекту и шаблону её закрывает. Число «на проверке» — у пункта «Доказательства» (тем, кто проверяет).
   - **Файлы:** до 25 МБ; pdf, png, jpg, txt, csv, xlsx, docx — тип проверяется по содержимому: подмена расширения, SVG, HTML и документы с макросами не проходят. Загружают сотрудники ИБ и участники документооборота. Файлы хранятся в томе портала по пути без имени файла и выдаются только через backend с проверкой прав (attachment, nosniff). Физически файл не удаляется; без ссылок — помечается удалённым, непривязанный — через сутки.
   - Карточка доказательства: данные, поля формы со значениями и отметкой соответствия, файлы, история, принять/отклонить. Файлы просматриваются прямо в карточке (изображения, PDF, текст/CSV), к доказательству можно добавить файлы, файл можно сохранить.
   - Шаблоны форм подтверждения (парольная защита, пересмотр прав доступа и новые) настраиваются в справочниках: название, документ-основание, срок действия, поля с типом проверки (число не менее / не более, да-нет, текст). Загруженная форма хранит снимок полей и значений, поэтому изменения шаблона не меняют старые формы.
9. **Настройки** (по образцу RISK CONSOLE): справочники — категории задач (с цветом), статусы задач (только переименование), приоритеты, правила разбора почты, системы (с владельцем системы), получатели уведомлений (метка → участники и e-mail), типы документов, производственный календарь РТ, шаблоны форм подтверждения; пользователи и роли; журнал изменений.
   - Справочники меняет роль с правом «Настройки: справочники и шаблоны форм», пользователей и роли — с правом «Настройки: пользователи, роли и права»; остальные видят настройки для просмотра.
   - Переименование обновляет все записи с этим значением. Используемое значение не удаляется, а уходит в архив: пропадает из списков выбора, старые записи его сохраняют. Системные значения (замок) не удаляются и не переименовываются — на них опирается логика (например, «Реестр» ставят автоматизации, «Высокий» — разбор письма со словом «срочно»).
   - Руководитель (релиз 1.2.0, ADR-0020): у пользователя можно указать руководителя — активного сотрудника ИБ; все, кто выше по цепочке руководителей, — «старшие» над пользователем (на этом строятся проверка задач и маршрут документов). Руководитель и подчинённые — только сотрудники ИБ; цикл («A подчинён B, B подчинён A») не сохраняется. Отключённый руководитель остаётся в цепочке. В списке пользователей — руководитель и число подчинённых.
   - Роли и права: матрица «право × роль» с отметками, добавление, переименование и удаление ролей (без пользователей). Пользователи: заведение учётной записи, назначение ролей, отключение. Нельзя снять право управлять ролями с себя и с последнего, у кого оно есть.
   - Удаление значения — мягкое: оно пропадает из настроек, а журнал хранит, кто и когда его удалил. Удалить можно только несистемное неиспользуемое значение.
   - Производственный календарь РТ: выходные дни недели (по умолчанию пятидневка, настраивается) и отклонения — праздники и рабочие дни-переносы. Постоянные праздники (1.01, 8.03, 21–24.03, 1.05, 9.05, 27.06, 9.09, 6.11) на 2026 и 2027 годы внесены заранее; Иди Рамазон, Иди Курбон и переносы администратор добавляет сам. По календарю считаются сроки в рабочих днях (п. 7.4, разбор почты).
   - Если при обновлении появляется новое системное значение, а администратор уже завёл значение с тем же названием, оно становится системным; seed пишет об этом в журнал изменений (автор — «Система») и в свой вывод.
   - Стартовые значения (категории «Проект» и «Оперплан», системы, типы документов, правила почты, два шаблона форм) создаются только при первой установке и не возвращаются, если администратор их удалил или отправил в архив. Ответственных в правилах почты назначает администратор.
   - Пользователи: логин после создания не меняется. Временный пароль при создании и сбросе генерирует портал, он показывается администратору один раз; при входе пользователь задаёт свой. Сброс закрывает сессии пользователя и снимает блокировку входа; блокировку можно снять и отдельно. Отключение закрывает сессии; себя отключить нельзя. Свой пароль администратор меняет обычной сменой пароля. В окне временный пароль по умолчанию скрыт: «Показать» и «Скопировать».
   - Вход и смена пароля: у полей пароля кнопка «показать / скрыть». «Запомнить логин» хранит в браузере только логин; пароль портал нигде не хранит (ни в браузере, ни в БД в открытом виде, ни в логах и журнале) — сохранить его может только менеджер паролей браузера.
   - Срок действия пароля — 90 дней, после него смена обязательна. MFA не делается (решение 28.10.2026: портал работает только во внутренней сети, ADR-0006). Вместо неё пользователи с правами на настройки и пользователей входят только с рабочих мест администраторов (`ADMIN_ALLOWED_IPS`, ADR-0015); с другого адреса вход отклоняется, уже открытая сессия закрывается.
   - Роль «Супер-администратор»: права на справочники и на пользователей не снимаются, права этапов согласования ей не выдаются. Удалить можно только несистемную роль без пользователей.
   - Журнал изменений настроек — с релиза 1.2.0 в разделе «Журнал» (фильтр «Настройки — всё»), п. 11.

10. **Разрешения на доступ и реестр агентов DLP** (этап 8б, ADR-0013). В банке работает InfoWatch Device Monitor. По почте приходят документы-разрешения трёх видов: соцсети и мессенджеры (Telegram, WhatsApp), облачные хранилища, удалённая работа через VPN. Любое разрешение действует не дольше 31.12 года выдачи. Портал хранит все документы, ищет по ним и сверяет разрешения с фактическими доступами в DLP.
   - **Реестр «Устройства DLP»** — стартовый, несистемный, seed создаёт его один раз. Поля: Имя хоста (текст, заголовок, ключ импорта), IP-адрес (текст), Сотрудник (текст — ФИО; сотрудники банка не пользователи портала), Подразделение (список, группировка), Группа Device Monitor (список по двухуровневой схеме групп, группировка), Соцсети и мессенджеры (Запрещены / Разрешён Telegram / Разрешён WhatsApp / Разрешены Telegram и WhatsApp, группировка), Облачные хранилища (Запрещены / Только чтение / Разрешены, группировка), USB (Запрещён / Только чтение / Белый список устройств / Разрешён, группировка), Последняя связь агента (дата), Статус (Активно / Выведено — закрывает запись). Данные — выгрузка Device Monitor в Excel, импорт с ключом «Имя хоста» (этап 8). Плитки дашборда: «Доступ к соцсетям», «Доступ к облаку», «Доступ к USB».
   - **Реестр «Разрешения на доступ»** — стартовый, несистемный. Поля: Сотрудник (текст, заголовок), Подразделение (список), Вид (Соцсети и мессенджеры / Облачные хранилища / Удалённый доступ (VPN), группировка), Сервисы (текст: Telegram, WhatsApp, Яндекс Диск…), Устройства (связь с записями «Устройства DLP»), Документ-основание (файл: PDF или скан из письма), № документа (текст), Дата документа (дата), Кто разрешил (текст), Действует до (дата, не позже 31.12 года «Даты документа», по умолчанию 31.12 текущего года, контроль сроков), Исполнено (Ожидает настройки / Настроено в DLP / Настроено в VPN, группировка), Место хранения оригинала (текст: дело / папка №), Оригинал передан в архив (дата), Статус (Оформляется / Действует / Истекло / Отозвано; «Оформляется» — пока прикладывают документ, ещё не фиксирует). Документ-основание — решение руководства, а не доказательство ИБ: проверки «принять / отклонить» нет.
   - **Разрешение выдаётся на устройство** (имя хоста). Поле «Устройства» — связь с записями «Устройств DLP»; одно разрешение может покрывать несколько хостов. Сверка — по связи, не по ФИО.
   - **Портал — основной электронный архив** разрешений; бумажные оригиналы хранятся для регулятора (место хранения и дата передачи в архив — в полях записи).
     - После статуса «Действует» (и в «Истекло», «Отозвано») фиксируются: файл документа-основания, № документа, Дата документа, Кто разрешил, Вид, Сервисы, Действует до. Изменить их нельзя — только новым разрешением (backend отвечает 422, в БД — триггер). «Устройства» у действующего разрешения менять можно только с обязательной причиной; причина попадает в историю записи и журнал. Остальные поля редактируются как обычно, с историей.
     - Запись с зафиксированными полями не удаляется (ни мягко, ни физически); истёкшие и отозванные разрешения остаются навсегда, их файлы не удаляются.
     - У каждого файла в карточке видны sha256 и дата загрузки.
     - Выгрузка для проверки: реестр за период по «Дате документа» в Excel и все файлы полей «Файл» одним zip. Имена файлов — «<№ документа>_<хост>.pdf»: несколько хостов перечисляются через «_», имя длиннее 120 символов сокращается до «<№>_<хост1>_и_ещё_N»; недопустимые символы заменяются на «-», совпадающие имена получают «_2», «_3»; сканы — со своим расширением.
   - **Новые механизмы конструктора:**
     - тип поля «Файл» — один или несколько файлов по правилам хранения файлов портала; загрузка, предпросмотр и скачивание в карточке; в таблице — значок с числом файлов; в Excel — имена файлов, только чтение, импорт их не меняет; отвязка файла мягкая, с записью в историю;
     - тип поля «Связь с записью» — ссылка на одну или несколько записей другого реестра; в карточке связанной записи — обратный список со статусом и сроком;
     - ограничение даты «не позже 31.12 года поля N» и значение по умолчанию «31.12 текущего года»;
     - фиксация полей: у любого поля можно указать «фиксировать при статусах …» — пока статус записи в этом списке, значение не меняется (для файлов — нельзя отвязать или добавить); у поля «Связь с записью» вместо этого можно требовать причину изменения при этих статусах.
   - **Сверка с DLP:** в карточке и таблице устройства по каналам «Соцсети и мессенджеры» и «Облачные хранилища» — статус основания, вычисляется при чтении и не хранится: «есть основание — разрешение №, до», «нет основания» (канал открыт, действующего разрешения нет), «истекло».
   - **Автоматизации:**
     - 1 декабря — задача получателям метки «Разрешения DLP» «Продление разрешений на <следующий год>» со списком действующих разрешений;
     - 1 января — непродлённые разрешения получают статус «Истекло» (история записи и журнал);
     - устройство с открытым каналом без основания — задача «Закрыть доступ в Device Monitor или получить разрешение» (без дублей, по правилам событий → задачи);
     - за 14 дней до «Действует до», если срок раньше конца года, — задача ответственному.
   - **Почта:** стартовое правило разбора «Разрешения» (стоит выше правила «Доступ») с ключевыми словами telegram, телеграм, whatsapp, ватсап, облако, vpn, впн, удалённ. Письмо вставляется в «Задачу из письма», ответственный создаёт разрешение и прикладывает документ.
   - **Дашборд:** «Доступ без основания» (главная цифра), «Действующие разрешения по видам», «Истекают в этом месяце», «Ожидают настройки», разбивка по подразделениям.
   - **Глобальный поиск:** одна строка по записям всех реестров, доказательствам и файлам — ФИО, имя хоста, № документа, сервис, подписант, имя файла; по тексту внутри PDF, если есть текстовый слой (текст извлекается при загрузке и хранится в БД, полнотекстовый поиск PostgreSQL с русской морфологией). Результаты — с учётом прав. Документы приходят в PDF: при загрузке текстовый слой извлекается (pdf.js в отдельном потоке, с ограничением времени и памяти) и индексируется. Если текста нет (скан, сохранённый как PDF) — в карточке пометка «текст не распознан, поиск только по полям», в поиске — счётчик таких файлов. Распознавание сканов (OCR) — отдельный шаг позже: нужна оценка движка (например, Tesseract с русской моделью), его размера в образе и нагрузки; сейчас не делается.

**Внешние интеграции:** нет и не планируются (решение 27.10.2026) — ни почта (MDaemon), ни PT AF, ни API OnlyOffice; во время работы портал не обращается к внешним сервисам и интернету.

11. **Журнал** (релиз 1.2.0, ADR-0021) — все действия пользователей из журнала аудита: вход и выход, неудачные попытки, изменения во всех разделах и настройках, выгрузки. Раздел и пункт меню — только по праву «Журнал действий» (`audit.view`); без права раздела нет, API отвечает 403.
   - Фильтры: период (по умолчанию 7 дней), пользователь (и «Система» — автоматизации, обновления), раздел (в том числе «Настройки — всё»), действие, IP, поиск по тексту, ФИО, логину и ID объекта. Новые сверху, «Показать ещё».
   - Строка: когда, кто, действие и раздел, что сделано, IP; щелчок — подробности (код действия, ID объекта, роли на момент действия, изменения); «Открыть» — карточка или страница объекта; удалённый объект помечен.
   - «Выгрузить в Excel» — по текущему фильтру, до 100 000 строк; больше — сообщение «Сузьте период». Выгрузка тоже попадает в журнал.
   - Записи журнала не меняются и не удаляются. Паролей в журнале нет.
   - История изменений в карточках задач, записей реестров, документов и доказательств — только по праву «История в карточках» (`history.view`). Комментарии к задачам видят все, кто видит задачу; в документе блок «кто какой этап согласовал» — всем, кто видит документ.
