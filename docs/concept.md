# Портал ИБ — концепция

Самостоятельный внутренний инструмент отдела ИБ, в будущем — портал. С RISK CONSOLE не интегрируется. Работает в закрытом контуре банка.

**Принцип:** ядро — конструктор реестров. Дашборд, мониторинг, задачи, документы и доказательная база работают поверх него, поэтому новый реестр сразу получает аналитику, задачи, контроль сроков и карточку записи без доработки кода.

**Обмен данными — Excel.** Импорт и экспорт реестров идут через .xlsx: отчёт сканера загружается как есть, реестр выгружается для ДИКТ, заполненный файл импортируется обратно и обновляет записи по колонке ID.

**Оформление:** в стиле Apple Liquid Glass — стеклянные панели, синий акцент Apple (#007AFF / #0A84FF), светлая тема и чёрная (#000) тёмная; переключатель «Авто / Светлая / Чёрная».

**Доступ — RBAC внутри портала.** Интеграции с AD и FreeIPA нет. Учётные записи портала с логином и паролем; право → роль → пользователь, пользователь получает сумму прав своих ролей. Права: работа в разделах ИБ, правка и удаление записей реестров, удаление задач, проверка доказательств, управление документами, согласование каждого этапа документа, справочники, пользователи и роли. Роли и их права настраиваются в матрице «Роли и права». Пользователь без права «Работа в разделах ИБ» видит только раздел «Документы».

**Про демо-макет:** переключатель «Демо: войти как» в меню слева и примерные данные есть только в прототипе — чтобы показать, как работают роли. В продукте пользователь определяется входом в систему.

1. **Конструктор реестров** — поля (текст, список, число, дата, сотрудник, вычисляемое, решение другого отдела, значение справочника), роль поля для аналитики, автоматизации «условие → действие». Вкладка «Записи» — на всю ширину одного экрана, шапка закреплена, первые 0–4 столбца закрепляются, поиск по реестру.
   - Шапка: выбор реестра (поиск, архивные, создание), владелец, вкладки «Записи / Поля / Автоматизация» и меню реестра. Выбор хранится в адресе: обновление страницы его не сбрасывает. На вкладке «Поля» справа — «Попадёт на дашборд»; настройки поля открываются щелчком по строке в боковой панели.
   - Структуру реестров меняет роль с правом «Реестры: создание и настройка полей» (по умолчанию — супер-администратор). У поля можно назначить заголовок записи (текстовое поле) и статус (список, у значений — признак «закрывает запись»).
   - Значения хранятся по полю, а не по названию: переименование поля или значения списка ничего не ломает. Поле с данными нельзя удалить — только в архив; значение списка, которое используется, — тоже. Тип поля с данными меняется только в текст или из текста в число, дату или список (если все значения подходят), с предпросмотром «изменится N записей».
   - Вычисляемое поле: дата + срок в днях по значению списка, с переопределением другим полем-датой (по желанию — только если заполнено ещё одно поле) и переносом срока с выходного или праздника на ближайший рабочий день по календарю РТ. Только для чтения; сортируется в таблице.
   - Поле «Значение справочника» (этап 5): значения берутся из справочника («Системы», «Типы документов», категории задач и т. п., кроме статусов, правил почты и меток получателей) и правятся в настройках; запись ссылается на значение по id. Справочник выбирается при создании поля; такое поле можно перевести только в текст. Используемое значение справочника не удаляется.
   - Системные поля и значения (реестр уязвимостей): переименовать можно, удалить, архивировать и сменить тип — нет; системный реестр не уходит в архив. Свои поля в системный реестр добавлять можно.
   - **Автоматизация** (вкладка конструктора, любой реестр): правило «условие → действие». Условия: «за N дней до даты», «дата просрочена» (по желанию — не меньше N рабочих дней и пока пусто указанное поле), «поле = значение». Действие — событие «напоминание / уведомление / эскалация» получателям. С этапа 5 событие в том же прогоне превращается в задачи и отмечается «обработано» со ссылками на задачи (журнал событий реестра и карточка записи).
     - Получатели: поле-сотрудник записи («Ответственный»), сотрудник портала или метка справочника «Получатели уведомлений» — «Руководитель ДИКТ», «Владелец системы», «Начальник ИБ», «Руководство Банка» или своя. В событие пишется снимок получателей на момент срабатывания.
     - Кто стоит за меткой:
       - справочник «Получатели уведомлений»: метка → участники (только пользователи с доступом к разделам ИБ, им ставятся задачи) и/или e-mail (люди вне портала — руководство банка, ДИКТ без доступа; письма — этап 9). При попытке добавить участником пользователя без доступа к ИБ редактор отказывает и предлагает указать его e-mail. При смене руководителя меняется одна строка справочника, правила остаются как есть;
       - «Владелец системы» — системная метка без участников: владелец берётся из справочника «Системы» (поле «Владелец системы» — любой активный пользователь портала) по полю «Система» записи. В реестре уязвимостей «Система» — системное поле; при загрузке отчёта сканера система выбирается для всех новых записей, в карточке её можно поправить;
       - правила ссылаются на метку по id значения справочника (как везде), поэтому метку можно переименовать — правила остаются привязаны. Используемую в правилах метку нельзя удалить, только отправить в архив; системные метки не удаляются и не переименовываются. Если метки нет в справочнике (старое правило с названием, которого нет), правило работает, в «Автоматизации» у него отметка «получатель не найден», а задачи по этой метке — без ответственного.
     - Событие → задачи: по задаче каждому пользователю-получателю (дубли убираются), категория «Реестр», связь с записью и правилом, метка получателя в задаче. Напоминание — срок задачи = срок записи, обычный приоритет; уведомление — 3 рабочих дня, высокий; эскалация — 1 рабочий день, высокий.
       - Если после разворачивания метки нет ни одного пользователя (метка пустая, только e-mail; владелец системы без доступа к ИБ, не задан или у записи нет системы), создаётся одна задача без ответственного с этими метками; в её карточке видны метки и их e-mail, чтобы сотрудник ИБ написал вручную или назначил задачу.
       - Если по той же записи и правилу у этого ответственного (или «не назначен») уже есть открытая задача, новая не создаётся — в неё добавляется комментарий «Повторное срабатывание». После «Готово», архива или удаления следующее срабатывание создаёт новую задачу.
       - Повторная обработка дублей не даёт: событие отмечается обработанным в той же транзакции, где создаются задачи; одна открытая задача на (правило, запись, ответственный) закреплена уникальным индексом. Событие записи, убранной в архив или удалённой, отмечается обработанным без задач.
     - Правила проверяются раз в час внутри backend (интервал — `AUTOMATION_INTERVAL_MIN`, «сегодня» — в часовом поясе `APP_TZ`), сразу после загрузки отчёта сканера и по кнопке «Проверить сейчас»; событие одно на правило, запись и срок — повторная проверка дублей не создаёт, перенос срока даёт новое событие.
     - Журнал событий реестра показывает события действующих записей; события записи в архиве остаются в её карточке.
   - Контроль сроков в таблице: колонка «Дней до срока» после заголовка — «Просрочено N дн.», «Осталось N дн.» (≤ 7), «В срок · N дн.», «Закрыто»; реестр со сроком открывается «срочное сначала». Колонка есть и в выгрузке Excel (при импорте пропускается). Номер записи с открытыми задачами из автоматизаций отмечен, фильтр «С задачами».
   - Решение другого отдела вносится только с документом-основанием: «Внести решение» в карточке записи — решение, документ, его номер и дата, файл документа (обязательно), по желанию «Пересмотр до» и номер в реестре другого отдела. Без файла решение не сохраняется. Решения только пополняются; история решений с просмотром документа — в карточке. Документ сразу попадает в доказательную базу. Запись с решениями или доказательствами удаляется только в архив.
   - Удаление записи — по праву «Записи реестров: удаление», запись пропадает из реестра, в журнале остаётся снимок. Восстановления в интерфейсе нет; архив записи — обратимый.
   - Excel: выгрузка с колонкой ID и листом «Справка»; загрузка — предпросмотр (что добавится, изменится, ошибки по строкам), затем применение целиком. Пустой ID — новая запись, неизвестный ID — ошибка, пустая ячейка не меняет значение, сотрудник — «ФИО (логин)».
   - **Карточка записи:** клик по строке или «Новая запись» открывает боковую панель с формой, собранной из полей реестра: список → выпадающий список, сотрудник → выбор сотрудника, дата → календарь, вычисляемое поле — только просмотр с формулой, решение ОУР — через документ. Новое поле в конструкторе сразу появляется в форме. История изменений записи; удаление — по праву «Записи реестров: удаление».
2. **Реестр уязвимостей** — системный реестр конструктора, создаётся при установке. Структура по отчёту сканера: Пакет, CVE, Уровень, CVSS, Эксплойт, Сетевой вектор, Обновить до версии, Описание, Обнаружений + лист «Хосты»; плюс «Исправление» (выпущено / не выпущено), «Отчёт сканирования», «Уведомлено ДИКТ», Оценка, Критичность, Срок устранения, Статус, Комментарий ДИКТ, Компенсирующие меры, Срок после пересмотра ИБ, Ответственный.
   - **Импорт отчёта сканера** — та же кнопка «Импорт из Excel», что и для выгрузки реестра: тип файла определяется сам. Отчёт сканера — есть лист «Хосты» и лист с колонками «CVE» и «Пакет»; выгрузка реестра — колонка ID или скрытый лист «_поля»; иначе — ошибка со списком ожидаемых и найденных листов и колонок. В предпросмотре написано, как распознан файл: «Отчёт сканера» или «Выгрузка реестра». Отчёт сканера в другой реестр не загружается. Лист уязвимостей распознаётся по колонкам «Пакет» и «CVE», лист «Хосты» — по колонке «Имя хоста», ячейка A1 — отдел. Дата отчёта — из имени файла (ГГГГ-ММ-ДД), иначе вводится в предпросмотре; там же дата передачи в ДИКТ (по умолчанию = дата отчёта). Два шага: предпросмотр (новые, дубли с «было → станет» по «Обнаружений», хосты, новые значения списков, ошибки по строкам), затем применение одной транзакцией; если после предпросмотра дубль изменили или такую же пару завели вручную — не применяется ничего. Отчёт с хостами сохраняется и виден над таблицей.
   - Дубли: открытая запись (статус не закрывает запись, не в архиве) с той же парой «CVE + пакет» (без учёта регистра и пробелов) не создаётся заново, «Обнаружений» берётся по максимуму; дубли внутри файла тоже объединяются. Закрытая запись дублем не считается — уязвимость заводится снова.
   - Оценка (п. 7.1) = CVSS × Кэ × Ки, округление вверх до 0,1: Кэ = 1,00 «есть, эксплуатируется», 0,94 «есть», 0,91 остальное; Ки = 0,95, если исправление выпущено. «Исправление» при импорте — «выпущено», если заполнено «Обновить до версии» (и там не «не выпущено»); дальше правится вручную. Оценка — вычисляемое поле, пересчитывается при любой правке CVSS, эксплойта или исправления.
   - Критичность: ≥ 9,0 — критическая, ≥ 7,0 — высокая, ≥ 4,0 — средняя, иначе низкая; нет CVSS — высокая. Сотрудник ИБ может выбрать её вручную (форма или импорт Excel) — тогда пересчёт её не трогает, в карточке отметка «вручную» и кнопка «Считать автоматически»; очистить поле — тоже вернуть расчёт.
   - Сроки по п. 7.2 (от передачи отчёта в ДИКТ, календарные дни): Критическая — 14; Высокая — 30; Средняя — 90; Низкая — 180. Срок, выпавший на выходной или праздник, переносится на ближайший рабочий день по календарю РТ.
   - П. 7.3: если заполнены и «Компенсирующие меры», и «Срок после пересмотра ИБ» — срок берётся из решения ИБ (без переноса). Одна дата без мер срок не меняет.
   - П. 7.4 — системные правила автоматизации (только выключаются): за 3 дня до срока — напоминание ответственному и «Руководителю ДИКТ»; срок просрочен — уведомление «Руководителю ДИКТ» и «Владельцу системы»; просрочка 10 рабочих дней (по календарю РТ) и пусто «Компенсирующие меры» — эскалация «Руководству Банка» и «Начальнику ИБ», запись попадает в отчётность.
3. **Мониторинг** — один экран для настенного монитора, без мыши: KPI, уязвимости с днями до срока / просрочки, распределение по срокам, задачи, документы, риски и доказательства с днями; страницы листаются сами каждые 12 с, экран не гаснет. Ссылка с #monitor.
   - Панель управления (появляется при движении мыши, прячется через 3,5 с): назад, пауза/продолжить, вперёд, номер страницы с полосой времени до перелистывания, на весь экран, закрыть. Клавиши: ← → листать, пробел — пауза, Esc — выход.
4. **Дашборд** — виджеты из полей с ролью аналитики.
5. **Задачи** — одна доска для почты, проектов, оперплана и автозадач из реестров. Колонки — статусы справочника (Новые / В работе / На проверке / Готово, названия можно менять); в колонке сначала ближний срок. Перетаскивание карточки мышью меняет статус (в карточке — тот же статус списком). Фильтры по категориям с числами и «Архив». Быстрая постановка над доской: название, категория, ответственный, срок. Срочные (высокий приоритет) отмечены «срочно», просроченные — красным «просрочено · дата»; у задач из реестров — «авто», без ответственного — «не назначен». Справа — загрузка сотрудников по открытым задачам.
   - Карточка открывается в боковой панели (и по ссылке `/tasks?task=…`): название, описание, статус, ответственный, срок, приоритет, категория; «Отметить выполненной»; комментарии; история изменений из журнала аудита (кто, когда, что поменял); исходное письмо с правилом и причиной срока, если задача из почты; ссылка на запись реестра и получатели с e-mail, если задача из автоматизации. Правка сохраняет только изменённое, с версией: если задачу успели изменить, карточка предлагает перечитать.
   - Ответственный — только активный пользователь с доступом к разделам ИБ. Переход в «Готово» закрывает задачу (не просрочена), уход из «Готово» открывает снова.
   - Архив: задачу может отправить в архив и вернуть любой сотрудник ИБ; архивная задача не правится. Архив открывается кнопкой «Архив» в фильтрах. Удаление — мягкое, по праву «Задачи: удаление», с подтверждением и записью в журнале.
   - Уведомления пока только внутри портала: у пункта «Задачи» в меню — число просроченных задач отдела (в подсказке — сколько из них мои). Письма — этап 9.
   - **Почта → задача (без интеграции):** кнопка «Задача из письма», текст письма вставляется целиком, портал разбирает «От / Тема / Отправлено» (и английские From / Subject / Sent); название — тема без RE/FW. Срок: «до ДД.ММ(.ГГГГ)» (без года — ближайшая такая дата не раньше сегодня), «сегодня», «завтра» (выходной или праздник — ближайший рабочий день), «в течение N дней» (календарных) и «в течение N рабочих дней» по производственному календарю; по умолчанию 3 рабочих дня. «Срочно» — высокий приоритет и, если срока в письме нет, 1 рабочий день. Правило разбора почты — с наибольшим числом совпавших ключевых слов (при равенстве — первое по порядку справочника) → его ответственный (если он сотрудник ИБ). Черновик показывает, почему такой срок и ответственный; разбор ничего не сохраняет. Задача создаётся только после проверки: категория «Почта», письмо и сработавшее правило сохраняются в карточке.
   - **Интеграция с MDaemon (позже, отдельный этап):** (1) отдельный ящик, например ib-tasks@, портал читает его по IMAP — сотрудники пересылают письма туда, или правило Content Filter копирует письма отделу ИБ в этот ящик; номер задачи в теме [ИБ-123] — ответы добавляются комментариями; (2) Content Filter → действие «Run Process» с $MESSAGEFILENAME$ — скрипт на почтовом сервере передаёт письмо в API портала; уведомления из портала — через MDaemon как SMTP-релей.
6. **Документы** — реестр внутренних документов ИБ, маршрут согласования (Автор → Начальник ИБ → Юридический отдел → Утверждение правлением), контроль пересмотра; файлы в OnlyOffice.
   - Реестр: название, тип (справочник «Типы документов»), владелец, версия, дата утверждения, цикл пересмотра (по умолчанию 12 месяцев), дата следующего пересмотра, статус — черновик, на согласовании, утверждён, на пересмотре (новая версия утверждённого документа в работе), пересмотр просрочен (важнее «на пересмотре»: пока новая версия не утверждена, срок нарушен). Справа — карточка выбранного документа: маршрут, действия, версии, история. Фильтры: «Ждут вас», статусы, «Архив»; поиск по названию.
   - Номер версии (1, 2, 3…) ставит портал; необязательная «Редакция» («3.1») — только для отображения. Владелец — активный сотрудник с доступом к разделам ИБ: ему ставятся задачи.
   - Файл остаётся в OnlyOffice: у версии хранится ссылка (только http:// или https://), кнопка «Открыть в OnlyOffice». Интеграции с API OnlyOffice пока нет (ADR-0010).
   - **Маршрут.** Этап «Автор» — владелец документа или право «Документы: управление» (отправка за автора). Этапы 1–3 — только пользователь с правом этапа. Разделение полномочий: владелец документа не согласует ни один этап своего документа, кроме «Автор», — даже если документ отправил на согласование другой пользователь; супер-администратор не согласует ни один этап, даже если другая его роль даёт право этапа; один человек не согласует два этапа одной версии. Если этап некому согласовать, кроме владельца (у владельца есть право этапа, других активных согласующих нет), этап отмечается «Не требуется: автор — <этап>» с записью в истории (кто владелец, почему пропущен) и документ идёт дальше; пропуск последнего этапа утверждает документ. Остальные этапы обязательны; если права этапа нет ни у кого, документ ждёт («никто не назначен»). У каждого этапа видно, кто может его согласовать; в реестре отмечено «ждёт вас». Экран, отставший от документа (документ уже на другом этапе или изменён), получает отказ и предложение обновить.
   - **Возврат на доработку** — с этапов 1–3, только с замечанием. Маршрут начинается заново (новый круг), владельцу ставится задача «Доработать документ» (категория «Документы», 3 рабочих дня) с замечанием; если такая задача ещё открыта — замечание добавляется в неё комментарием. Повторная отправка на согласование закрывает задачу сама.
   - **История согласования** только пополняется (права и триггер, как у журнала аудита): кто, когда, этап, решение (отправил, согласовал, вернул, этап не требуется, начал новую версию), комментарий, номер версии, круг.
   - **Версии.** Черновик правят владелец или «Документы: управление» — только на этапе «Автор». Утверждённую версию изменить нельзя: правка утверждённого документа — это новая версия, она проходит весь маршрут; пересмотр без изменений — тоже новая версия. До утверждения новой версии действует прежняя. Утверждённые версии не меняются и не удаляются (права и триггер) и видны в списке версий карточки.
   - **Пересмотр.** Дата следующего пересмотра = дата утверждения + цикл (31-е число → последний день месяца); смена цикла пересчитывает её от даты утверждения. За 30 дней до даты владельцу ставится задача «Пересмотреть документ» (событие автоматизации → задача, проверка раз в час вместе с автоматизациями реестров; повторная проверка дублей не даёт). Если новая версия уже в работе, задача не ставится; утверждение новой версии закрывает задачу. Просроченный пересмотр виден в реестре и красным числом у пункта «Документы» (сотрудникам ИБ).
   - **Пользователи без доступа к разделам ИБ** (юрист, правление) видят только «Документы»: утверждённые документы (действующую версию), документы, которые ждут их этапа, и согласованные ими в текущем круге. Черновики, документы на чужом этапе и архив им не видны; задачи им не ставятся — вместо этого число «ждёт вас» у пункта «Документы» (синее; видят все).
   - Тип, владельца и цикл меняет «Документы: управление»; он же отправляет документ в архив (пересмотр архивного не контролируется) и возвращает из архива. Физического удаления нет.
   - **Итоговый PDF (этап 7).** Ссылка на OnlyOffice не фиксирует содержимое, поэтому автор прикладывает итоговый PDF при отправке на согласование: без него документ не отправить, и все этапы согласуют именно этот файл (sha256 — в истории каждого решения). Замена PDF во время согласования возвращает маршрут к началу (новый круг). Версия, ушедшая на согласование без PDF, не утверждается, пока автор не приложит файл. Утверждённая до этапа 7 версия без PDF показывается с пометкой «текст не зафиксирован»; задним числом PDF не прикладывается — текст зафиксирует следующий пересмотр. PDF версии просматривается прямо в карточке; юрист и правление видят PDF тех версий, которые им видны.
   - Уведомления согласующим по e-mail — этап 9.
7. **Риски ИБ** — системный «Реестр рисков ИБ» конструктора, отдельно от рисков банка; связь с реестром ОУР по номеру. Поля: риск, актив / система (справочник «Системы»), уровень, статус ИБ, № в реестре ОУР, решение ОУР, пересмотр до, владелец риска. Решение выносит ОУР; ИБ фиксирует его только с документом ОУР — решение заполняет «№ в реестре ОУР» и «Пересмотр до». Автоматизации: за 30 дней до пересмотра решения — задача владельцу риска; пересмотр просрочен — владельцу и начальнику ИБ.
8. **Доказательная база** — доказательства по объектам, формы подтверждения со сверкой требований и проверкой ИБ.
   - Доказательство привязано к объекту: записи реестра, документу или системе. Вид: форма подтверждения по шаблону, решение другого отдела (из реестра), файл (протокол, скриншот, выгрузка). У каждого — один или несколько файлов.
   - Реестр: объект, тип, файл, загрузил, дата, действует до, результат сверки, проверка ИБ; фильтры «На проверке / Принято / Истекает / Истекло / Отклонено», архив, поиск. Справа — «Загрузить» с покрытием систем формами выбранного шаблона.
   - Форма заполняется целиком; отметка соответствия видна сразу; срок действия — дата загрузки + срок шаблона. Файл без формы — по желанию со сроком «действует до».
   - Проверка — право «Доказательства: проверка», но не своё: проверяющий не принимает доказательство, которое загрузил или к которому приложил файл. Отклонение — с комментарием, загрузившему — задача «Исправить и загрузить заново» (категория «Доказательства», 7 дней); задача закрывается, когда приложен исправленный файл или загружена новая форма. Новый файл возвращает принятое доказательство на проверку; убрать файл можно только у доказательства на проверке (не последний).
   - Срок действия: «истекает» — за 30 дней, «истекло» — после даты. За 30 дней ответственному — задача «Обновить доказательство» (раз в час, вместе с автоматизациями); принятие новой формы по тому же объекту и шаблону её закрывает. Число «на проверке» — у пункта «Доказательства» (тем, кто проверяет).
   - **Файлы:** до 25 МБ; pdf, png, jpg, txt, csv, xlsx, docx — тип проверяется по содержимому: подмена расширения, SVG, HTML и документы с макросами не проходят. Загружают сотрудники ИБ и участники документооборота. Файлы хранятся в томе портала по пути без имени файла и выдаются только через backend с проверкой прав (attachment, nosniff). Физически файл не удаляется; без ссылок — помечается удалённым, непривязанный — через сутки.
   - Карточка доказательства: данные, поля формы со значениями и отметкой соответствия, файлы, история, принять/отклонить. Файлы просматриваются прямо в карточке (изображения, PDF, текст/CSV), к доказательству можно добавить файлы, файл можно сохранить.
   - Шаблоны форм подтверждения (парольная защита, пересмотр прав доступа и новые) настраиваются в справочниках: название, документ-основание, срок действия, поля с типом проверки (число не менее / не более, да-нет, текст). Загруженная форма хранит снимок полей и значений, поэтому изменения шаблона не меняют старые формы.
9. **Настройки** (по образцу RISK CONSOLE): справочники — категории задач (с цветом), статусы задач (только переименование), приоритеты, правила разбора почты, системы (с владельцем системы), получатели уведомлений (метка → участники и e-mail), типы документов, производственный календарь РТ, шаблоны форм подтверждения; пользователи и роли; журнал изменений.
   - Справочники меняет роль с правом «Настройки: справочники и шаблоны форм», пользователей и роли — с правом «Настройки: пользователи, роли и права»; остальные видят настройки для просмотра.
   - Переименование обновляет все записи с этим значением. Используемое значение не удаляется, а уходит в архив: пропадает из списков выбора, старые записи его сохраняют. Системные значения (замок) не удаляются и не переименовываются — на них опирается логика (например, «Реестр» ставят автоматизации, «Высокий» — разбор письма со словом «срочно»).
   - Роли и права: матрица «право × роль» с отметками, добавление, переименование и удаление ролей (без пользователей). Пользователи: заведение учётной записи, назначение ролей, отключение. Нельзя снять право управлять ролями с себя и с последнего, у кого оно есть.
   - Удаление значения — мягкое: оно пропадает из настроек, а журнал хранит, кто и когда его удалил. Удалить можно только несистемное неиспользуемое значение.
   - Производственный календарь РТ: выходные дни недели (по умолчанию пятидневка, настраивается) и отклонения — праздники и рабочие дни-переносы. Постоянные праздники (1.01, 8.03, 21–24.03, 1.05, 9.05, 27.06, 9.09, 6.11) на 2026 и 2027 годы внесены заранее; Иди Рамазон, Иди Курбон и переносы администратор добавляет сам. По календарю считаются сроки в рабочих днях (п. 7.4, разбор почты).
   - Если при обновлении появляется новое системное значение, а администратор уже завёл значение с тем же названием, оно становится системным; seed пишет об этом в журнал изменений (автор — «Система») и в свой вывод.
   - Стартовые значения (категории «Проект» и «Оперплан», системы, типы документов, правила почты, два шаблона форм) создаются только при первой установке и не возвращаются, если администратор их удалил или отправил в архив. Ответственных в правилах почты назначает администратор.
   - Пользователи: логин после создания не меняется. Временный пароль при создании и сбросе генерирует портал, он показывается администратору один раз; при входе пользователь задаёт свой. Сброс закрывает сессии пользователя и снимает блокировку входа; блокировку можно снять и отдельно. Отключение закрывает сессии; себя отключить нельзя. Свой пароль администратор меняет обычной сменой пароля.
   - Срок действия пароля — 90 дней, после него смена обязательна. MFA (TOTP) для пользователей с правами на настройки и пользователей — запланирована до первой рабочей выкладки.
   - Роль «Супер-администратор»: права на справочники и на пользователей не снимаются, права этапов согласования ей не выдаются. Удалить можно только несистемную роль без пользователей.
   - Журнал изменений: кто, когда, с какими ролями, что поменял. Строится из журнала аудита; вход и выход в него не попадают.
