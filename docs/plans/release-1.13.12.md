# План релиза 1.13.12 — Уязвимости: «Аннулировать скан»

Задание: `docs/tasks/1.13.12-vuln-scan-annul.md` (текст владельца от 12.11.2026). От `v1.13.11`. Новых зависимостей, переменных `.env` и прав нет. **Код — после подтверждения: нужна миграция, которая не сводится к nullable-колонкам (раздел 1).**

## 1. Почему стоп: что нужно менять в схеме

Скан защищён триггером `vuln_scans_guard` (миграция `20261030172054_vuln_groups_scans`). Он разрешает менять только поля передачи ИКТ и только один раз. Любая другая правка строки скана, в том числе запись новых колонок, падает. Поэтому чисто аддитивной миграции (только nullable-колонки) для аннулирования нет. Есть два варианта.

| | A. Колонки на скане | B. Событие в корзине (рекомендую) |
|---|---|---|
| Что меняется в схеме | `vuln_scans`: nullable `annulled_at`, `annulled_by`, `annul_reason_code`, `annul_reason`, `deletion_id`; **новая версия функции `vuln_scans_guard`**: дополнительно разрешает установить поля аннулирования и снять их при восстановлении | `deletions`: **расширить два CHECK** — `entity` + `'vuln_scan'`, `reason_code` + `'reupload'`, `'wrong_file'`; индекс `deletions (entity, entity_id) WHERE restored_at IS NULL` |
| Строки скана | меняются (новые поля) | не меняются: `vuln_scans_guard` остаётся как есть, скан по-прежнему неизменен |
| Признак «аннулирован» | колонка `annulled_at` | есть невосстановленное событие `deletions` с `entity = 'vuln_scan'` и `entity_id` скана |
| Корзина и восстановление | событие в `deletions` всё равно нужно (п. 3 задания) — те же CHECK расширяются и здесь | тот же механизм, что у групп, узлов и записей |
| Влияние на данные | 0 изменённых строк; новые колонки пустые | 0 изменённых строк; старые значения CHECK остаются допустимыми |
| Откат на 1.13.11 без отката базы | да; 1.13.11 не знает колонок, аннулированные сканы снова видны как обычные | да; то же |

★ **Рекомендую B.** Аннулирование и есть мягкое удаление со снимком в корзине (раздел 3.4 CLAUDE.md, ADR-0033), а неизменность скана сохраняется без правки защитной функции. Вариант A меняет `vuln_scans_guard` и всё равно требует расширить CHECK у `deletions` для корзины.

Миграция B (одна, `--create-only`, SQL — до применения):

```sql
ALTER TABLE "deletions" DROP CONSTRAINT "deletions_entity_check",
  ADD CONSTRAINT "deletions_entity_check" CHECK ("entity" IN ('register', 'vuln_group', 'vuln_node', 'register_records', 'vuln_scan'));
ALTER TABLE "deletions" DROP CONSTRAINT "deletions_reason_code_check",
  ADD CONSTRAINT "deletions_reason_code_check" CHECK ("reason_code" IS NULL OR "reason_code" IN ('wrong_import', 'false_positive', 'duplicate', 'other', 'reupload', 'wrong_file'));
CREATE INDEX "deletions_active_entity_idx" ON "deletions" ("entity", "entity_id") WHERE "restored_at" IS NULL;
```

Влияние на данные: 0 изменённых строк, существующие значения остаются допустимыми, новые колонки не добавляются.

## 2. Аннулирование (backend, `vulns/scans.service.ts`)

- `POST /vulns/scans/:id/annul` `{ reason: 'reupload' | 'wrong_file' | 'other', comment? }` — право `data.delete` (403 без него). «Другое» — комментарий обязателен (400 `REASON_REQUIRED`).
- Условия — одной транзакцией, со строкой скана и узла `FOR UPDATE`:
    - скан не передан ИКТ, иначе 409 `SCAN_HANDED_OVER` «Скан передан ИКТ — аннулировать нельзя»;
    - в узле есть более поздний неаннулированный скан (порядок — как у «прошлого скана»: дата скана, затем время загрузки), иначе 409 `SCAN_LAST` «Это последний скан узла — аннулировать нельзя»;
    - уже аннулирован — 409 `SCAN_ANNULLED`.
- Событие `deletions`: `entity = 'vuln_scan'`, `entity_id` — скан, название «Скан от ДД.ММ.ГГГГ, файл …», причина, `counts { findings }`. Скан, файл, снимок находок и сравнение не меняются. Журнал — `vuln.scan.annulled`.
- `GET /vulns/scans/:id` → `annulled: { at, by, reasonCode, reasonLabel, reason, deletionId } | null` и `canAnnul` (условия выполнены).

## 3. Последствия — где учитывается

Один помощник `activeScanWhere()` / SQL-условие «нет невосстановленного события `vuln_scan`»:

| Место | Как сейчас | После |
|---|---|---|
| Дерево узла (`listScans`) | все сканы | без аннулированных; `?annulled=1` — с ними и пометкой (переключатель «Показать аннулированные») |
| «Сканы ждут передачи ИКТ», последний скан и возраст узла, показатели раздела (`section.overview`) | все | без аннулированных |
| «Передать ИКТ» (`handOverScan`) | любой непереданный | аннулированный — 409 `SCAN_ANNULLED` |
| «Прошлый скан» предпросмотра и сравнение охвата (`previousScanOf`) | последний скан узла | последний неаннулированный |
| Число сканов узла (`groups.service`), хосты сканов для сверки активов (`assets.service`) | все | без аннулированных |
| Карточка записи — список сканов | все | все, у аннулированного — отметка «аннулирован» |
| Карточка записи — «впервые» и «последний раз» | из `vuln_records.first_scan_id` / `last_scan_id` | ★ по встречам записи в неаннулированных сканах (`vuln_record_scans`); строки `vuln_records` не меняются |
| Срок | `deadline_scan_id` ставит только передача ИКТ | **без изменений, проверено по коду:** аннулировать можно только непереданный скан, а аннулированный передать нельзя, поэтому он никогда не становится сканом срока |
| Сканы, загруженные после аннулированного | их `previous_scan_id` и сравнение — как были | без изменений: история, «изменения не откатываются» |

`check-integrity`: нет событий `vuln_scan` у переданных ИКТ сканов; у каждого узла с аннулированными сканами есть хотя бы один неаннулированный.

## 4. Корзина и восстановление

- Корзина (`trash.service`): `vuln_scan` — «Скан», путь «Группа / тип», раздел «Уязвимости»; причины «Повторная загрузка», «Ошибочный файл», «Другое».
- Восстановление — супер-администратор, `restoreDeletion` (тот же механизм): событие получает `restored_at`, скан снова обычный. Журнал — как у остального восстановления.
- ★ **Условия восстановления:** только одно — узел и его группа не удалены (иначе 409 `PARENT_DELETED` «Сначала восстановите тип / группу»). Других не нужно:
    - восстановленный скан снова «ждёт передачи ИКТ» — так и было до аннулирования;
    - если его передадут позже более позднего скана, срок записей не сдвинется — правило ADR-0030 «поздняя передача более раннего скана срок не сдвигает» уже действует;
    - сравнения и «прошлый скан» более поздних сканов не пересчитываются — это история.

## 5. Интерфейс (frontend)

- Страница скана: кнопка «Аннулировать скан» (только при `canAnnul` и праве `data.delete`) → окно: причина (три варианта, «Другое» — с текстом), текст «Изменения, которые этот скан внёс в реестр, не откатываются. Скан остаётся в истории с отметкой „Аннулирован“», «Аннулировать».
- Аннулированный по прямой ссылке: плашка «Аннулирован <дата>, <кто>, <причина>», без «Передать ИКТ».
- Дерево узла: аннулированных нет; под списком сканов — переключатель «Показать аннулированные» (зачёркнутая дата, без точки «ждёт передачи»).
- Карточка записи: у аннулированного скана — чип «аннулирован».
- Корзина: строки «Скан» с причиной и «Восстановить».

## 6. Тесты

- DB: аннулирование при выполненных условиях (событие, журнал, скан не изменился); 409 для переданного ИКТ и для последнего скана узла; повторное — 409; «Другое» без текста — 400; 403 без `data.delete` (HTTP); скан пропал из дерева и из «ждут передачи»; «Передать ИКТ» — 409; следующий импорт берёт «прошлым» неаннулированный скан; «впервые» в карточке — по неаннулированному; восстановление из корзины (и 409 при удалённом узле).
- Миграция: `prisma migrate dev` на dev, `check:schema`, `check:integrity`.
- e2e: два импорта одного файла в узел → аннулировать первый → точка «ждёт передачи» в дереве исчезла, «Показать аннулированные» показывает его с отметкой.
