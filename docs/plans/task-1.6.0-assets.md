## 0. Данные банка в репозиторий не попадают

## 1. Шкала критичности: по процедуре классификации ИТ-активов

Категории (список, в этом порядке): **Mission Critical, Business Critical, Operational, Non-Critical**.
- Значимыми для сверки и самооценки считаются Mission Critical и Business Critical. Набор значимых категорий хранится в app_settings, а не в коде.
- Значения по умолчанию по категории (Приложение 3 процедуры), подставляются при выборе категории, можно изменить вручную:

| Категория | Макс. простой (RTO) | RPO |
|---|---|---|
| Mission Critical | 2 ч | до 4 ч |
| Business Critical | 12 ч | 4–24 ч |
| Operational | 72 ч | 1–7 дн. |
| Non-Critical | не задано | не задано |

- Перевод значений старой шкалы при импорте Excel: «Business Operatinal» (с опечаткой) и «Business Operational» → Operational; «Office Productivity» → Non-Critical; Mission Critical и Business Critical без изменений; пусто → пусто.
- Пересмотр классификации: раз в 6 месяцев (активы ЦОД по процедуре). «Пересмотр до» по умолчанию = дата классификации + 6 месяцев. За 30 дней — задача получателям метки, как ты предложил.

## 2. Три реестра вместо двух: Продукты → Компоненты → Хосты

В процедуре продукты (Приложение 2, несколько десятков: АБС, мобильный кошелёк, контроллер домена, WAF…) идентифицируются через сервисы-компоненты. Реестр Excel — это несколько сотен компонентов (микросервисы, БД, прокси) с IP:порт.

**Реестр «Сервисы» (уровень продукта)** — как в твоём плане, с изменениями:
- «Значимость» → «Категория критичности» (п. 1), плюс поля «RTO» и «RPO» (текст, значение по умолчанию из категории).
- «Основание значимости» переименовать в «Связь с ключевыми рисками». Это требование раздела 2.3 методики.
- Добавить «Владелец (должность)», «Подразделение», «Дата классификации», «Классифицировал» (сотрудник), «Согласовано руководителем ИБ» (дата). Последние три требует раздел «Документирование» процедуры.
- Остальные поля твоего плана сохраняются: Система (справочник), Назначение, Бизнес- и ИТ-владелец, Обрабатываемые данные, Доступ из интернета, Мониторинг, Устаревшая система и план, Пересмотр до, Статус.

**Новый реестр «Компоненты»:**

| Поле | Тип |
|---|---|
| Компонент | текст, заголовок; ключ импорта — пара «Компонент + Продукт» (имена вроде notification повторяются в разных продуктах) |
| Продукт | связь с записью «Сервисов» |
| Тип актива | список: Сервис, База данных, NoSQL база данных, Прокси-сервер, Web-сервис |
| Категория критичности | список п. 1 |
| Среда | список: Prod, Test |
| Статус | Работает, Выводится, Выведен (закрыт) |
| Описание | текст |
| ОС / ПО | текст, нормализованный (п. 3) |
| IP-адрес | текст |
| Порт | текст |
| Хост | связь с записью «Хостов» |
| Местоположение | список (значения из файла: ЦОД 1, облако и т. п.) |
| Владелец | текст (ФИО) |
| Команда | текст |

В карточке продукта — обратный список компонентов, в карточке хоста — обратный список компонентов.

**Реестр «Хосты»** — как в плане, с полями Kaspersky из п. 4 и полями ЦОД из Приложения 4 процедуры: «Кластер» (текст), «Местоположение» (список, общий с компонентами), «Инвентарный номер» (текст). Поле «Состояние защиты» убрать: такой колонки в отчётах Kaspersky нет, его заменяют «Покрытие защиты» и «Статус антивирусных баз».

## 3. Импорт реестра сервисов (Excel v3)

Формат файла владельца:
- Лист «Список активов». Строки 1–4 — шапка формы (подразделение, дата заполнения), строка 5 пустая, **заголовки в строке 6**, данные с 7-й строки.
- Колонки: №, Наименование актива, Тип актива, Важность/Критичность, Местоположение, Описание/назначение, Операционная система/ПО, IP-адрес, Владелец, Класификация, Команда.
- Листы «Справочник» (старая шкала) и «контакты» не импортируются.

Правила:
- Если импорт конструктора не умеет начинать со строки 6, не меняй его ради этого. В инструкции напиши, что владелец удаляет строки 1–5 перед загрузкой. Сначала проверь, что импорт берёт нужный лист.
- «Важность/Критичность» → «Категория критичности» по таблице перевода из п. 1.
- Колонка «Класификация» на самом деле содержит статус: «В эксплуатации» → Среда Prod, Статус «Работает»; «Тест/внедрение» и «Тест» → Среда Test, Статус «Работает».
- «IP-адрес» в формате `IP:порт` делится на IP и порт. Неполный адрес (меньше четырёх октетов) не отбрасывать: сохранить как есть и показать в предпросмотре предупреждением.
- «Команда» → «Продукт» по таблице соответствия. Таблица хранится в app_settings и редактируется в настройках, в коде её нет. Начальное наполнение — около десяти пар вида «Команда А → Продукт А», «Команда Б (с опечаткой) → Продукт Б»; несколько команд дают один продукт.
  Части продуктов в Приложении 2 нет. Если продукта с таким именем нет в «Сервисах», импорт создаёт его со статусом «Работает» без категории и показывает в предпросмотре «Будут созданы продукты: …». Категорию ставит владелец.
- «ОС/ПО»: нормализация написаний к одному виду. В файле 10 написаний четырёх систем: «Linux Centos 7», «CentOS Linux 7 (Core)», «CentOS Linux 7» → «CentOS 7»; «Linux Debian 11 (Bullseye)», «Debian GNU/Linux 11 (bullseye)», «Linux/Debian 11 (bullseye)», «Linux/Debian 11» → «Debian 11»; «Linux/Ubuntu 22.04.3 LTS» → «Ubuntu 22.04»; «Linux/Ubuntu» → «Ubuntu». Таблица нормализации — в app_settings, исходное значение не теряется (храни в истории записи или отдельном поле, предложи).
- Хосты из IP компонентов: для каждого уникального IP, которого нет в «Хостах», импорт предлагает создать хост (Тип «Сервер», Источник «Реестр сервисов», имя = IP, пока не известно имя) и связывает компонент с хостом. В предпросмотре — отдельный блок «Будут созданы хосты: N», можно снять.
- Пустая категория не блокирует импорт, такие компоненты попадают в сверку.

## 4. Импорт отчётов Kaspersky Security Center

Разбор шести настоящих отчётов показал, что готовым импортом конструктора их не загрузить. Здесь нужен небольшой новый код: адаптер, который превращает отчёт KSC в строки и передаёт их в существующий конвейер импорта (предпросмотр, одна транзакция, сравнение ADR-0017). Конвейер не дублируй.

### 4.1 Формат файла

- KSC сохраняет отчёт как **XML Spreadsheet 2003 (SpreadsheetML)** с расширением `.xls`. Это не BIFF и не xlsx: файл начинается с `<?xml …?><?mso-application progid="Excel.Sheet"?><Workbook xmlns="urn:schemas-microsoft-com:office:spreadsheet">`.
- Адаптер принимает и этот формат, и `.xlsx` (если владелец пересохранит файл в Excel). Определять по содержимому, а не по расширению.
- Разбор XML безопасный: внешние сущности и DTD запрещены, ограничение размера файла как у остального импорта. Ячейки `ss:Data` с `ss:Type="String"` / `"DateTime"` / `"Number"`; учитывать `ss:Index` (пропуск ячеек) и `ss:MergeAcross`.
- В файле два листа: **Summary** (строка 1 «Kaspersky Security Center», строка 2 — название отчёта, строка 3 — описание и для какой группы сформирован, затем сводная таблица) и **Details** (строка 1 — заголовки, дальше по строке на устройство).
- Тип отчёта определяется по строке 2 листа Summary. Неизвестный отчёт отклоняется с понятным сообщением.

### 4.2 Обрезанные отчёты: блокировать

У всех шести файлов на листе Details ровно 1000 строк, а устройств по сводке больше лимита — и в отчёте о развёртывании, и в отчёте о статусе баз. KSC по умолчанию ограничивает детальную часть 1000 записями.
- Адаптер сравнивает число строк Details с итогом из Summary. Где итог считается однозначно (развёртывание — сумма «Количество устройств»; статус баз — сумма «Количество устройств»), при расхождении импорт **блокируется**: «Отчёт обрезан: в сводке N устройств, в таблице M. Увеличьте в KSC лимит записей в свойствах шаблона отчёта и выгрузите заново».
- Где итог однозначно не посчитать, и в Details ровно 1000 строк (или другое круглое число, совпадающее с известным лимитом), показывать предупреждение и **не запускать «Нет в файле»**.
- Без этой проверки сравнение пометило бы половину станций как пропавшие.

### 4.3 Какие отчёты принимаем

Принимаются три отчёта. Каждый обновляет только свои поля хоста:

**«Отчет о развертывании защиты»** — основной. Формируется для всей сети, поэтому включает и устройства без агента (в домене их часть устройств, среди них серверы). Только этот отчёт запускает «Нет в файле».
- Колонки Details: Виртуальный Сервер администрирования, Группа, Устройство, Версия Агента администрирования, Название программы безопасности, Версия программы безопасности.
- «Неизвестно» означает отсутствие значения.
- Поля хоста: Группа KSC, Версия агента, Продукт защиты, Версия защиты.
- Вычисляемое «Покрытие защиты»: «Агент и защита» (обе версии есть), «Только агент» (версия агента есть, программы нет), «Нет агента» (нет версии агента). Сводка отчёта даёт те же три группы, сверяй с ней в тесте.

**«Отчет о статусе антивирусных баз»** (у отчёта «об используемых антивирусных базах» те же колонки; принимай оба, это один тип данных).
- Колонки: Виртуальный Сервер администрирования, Группа, Устройство, Программа, Номер версии, Созданы, Статус антивирусных баз, IP-адрес, NetBIOS-имя, Windows-домен, IPv6-адрес.
- Поля хоста: Статус антивирусных баз (список значений из отчёта: «Актуальные», «Обновлены в последние 24 часа», «Обновлены в последние 3 дня», «Обновлены в последние 7 дней», «Обновлены более 7 дней назад»), Дата баз (= «Созданы»), IP-адрес, Домен.
- Незнакомое значение статуса не ломает импорт: сохраняется как есть, в предпросмотре предупреждение.

**«Отчет о версиях программ "Лаборатории Касперского"»**.
- Колонки: Программа, Номер версии, Виртуальный Сервер администрирования, Группа, Устройство, Установлено, Последнее появление в сети, Последнее подключение к Серверу администрирования, IP-адрес, Установленные обновления, IPv6-адрес.
- Строка = программа × устройство: одно устройство встречается и строкой агента, и строкой продукта защиты. Брать строки программы безопасности (Kaspersky Endpoint Security для Windows / for Mac, Kaspersky Security для Windows Server). Строки «Агент администрирования…» использовать только для версии агента, а строку «Сервер администрирования…» пропускать.
- Поля хоста: Последняя связь с Kaspersky (= «Последнее подключение к Серверу администрирования»), Последнее появление в сети, Защита установлена (= «Установлено»).

**Не принимаем** (отклонять с подсказкой, что отчёт не нужен):
- «Отчет о владельцах устройств» — колонки «Владелец» и «Электронная почта» пусты у всех устройств.
- «Отчет о реестре оборудования» — комплектующие (материнская плата, диски, звуковая карта), для ИБ не нужны.

### 4.4 Ключ, дубли, тип

- Ключ — нормализованное имя: колонка «Устройство», в нижнем регистре, без пробелов по краям, без доменного суффикса после первой точки. Там, где есть «NetBIOS-имя», использовать его как подтверждение.
- **Дубли внутри одного отчёта.** В KSC одна машина бывает двумя записями (пример: `TEST-PC01NB` со старыми базами и `test-pc01nb.example.local` с актуальными базами — переустановка). После нормализации имена совпадают. В хост пишется строка с самой свежей датой («Созданы» или «Последнее подключение…»), а устаревшая запись показывается в предпросмотре блоком «Дубли в KSC — удалить устаревшие записи в консоли». Это заменяет общее правило «не склеивать, предупреждать» для источника Kaspersky.
- Совпадение нормализованного имени с хостом из другого источника (реестр сервисов, сканер) — предупреждение, без склейки, как ты предложил.
- «Тип» у нового хоста (у существующего не перезаписывать): «Сервер», если продукт «…для Windows Server», или группа KSC «Servers», или имя содержит SRV / SERVER / начинается с DC и цифры; «Рабочая станция», если имя оканчивается на NB, PC или MAC (с цифрами после или без); иначе «Другое». Владелец исправит вручную. Правила — в app_settings.
- Группа KSC сохраняется текстом и в «Подразделение» не переносится: в группах вперемешку филиалы и политики («Филиал 1», «Филиал 2» рядом с группами политик Wi-Fi и USB).
- ОС в отчётах KSC нет. Поле «ОС» заполняется из реестра сервисов и из хостов сканов VM (`vuln_scans.hosts` содержит `os`). Если у хоста ОС пуста, а в последнем скане есть, предложи подставлять при сверке, а не молча.

### 4.5 Объём

- Реальный объём — несколько тысяч устройств в отчёте о развёртывании. Проверить на сгенерированном файле в 3–5 тысяч строк: время разбора, предпросмотр и «Нет в файле». Если есть лимит строк или размера, он должен быть больше и описан в инструкции.

## 5. Сверка

Форма факта и правило «Нет данных», как договорились:
- каждая проверка возвращает: код, раздел методики, числитель, знаменатель, процент, список записей со ссылками, дату расчёта;
- если реестр-источник пуст (например, реестр рисков ИБ), проверка возвращает «Нет данных: <реестр> не заполнен» без процента и списка;
- выведенные и закрытые записи в проверки не входят.

Список проверок — твой, с изменениями:
- Сервисы и компоненты: без категории; значимые без владельца, назначения, связи с ключевыми рисками; пересмотр просрочен; нет даты классификации или согласования (2.2, 2.3).
- **Компонент критичнее своего продукта** (например, компонент Mission Critical у продукта Business Critical) — 2.3.
- Значимые продукты без компонентов или без хостов (2.2); значения справочника «Системы» без продукта и наоборот (2.2).
- Компоненты и хосты с ОС из списка неподдерживаемых (CentOS 7, Debian 11 и т. п.), без плана в продукте (8.2). Список неподдерживаемых ОС — в app_settings, начальные значения: CentOS 7, Debian 11.
- Значимые продукты: хосты не встречались в сканах 90 дней (5.2); хосты из сканов, которых нет в реестре (2.2); нет риска в реестре рисков ИБ (2.3, 1.2); не подключены к мониторингу (3.2).
- Среда: доля компонентов Test у значимых продуктов, компоненты Test и Prod на одном хосте (9.3).
- Kaspersky (9.2):
  - Покрытие «Нет агента» и «Только агент», отдельно по типу Сервер и Рабочая станция (в отчётах есть серверы без агента — это важнее станций);
  - статус баз «Обновлены более 7 дней назад» (по сводке — заметная часть устройств);
  - агент молчит: «Последнее появление в сети» за 7 дней, а «Последнее подключение к Серверу» старше 30 дней (в выборке такие устройства есть);
  - версия защиты ниже минимальной (порог в app_settings, по умолчанию пусто = проверка «Нет данных»);
  - рабочие станции без агента DLP и агенты DLP без хоста;
  - последний импорт отчёта о развёртывании старше 35 дней.
- Источник фактов для «Что видит портал» — эта же сверка, без пересчёта.

## 6. Остальное

- Правило из процедуры для уровня 4 раздела 2.3: у продукта нельзя поставить статус «Работает», пока не заполнена категория критичности. Если конструктор не умеет условную обязательность поля, не добавляй её ради этого: тогда это проверка сверки «работает без категории». Скажи в плане, какой вариант получился.
- Реестр инцидентов: необязательное поле «Сервис» (связь с продуктом), как в плане.
- Права: просмотр сверки — ib.work; импорт и правка реестров — права конструктора, как у остальных реестров.
- Схема БД и коды прав не меняются; если для адаптера Kaspersky понадобится хранить сведения об импорте (тип отчёта, итог сводки, число дублей), сначала предложи без миграции, а если без неё никак — покажи SQL до применения.
