# Предложение: названия задач автоматизаций — номер и тип отдельно (без реализации)

Статус: на решение владельца, 04.11.2026. Повод — раздел 7 `docs/ui-audit-1.6.5.md`: на доске в колонке 196 px заголовок задачи автоматизации занимает 5–6 строк, а обрезка до 3 строк срезает конец «— #3870 …», по которому карточки различаются.

## Как сейчас

`backend/src/modules/tasks/from-events.ts`:

| Вид задачи | Название | Строка |
|---|---|---|
| По записи | `{Напоминание \| Уведомление \| Эскалация}: {условие правила} — #{номер записи} {заголовок записи}`, или свой шаблон правила `action.title` вместо первой части | 159–160 |
| Сводка по реестру (digest) | `{Тип}: {условие правила}` или `action.title`; номеров нет | 250 |

Пример: «Напоминание: За 3 дн. до «Срок устранения» — #3870 E2E-mvseemeb-03» (66 символов, предел `TITLE_MAX`).

Что уже есть в данных:
- у задачи хранятся `record_id` и `automation_id`; список `GET /api/v1/tasks` отдаёт `record: { id, registerId, number }` (`tasks/routes.ts`, строка 43) — **номер записи для бейджа есть уже сейчас**, без изменения API;
- **типа события у задачи нет**: он лежит в `automation_events.event_type` и связан с задачей через `automation_event_tasks`; в список задач не отдаётся;
- заголовок записи (поле `is_title`) в список не отдаётся — только в карточку (`service.ts`, строка 202).

Dev-база 04.11.2026: 545 задач автоматизаций, у всех 545 название с «— #N», у всех есть `record_id`, самое длинное название — 73 символа. На продуктиве посчитать до решения:

```sql
SELECT count(*)                                        AS automation_tasks,
       count(*) FILTER (WHERE title ~ ' — #[0-9]+')    AS with_number_suffix,
       count(*) FILTER (WHERE completed_at IS NULL AND archived_at IS NULL AND deleted_at IS NULL) AS open_tasks
FROM tasks WHERE source = 'automation';
```

## Предложение

**Название** новых задач по записи: `{заголовок записи}: {условие правила}`; нет заголовка — `Запись #{номер}: {условие правила}`. Свой шаблон правила `action.title` — как сейчас, без суффикса « — #N …».
Пример: «E2E-mvseemeb-03: за 3 дн. до «Срок устранения»» вместо «Напоминание: За 3 дн. до «Срок устранения» — #3870 E2E-mvseemeb-03».

**Тип и номер — бейджами на карточке**, из полей, а не из текста:
- номер записи — `#3870` (`record.number`, уже в API);
- тип — «напоминание» / «уведомление» / «эскалация» (эскалация — тоном `crit`, остальные — `src`, как метка источника).

**Что меняется:**

| Зона | Изменение | Совместимость |
|---|---|---|
| БД | Миграция «расширить»: `tasks.event_type text NULL` (`remind` / `notify` / `escalate`), без значения по умолчанию. Влияние на данные: новая пустая колонка, существующие строки не меняются (0 строк) | Backend 1.6.x колонку не читает — откат без отката базы |
| Backend | `from-events.ts`: новый шаблон названия, запись `event_type` при создании (по записи и в сводке). `routes.ts` / `service.ts`: в элемент списка — `eventType` (nullable) и `record.title` (заголовок записи, nullable). Описание задачи не меняется — в нём остаются реестр, номер, заголовок, правило и дата | Новые поля необязательные: frontend 1.6.5 их игнорирует |
| Frontend | Бейджи «#номер» и тип на карточке и в шапке карточки задачи; перегенерировать типы из OpenAPI | Задачи без `eventType` — без бейджа типа |
| Тесты | Модульные — шаблон названия; БД — `event_type` при создании и при сводке; e2e — бейджи на доске | — |

Где ещё видно название и что с этим: уведомление «назначена задача» хранит снимок текста (`notifications`) — старые уведомления не меняются, новые короче; отчёт по задачам в Excel и поиск получают новое название — проверить при реализации, не нужна ли в отчёте отдельная колонка с номером записи; журнал аудита — `summary` с номером задачи, не меняется.

Оценка: backend с миграцией и тестами — около 1 дня, frontend — 0,5 дня, проверка e2e и выкладка — 0,5 дня.

## Что делать с уже созданными задачами

| Вариант | Что делается | Плюсы | Минусы |
|---|---|---|---|
| **А. Оставить как есть** (рекомендую) | Старые названия не трогаем. Бейдж номера показываем всем задачам автоматизаций сразу (`record.number` уже есть). Бейдж типа — только новым | Данные не переписываются, миграция только добавляет колонку, история и журнал совпадают с тем, что люди видели | На доске какое-то время рядом старые длинные и новые короткие названия; дубль номера в старых («#3870» в бейдже и в тексте) |
| Б. Укорачивать при показе | Как А, плюс frontend при отображении срезает суффикс « — #{record.number} …», если он совпадает с номером записи задачи. Полное название — в подсказке и в карточке | Доска сразу единообразна, данные не трогаются | Логика разбора текста на frontend; если шаблон правила сам содержит « — #», срез ошибётся (проверка по `record.number` это сужает) |
| В. Переписать названия миграцией | `UPDATE tasks SET title = … WHERE source = 'automation' AND title ~ ' — #[0-9]+'` + заполнение `event_type` из `automation_events` | Данные однородны | Переписывает бизнес-данные (CLAUDE.md, 3.1 и 3.3: только после письменного подтверждения, с резервной копией); история изменений задачи и снимки уведомлений расходятся с новым названием; каждую правку нужно писать в `audit_log`; откатить можно только из резервной копии |

Отдельно, для любого варианта: заполнить `event_type` у **открытых** старых задач можно шагом seed (как в 1.6.3–1.6.4), только в пустую колонку — это добавление значения, а не переписывание. Тогда бейдж типа появится и у них. Влияние на данные — «заполняется `event_type` у N открытых задач автоматизаций, остальные строки не меняются; откат — колонку не читает прежний backend».

Рекомендация: **А + заполнение `event_type` у открытых задач seed-шагом**; вариант Б — если на доске мешает смесь старых и новых названий.

## Как seed определяет `event_type` у открытых задач

**Источник — событие, по которому задача создана, а не правило и не текст названия.**

```sql
-- Заполнение (только пустая колонка, только открытые задачи автоматизаций); выполняет шаг seed в транзакции migrate.
UPDATE tasks t
SET    event_type = e.event_type
FROM   automation_event_tasks l
JOIN   automation_events e ON e.id = l.event_id
WHERE  l.task_id = t.id
  AND  l.action = 'created'
  AND  t.source = 'automation'
  AND  t.event_type IS NULL
  AND  t.completed_at IS NULL AND t.archived_at IS NULL AND t.deleted_at IS NULL;
```

Почему так:
- **Связь есть у каждой задачи автоматизации.** `from-events.ts` при создании задачи — и по записи (строка 202), и сводной (строка 275) — в той же транзакции пишет `automation_event_tasks` с `action = 'created'`; повторные срабатывания добавляют только `commented`. Проверка на dev-базе 04.11.2026: 545 задач автоматизаций (41 открытая), без связи `created` — 0, больше одной связи `created` — 0.
- **Тип события — снимок на момент срабатывания.** Правило (`register_automations.action.eventType`) можно поменять после создания задачи; событие (`automation_events.event_type`) не меняется. На dev-базе сейчас расхождений правила и события нет (0), но опираться на правило нельзя.
- **Текст названия не подходит.** Префикс «Напоминание: / Уведомление: / Эскалация:» есть только у задач без своего шаблона правила. На dev-базе у 11 из 545 задач (правило DLP «Закрыть доступ в Device Monitor или получить разрешение — #N …») префикса нет, и тип по тексту не определить. По тексту можно было бы только перепроверить результат: у 534 задач с префиксом он совпадает с типом события (`Уведомление` — `notify` 257, `Напоминание` — `remind` 277).

Порядок шага seed:
1. Отметка в `seed_markers`, как у прочих разовых шагов (1.6.3–1.6.4): шаг выполняется один раз; повторный `migrate` ничего не меняет — условие `event_type IS NULL` к тому же делает запрос идемпотентным.
2. До `UPDATE` — подсчёт открытых задач автоматизаций без связи `created` (ожидается 0). Если не 0 — такие задачи остаются с `event_type = NULL` (без бейджа типа), число и номера задач — в выводе `migrate`; шаг не останавливается.
3. В выводе `migrate` — сколько задач заполнено. В `audit_log` — одна строка на шаг (`action = 'seed.tasks.event_type'`, `diff` — число задач и список номеров), не по строке на задачу: значение добавляется в пустую колонку, бизнес-данные задачи не меняются.
4. Закрытые и архивные задачи не заполняются: на доске их нет, бейдж им не нужен (в архиве — без бейджа типа).

«Влияние на данные» для `CHANGELOG.md`: «Шаг seed (один раз): у открытых задач автоматизаций заполняется новая колонка `event_type` из события, по которому задача создана, — N строк (на dev-базе 04.11.2026 — 41); названия и прочие поля не меняются. Откат на 1.6.x совместим: колонку прежний backend не читает».
