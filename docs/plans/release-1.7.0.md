# План релиза 1.7.0: цепочки задач

**Статус: реализовано 04.11.2026, релиз не собран — ждёт «ок» владельца.** Коммиты по шагам (раздел 10): модель и нормализация, API, подсказка, доска и список, старые задачи, документация. Решения владельца — раздел «Решения владельца» в конце; где они расходятся с текстом выше, действуют они.

**Базовая версия — `v1.6.7`.** Задание готовилось под 1.4.1. Ниже каждый пункт сверен с кодом задач 1.6.7 (`backend/src/modules/tasks`, `frontend/src/pages/tasks`). Расхождения и предложения — в разделе 2.

**Ограничения:**
- без новых npm-зависимостей;
- без расширений PostgreSQL (`pg_trgm` не используется);
- `deploy/`, тома, `.env` и сертификаты не трогаются;
- ничего из раздела 3.1 CLAUDE.md;
- работа только с кодом и dev-данными.

**Новых кодов прав нет** (раздел 5).

**Зачем.** Обсуждение продолжается в нескольких задачах с похожим заголовком (в почте — «RE: тема»). Цепочка собирает их вместе. Решает человек одним щелчком, портал только подсказывает, автоматически ничего не склеивается.

## 0. Данные банка

Репозиторий публичный. В seed, тестах, фикстурах и документации только вымышленные заголовки и люди: «RE: Тестовая тема», «Иванов И.И.». Seed цепочек не создаёт. Перед каждым коммитом — проверка diff на ФИО, хосты, IP и e-mail, как в 1.6.7.

## 1. Как сейчас устроены задачи (1.6.7)

- **Видимость.** Отдельных правил видимости у задачи нет.
    - Все маршруты `/tasks*` закрыты одним правом `ib.work` (`routes.ts`, `view = requirePerm('ib.work')`).
    - Кто его имеет, видит все задачи: доску, архив, карточку, комментарии.
    - Не видны только удалённые (`deleted_at`). История в карточке — дополнительно `history.view`.
    - Без `ib.work` (например, «Читатель документов», «Самооценка» без других ролей) задач не видно совсем: 403.
- **Правка.** `PATCH /tasks/:id` доступен любому с `ib.work`, но с ограничениями процесса:
    - исполнителя другому ставит `tasks.assign`;
    - статус в обход кнопок — `tasks.status.override`;
    - из «На проверке» переносит только проверяющий (`NOT_REVIEWER`);
    - в «Выполнено» мимо проверки нельзя (`REVIEW_REQUIRED`);
    - в «На проверке» без руководителя нельзя (`NO_REVIEWER`).

  Задачу в архиве править нельзя (`TASK_ARCHIVED`). Удаление — `tasks.delete`, мягкое.
- **Права с «tasks» в коде:** `tasks.delete`, `tasks.assign`, `tasks.status.override`, `tasks.report` и выведенное `tasks.review`. Права «управление задачами» (`tasks.manage`) нет.
- **Создание:**
    - строка «Быстрая задача» над доской: название, категория, ответственный, срок;
    - «Задача из письма» (`MailDrawer`, черновик `POST /tasks/mail-draft`, затем `POST /tasks`).

  Отдельной формы создания нет. Название меняется в карточке (`TaskDrawer`).
- **Источники задач:** `manual`, `mail`, `automation`, `document` (в том числе задачи этапов маршрута 1.6.3 и общие задачи 1.6.4), `evidence`.
- **Доска** — колонки по статусам. «Выполнено» — обычная колонка: выполненные задачи стоят на доске, пока их не отправят «В архив». Архив — та же доска с `archive=1`. Лимит — 500 задач.
- **Журнал.** Действия с задачей пишутся в `audit_log` (`entity = 'task'`). История в карточке строится из этих записей.
- **Тема письма.** `lib/mail-parse.ts` уже снимает с темы «RE:», «FW:», «Fwd:», «Ответ:», «Пересл:» при построении названия задачи (`REPLY_PREFIX`).
- **Глобальный поиск** (строка в меню) ищет и по задачам.

## 3. Модель данных: одна миграция `task_chains`

Черновик SQL. Окончательный — из `prisma migrate dev --create-only` с проверкой перед применением.

```sql
-- Цепочки задач (1.7.0, ADR-0035). Только добавление: существующие строки не меняются.
CREATE TABLE "task_chains" (
  "id"          UUID         NOT NULL DEFAULT gen_random_uuid(),
  "number"      SERIAL       NOT NULL,                 -- «Цепочка #12» в журнале и ссылках
  "title"       TEXT         NOT NULL,
  "title_key"   TEXT         NOT NULL,                 -- нормализованный ключ (lib/title-key.ts), не уникален
  "owner_id"    UUID,                                  -- ответственный, необязательно
  "status"      TEXT         NOT NULL DEFAULT 'open',
  "due_date"    DATE,
  "summary"     TEXT         NOT NULL DEFAULT '',
  "created_by"  UUID         NOT NULL,
  "created_at"  TIMESTAMPTZ(3) NOT NULL DEFAULT CURRENT_TIMESTAMP,
  "updated_at"  TIMESTAMPTZ(3) NOT NULL,
  "closed_at"   TIMESTAMPTZ(3),
  "deleted_at"  TIMESTAMPTZ(3),
  "version"     INTEGER      NOT NULL DEFAULT 1,
  CONSTRAINT "task_chains_pkey" PRIMARY KEY ("id"),
  CONSTRAINT "task_chains_status_check" CHECK ("status" IN ('open', 'closed')),
  CONSTRAINT "task_chains_closed_at_check" CHECK (("status" = 'closed') = ("closed_at" IS NOT NULL)),
  CONSTRAINT "task_chains_title_key_check" CHECK ("title_key" <> '')
);
CREATE UNIQUE INDEX "task_chains_number_key" ON "task_chains"("number");
-- Подсказка: открытые цепочки с тем же ключом.
CREATE INDEX "task_chains_open_key_idx" ON "task_chains"("title_key") WHERE "status" = 'open' AND "deleted_at" IS NULL;
-- Подсказка «Вернуть в работу»: закрытые с тем же ключом не старше N дней.
CREATE INDEX "task_chains_closed_key_idx" ON "task_chains"("title_key", "closed_at") WHERE "status" = 'closed' AND "deleted_at" IS NULL;
CREATE INDEX "task_chains_owner_idx" ON "task_chains"("owner_id") WHERE "deleted_at" IS NULL;
ALTER TABLE "task_chains" ADD CONSTRAINT "task_chains_owner_id_fkey" FOREIGN KEY ("owner_id") REFERENCES "users"("id") ON DELETE RESTRICT ON UPDATE CASCADE;
ALTER TABLE "task_chains" ADD CONSTRAINT "task_chains_created_by_fkey" FOREIGN KEY ("created_by") REFERENCES "users"("id") ON DELETE RESTRICT ON UPDATE CASCADE;

-- Ссылка задачи на цепочку: необязательная, новая колонка пустая у всех строк.
ALTER TABLE "tasks" ADD COLUMN "chain_id" UUID;
CREATE INDEX "tasks_chain_id_idx" ON "tasks"("chain_id") WHERE "chain_id" IS NOT NULL;
ALTER TABLE "tasks" ADD CONSTRAINT "tasks_chain_id_fkey" FOREIGN KEY ("chain_id") REFERENCES "task_chains"("id") ON DELETE RESTRICT ON UPDATE CASCADE;
```

**Права роли приложения** на новую таблицу и последовательность выдаёт `ALTER DEFAULT PRIVILEGES` из `db/init/01-app-role.sh`. Ручных `GRANT` не нужно; на dev это проверяется тестом `test:db` под ролью приложения.

**Влияние на данные:**
- новая пустая таблица `task_chains`;
- в `tasks` новая колонка `chain_id`, у всех существующих строк `NULL`;
- существующие строки не меняются;
- `ALTER TABLE ... ADD COLUMN` без значения по умолчанию меняет только описание таблицы, без перезаписи строк;
- индекс по `tasks` строится за доли секунды: в нём только строки с `chain_id`, при выкладке таких нет;
- данные не удаляются.

**Откат на 1.6.7 без отката базы безопасен:**
- клиент Prisma 1.6.7 выбирает колонки явно и о `chain_id` не знает;
- запросы `SELECT ... FROM tasks t` в `report.ts`, `stats.ts`, `bulk.ts` и `records.service.ts` перечисляют колонки, `SELECT *` по `tasks` нет;
- вставка задачи в 1.6.7 оставляет `chain_id = NULL`;
- `task_chains` 1.6.7 не читает;
- связанные задачи работают в 1.6.7 как обычные, группировка просто не видна.

Удалить задачу физически в 1.6.7 нельзя (мягкое удаление), поэтому внешний ключ не мешает. Это проверяется на dev: применить миграцию, запустить backend 1.6.7 из отдельного рабочего каталога git (`git worktree`, тег `v1.6.7`) против той же dev-базы с новой колонкой и пройти e2e задач и документов 1.6.7. `test:db` 1.6.7 для этого не подходит: он создаёт базу по своим миграциям, без `chain_id`. Образы при этом не собираются.

## 4. Нормализация заголовка: `lib/title-key.ts`

Шаги:
1. Unicode NFKC.
2. Нижний регистр (`toLocaleLowerCase('ru')`), «ё» → «е».
3. Схлопывание пробелов (в том числе неразрывных).
4. Снятие повторяющихся префиксов в начале, в любом порядке, с двоеточием и без. Без двоеточия префикс снимается, только если за ним пробел и есть остаток: «Ответственный за…» не трогается. Префиксы:
    - `re`, `re[N]`, `re(N)`, `re N`;
    - `fw`, `fwd`;
    - `отв`, `ответ`, `во`;
    - `пересл`, `переслать`, `переадр`;
    - `aw`, `wg`, `sv`, `vs`, `tr`, `rv` — частые в почтовых клиентах;
    - `[ext]`, `[external]`, `[внешнее]`, любые `[...]` из этого списка, `(ext)`.
5. Обрезка пунктуации и пробелов по краям: `.,:;!?-–—«»"'()[]` и т. п.
6. Пустой остаток — ключа нет (`null`): подсказки нет, цепочку «по ключу» не создать.

Отдельно — `stripReplyPrefixes(title)`: то же снятие префиксов с сохранением регистра. Для названия новой цепочки («RE: Тестовая тема» → «Тестовая тема») и для `mail-parse`.

**Похожесть** (для подсказки «похожая»):
- слова ключа длиной от 3 символов, без чисто служебных («и», «в», «на», «по», «для», «the», «of»…);
- коэффициент Жаккара ≥ 0,6 и не меньше двух общих слов;
- ключ из одного слова — только точное совпадение.

Порог — константа с тестами: «тестовая тема по доступу» ~ «тема по доступу тестовая» — да; «тестовая тема» ~ «тестовая проверка» — нет.

Ответственный цепочки — активный пользователь с `ib.work`, как исполнитель задачи. Проверка — тем же `assertAssignee`.

## 6. API

Все маршруты с `requirePerm('ib.work')`, остальное — в сервисе (раздел 5). Изменения — с `version` (409 `VERSION_CONFLICT`). Ошибки в общем формате.

| Метод и путь | Что делает |
|---|---|
| `GET /task-chains?status=open\|closed&ownerId=&q=&limit=&cursor=` | список цепочек с видимыми задачами: счётчики N и M, ответственный, срок |
| `POST /task-chains` | создать: `{ title, ownerId?, dueDate?, summary?, taskIds?: [{ id, version }] }`; задачи привязываются в той же транзакции |
| `GET /task-chains/:id` | цепочка и её видимые задачи по дате создания (хронология), включая выполненные и архивные; флаг «все выполнены» |
| `PATCH /task-chains/:id` | название, ответственный, срок, сводка; новое название пересчитывает ключ |
| `POST /task-chains/:id/close` | `{ version }`; если есть незавершённые задачи, ответ содержит `openTasks: N` — интерфейс предупреждает до вызова |
| `POST /task-chains/:id/reopen` | `{ version }` |
| `POST /task-chains/:id/delete` | `{ version }`: мягко, задачи отвязываются |
| `POST /task-chains/:id/tasks` | привязать `{ tasks: [{ id, version }] }`; задача в другой цепочке — 409 `TASK_IN_OTHER_CHAIN` (для этого есть перенос) |
| `POST /task-chains/:id/tasks/:taskId/detach` | `{ version }` задачи |
| `POST /tasks/:taskId/move-chain` | `{ version, toChainId }`: перенос одной транзакцией |
| `GET /task-chains/suggest?title=&taskId=` | до 5 подсказок (раздел 7.1); `taskId` — исключить саму задачу при правке |
| `POST /tasks` | новый необязательный параметр `chain: { id } \| { newTitle }`: создать задачу сразу в цепочке |
| `POST /task-chains/discover/preview`, `/discover/apply` | поиск среди старых задач (раздел 9) |
| `GET /tasks` | в задаче — `chain: { id, number, title, status } \| null`; новый фильтр `chainId=` |

**Привязка меняет `tasks.chain_id` и увеличивает `version` задачи**, поэтому нужна версия задачи. Открытая в это время карточка получит 409 и перечитает задачу — как при любой другой правке.

**Журнал.**
- По задаче (`entity = 'task'`, видно в истории карточки): `task.chain_linked`, `task.chain_unlinked`, `task.chain_moved` (из какой в какую).
- По цепочке (`entity = 'task_chain'`): `task_chain.created`, `.updated`, `.closed` (с числом незавершённых), `.reopened` (в том числе «из подсказки при добавлении задачи #…»), `.deleted` (со списком отвязанных задач), `.discovered` (сводка применения поиска).

## 7. Подсказка и интерфейс

### 7.1. Подсказка

Запрос — после паузы 400 мс в вводе названия, от 3 символов ключа. Порядок, не больше 5 вариантов:
1. Открытые цепочки с тем же ключом — независимо от статусов задач, в том числе когда все выполнены.
2. Открытые цепочки с похожим ключом (раздел 4).
3. Закрытые цепочки с тем же ключом, закрытые не раньше **N = 30 дней** назад, с действием «Вернуть в работу и добавить» (вопрос 5).
4. Задачи без цепочки с тем же ключом (`manual` и `mail`, в том числе выполненные и архивные): «Создать цепочку из этих задач (K)».

Внутри групп — сначала свежие (по последней задаче).

Ключ цепочки сравнивается с ключом цепочки и с ключами её видимых задач: переименованная цепочка находится и по старым «RE: …».

Блок под названием: «Похоже на цепочку „Тестовая тема“ · 3 задачи, 1 выполнена» и кнопки «Добавить в цепочку» и «Создать новую». Блок закрывается крестиком и ничего не блокирует. В быстрой строке и «Задаче из письма» выбор применяется при создании задачи (параметр `chain` у `POST /tasks`), в карточке — сразу.

### 7.2. Доска

- **Переключатель «Группировать по цепочкам»** (по умолчанию включён, запоминается в localStorage).
- **Цепочка с задачами в разных колонках.** В каждой колонке, где есть её задачи, — свёрнутая карточка цепочки: «Тестовая тема · 5 задач, 2 выполнено · здесь 2». По щелчку она раскрывается задачами этой колонки, ссылка «Цепочка» открывает панель цепочки.
    - Так колонка по-прежнему показывает, что в ней лежит, а перетаскиваются отдельные задачи, а не цепочка. Цепочка не перетаскивается.
    - Отвергнутые варианты: одна карточка в «первой» колонке скрыла бы задачи из остальных колонок; отдельная полоса цепочки поперёк доски ломает вертикальную прокрутку колонок.
- **Задача внутри раскрытой цепочки** — обычная карточка: те же кнопки шага, та же проверка, то же перетаскивание. Ограничения переноса (`REVIEW_REQUIRED`, `NO_REVIEWER`, `NOT_REVIEWER`, `NO_OVERRIDE`) действуют без изменений.
- **В архиве** группировка та же.
- **Фильтр «Цепочка»** (список открытых цепочек с видимыми задачами; адрес `?chainId=`) и поле «Поиск» по номеру, названию задачи и названию цепочки.

### 7.3. Карточка задачи

Блок «Цепочка»:
- название со ссылкой на панель;
- хронология задач цепочки по дате: номер, название, статус, исполнитель; выполненные и архивные помечены, текущая выделена;
- переход к каждой;
- кнопки «Отвязать» и «Перенести в другую цепочку»;
- без цепочки — «Добавить в цепочку» с поиском.

В истории задачи — «Добавлена в цепочку „…“», «Перенесена из „…“ в „…“».

### 7.4. Панель и экран цепочки

- **Панель** (`DetailPanel`, режим `sheet`, адрес `?chain=`): название, ответственный, срок, статус, сводка (многострочный текст), задачи по дате, счётчики. В подвале — «Сохранить», «Закрыть цепочку» или «Открыть заново», «Удалить».
- **Когда все задачи выполнены** — заметка «Все задачи выполнены» с кнопкой «Закрыть цепочку». Автоматически цепочка не закрывается.
- **Закрытие с незавершёнными** — окно «В цепочке 2 незавершённые задачи. Закрыть цепочку? Задачи останутся на доске» и «Закрыть». Не блокирует.
- **Экран «Задачи → Цепочки»** (вкладка рядом с «Отчёт»): таблица цепочек с фильтрами по статусу и ответственному и поиском по названию. Строка открывает панель. Там же для `tasks.assign` — «Найти цепочки среди старых задач».

Светлая и чёрная темы, токены проекта, кнопки главного действия — `--accent-btn`.

## 8. Связь с остальным

- **Проверка задач не меняется.** У каждой задачи свой исполнитель и проверяющий по ADR-0028, «Проверяет: <ФИО>», «Завершить» без руководителя. Цепочка их не объединяет и не меняет. Код процесса (`flow.ts`, `process.ts`, `reviewer.ts`, `updateTask`) не трогается; тест подтверждает, что перенос задачи внутри цепочки получает те же 409 и 403.
- **Статус цепочки не зависит от статусов задач.** Выполненные остаются в цепочке и в счётчике.
- **Закрытие с незавершёнными задачами — предупреждение без блокировки**, как в задании. Проблему вижу одну: закрытая цепочка с открытыми задачами выпадает из подсказок «открытых». Поэтому закрытую цепочку с открытыми задачами подсказка показывает в группе 1, с пометкой «закрыта» и кнопкой «Вернуть в работу и добавить». Вопрос 6.
- **Индикаторы и уведомления.** Цепочки не влияют на `/me/attention`, уведомления, дашборд, монитор, отчёт и статистику задач. Единственный след — записи «добавлена в цепочку» в истории задачи.
- **Удаление задачи** (мягкое, `tasks.delete`) оставляет `chain_id`, но удалённая задача не видна и не считается.
- **Удаление цепочки** отвязывает задачи (`chain_id = NULL`, версия задачи +1, запись в истории каждой).

## 9. Старые задачи: «Найти цепочки среди старых задач»

- **Кнопка** на экране «Цепочки», право `tasks.assign`.
- **Предпросмотр.** Все неудалённые задачи `manual` и `mail` без цепочки, включая выполненные и архивные, группируются по точному ключу. Показываются группы от двух задач: предлагаемое название (снятые префиксы у самой ранней задачи), задачи, даты. Если с тем же ключом уже есть открытая цепочка, группа предлагает «Добавить в цепочку #N», а не создавать новую. Группы можно снять.
- **Применение** — после подтверждения в окне, одной транзакцией. Передаётся `expected`: для каждой группы задачи и их версии. Если задача успела попасть в цепочку или измениться — 409 `BULK_CHANGED`, ничего не применяется.
- **Повторный запуск безопасен:** задачи с цепочкой в поиск не попадают, поэтому второй запуск находит только новые совпадения.
- **Журнал:** `task_chain.discovered` (сводка) плюс обычные записи о создании и привязке.
- **Миграция старые задачи не трогает.**

## 11. Тесты

- **Unit** (`title-key.test.ts`):
    - вложенные префиксы «RE: RE: FW: тема»;
    - «Re[2]:», «Отв:», «ВО:», «Пересл.:», «[EXT]», без двоеточия;
    - «Ответственный за доступ» не режется;
    - смешанный регистр, кириллица и латиница, NFKC (полноширинные символы, неразрывный пробел), «ё»;
    - лишние пробелы, пунктуация по краям;
    - пустой остаток — `null`;
    - похожесть: порог, одно слово, служебные слова.

  Плюс тесты `mail-parse` с расширенным снятием префиксов.
- **API и DB** (`chains.db.test.ts`, `chains.http.db.test.ts`):
    - **два пользователя с разной видимостью:** сотрудник ИБ видит цепочку, счётчики и подсказки, а пользователь без `ib.work` («Читатель документов») получает 403 на всех маршрутах цепочек и не видит цепочек в глобальном поиске. Удалённые задачи не входят ни в счётчики, ни в состав, ни в подсказки. Цепочка, все задачи которой удалены, никому не показывается;
    - «RE: Тестовая тема» → подсказка с открытой цепочкой «Тестовая тема» → создание задачи с `chain` → задача в цепочке, запись `task.chain_linked`;
    - цепочка, где все задачи выполнены и одна в архиве, остаётся в подсказке группы 1 и в хронологии со счётчиком «3 задачи, 3 выполнено»;
    - закрытая цепочка: подсказка группы 3 в пределах 30 дней и не старше; «Вернуть в работу и добавить» открывает её и пишет `task_chain.reopened`; без прав — 403;
    - отвязка и перенос: журнал у задачи; `TASK_IN_OTHER_CHAIN`; устаревшая версия задачи — 409;
    - мягкое удаление цепочки: задачи остаются, `chain_id` пустой, журнал со списком; удалённая цепочка не в списке и не в подсказках;
    - права правки и закрытия: создатель, ответственный, `tasks.assign` — да; другой сотрудник ИБ — 403;
    - закрытие с незавершёнными — проходит, в журнале число;
    - перенос по доске задачи в цепочке получает `REVIEW_REQUIRED` и `NO_REVIEWER`, как без цепочки;
    - цепочки не меняют `/me/attention` и не создают уведомлений;
    - поиск среди старых задач: группы только от двух задач и по точному ключу; системные источники не участвуют; повторный запуск — пусто; `BULK_CHANGED`.
- **E2E** (`chains.e2e.mjs`):
    - быстрая задача «RE: Тестовая тема <прогон>» → блок подсказки → «Добавить в цепочку» → карточка задачи с блоком «Цепочка»;
    - доска: свёрнутая карточка цепочки в двух колонках, раскрытие, перенос задачи из раскрытой цепочки по обычным правилам;
    - «Задача из письма» с темой «FW: RE: …» → подсказка;
    - выполненная задача остаётся в хронологии, заметка «Все задачи выполнены» → «Закрыть цепочку» → новая «RE: …» → «Вернуть в работу и добавить»;
    - отвязка из карточки;
    - удаление цепочки → задачи на доске без группы;
    - пользователь без `ib.work` не видит раздела.

## Решения владельца (04.11.2026)

Расхождения раздела 2 приняты как предложено:
- одна функция видимости;
- привязка выполненных и архивных задач;
- системные задачи не участвуют в подсказках и поиске;
- `mail-parse` на общей нормализации;
- группировка на доске и в архиве, экран «Цепочки», поиск над доской, цепочки в глобальном поиске.

1. **Права.** Править, закрывать и удалять цепочку — создатель, ответственный и держатель `tasks.assign`. Новых кодов прав нет.
2. **Табличный список задач** в 1.7.0 не делается.
3. **Общее снятие префиксов в `mail-parse`** действует только для новых задач из письма. Заголовки существующих задач не меняются, исходная тема хранится в «Исходном письме» как есть.
4. **Удалённая цепочка в интерфейсе не восстанавливается.**
    - Перед удалением — диалог «Задачи (N) будут отвязаны от цепочки, сами задачи останутся».
    - Для обычного завершения работы — «Закрыть», а не «Удалить».
5. **Похожесть:** Жаккар ≥ 0,6 и не меньше двух общих слов; закрытые цепочки — 30 дней.
    - Слова из одной-двух букв не учитываются ни в Жаккаре, ни в общих словах. Поэтому «Доступ к VPN Иванов» и «Доступ к VPN Петров» не похожи: общих слов 2 из 4.
    - Порог, минимум общих слов и срок — в `app_settings`, параметр «Задачи: подсказка цепочек» в «Параметрах портала»: `{ "minJaccard": 0.6, "minCommonWords": 2, "closedDays": 30 }`.
6. **Закрытая цепочка с незавершёнными задачами** предлагается без ограничения в 30 дней, сразу после открытых цепочек с точным ключом. Пометка «закрыта, есть незавершённые задачи», действие «Вернуть в работу и добавить».

   Порядок подсказки:
    1. открытые цепочки с точным ключом;
    2. закрытые с точным ключом и незавершёнными задачами;
    3. открытые с похожим ключом;
    4. закрытые с точным ключом за `closedDays` дней;
    5. задачи без цепочки — «Создать цепочку из этих задач».

   Всего не больше 5 вариантов.
7. **Предварительный отбор SQL по самому длинному слову** — только для задач без цепочки: сравнение там точное, ничего не теряется. Открытые и закрытые цепочки сравниваются в приложении со всеми, без предварительного отбора. Ключи их видимых задач тоже: похожая цепочка не должна выпасть из-за другого самого длинного слова.
8. **ADR-0035** — за 1.7.0. Номера ADR в плане 1.8.0 поправляются, когда к нему вернёмся.

## Правки перед выпуском (решение владельца 04.11.2026)

1. Одна задача цепочки в колонке не сворачивается: обычная карточка с меткой «Цепочка: …», метка открывает панель цепочки. Сворачивается — от двух задач в колонке.
2. «Найти цепочки среди старых задач» — `tasks.assign` или `settings.manage`. Новых кодов прав нет; с разделением полномочий не конфликтует (процесс задач и согласование документов не затрагиваются).
3. Не в этот релиз: нестабильный e2e «Самооценки» — отдельным коммитом после выкладки, только тесты, до начала 1.8.0; поиск задач в глобальном поиске — в «Запланировано» CHANGELOG.
