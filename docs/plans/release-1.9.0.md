# План релиза 1.9.0: осведомлённость — учебные письма и расписание

**Статус: план принят владельцем 05.11.2026. Шаги 0–16 выполнены (ADR-0039, ADR-0040), релиз собран 05.11.2026 по «ок» владельца (тег `v1.9.0`).** Расхождения 1–8 — по решениям плана, ответы на вопросы 1–11 и условие к триггерам — в разделе «Ответы владельца». Работа начата с шага 0. База — `v1.8.0` (`d8613bf`).

Задание — вторая часть этапа 1 раздела «Осведомлённость»:
- учебные письма как редактируемые объекты с версиями и согласованием;
- шаблоны и системный фрагмент «Подпись ИБ»;
- расписание рассылок с автозадачами;
- реестр «Рассылки» — журнал отправок.

Отправка остаётся ручной, из почтового клиента: портал письма не отправляет (CLAUDE.md, раздел 1). Проверка перехода по ссылке (фишинг-симуляция) в релиз не входит. Под неё ничего не закладывается: ни полей, ни параметров, ни таблиц.

Спецификация — `docs/specs/awareness.md`, часть 2 (разделы 11–21). Ниже — сверка с кодом, решения, зависимости, схема, порядок работ и проверка.

Одна миграция. Она только добавляет таблицы и триггеры: существующие таблицы и ограничения не меняются (раздел «Схема»). Коды прав не меняются. Новые зависимости — две, нужно согласие (раздел «Зависимости»). Сборка релиза — только при зелёных typecheck, lint, test, test:db, e2e и check:integrity на последнем коммите с кодом.

### Расхождения (решения приняты владельцем 05.11.2026)

1. **`docs.approve.head` в коде не проверяется с 1.4.0** (ADR-0027). Код права есть только в `lib/permissions.ts` с пометкой «Не используется… остаётся ради отката на 1.3.0». Системная роль «Начальник ИБ» на новой установке его не получает (`permissions.ts:110`). Этап «Начальник ИБ» в документах выполняет пользователь с отметкой `users.is_ib_head`. Кто держит `docs.approve.head` на проде сейчас, неизвестно: возможно, только старые роли. Если согласовывать письма по этому праву, мы вернём в работу выведенный код, и согласующим может оказаться не начальник ИБ. **Предлагаю:** согласует пользователь с отметкой «Является начальником ИБ», как этап 13 документов. Своё письмо он согласует сам, с пометкой «без независимого согласования» (`self_approved`). Новых кодов прав нет. → принято (ответ 1).
2. **«Держатели роли «Начальник ИБ»» для эскалации.** Есть и системная роль `ib_head`, и отметка (не больше одного человека). **Решение:** получатель — пользователь с отметкой. Если отметки нет или её держатель отключён — держатели системной роли `ib_head`. Оба списка — через `workUsersWhere()`.
3. **Новое значение `tasks.source` ломает откат на 1.8.0.** В 1.8.0 `source` в ответе API — закрытый `z.enum(['manual', 'mail', 'automation', 'document', 'evidence'])` (`tasks/routes.ts:42`), в БД — `tasks_source_check`. Если 1.9.0 заведёт `source = 'awareness'`, backend 1.8.0 после отката не сможет сериализовать такие задачи: доска и карточка отдадут 500. **Было принято** `source = 'automation'`, но при DB-тестах шага 2 выяснилось: `tasks_automation_check` требует `(source = 'automation') = (automation_id IS NOT NULL)`, а `document` и `evidence` так же требуют свою ссылку. **Решение владельца 05.11.2026 — вариант A:** задачи модуля — `source = 'manual'`, `created_by = NULL`; связь с правилом и письмом — только в таблицах модуля. `tasks_source_check` и `tasks_automation_check` не меняются, откат безопасен. Из подсказок цепочек и «Найти среди старых» их отсекает проверка связи (с DB-тестом). В 1.9.0 карточка и доска показывают настоящее происхождение по таблицам модуля: «Создана расписанием: <правило>» или «Учебное письмо № N», а не «поставлена вручную». В 1.8.0 после отката — «поставлена вручную».
4. **Чек-листа у задач нет.** В модели `tasks` нет пунктов. **Предлагаю** не заводить чек-лист в задачах. Этапы и их даты хранятся в строке запуска правила (`awareness_schedule_runs`), а отметка «выполнено» выводится из статуса письма:
    - черновик готов, когда письмо отправлено на согласование;
    - согласование готово, когда письмо утверждено;
    - отправка готова, когда письмо отмечено отправленным.

   Блок «Этапы» в карточке задачи берёт данные из маршрута модуля писем. В описании задачи те же этапы и даты записываются текстом, поэтому 1.8.0 после отката их тоже покажет. Отметить этап вручную нельзя: он следует за письмом.
5. **«Взять в работу» у задачи роли.** В процессе задач (ADR-0022) у общей задачи есть кнопка «Взять себе» (Backlog → «Поставленные»), за ней — «Взять в работу». **Предлагаю** оставить существующие кнопки: тогда процесс задач не меняется, а у задач документов то же поведение. Альтернатива — для задач рассылки «Взять себе» сразу переводит в «В работе». Это особый случай в `process.ts`. → принято (ответ 4).
6. **Категория «Осведомлённость» при одноимённом значении.** У значений справочников названия уникальны, поэтому «Осведомлённость (системный)» рядом с «Осведомлённостью» администратора — плохой вариант. Существующий механизм (`prisma/seed/system-items.ts`) делает одноимённое значение администратора системным и пишет это в журнал. Так приняты «Почта», «Реестр», «Документы», «Доказательства». **Предлагаю** так же. Запрос до выкладки покажет, есть ли такое значение. Задачи, которые уже стоят в этой категории, в ней и останутся. → принято (ответ 5).
7. **Связь реестра с письмом и задачей.** Тип поля «Связь с записью» (`link`) ссылается только на записи реестров, типа «ссылка» нет. **Предлагаю:**
    - «Письмо» — текст «№ 12, версия 3». Экран записи реестра «Рассылки» (`systemKey = awareness_mailings`) показывает такое значение ссылкой на карточку письма. Это одна проверка в выводе поля по `systemKey`, как у служебных полей уязвимостей.
    - «Задача» — текст «Задача #123». Ссылка на задачу — из карточки письма.

   При ручном вводе и импорте истории можно писать что угодно. Ссылкой станет только «№ N, версия V» существующего письма. → принято (ответ 6).
8. **Новый вид слайда ломает откат монитора.** В 1.8.0 вид слайда — `z.enum(SLIDE_KINDS)`, данные слайда — закрытый `discriminatedUnion` (`monitor/routes.ts`). Слайд нового вида после отката сломает `/monitor`. **Решение без вопроса:** «Ближайшая рассылка» и «Рассылки с просрочкой» становятся показателями (KPI) существующего слайда «Ключевые показатели». 1.8.0 неизвестные ключи KPI просто отбрасывает (`slides.service.ts`, `slideData`). Раскладки дашборда отбрасывают неизвестные ключи виджетов (`dashboard/layout.ts`, `mergeLayout`). Значит, откат безопасен.
9. **Буфер обмена с оформлением** (`navigator.clipboard.write` с `text/html`) работает только в защищённом контексте: на проде это HTTPS, в dev — `localhost`. Если API недоступен, кнопка показывает «Выделите текст в предпросмотре и нажмите Ctrl+C». Новой зависимости это не требует.
10. **CSP страниц** (`frontend/nginx.conf`): `default-src 'self'; img-src 'self' data: blob:; style-src 'self'`. Изображения `data:` в редакторе и предпросмотре разрешены. Встроенные скрипты запрещены, и это вторая линия защиты после санитайзера. Атрибуты `style` тоже запрещены, поэтому санитайзер их вырезает. Оформление предпросмотра задаёт CSS из сборки. Встроенные стили для почтовых клиентов добавляет только экспорт (`.eml`, буфер). В БД их нет.

## Решения (предлагаю; вопросы — в конце)

### Модуль и экраны
- Backend: `modules/awareness-letters/` — `letters`, `versions`, `templates`, `fragments`, `schedule`, `export` (`eml.ts`, `html.ts`, `text.ts`), `sanitize.ts`, `variables.ts`, `cadence.ts`.
- Frontend:
    - новый пункт меню «Осведомлённость» с тремя экранами: «Письма» (`/awareness/letters`, список + `DetailPanel`, `?letter=`), «Шаблоны», «Расписание»;
    - вкладка «Подпись ИБ» в «Настройках» — по `settings.manage` и `ib.work`;
    - страница печати письма для PDF.
- Все маршруты модуля — `ib.work`, «Подпись ИБ» на запись — `settings.manage` и `ib.work` (`requireAllPerms`). Служебная учётная запись получает 403 `SERVICE_ACCOUNT` на всём модуле.

### Письмо, версии, статусы (ADR-0039)
- **Версия** — неизменяемая строка: тема и текст на двух языках, кто и когда, причина (`edit`, `restore`, `template`, `copy`, `sent`). Каждое сохранение — новая версия. Сохранение без изменений версию не создаёт.
- **Статусы:**
    - **Черновик.** Правка — любой с `ib.work`, с проверкой `version`.
    - **Черновик → На согласовании.** Любой с `ib.work`. В тексте нет незаполненных `{{…}}`. Плановому письму обязательны тема и текст на обоих языках. Срочному достаточно одного языка: тогда в карточке и в «Рассылках» видна пометка «только RU» или «только TJ», а экспорт предлагает только этот язык. То же условие проверяется при «Отметить отправленным».
    - **Отозвать.** Тот, кто отправил, или автор.
    - **Утвердить.** Начальник ИБ по отметке (расхождение 1).
    - **Вернуть на доработку.** Начальник ИБ, с обязательным комментарием. Письмо — в «Черновик», автору ставится задача (раздел «Задачи модуля»).
    - **Правка утверждённого** — только с подтверждением «Утверждение будет снято». Письмо возвращается в «Черновик», событие пишется в журнал.
    - **Отметить отправленным:**
        - если письмо утверждено, то только когда последняя версия равна утверждённой;
        - срочное письмо можно отметить из «Черновика» или «На согласовании» с обязательным комментарием «Отправлено без согласования: причина».
- **Заморозка.** При первой отметке «Отправлено» создаётся версия `sent`: «Подпись ИБ» подставляется текстом на момент отправки. Письмо получает `frozen`. Дальше backend отклоняет правку текста, темы и статуса: 409 `LETTER_FROZEN`.
    - Разрешены: «Создать копию» (новый черновик из версии `sent`, без задачи и без события отправки), архив и повторная отметка «Отправлено». Повторная отметка — это новая запись в «Рассылках» с другой датой или аудиторией. Текст не меняется.
    - Защита в БД: триггер запрещает менять версию и снимать `frozen`.
- **«Восстановить версию N»** создаёт новую версию с содержимым N (`restore`, `restored_from = N`). Старые версии не меняются: таблица только пополняется, триггер.
- **Сравнение версий** — на frontend: построчное сравнение текста, извлечённого из HTML (своя функция, без зависимости), и тем.
- **Архив вместо удаления.** Архивировать и вернуть из архива может любой с `ib.work`. Физического удаления нет. Все действия — в `audit_log`, `entity = 'awareness_letter'`.

### Редактор, санитизация, изображения
- Редактор — TipTap 3 (раздел «Зависимости»): заголовки 2–4 уровня, жирный, курсив, подчёркивание, зачёркнутый, списки, ссылки, таблицы, изображения, горизонтальная линия. Вкладки RU и TJ. «Подпись ИБ» — свой узел редактора, без зависимости. Это неделимый блок `<div data-ib-fragment="signature">`, показывает текущую подпись.
- **Санитизация — на backend при каждом сохранении** письма, шаблона и подписи (`sanitize-html`, белый список):
    - теги: `h2 h3 h4 p br strong b em i u s ul ol li a table thead tbody tr th td img hr blockquote div span`;
    - атрибуты:
        - `a[href]` — только `http:`, `https:`, `mailto:`;
        - `img[src alt width height]` — `src` только `data:image/png|jpeg|gif;base64`;
        - `td/th[colspan rowspan]`;
        - `div[data-ib-fragment]` — только `signature`.

   Всё остальное вырезается: `script`, `iframe`, `object`, `embed`, `form`, `style`, `svg`, атрибуты `on*`, `style`, `class`, `javascript:` и `data:` в ссылках, внешние и относительные `src`. Результат санитизации сохраняется, исходник — нет.
- **Ссылки на портал запрещены.** `href` на хост из `PORTAL_URL` отклоняется с ошибкой 400 `PORTAL_LINK`: «В письме ссылка на портал — сотрудники его не видят». Относительные ссылки вырезаются.
- **Изображения хранятся внутри письма** (`data:` в HTML версии). Тип проверяется по содержимому (`lib/file-type.ts`): PNG, JPEG, GIF. SVG и WebP не принимаются: в Outlook они ненадёжны.
    - Лимиты — «Параметры портала», `awareness.letters`: `{ maxImageKb: 1024, maxLetterKb: 2048, warnLetterKb: 1024 }`. Письмо уходит на 1500+ ящиков, и каждая копия лежит на почтовом сервере.
    - Лимит письма — сумма HTML обоих языков вместе с изображениями. Тогда экспорт RU+TJ тоже в него укладывается. Начиная с `warnLetterKb` редактор показывает предупреждение с размером, сохранение не блокируется.
    - Проверка параметра: `warnLetterKb ≤ maxLetterKb`, `maxImageKb ≤ maxLetterKb`.
    - Превышение — 413 `LETTER_TOO_LARGE` или `IMAGE_TOO_LARGE`, с размерами в сообщении.
    - Почему не в хранилище файлов: файл письма — это его версия. Хранение в томе потребовало бы ссылок на файлы из HTML, новых правил удаления и изменения формата хранения (CLAUDE.md, раздел 9.7). Объём небольшой: десятки писем в год. Повтор изображения в версиях — цена простоты, лимит её ограничивает.

### Экспорт
- **Один сборщик HTML для почты** (`export/html.ts`): санитизированный HTML, плюс встроенные стили для таблиц, заголовков и шрифта. Подпись подставляется. Для RU+TJ — сначала русский, затем `<hr>` и таджикский.
- **«Скопировать с оформлением»:** `ClipboardItem` с `text/html` (изображения как `data:`) и `text/plain`.
- **`.eml`** — `GET /awareness/letters/:id/export.eml?lang=ru|tj|both&version=N`, без новой зависимости:
    - `MIME-Version: 1.0`, `X-Unsent: 1`, `Subject` по RFC 2047 (`=?UTF-8?B?…?=`, куски не длиннее 75 символов). Для RU+TJ тема — «тема RU / тема TJ».
    - Без `From`, `To` и `Date`.
    - Структура: `multipart/alternative` → `text/plain` + `multipart/related` → `text/html` + изображения. Изображения: `Content-ID: <img-<sha256:16>@ibportal>`, `Content-Disposition: inline`, `src="cid:…"`. Одинаковые изображения вкладываются один раз.
    - Части — `base64`, UTF-8, строки по 76 символов, CRLF.
    - Имя файла — из названия письма, через `Content-Disposition` с `filename*`.
- **Текстовая часть** (`export/text.ts`): заголовки, абзацы, списки «•» и «1.», ссылки «текст (адрес)», таблицы через табуляцию.
- **PDF** — через печать браузера: страница `/awareness/letters/:id/print?lang=`, свой `@media print`, без новой зависимости.
- Экспорт пишется в журнал: `awareness_letter.exported`, формат и язык.

### Шаблоны и «Подпись ИБ»
- **Шаблон:** название, тема и текст RU и TJ. Правка — `ib.work`, архив вместо удаления, история изменений — из `audit_log`.
- **Переменные** `{{описание}}` извлекаются из обеих тем и текстов (`variables.ts`):
    - имя без регистра, пробелы схлопываются;
    - одинаковое имя в RU и TJ — одна переменная;
    - не больше 30 переменных, имя не длиннее 60 символов;
    - `{{подпись}}` — служебная, в форму не попадает.
- **«Письмо из шаблона»:** форма по переменным → подстановка → черновик (версия `template`, `template_id`).
    - Значения — простой текст, в HTML экранируются.
    - Пустая переменная — 400 `UNFILLED_VARIABLES` со списком, черновик не создаётся.
    - `{{подпись}}` становится узлом «Подпись ИБ».
- **«Подпись ИБ»** — одна строка `awareness_fragments` (`code = 'signature'`), HTML RU и TJ. Seed пишет заглушку «Отдел информационной безопасности».
    - Правка — `settings.manage` и `ib.work`, с санитизацией и `version`.
    - Служебный администратор её не видит.
    - В незамороженных письмах показывается текущая подпись, в замороженных — текст из версии `sent`.

### Реестр «Рассылки» (`awareness_mailings`)
- Системный реестр конструктора, seed `awareness.v2`, без записей. Поля: Дата отправки (дата, роль «дата»), Письмо (текст), Тема (текст, заголовок), Тип (список: Плановое, Срочное; «измерение»), Повод (текст), Аудитория (текст, «измерение»), Подготовил (сотрудник), Задача (текст).
- Поля не служебные: ручной ввод и импорт Excel разрешены (история прошлых рассылок).
- **Запись при «Отметить отправленным»** создаётся в той же транзакции обычным созданием записи (`via: awareness_letter`). Поля:
    - «Письмо» — «№ N, версия V», у одноязычного срочного — с пометкой «, только RU» или «, только TJ» (ответ 9);
    - «Подготовил» — автор письма, если он среди `workUsersWhere()`, иначе пусто;
    - «Задача» — «Задача #K», если письмо связано с задачей.

   Номер записи сохраняется в событии отправки.
- Сам «Отправлено без согласования» в реестр не пишется: он виден в карточке письма и в журнале. Если нужен столбец — скажите.

### Роль-исполнитель
- `workRolesWhere()` в `lib/work-users.ts`: у роли есть право `ib.work` и код не `portal_admin`. «Настенный монитор» без `ib.work` в этот список не попадает сам.
- Выбор роли в правиле — только из этого списка. API проверяет то же самое: иначе 400 `BAD_ROLE` «Эта роль не участвует в работе». Служебную роль выбрать нельзя ни в интерфейсе, ни через API.
- **Кандидаты задачи** — держатели роли, отобранные `workUsersWhere()`. Список снимается при создании задачи. Пока задачу никто не взял, каждый прогон его обновляет: добавляет новых держателей и убирает тех, кто роль потерял или отключён.
- У роли нет держателей — задача создаётся без кандидатов (тогда её может взять любой сотрудник ИБ, как сейчас). Эскалация срабатывает сразу, текст — «у роли «…» нет участников».

### Расписание (ADR-0040)
- **Правило:** название, периодичность, дата начала, опережение в днях (7–90, по умолчанию 10: этап «черновик» — за 7 дней, поэтому меньше 7 нельзя — CHECK в БД, проверка API и формы; решение владельца 05.11.2026), роль-исполнитель, шаблон (необязательно), «активно».
- **Периодичность** (`cadence.ts`, параметры — `jsonb` с проверкой zod):
    - ежемесячно в день N;
    - дважды в месяц в дни N и M;
    - ежеквартально в день N K-го месяца квартала (K = 1–3, по умолчанию 1);
    - ежегодно D.M;
    - каждую N-ю неделю (1–12) в выбранный день недели, отсчёт — от даты начала.

   День 29–31 в коротком месяце — последний день месяца, 29.02 — 28.02 в невисокосный год. Ни одна дата не раньше даты начала.
- **Номинальная и плановая дата.** Номинальная — по периодичности. Плановая — номинальная, перенесённая на предыдущий рабочий день (`onOrPrevWorkingDay`, производственный календарь РТ).
- **Ключ идемпотентности — «правило + номинальная дата»**: `UNIQUE (rule_id, nominal_date)` в `awareness_schedule_runs`. Плановую дату в ключ не берём: если в календаре добавят праздник, плановая дата сдвинется, и ключ по ней создал бы дубль. Задание требует хранить «правило + плановую дату» — плановая дата хранится в той же строке. Если две номинальные даты одного правила перенеслись на один день, задача создаётся одна.
- **Окно прогона:** создаются запуски с плановой датой в `[сегодня; сегодня + опережение]`.
    - Догон после простоя получается сам: всё, что ещё не наступило, но уже попало в окно, создаётся.
    - Даты раньше сегодня не создаются никогда.
    - Отключённое или архивное правило не участвует.
    - Правка правила не трогает созданные запуски и задачи. Новые запуски строятся по новой периодичности, и форма об этом предупреждает.
- **Задача:**
    - название — «Рассылка: <название правила> — ДД.ММ.ГГГГ»;
    - категория «Осведомлённость», приоритет «Обычный», срок — плановая дата;
    - `source = 'manual'`, без автора и без исполнителя, с кандидатами роли (расхождение 3, вариант A).
- **Этапы с датами** (в строке запуска):
    - черновик — за 7 календарных дней;
    - согласование — за 3;
    - отправка — в плановую дату.

   Даты этапов тоже переносятся на предыдущий рабочий день, но не раньше дня создания задачи. В описании задачи этапы записаны текстом.
- **Шаблон в правиле:**
    - черновик создаётся сразу (`template_id`, `task_id`). Незаполненные переменные остаются в тексте подсвеченными и блокируют «На согласование»;
    - шаблон в архиве — задача создаётся без черновика, с пометкой в описании.
- **Эскалация:** `workingDaysBetween(сегодня, срок) ≤ 3`, исполнителя нет, задача открыта → уведомление `awareness_unclaimed` получателям из расхождения 2. Срабатывает один раз (`dedupe_key = awareness_unclaimed:<task>`), время сохраняется в `escalated_at`.
- **Прогон:** `runAwarenessSchedule(db, now)` в ежечасном `tick` (`plugins/jobs.ts`), после `runAutomations`. Одна транзакция, свой ключ `pg_try_advisory_xact_lock`. Итог пишется в лог. «Проверить сейчас» на правиле запускает тот же прогон для одного правила.

### Задачи модуля
Все с `source = 'manual'`, `created_by = NULL`, категория «Осведомлённость» (расхождение 3, вариант A). Происхождение — по таблицам модуля: в DTO задачи (`GET /tasks`, карточка) добавляется необязательное поле `origin` — `{ kind: 'schedule', rule }` или `{ kind: 'letter', number }`; доска и карточка показывают его вместо «поставлена вручную»:

| Задача | Кому | Срок |
|---|---|---|
| Рассылка по правилу | кандидаты роли | плановая дата |
| «Срочная рассылка: <название>» | создатель (он сам себе исполнитель), приоритет «Высокий» | 1 рабочий день |
| «Доработать письмо: <название>» после возврата | автор письма | срок отправки по запуску, если письмо из расписания, иначе 3 рабочих дня |

- Связь задачи с письмом — `awareness_letters.task_id` (рассылка и срочная) и `awareness_letter_events.task_id` (доработка).
- Отметка «Отправлено» задачу **не закрывает**: её проходят по обычным правилам проверки (ADR-0022). В историю задачи пишется запись «Письмо № N отмечено отправленным» (`audit_log`, `entity = 'task'`, в транзакции отметки). В карточке задачи появляется подсказка «Письмо отправлено — завершите задачу».

### Дашборд и монитор
- **Системный виджет «Ближайшая рассылка»** (`dashboard/awareness-widgets.ts`):
    - ближайший открытый запуск: «<название>, через N дн.» и этапы;
    - просроченный этап — красным (`--crit`);
    - если открытых запусков нет — «Запланированных рассылок нет».
- **Счётчики** (там же):
    - «Отправлено за <год>: плановых N / срочных M» — события отправки по дате отправки, текущий календарный год, каждая отметка считается;
    - «Рассылки с просрочкой» — открытые запуски, у которых наступила дата этапа, а этап не выполнен.
- **Монитор** — ключи KPI `awareness_next` (значение — дней до отправки, подпись — название, `tone = bad` при просроченном этапе) и `awareness_overdue` в слайде «Ключевые показатели» (расхождение 8).

## Схема

Одна миграция `awareness_letters`. Создаётся `prisma migrate dev --create-only`, SQL показывается до применения. Набросок:

```sql
CREATE TABLE awareness_templates (
  id uuid PRIMARY KEY DEFAULT gen_random_uuid(),
  title text NOT NULL CHECK (length(btrim(title)) BETWEEN 1 AND 200),
  subject_ru text NOT NULL DEFAULT '', subject_tj text NOT NULL DEFAULT '',
  html_ru text NOT NULL DEFAULT '', html_tj text NOT NULL DEFAULT '',
  version int NOT NULL DEFAULT 1, archived_at timestamptz(3),
  created_by uuid NOT NULL REFERENCES users(id), updated_by uuid NOT NULL REFERENCES users(id),
  created_at timestamptz(3) NOT NULL DEFAULT now(), updated_at timestamptz(3) NOT NULL);

CREATE TABLE awareness_fragments (
  code text PRIMARY KEY CHECK (code IN ('signature')),
  html_ru text NOT NULL, html_tj text NOT NULL, version int NOT NULL DEFAULT 1,
  updated_by uuid REFERENCES users(id), updated_at timestamptz(3) NOT NULL DEFAULT now());

CREATE TABLE awareness_letters (
  id uuid PRIMARY KEY DEFAULT gen_random_uuid(),
  number serial UNIQUE,
  title text NOT NULL CHECK (length(btrim(title)) BETWEEN 1 AND 200),
  kind text NOT NULL CHECK (kind IN ('planned', 'urgent')),
  reason text NOT NULL DEFAULT '',
  status text NOT NULL DEFAULT 'draft' CHECK (status IN ('draft', 'review', 'approved', 'sent')),
  frozen boolean NOT NULL DEFAULT false,
  template_id uuid REFERENCES awareness_templates(id) ON DELETE RESTRICT,
  task_id uuid REFERENCES tasks(id) ON DELETE RESTRICT,
  current_version_id uuid, approved_version_id uuid, sent_version_id uuid,  -- FK ниже, после таблицы версий
  version int NOT NULL DEFAULT 1, archived_at timestamptz(3),
  created_by uuid NOT NULL REFERENCES users(id),
  created_at timestamptz(3) NOT NULL DEFAULT now(), updated_at timestamptz(3) NOT NULL,
  CONSTRAINT awareness_letters_reason_check CHECK (kind <> 'urgent' OR length(btrim(reason)) > 0),
  CONSTRAINT awareness_letters_frozen_check CHECK (frozen = (status = 'sent') AND (NOT frozen OR sent_version_id IS NOT NULL)));

CREATE TABLE awareness_letter_versions (
  id uuid PRIMARY KEY DEFAULT gen_random_uuid(),
  letter_id uuid NOT NULL REFERENCES awareness_letters(id) ON DELETE RESTRICT,
  no int NOT NULL,
  reason text NOT NULL CHECK (reason IN ('edit', 'restore', 'template', 'copy', 'sent')),
  restored_from int,
  subject_ru text NOT NULL, subject_tj text NOT NULL, html_ru text NOT NULL, html_tj text NOT NULL,
  created_by uuid NOT NULL REFERENCES users(id), created_at timestamptz(3) NOT NULL DEFAULT now(),
  UNIQUE (letter_id, no));
-- FK current/approved/sent_version_id → awareness_letter_versions(id)

CREATE TABLE awareness_letter_events (          -- только пополняется (триггер), как document_approvals
  id uuid PRIMARY KEY DEFAULT gen_random_uuid(),
  letter_id uuid NOT NULL REFERENCES awareness_letters(id) ON DELETE RESTRICT,
  version_id uuid REFERENCES awareness_letter_versions(id),
  action text NOT NULL CHECK (action IN ('submitted', 'withdrawn', 'approved', 'returned', 'approval_dropped', 'sent', 'archived', 'unarchived')),
  comment text NOT NULL DEFAULT '',
  self_approved boolean NOT NULL DEFAULT false,
  without_approval boolean NOT NULL DEFAULT false,
  sent_on date, audience text,
  record_id uuid REFERENCES register_records(id) ON DELETE RESTRICT,
  task_id uuid REFERENCES tasks(id) ON DELETE RESTRICT,
  actor_id uuid NOT NULL REFERENCES users(id), at timestamptz(3) NOT NULL DEFAULT now(),
  CHECK (action <> 'sent' OR (sent_on IS NOT NULL AND length(btrim(coalesce(audience, ''))) > 0)),
  CHECK (action <> 'returned' OR length(btrim(comment)) > 0),
  CHECK (NOT without_approval OR (action = 'sent' AND length(btrim(comment)) > 0)));

CREATE TABLE awareness_schedule_rules (
  id uuid PRIMARY KEY DEFAULT gen_random_uuid(),
  title text NOT NULL CHECK (length(btrim(title)) BETWEEN 1 AND 200),
  cadence jsonb NOT NULL, starts_on date NOT NULL,
  lead_days int NOT NULL DEFAULT 10 CHECK (lead_days BETWEEN 7 AND 90),
  role_id uuid NOT NULL REFERENCES roles(id) ON DELETE RESTRICT,
  template_id uuid REFERENCES awareness_templates(id) ON DELETE RESTRICT,
  active boolean NOT NULL DEFAULT true, version int NOT NULL DEFAULT 1, archived_at timestamptz(3),
  created_by uuid NOT NULL REFERENCES users(id),
  created_at timestamptz(3) NOT NULL DEFAULT now(), updated_at timestamptz(3) NOT NULL);

CREATE TABLE awareness_schedule_runs (
  id uuid PRIMARY KEY DEFAULT gen_random_uuid(),
  rule_id uuid NOT NULL REFERENCES awareness_schedule_rules(id) ON DELETE RESTRICT,
  nominal_date date NOT NULL, planned_date date NOT NULL,
  draft_due date NOT NULL, review_due date NOT NULL,
  task_id uuid NOT NULL UNIQUE REFERENCES tasks(id) ON DELETE RESTRICT,
  letter_id uuid REFERENCES awareness_letters(id) ON DELETE RESTRICT,
  escalated_at timestamptz(3), created_at timestamptz(3) NOT NULL DEFAULT now(),
  UNIQUE (rule_id, nominal_date));
CREATE INDEX ON awareness_schedule_runs (rule_id, planned_date);
```

- **Триггеры:**
    - `awareness_letter_versions` и `awareness_letter_events` — запрет `UPDATE` и `DELETE`;
    - `awareness_letters`: при `frozen = true` запрещено менять `status`, `frozen`, `current_version_id`, `approved_version_id`, `sent_version_id`, `title`, `kind`, `reason`, `template_id`, `task_id`. Разрешены только `archived_at`, `version` и `updated_at` (условие владельца: заморозка не мешает архиву);
    - `awareness_letter_versions`: вставка новой версии у замороженного письма запрещена. Версия `sent` вставляется до того, как письмо получает `frozen`.
- **Права:** приложение получает обычные права на новые таблицы через `ALTER DEFAULT PRIVILEGES` (ADR-0002). Отдельных `GRANT` нет.
- **Расширений PostgreSQL нет**, `gen_random_uuid()` встроен в PostgreSQL 16.

**Влияние на данные:** добавляются новые таблицы, существующие данные не меняются. Миграция затрагивает 0 строк. Существующие таблицы получают только входящие внешние ключи (`users`, `roles`, `tasks`, `register_records`, `awareness_templates`); их ограничения не меняются. Откат миграции не нужен.

**Seed `awareness.v2`** (один раз, `seed_markers`):
- категория задач «Осведомлённость» (`systemKey = awareness`; одноимённое значение администратора становится системным — расхождение 6);
- реестр «Рассылки» без записей (при одноимённом реестре — «Рассылки (системный)»);
- фрагмент «Подпись ИБ» с заглушкой;
- строка `app_settings` `awareness.letters` с лимитами `{ maxImageKb: 1024, maxLetterKb: 2048, warnLetterKb: 1024 }`.

Писем, шаблонов и правил seed не создаёт.

**Откат на 1.8.0 без отката базы:**
- новые таблицы 1.8.0 не читает;
- задачи модуля — `source = 'manual'`, это значение 1.8.0 знает (покажет «поставлена вручную», может предложить такую задачу в подсказке цепочки);
- категория и реестр — обычные данные;
- ключи KPI и виджетов 1.8.0 отбрасывает;
- уведомления `awareness_*` — `kind` строкой: 1.8.0 показывает снимок текста. Отдельный тест на frontend 1.8.0 не прогоняется, поэтому на репетиции открою колокольчик после отката;
- задачи рассылок остаются на доске, взять и закрыть их можно, а новые не создаются.

Перед откатом ничего отключать не нужно. Проверка — на репетиции (шаг 13).

**Удаление задач и записей, на которые ссылаются письма (замечание владельца 05.11.2026, п. 3).** Внешние ключи из новых таблиц на `tasks` и `register_records` — `ON DELETE RESTRICT`. Сверено с кодом 1.8.0: путей физического удаления задач и записей реестров в коде нет.
- «Удалить задачу» (`tasks.delete`, `deleteTask`) и массовое удаление (`tasks/bulk.ts`) — мягкие: ставят `deleted_at`.
- Удаление записи реестра (`records.delete`, `records.service.ts`) — мягкое: `deleted_at` и `deletion_id`, запись уходит в «Корзину».
- «Корзина» (`modules/trash`) умеет только список и «Восстановить»: очистки, то есть физического удаления, в ней нет.
- В скриптах и seed нет `DELETE` по `tasks` и `register_records`.

Поэтому `RESTRICT` в работе портала не срабатывает, и ответа 500 при удалении нет — ни в 1.9.0, ни в 1.8.0. Защита, о которой просил владелец, — на штатном (мягком) удалении:
- **задача** письма, задача доработки и задача запуска правила: «Удалить» — 409 `TASK_LINKED_TO_LETTER` «Задача #K связана с учебным письмом № N — её нельзя удалить, можно отправить в архив» (для запуска без письма — «создана правилом расписания «…»»); массовое удаление пропускает такие задачи и продолжает с остальными, в предпросмотре — `linkedToLetters`;
- **запись «Рассылок»** из отметки «Отправлено»: новая причина зависимости `letters` в общем механизме (`registers/dependencies.ts`) — одиночное удаление 409 `RECORD_LINKED_TO_LETTER` с номером письма, массовое отправляет такие записи в архив, как записи с решениями и доказательствами;
- архив разрешён всегда; `RESTRICT` остаётся второй линией на физический `DELETE` (DB-тест).

**Откат на 1.8.0:** 1.8.0 о письмах не знает, поэтому там такую задачу или запись можно удалить — мягко, без ошибки: строка остаётся в БД, внешние ключи не срабатывают. После возврата на 1.9.0 письмо покажет ссылку на удалённую задачу. Строка — в `RELEASE.md`.

## Проверка

- **Unit:**
    - плановые даты для каждой периодичности;
    - 31-е в 30-дневном месяце и в феврале, 29.02 в невисокосный год;
    - перенос с выходного и с праздника на предыдущий рабочий день, в том числе через границу месяца;
    - граница суток по +05 (`now` = 18:59Z и 19:00Z);
    - окно опережения и догон после простоя: в окне — создать, раньше сегодня — нет;
    - две номинальные даты на одну плановую;
    - «каждую N-ю неделю» от даты начала;
    - санитайзер: вырезает `script`, `iframe`, `object`, `form`, `style`, `on*`, `javascript:`, `data:` в ссылках, внешние и относительные `src`, SVG; ссылка на портал — `PORTAL_LINK`; неподдельный тип изображения по сигнатуре;
    - переменные: извлечение из темы и текста обоих языков, одинаковое имя, `{{подпись}}`, экранирование значений, пустая переменная — ошибка;
    - `.eml`: `multipart/alternative` + `multipart/related`, `Content-ID` и `cid:`, одно изображение — одна часть, RFC 2047 на длинной кириллической теме, `X-Unsent: 1`, нет `From`, `To`, `Date`, CRLF;
    - текстовая часть;
    - переходы статусов и заморозка (`flow.ts`).
- **DB:**
    - отправленное письмо не правится через API (409 `LETTER_FROZEN`) и через SQL (триггер): тема, текст, статус, новая версия, правка старой версии;
    - замороженное письмо архивируется и возвращается из архива — через API и через SQL (`archived_at`);
    - плановое письмо с одним языком на согласование не уходит, срочное уходит — с пометкой «только RU» в карточке и в «Рассылках»;
    - отметка «Отправлено» не закрывает задачу и пишет запись в историю задачи;
    - эскалация: отметка есть — ему; отметки нет или её держатель отключён — держателям роли «Начальник ИБ»;
    - копия создаёт новый черновик и не меняет оригинал;
    - «Восстановить» добавляет версию, старые не меняются;
    - повторный прогон планировщика не создаёт дублей, в том числе после смены календаря;
    - отключённое и архивное правило задач не создают;
    - правка правила не трогает созданные задачи;
    - догон: простой 5 дней — создано только то, что в окне;
    - служебную роль нельзя сделать ролью-исполнителем (400 `BAD_ROLE`), роль без `ib.work` — тоже;
    - служебный пользователь получает 403 `SERVICE_ACCOUNT` на всех маршрутах модуля и на «Подписи ИБ»;
    - служебного пользователя нет среди кандидатов и получателей эскалации;
    - кандидаты обновляются, пока задачу не взяли;
    - эскалация — один раз;
    - отметка без согласования — только у срочного и только с комментарием;
    - утверждение своего письма — `self_approved`;
    - возврат без комментария — 400, с комментарием — задача автору;
    - запись в «Рассылках» создаётся при отметке, повторная отметка — новая запись;
    - задачи модуля не попадают в подсказки цепочек и в «Найти среди старых»;
    - seed идемпотентен; одноимённые реестр и категория.
- **E2E:**
    - сквозной сценарий: правило с шаблоном → «Проверить сейчас» → задача на доске → «Взять себе» → письмо из шаблона заполнено → на согласование → начальник ИБ утверждает → «Отметить отправленным» → запись в «Рассылках» → письмо заморожено, правка недоступна, «Создать копию» работает;
    - отдельный короткий тест: срочная рассылка без согласования с комментарием;
    - тесты сами создают и убирают свои данные (правило, шаблон, письма — в архив, вымышленные пользователи) и ждут появления текста на странице, а не сетевых ответов.
- **Существующее не меняется:**
    - полный прогон `test:db` и e2e;
    - доска, документы, автоматизации и уведомления о сроках дают те же результаты;
    - `CHAIN_SOURCES` не меняется.

В тестах — вымышленные письма («Осторожно: поддельные письма о выигрыше») и люди («Иванов Иван Иванович»). Подпись в seed — заглушка.
