## 0. Иерархия пользователей (основа для задач и документов)

- Нужно понимать, кто «старший» над пользователем: задачи ставит и проверяет не каждый, документы двигают автор и старшие по иерархии.
- Предложение: у пользователя поле «Руководитель» (ссылка на пользователя), задаётся в «Настройки → Пользователи» по праву users.manage. «Старший» — любой пользователь выше по цепочке руководителей. Без циклов, проверка на backend.
- Если видишь вариант лучше (уровни, группы) — предложи в плане с плюсами и минусами.

## 1. Задачи

1. **Право на свободную смену статуса.** Новое право (например, tasks.status.override): перетаскивание карточки между колонками и смена статуса в обход процесса. Выдаётся роли в матрице «Роли и права».
2. **Без этого права карточки не перетаскиваются.** На frontend перетаскивание отключено, backend отклоняет смену статуса в обход процесса (403).
3. **Процесс по кнопкам.**
   - Колонки: «Backlog» — задачи без исполнителя; «Поставленные» — задачи с исполнителем, ещё не взятые; «В работе»; «На проверке»; «Выполнено».
   - Назначение исполнителя переносит задачу из «Backlog» в «Поставленные»; снятие исполнителя — обратно.
   - Исполнитель открывает свою поставленную задачу → кнопка «Взять в работу» → «В работе».
   - «Отправить на проверку» → «На проверке», с обязательным комментарием (причина смены статуса).
   - В колонке «На проверке» кнопки «Принять» → «Выполнено» и «Вернуть в работу» → «В работе». Нажимать их могут только пользователи с правом проверки (например, tasks.review), и только по задачам, где они автор задачи или старшие по иерархии над исполнителем — уточни правило в плане.
   - Ставить задачи другим может только пользователь с правом (например, tasks.assign); кому именно можно назначать (любому или только подчинённым) — вопрос ко мне в плане.
   - **Требование комментария — настройка колонки**, а не код: у колонки (статуса) признак «при переходе в эту колонку обязателен комментарий». Новые колонки, добавленные в настройках, получают этот признак тоже. По умолчанию включён для «На проверке», «Выполнено» и для возврата «Вернуть в работу».
   - Комментарий перехода сохраняется в задаче и в истории (кто, когда, из какой колонки в какую, текст).
   - Существующие задачи: перенос по правилу «есть исполнитель → Поставленные/текущий рабочий статус, нет → Backlog». Таблица соответствия и число задач на dev — в плане.
4. **Отчёт по задачам.** Выгрузка в Excel с фильтрами: период, исполнитель, автор, категория, колонка, просроченные. В отчёте: задача, автор, исполнитель, срок, текущая колонка, даты переходов, просрочка. Отдельное право (например, tasks.report) в матрице ролей.
5. **Уведомления в системе.**
   - Значок с числом непрочитанных в шапке, список уведомлений, «прочитать все», переход к задаче по клику.
   - События: задача назначена вам; задачу вернули в работу; задача отправлена на проверку (тем, кто может принять); задача принята; новый комментарий в вашей задаче; срок задачи завтра и просрочен. Для документов — события этапов Г (документ ждёт вашего действия, вернули на доработку, изменили срок).
   - Без внешних сервисов и WebSocket: опрос раз в 30–60 секунд. Почта (MDaemon) — не в этом релизе.
   - Уведомления видит только адресат; хранить с датой прочтения; старые прочитанные — очистка по сроку (предложи).

## 2. Документы

1. **Убрать роли «Юрист» и «Правление»** и этапы «Юридический отдел» и «Утверждение правлением». Если у ролей есть пользователи — не удалять молча: показать, у кого, и предложить порядок. Права docs.approve.legal и docs.approve.board выводятся из матрицы; история прошлых согласований с этими этапами сохраняется и читается.
2. **Новый маршрут из 6 этапов — внутри команды ИБ.**
   1. **Драфт.** Автор создаёт документ: ссылка на файл в OnlyOffice и, опционально, несколько файлов .docx.
   2. **Проверка сотрудниками.** Другие пользователи открывают документ и оставляют комментарии. Перевести на этап 3 могут автор и старшие по иерархии над автором.
   3. **Согласование начальника ИБ** (право docs.approve.head). Начальник может вернуть документ на доработку сразу на этап 1 (обязательный комментарий) или одобрить — тогда документ переходит на этап 4.
   4. **Согласование с ответственными лицами.** Автор указывает, кому документ отправлен по почте на согласование, и срок по каждому лицу. Срок можно менять, но только с обязательным комментарием; история сроков сохраняется. Есть список блокеров по документу (что мешает, открыт/снят). Автор отмечает согласование по каждому лицу (с возможностью приложить ответ, например PDF письма). Когда все согласовали, начальник ИБ повторно знакомится с финальной версией и переводит документ на этап 5.
   5. **Перевод.** Указываются переводчики (сотрудники), языки и сроки по каждому языку; прикладываются файлы переводов. После получения переводов перевести на этап 6 могут начальник ИБ и старший по иерархии пользователь.
   6. **Подписание.** Загружается подписанный документ (PDF) и дата подписания. От даты подписания система считает срок актуальности и цикл пересмотра (по умолчанию 12 месяцев, задача за 30 дней — как сейчас).
   - Возвраты, кроме «этап 3 → этап 1», — вопрос ко мне в плане (нужны ли «4 → 1», «5 → 4» и т.п.).
   - Каждый переход этапа — в истории документа: кто, когда, откуда, куда, комментарий.
   - Существующие документы: таблица «текущий статус/этап → новый этап» и число документов на dev. Утверждённые документы сохраняют даты утверждения и пересмотра.
3. **Удаление документа — отдельное право** (например, docs.delete). Удаление мягкое (deleted_at), с записью в журнал. Можно ли удалять подписанные документы — вопрос ко мне в плане.

## 3. Журнал действий

1. **Убрать журналы и историю из разделов** (вкладки истории в карточках задач, записей реестров, документов, доказательств, журналы справочников и т. п.). Показывать их только пользователям с правом (например, history.view), выдаваемым по роли.
2. **Отдельный раздел «Журнал»** — все действия пользователей из audit_log: фильтры (период, пользователь, действие, раздел/сущность, IP), поиск, пагинация, переход к объекту, выгрузка в Excel. Доступ по отдельному праву (например, audit.view). Без права раздела нет в меню и маршрут отвечает 403.
- Запись в audit_log не меняется — меняется только то, кто его видит (CLAUDE.md, раздел 3.5).
- Пароли и секреты в журнале не показываются (они туда и не пишутся — проверить тестом).
- Предложи в плане: одно право на оба пункта или два раздельных.
