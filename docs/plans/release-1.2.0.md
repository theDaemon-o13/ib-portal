## 0. Иерархия пользователей (основа для задач и документов)

- Нужно понимать, кто «старший» над пользователем: задачи ставит и проверяет не каждый, документы двигают автор и старшие по иерархии.
- Предложение: у пользователя поле «Руководитель» (ссылка на пользователя), задаётся в «Настройки → Пользователи» по праву users.manage. «Старший» — любой пользователь выше по цепочке руководителей. Без циклов, проверка на backend.
- Если видишь вариант лучше (уровни, группы) — предложи в плане с плюсами и минусами.

## 1. Задачи

1. **Право на свободную смену статуса.** Новое право (например, tasks.status.override): перетаскивание карточки между колонками и смена статуса в обход процесса. Выдаётся роли в матрице «Роли и права».
2. **Без этого права карточки не перетаскиваются.** На frontend перетаскивание отключено, backend отклоняет смену статуса в обход процесса (403).
3. **Процесс по кнопкам.**
   - Колонки: «Backlog» — задачи без исполнителя; «Поставленные» — задачи с исполнителем, ещё не взятые; «В работе»; «На проверке»; «Выполнено».
   - Назначение исполнителя переносит задачу из «Backlog» в «Поставленные»; снятие исполнителя — обратно.
   - Исполнитель открывает свою поставленную задачу → кнопка «Взять в работу» → «В работе».
   - «Отправить на проверку» → «На проверке», с обязательным комментарием (причина смены статуса).
   - В колонке «На проверке» кнопки «Принять» → «Выполнено» и «Вернуть в работу» → «В работе». Нажимать их могут только пользователи с правом проверки (например, tasks.review), и только по задачам, где они автор задачи или старшие по иерархии над исполнителем — уточни правило в плане.
   - Ставить задачи другим может только пользователь с правом (например, tasks.assign); кому именно можно назначать (любому или только подчинённым) — вопрос ко мне в плане.
   - **Требование комментария — настройка колонки**, а не код: у колонки (статуса) признак «при переходе в эту колонку обязателен комментарий». Новые колонки, добавленные в настройках, получают этот признак тоже. По умолчанию включён для «На проверке», «Выполнено» и для возврата «Вернуть в работу».
   - Комментарий перехода сохраняется в задаче и в истории (кто, когда, из какой колонки в какую, текст).
   - Существующие задачи: перенос по правилу «есть исполнитель → Поставленные/текущий рабочий статус, нет → Backlog». Таблица соответствия и число задач на dev — в плане.
4. **Отчёт по задачам.** Выгрузка в Excel с фильтрами: период, исполнитель, автор, категория, колонка, просроченные. В отчёте: задача, автор, исполнитель, срок, текущая колонка, даты переходов, просрочка. Отдельное право (например, tasks.report) в матрице ролей.
5. **Уведомления в системе.**
   - Значок с числом непрочитанных в шапке, список уведомлений, «прочитать все», переход к задаче по клику.
   - События: задача назначена вам; задачу вернули в работу; задача отправлена на проверку (тем, кто может принять); задача принята; новый комментарий в вашей задаче; срок задачи завтра и просрочен. Для документов — события этапов Г (документ ждёт вашего действия, вернули на доработку, изменили срок).
   - Без внешних сервисов и WebSocket: опрос раз в 30–60 секунд. Почта (MDaemon) — не в этом релизе.
   - Уведомления видит только адресат; хранить с датой прочтения; старые прочитанные — очистка по сроку (предложи).

## 2. Документы

1. **Убрать роли «Юрист» и «Правление»** и этапы «Юридический отдел» и «Утверждение правлением». Если у ролей есть пользователи — не удалять молча: показать, у кого, и предложить порядок. Права docs.approve.legal и docs.approve.board выводятся из матрицы; история прошлых согласований с этими этапами сохраняется и читается.
2. **Новый маршрут из 6 этапов — внутри команды ИБ.**
   1. **Драфт.** Автор создаёт документ: ссылка на файл в OnlyOffice и, опционально, несколько файлов .docx.
   2. **Проверка сотрудниками.** Другие пользователи открывают документ и оставляют комментарии. Перевести на этап 3 могут автор и старшие по иерархии над автором.
   3. **Согласование начальника ИБ** (право docs.approve.head). Начальник может вернуть документ на доработку сразу на этап 1 (обязательный комментарий) или одобрить — тогда документ переходит на этап 4.
   4. **Согласование с ответственными лицами.** Автор указывает, кому документ отправлен по почте на согласование, и срок по каждому лицу. Срок можно менять, но только с обязательным комментарием; история сроков сохраняется. Есть список блокеров по документу (что мешает, открыт/снят). Автор отмечает согласование по каждому лицу (с возможностью приложить ответ, например PDF письма). Когда все согласовали, начальник ИБ повторно знакомится с финальной версией и переводит документ на этап 5.
   5. **Перевод.** Указываются переводчики (сотрудники), языки и сроки по каждому языку; прикладываются файлы переводов. После получения переводов перевести на этап 6 могут начальник ИБ и старший по иерархии пользователь.
   6. **Подписание.** Загружается подписанный документ (PDF) и дата подписания. От даты подписания система считает срок актуальности и цикл пересмотра (по умолчанию 12 месяцев, задача за 30 дней — как сейчас).
   - Возвраты, кроме «этап 3 → этап 1», — вопрос ко мне в плане (нужны ли «4 → 1», «5 → 4» и т.п.).
   - Каждый переход этапа — в истории документа: кто, когда, откуда, куда, комментарий.
   - Существующие документы: таблица «текущий статус/этап → новый этап» и число документов на dev. Утверждённые документы сохраняют даты утверждения и пересмотра.
3. **Удаление документа — отдельное право** (например, docs.delete). Удаление мягкое (deleted_at), с записью в журнал. Можно ли удалять подписанные документы — вопрос ко мне в плане.

## 3. Журнал действий

1. **Убрать журналы и историю из разделов** (вкладки истории в карточках задач, записей реестров, документов, доказательств, журналы справочников и т. п.). Показывать их только пользователям с правом (например, history.view), выдаваемым по роли.
2. **Отдельный раздел «Журнал»** — все действия пользователей из audit_log: фильтры (период, пользователь, действие, раздел/сущность, IP), поиск, пагинация, переход к объекту, выгрузка в Excel. Доступ по отдельному праву (например, audit.view). Без права раздела нет в меню и маршрут отвечает 403.
- Запись в audit_log не меняется — меняется только то, кто его видит (CLAUDE.md, раздел 3.5).
- Пароли и секреты в журнале не показываются (они туда и не пишутся — проверить тестом).
- Предложи в плане: одно право на оба пункта или два раздельных.

| `tasks.review` | «Принять» и «Вернуть в работу» на проверке | Б | Начальник ИБ |

| `docs.delete` | Мягкое удаление документа | Г | Супер-администратор |

Удаляются: `docs.approve.legal`, `docs.approve.board` (этап Г). Права выдаются ролям однократным шагом seed: если администратор потом снимет право, при обновлении оно не вернётся.

Два раздельных права на журнал и историю (`audit.view` и `history.view`), а не одно: журнал показывает входы, IP и действия всех пользователей во всех разделах, а история карточки — только изменения одного объекта. Руководителю группы может быть нужна история задач без доступа к журналу входов.

### А2. Иерархия пользователей (коммит 2)

**Предложение — поле «Руководитель»** (цепочка руководителей). Сравнение вариантов:

| Вариант | Плюсы | Минусы |
|---|---|---|
| **Руководитель у пользователя** (рекомендую) | Одна ссылка; «старший» = выше по цепочке; отражает реальную подчинённость; легко проверить циклы | Нельзя двух руководителей; замещение (отпуск) не выражается |
| Уровни (1, 2, 3…) | Совсем просто | Старший по уровню становится «старшим» над людьми чужой группы; нет понятия «моя группа» |
| Группы с руководителем | Близко к оргструктуре, удобно при росте отдела | Второй справочник, руководитель группы всё равно нужен; правило «старший» по группам вложенных групп сложнее |

Замещение (отпуск начальника) — при необходимости потом: «временно исполняет обязанности».

- Миграция `users_manager`:

```sql
-- Влияние на данные: новая колонка users.manager_id (NULL у всех пользователей, сейчас на dev 334 строки, на проде —
-- все учётные записи); данные не переписываются. Триггер запрещает цикл в цепочке руководителей.
-- Откат: backend 1.1.0 колонку не читает; NULL — «руководитель не назначен».
ALTER TABLE "users" ADD COLUMN "manager_id" UUID;
ALTER TABLE "users" ADD CONSTRAINT "users_manager_id_fkey"
  FOREIGN KEY ("manager_id") REFERENCES "users"("id") ON DELETE RESTRICT ON UPDATE CASCADE;
ALTER TABLE "users" ADD CONSTRAINT "users_manager_not_self" CHECK ("manager_id" IS NULL OR "manager_id" <> "id");
CREATE INDEX "users_manager_id_idx" ON "users"("manager_id");

CREATE FUNCTION users_manager_no_cycle() RETURNS trigger LANGUAGE plpgsql AS $$
BEGIN
  IF NEW.manager_id IS NULL THEN RETURN NEW; END IF;
  -- Одновременная смена руководителей не может обойти проверку.
  PERFORM pg_advisory_xact_lock(hashtext('users.manager_id'));
  IF EXISTS (
    WITH RECURSIVE up(id, depth) AS (
      SELECT NEW.manager_id, 1
      UNION ALL
      SELECT u.manager_id, up.depth + 1 FROM users u JOIN up ON u.id = up.id
      WHERE u.manager_id IS NOT NULL AND up.depth < 100
    )
    SELECT 1 FROM up WHERE id = NEW.id
  ) THEN
    RAISE EXCEPTION 'manager cycle' USING ERRCODE = '23514';
  END IF;
  RETURN NEW;
END $$;
CREATE TRIGGER users_manager_no_cycle BEFORE INSERT OR UPDATE OF manager_id ON "users"
  FOR EACH ROW EXECUTE FUNCTION users_manager_no_cycle();
```

- Backend:
  - `lib/hierarchy.ts`: `seniorsOf(userId)`, `isSeniorOf(senior, user)`, `subordinatesOf(userId)` — рекурсивные запросы; цепочка не длиннее 100.
  - `users`: поле `managerId` в списке, создании и правке (право `users.manage`); руководителем может быть только активный пользователь с `ib.work`, не киоск, не сам пользователь; цикл — 409 «Нельзя: X уже подчинён Y» (до триггера, с понятным текстом). Отключённый руководитель остаётся в цепочке (старшие выше него не теряются); в списке пользователей у него пометка «отключён».
  - Аудит: `user.manager_changed` с «было → стало» (ФИО и логины).
- Frontend: «Настройки → Пользователи» — колонка «Руководитель», поле в окне пользователя (список активных сотрудников ИБ), у руководителя — «Подчинённые: N».
- Тесты: unit — разбор цепочки; db — цикл A→B→A и A→B→C→A отклоняются (и сервисом, и триггером), `isSeniorOf` через 2 уровня, отключённый руководитель в цепочке; e2e — назначить руководителя в настройках, увидеть в списке.
- ADR-0020 «Иерархия пользователей: руководитель у пользователя».

- Право `audit.view`. Без права пункта нет в меню, маршрут `/audit` на frontend показывает «Нет доступа», backend отвечает 403.
- Backend `modules/audit/routes.ts`:

-- Влияние на данные: только индекс для фильтра «пользователь» в разделе «Журнал»; строки audit_log не меняются
-- (на dev 32 975, построение — доли секунды; на проде на время построения запись в журнал ждёт). Откат: индекс не мешает 1.1.0.

## Вопросы к владельцу

**Иерархия и права**
1. Подходит ли «Руководитель у пользователя» (цепочка)? Руководитель и подчинённые — только пользователи с `ib.work`?
2. `tasks.assign`: назначать **любому** сотруднику ИБ или **только подчинённым** (по цепочке)? Предлагаю: любому, а без права — только себе. Может ли пользователь без права **сам взять задачу из Backlog** («Взять себе»)?
3. Кто нажимает «Принять / Вернуть»: `tasks.review` **и** (автор задачи **или** старший над исполнителем) — подтверждаете «или»? Если автор и исполнитель — один человек, принимать может только старший? Если у исполнителя нет руководителя и он сам автор — кто принимает (предлагаю: любой с `tasks.review`)?
4. Задачи автоматизаций, документов и доказательств создаются с исполнителем → «Поставленные». Система закрывает их сама («Выполнено», без проверки) — так и оставить?

**Колонки задач**
6. Новые колонки, добавленные в настройках: где они в процессе? Предлагаю: попасть в них можно только по `tasks.status.override` (перетаскиванием), кнопки процесса работают только с пятью системными колонками. Либо нужна настройка «после какой колонки» с кнопкой «Перевести в …» у исполнителя?
7. Два признака у колонки — «комментарий при переходе вперёд» и «при возврате» — подходят? Иначе «Взять в работу» потребует комментарий, раз он нужен для «Вернуть в работу».

**Журнал**

9. Документы: блок маршрута «кто и когда согласовал этап» оставить всем, кто видит документ, а под `history.view` спрятать подробную историю (все решения, круги, комментарии)?

**Документы и роли (этап Г, ответ можно позже)**

## Решения владельца (29.10.2026)

Коды прав из таблицы подтверждены. Удаление ролей «Юрист» и «Правление» — в этапе Г. План этапа А утверждён.

1. Иерархия — «Руководитель у пользователя». Руководители и подчинённые — только пользователи с `ib.work`.
2. `tasks.assign` — назначать любому сотруднику ИБ; без права — только себе. «Взять себе» из Backlog — любой с `ib.work`.
3. «Принять / Вернуть» — `tasks.review` и (автор задачи или старший над исполнителем). Нет руководителя — любой с `tasks.review`. **Исполнитель никогда не принимает свою задачу**, даже с `tasks.review` — проверка на backend и тест.
4. Системные задачи (автоматизации, документы, доказательства) система закрывает сама, без проверки.
5. По умолчанию всё новое — «Начальник ИБ»; `history.view` и `audit.view` — «Начальник ИБ» и «Супер-администратор». «Сотрудник ИБ» `history.view` не получает. Комментарии к задаче и комментарии переходов видны всем, кто видит задачу (это не история).
6. В пользовательские колонки — только перетаскиванием по `tasks.status.override`; кнопки — пять системных колонок.
7. Два признака колонки: «при переходе вперёд» и «при возврате».
8. `history.view` и `audit.view` — раздельные.
9. Блок «кто какой этап согласовал» — всем, кто видит документ; подробная история — `history.view`.
10. Журналы автоматизаций — под `registers.manage`.
11. Выгрузка журнала — до 100 000 строк; больше — сообщение «Сузьте период», без молчаливой обрезки.
12. Документы на этапах юриста и правления → этап 4, запись в истории «перенесён при обновлении на 1.2.0».
13. Правило «без `ib.work` видны только утверждённые документы» сохраняется. Пользователей ролей «Юрист» и «Правление» не отключать — перевести в новую роль «Читатель документов» (без `ib.work`, без новых прав). В RELEASE.md — запрос для DevOps с числом таких пользователей.
14. Возвраты — только начальник ИБ на этап 1 с этапов 3–5, с обязательным комментарием.
15. Подписанные — только в архив; удалять можно только неподписанные.
16. Уведомления: прочитанные удаляются через 90 дней, непрочитанные — через 180.
