# План релиза 1.13.7 — диагностика входа монитора, выбор языка перевода

Задание: `docs/tasks/1.13.7-kiosk-diagnostics-languages.md`. От 1.13.6. **Схема БД не меняется** (миграций нет), новых переменных `.env` и зависимостей нет. Выкладка — замена backend и frontend без `migrate`, откат на 1.13.6 — только код.

## 1. Диагностика входа (backend + frontend)

Ответ пользователю не меняется: 401 `INVALID_CREDENTIALS` «Неверный логин или пароль» при любой причине (423 при блокировке — как раньше).

- `modules/auth/reasons.ts` — причины отказа (`unknown_user`, `wrong_password`, `inactive`, `locked`, `kiosk_ip_denied`, `admin_ip_denied`) и их подписи; маска логина `maskLogin` — первые 2 символа и длина.
- `service.ts` — при каждом отказе строка `warn` «вход отклонён» через переданный логгер: `reason`, `login` (при `unknown_user` — только маска и длина), `userId`, `ip`. Пароль, его хеш и производные в объект лога не попадают (тест — по всем причинам, в том числе когда в поле логина введён пароль).
- `lib/startup-report.ts` — при старте: `info` с итоговыми списками `TRUSTED_PROXY_IPS`, `MONITOR_ALLOWED_IPS`, `ADMIN_ALLOWED_IPS` (адреса — не секреты); `warn`, если `MONITOR_ALLOWED_IPS` пуста. Вызывается из `server.ts`.
- «Журнал»: у `auth.login_failed` без `summary` подпись строится при чтении из `diff.reason` (и для старых записей): «Неудачный вход «логин»: адрес не разрешён для настенного монитора (MONITOR_ALLOWED_IPS)». При `unknown_user` логин в подписи — в маске. В таблице и в Excel. Записи журнала не меняются.
- `GET /users/kiosk-status` (`users.manage`): пуст ли список адресов монитора и у каждой учётки с `monitor.kiosk` — последний отказ по адресу после последнего успешного входа (время, IP). В «Пользователи и роли» — предупреждение на строке такой учётки.
- Тесты: на каждую причину — одинаковый ответ, `reason` в журнале, строка `warn`, отсутствие пароля в логе; стартовые строки; подписи журнала; `kiosk-status`.

## 2. Язык перевода из списка (backend + frontend)

- `backend/src/lib/languages.ts` — единственный список: `ru` Русский RU, `tg` Таджикский TJ, `en` Английский EN; псевдонимы для сопоставления старых строк (`ru`: русский, russian, ru, rus, рус; `tg`: таджикский, tj, tg, тоҷикӣ, tajik; `en`: английский, en, eng, english); `tj → tg` для учебных писем (`Content-Language` в `export/mail.ts` берётся отсюда; ключи `tj` в базе и API писем не меняются).
- Frontend получает тот же список сгенерированным файлом `frontend/src/api/generated/languages.ts` (пишет `npm run openapi:export`; тест backend сверяет файл со списком). Редактор учебных писем берёт названия и метки оттуда.
- API этапа 23: добавление — `code` (`ru` / `tg` / `en`, иначе 400); в базу пишется название («Таджикский»). Правка — `code` по желанию: не передан — язык строки не меняется (старый текст остаётся). Поле `language` текстом в API больше не принимается.
- Ответ: у строки перевода `language` (как в базе) и `code` (по названию или псевдониму; не сопоставлено — `null`).
- Дубль: 409 `DUPLICATE`, если в версии уже есть строка с тем же кодом — в том числе старая «таджикский» / «TJ». Уникальный индекс `(version_id, lower(btrim(language)))` остаётся как есть.
- Интерфейс: «Язык» — `Select` из трёх вариантов, занятые недоступны («уже добавлен»); при правке старой строки показан её текст, список — без выбора, пока язык не выбран заново.
- Правила 23 → 24 и «Утвердить» не меняются.
- Тесты: unit — список, псевдонимы, сопоставление; DB — выбор по коду, неизвестный код, дубль по коду и по старой строке, старая строка читается без изменений, правка без `code` не трогает язык; e2e этапа «Перевод».
