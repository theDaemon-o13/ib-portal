# Релиз 1.3.0 — этап Д «Самооценка уровня кибербезопасности» (план на «ок»)

Главный документ — `docs/self-assessment.md` (спецификация). Методика — `backend/prisma/seed/assessment-methodology.json`, прототип — `docs/prototype/self-assessment-demo.html`, исходный файл для тестов — `backend/test/fixtures/cyber-checklist-2025.xlsx`.

Правила работы — как в 1.2.0: план до кода, один коммит на задачу и push после каждого; после каждого — typecheck, lint, test, test:db, check:integrity, e2e затронутого (весь e2e — в конце этапа); миграции только расширяют схему и совместимы с backend 1.2.0, у каждой — «Влияние на данные»; документация вместе с кодом; выкладки нет. В конце: VERSION 1.3.0, CHANGELOG, тег v1.3.0, `dist/changes-1.3.0.zip`.

## Д0. Что проверено до плана

- **Методика** (JSON): 10 доменов, 24 раздела, шкала 1–4 («Базовый … Продвинутый»), уровни зрелости 0–43 / 44–66 / 67–85 / 86+, правило `effectiveRequiresMaxIn: 1.2, 4.2, 10.1` с откатом на «Трансформируемую КБ», порог критерия 85%. Сумма максимумов — 96, как в спецификации.
- **Исходный файл** разобран по правилу раздела 9 спецификации (без адресов ячеек): в столбце E 25 строк «Дополнительный комментарий», одна из них — в скрытом дубле «9.3. Технологическая устойчивость» (строка 240) и отсекается по признаку `hidden`. Остаётся 24 ответа: **34 балла, домены 5 / 4 / 5 / 2 / 3 / 5 / 1 / 2 / 6 / 1** — совпадает с эталоном. «Общая информация»: E7 «ЗАО МДО "Хумо"», E9 — дата 07.07.2025 (exceljs отдаёт `Date`), E11, E13, E32 «1800».
- **Подвох exceljs:** у объединённой ячейки с пустым основным значением `cell.text` бросает исключение (`MergeValue.toString` на `null`). Разбор читает значения через безопасную функцию; тест на это — тем же файлом.
- **Системные настройки:** таблица `app_settings` уже есть (`key`, `value jsonb`, `version`, `updated_at`), колонки `updated_by` нет — кто менял, видно в журнале аудита (так уже хранятся `work_week`, `notifications.overdue_since`). Новая таблица не нужна (вопрос 2).
- **Импорт xlsx** в backend уже принимается телом запроса (`addContentTypeParser` для xlsx и octet-stream, как у импорта реестров); multipart и новые зависимости не нужны.
- **Графики** — свои SVG, как на дашборде; режим «на весь экран», клавиши и панель — как у экрана мониторинга. Новых npm-зависимостей нет.

## Противоречия спецификации с текущим кодом — на решение

1. **Задачи по разрывам и права процесса задач (ADR-0022, этап Б).** Ставить задачу другому может только `tasks.assign`; исполнитель — только сотрудник с `ib.work`; список сотрудников (`/users/options`) — только с `ib.work`. Владелец самооценки по спецификации может не иметь ни `ib.work`, ни `tasks.assign`. Предлагаю: задачу по разрыву ставит раздел — право даёт `assessment.manage`, `tasks.assign` не проверяется; исполнитель — активный сотрудник с `ib.work` (как везде); список исполнителей — свой маршрут `GET /assessments/assignees`. Автор задачи — владелец (честно в журнале). Принимает задачу — по обычным правилам ADR-0022: автор, если у него есть `tasks.review`, иначе старшие над исполнителем. Уточните, так ли.
2. **Подпись «Спроектировано».** Спецификация описывает `app_settings(key, value, updated_by, updated_at)`; таблица есть, но без `updated_by`. Предлагаю: ключ `presentation.signature`, значение — текст после «Спроектировано:» (по умолчанию seed один раз ставит «И. Машарипов · Отдел информационной безопасности»), кто менял — в журнале аудита (`setting.updated`). Миграции под это нет. Если нужна колонка `updated_by` — добавлю (только расширение).
3. **Журнал действий и «личный раздел».** Раздел «Журнал» (`audit.view`, по умолчанию «Начальник ИБ» и «Супер-администратор», ADR-0021) показывает все действия. По спецификации каждое изменение ответа пишется в `audit_log` — значит, держатели `audit.view` увидят баллы и комментарии чужой самооценки. Предлагаю: в журнал — код раздела и «было → стало» по баллу и целевому уровню, вместо текста комментария — «комментарий изменён»; полный текст — только в самой оценке. Либо писать всё полностью (журнал — контроль, не раздел). Выберите.
4. **История раздела и право `history.view`.** История в карточках с 1.2.0 — только по `history.view` (ADR-0021). Предлагаю: историю раздела самооценки видит держатель `assessment.manage` без `history.view` — это его собственные данные, а другим раздел не виден.
5. **Физическое удаление пустого черновика.** CLAUDE.md 3.4: физическое удаление — только по праву `*.delete`. Спецификация разрешает удалять пустой черновик держателю `assessment.manage`. Предлагаю не заводить `assessment.delete`: удаляется только черновик, у которого все 24 балла пусты и нет связей, с записью в журнал; остальное — в архив. Отметить исключение в CLAUDE.md 3.4. Или удаления нет совсем, только архив.
6. **«Право не входит ни в одну другую роль».** Сейчас матрица «Роли и права» позволяет выдать любое право любой роли. Предлагаю как с правами согласования документов: `assessment.manage` нельзя выдать роли «Супер-администратор» (409), и `check-integrity` проверяет, что у супер-администратора его нет. Строже — запретить выдачу любой роли, кроме системной «Самооценка» (тогда раздел нельзя «размножить» через свою роль). Выберите.
7. **Импорт: multipart и токен.** Спецификация: `POST /:id/import` multipart и `confirm {token}`. Предлагаю как у импорта реестров: файл — телом запроса (xlsx), без multipart; предпросмотр ничего не пишет; `confirm` присылает разобранные ответы и `version` оценки — backend проверяет их заново по снимку методики, а если оценку успели изменить — 409 и ничего не применяет. Токен и отдельная таблица предпросмотров не нужны; исходный файл в хранилище не сохраняется (раздел личный, а файлы читаются по ссылкам). Если файл нужен как доказательство — сохраню в `files` со ссылкой из оценки.
8. **Источник задачи.** У задач есть `source` (manual, mail, automation, document, evidence), карточка показывает происхождение. Чтобы в карточке не было следа самооценки, предлагаю `source = 'manual'` (миграция `tasks_source_check` не нужна), категория «Самооценка» — по спецификации. Связь — только в `assessment_links`. Запись в журнале о задаче — нейтральная: «Задача #N создана», без названия раздела и баллов.
9. **Напоминание о переоценке (Г5).** «Владельцу роли» — всем активным держателям `assessment.manage`. У `notifications` есть ссылки только на задачу и документ: ссылку «/assessment» беру по виду уведомления (`assessment_reminder`), без новой колонки. Без повторов — `dedupe_key` по дате годовщины.
10. **Имя файла эталона.** В спецификации — `backend/test/fixtures/cyber-checklist-2025.xlsx`, в репозитории — `Chek_list_oczenki_urovnya_kiberbezopasnosti_9b2960eda6.xlsx`. Предлагаю в Д0 переименовать в имя из спецификации (`git mv`).

Миграция `assessments` (SQL ниже), seed: право `assessment.manage` (в `PERMISSIONS`), системная роль «Самооценка» без пользователей (описание «Обычно назначается одному сотруднику»), системное значение «Самооценка» в «Категориях задач», методика `cyber-express-v1` версии 1 (активная; повторный запуск не дублирует).

Все маршруты — `requirePerm('assessment.manage')`. Аудит каждого изменения (по вопросу 3).

## Миграция Д1 `assessments` (черновик SQL; точный — после `--create-only`)

```sql
-- Релиз 1.3.0, этап Д1: самооценка уровня кибербезопасности (docs/self-assessment.md, ADR-0025, ADR-0026).
-- Влияние на данные: четыре новые пустые таблицы; существующие таблицы и строки не меняются. Seed добавляет код права
-- assessment.manage, системную роль «Самооценка» без пользователей, значение «Самооценка» в «Категориях задач» и
-- методику cyber-express-v1. Откат: backend 1.2.0 новые таблицы не читает; незнакомое право в сумме прав не учитывается.

CREATE TABLE "assessment_methodologies" (
  "id" UUID PRIMARY KEY DEFAULT gen_random_uuid(),
  "code" TEXT NOT NULL, "name" TEXT NOT NULL, "version" INTEGER NOT NULL CHECK ("version" >= 1),
  "content" JSONB NOT NULL, "is_active" BOOLEAN NOT NULL DEFAULT false,
  "created_at" TIMESTAMPTZ(3) NOT NULL DEFAULT now(), "archived_at" TIMESTAMPTZ(3),
  UNIQUE ("code", "version")
);
-- Активна одна версия методики.
CREATE UNIQUE INDEX "assessment_methodologies_active_uq" ON "assessment_methodologies" ("code") WHERE "is_active";

CREATE TABLE "assessments" (
  "id" UUID PRIMARY KEY DEFAULT gen_random_uuid(),
  "methodology_id" UUID NOT NULL REFERENCES "assessment_methodologies"("id") ON DELETE RESTRICT,
  "methodology_snapshot" JSONB NOT NULL,
  "title" TEXT NOT NULL CHECK (length(btrim("title")) BETWEEN 1 AND 200),
  "assessed_on" DATE NOT NULL,
  "status" TEXT NOT NULL DEFAULT 'draft' CHECK ("status" IN ('draft', 'final', 'archived')),
  "profile" JSONB NOT NULL DEFAULT '{}',
  "previous_id" UUID REFERENCES "assessments"("id") ON DELETE RESTRICT,
  "result" JSONB,
  "finalized_by" UUID REFERENCES "users"("id") ON DELETE RESTRICT, "finalized_at" TIMESTAMPTZ(3),
  "reopen_comment" TEXT NOT NULL DEFAULT '' CHECK (length("reopen_comment") <= 4000),
  "created_by" UUID NOT NULL REFERENCES "users"("id") ON DELETE RESTRICT,
  "created_at" TIMESTAMPTZ(3) NOT NULL DEFAULT now(), "updated_at" TIMESTAMPTZ(3) NOT NULL DEFAULT now(),
  "version" INTEGER NOT NULL DEFAULT 1, "archived_at" TIMESTAMPTZ(3),
  -- Зафиксированная — с замороженным итогом; черновик — без него (итог считается при чтении).
  CHECK ("status" <> 'final' OR ("result" IS NOT NULL AND "finalized_at" IS NOT NULL)),
  CHECK ("status" <> 'draft' OR "result" IS NULL),
  CHECK (("status" = 'archived') = ("archived_at" IS NOT NULL))
);
-- Одна оценка в работе (правило 10).
CREATE UNIQUE INDEX "assessments_one_draft_uq" ON "assessments" ((true)) WHERE "status" = 'draft';

CREATE TABLE "assessment_answers" (
  "id" UUID PRIMARY KEY DEFAULT gen_random_uuid(),
  "assessment_id" UUID NOT NULL REFERENCES "assessments"("id") ON DELETE RESTRICT,
  "section_code" TEXT NOT NULL,
  "level" SMALLINT CHECK ("level" BETWEEN 1 AND 4),
  "target_level" SMALLINT CHECK ("target_level" BETWEEN 1 AND 4),
  "comment" TEXT NOT NULL DEFAULT '' CHECK (length("comment") <= 4000),
  "updated_by" UUID REFERENCES "users"("id") ON DELETE RESTRICT, "updated_at" TIMESTAMPTZ(3) NOT NULL DEFAULT now(),
  "version" INTEGER NOT NULL DEFAULT 1,
  UNIQUE ("assessment_id", "section_code")
);
-- Ответ меняется только в черновике (правило 9): проверка в сервисе (409) и триггер в БД.
CREATE FUNCTION assessment_answers_draft_only() RETURNS trigger LANGUAGE plpgsql AS $$
BEGIN
  IF (SELECT "status" FROM "assessments" WHERE "id" = NEW."assessment_id") <> 'draft' THEN
    RAISE EXCEPTION 'assessment_answers: ответы меняются только в черновике' USING ERRCODE = 'check_violation';
  END IF;
  RETURN NEW;
END;
$$;
CREATE TRIGGER "assessment_answers_draft_only" BEFORE UPDATE ON "assessment_answers"
  FOR EACH ROW EXECUTE FUNCTION assessment_answers_draft_only();

CREATE TABLE "assessment_links" (
  "id" UUID PRIMARY KEY DEFAULT gen_random_uuid(),
  "answer_id" UUID NOT NULL REFERENCES "assessment_answers"("id") ON DELETE RESTRICT,
  "entity_type" TEXT NOT NULL CHECK ("entity_type" IN ('task', 'evidence', 'document')),
  "entity_id" UUID NOT NULL,
  "created_by" UUID NOT NULL REFERENCES "users"("id") ON DELETE RESTRICT,
  "created_at" TIMESTAMPTZ(3) NOT NULL DEFAULT now(),
  UNIQUE ("answer_id", "entity_type", "entity_id")
);
CREATE INDEX "assessment_links_entity_idx" ON "assessment_links" ("entity_type", "entity_id");
```

Других миграций в этапе не планирую: подпись — в `app_settings` (вопрос 2), задачи — в существующей `tasks` (вопрос 8), уведомление — в существующей `notifications` (вопрос 9).
