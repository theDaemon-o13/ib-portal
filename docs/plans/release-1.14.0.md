# План релиза 1.14.0: системные цепочки автозадач реестров

Задание: `docs/tasks/1.14.0-register-chains.md` (текст владельца от 13.11.2026). Ветка `release/1.14.0` от `v1.13.12`. Режим — `docs/tasks/README.md`: план и сразу работа, вопросы по умолчанию отмечены ★.

Новых npm-зависимостей и кодов прав нет. Миграция одна, только добавляет колонки, ограничение и индекс. Существующие строки не меняются.

**Решение владельца в чате 13.11.2026:** создатель системной цепочки — служебная учётная запись «Портал» (раздел 4.3). Вариант «created_by без NOT NULL» отклонён: 1.13.12 отдаёт `createdBy` через строгую схему, и после отката список цепочек отвечал бы 500.

## 2. Как определить источник задачи

Только по ссылкам, заголовок не разбирается:

- `record_id` задан → `register_records.register_id`;
  - реестр с `system_key = 'vulns'` → `vuln_records.node_id` → `vuln_nodes.group_id` → цепочка группы. У записи «Без группы» узел «Из прежнего реестра» лежит в группе «Без группы», поэтому отдельного правила не нужно;
  - иначе → цепочка реестра;
- `record_id` пуст (сводная задача) → `register_automations.register_id` → цепочка реестра.

Источник не определяется в двух случаях:
- запись реестра `vulns` без строки `vuln_records` (в нормальной базе так не бывает: с 1.5.0 у каждой записи есть узел);
- ★ сводная задача по реестру `vulns`: группы у неё нет. Выбрано по умолчанию: такая задача в цепочку не попадает. Сводных правил у «Уязвимостей» seed не создаёт.

**Dev (13.11.2026):** задач `source = 'automation'` — 0 (35 ручных, 20 по документам), цепочек — 1 ручная. Неопределимых — 0. Для проверок данные создаёт тест и сценарий скриншотов. На проде то же покажет предпросмотр сборки старых задач (раздел 7): там есть список «Источник не определён».

## 3. Цепочки 1.7.0 в коде и что меняется

- Таблица `task_chains`: `number`, `title`, `title_key` (подсказки), `owner_id`, `status` open/closed (CHECK, `closed_at` вместе со статусом), `due_date`, `summary`, `created_by` NOT NULL → `users`, `deleted_at`, `version`. У задачи — `tasks.chain_id`.
- Права: привязать, отвязать и перенести может любой с `ib.work`. Править, закрыть, открыть и удалить — создатель, ответственный или `tasks.assign`.
- Видимость — одна функция `visibleTasksWhere`: с `ib.work` видны все неудалённые задачи, без права — ни одной. Цепочка без видимых задач не показывается.
- Доска (`TasksPage`, `columnEntries`): при «Группировать по цепочкам» задачи одной цепочки в колонке сворачиваются в карточку. Одна задача показывается обычной карточкой. Если задачи цепочки в разных колонках, в каждой колонке своя карточка.
- Фильтр «Цепочка» (`?chainId=`) и панель цепочки (`?chain=`, `ChainPanel`).
- «Найти цепочки среди старых задач» (`chain-discover.ts`, `tasks.assign` или `settings.manage`): только `manual` и `mail` без цепочки, группы с одинаковым ключом от двух задач.
- Подсказки (`chain-suggest.ts`): в расчёте участвуют все открытые цепочки, задачи — только `manual` и `mail`.

Расхождения с заданием и что делаю:
1. `created_by` NOT NULL, а у автоматизации нет пользователя. Создатель — служебная учётная запись «Портал» (решение владельца).
2. На доске системная цепочка сворачивается и при одной задаче в колонке: по тесту п. 10 в «В работе» должна быть карточка цепочки с одной задачей. ★ Выключенная «Группировать по цепочкам» показывает все задачи по одной, в том числе системные: так прочитан п. 5 «без группировки задачи видны по одной, как сейчас». Отдельного списка задач в портале нет, переключатель стоит на доске.
3. Подсказки: системные цепочки исключаются по `kind`. Их задачи и так не участвуют (`source = 'automation'`).
4. Старый поиск цепочек автозадачи не берёт. Для них отдельный блок — раздел 7.
5. ★ Метку «отвязана вручную» в схему не добавляю. Задача, у которой в `audit_log` есть хоть одна запись `task.chain_*`, системой больше не привязывается: её отвязывали, переносили или она была в удалённой ручной цепочке. Новая автозадача привязывается при создании, поэтому вопрос возникает только при сборке старых и при переносе записи.

## 4. Модель данных

### 4.1. Миграция `task_chain_system`

```sql
-- Влияние на данные: три новые колонки в task_chains. У существующих строк kind = 'manual' (значение по умолчанию,
-- в PostgreSQL 16 без перезаписи таблицы), source_type и source_id — NULL. Строки не меняются и не удаляются.
-- Откат на 1.13.12 без отката базы: старый код не читает новые колонки, его новые цепочки получают 'manual'.
ALTER TABLE "task_chains"
  ADD COLUMN "kind" TEXT NOT NULL DEFAULT 'manual',
  ADD COLUMN "source_type" TEXT,
  ADD COLUMN "source_id" UUID,
  ADD CONSTRAINT "task_chains_kind_check" CHECK (
    ("kind" = 'manual' AND "source_type" IS NULL AND "source_id" IS NULL)
    OR ("kind" = 'system' AND "source_type" IN ('register', 'vuln_group') AND "source_id" IS NOT NULL));
CREATE UNIQUE INDEX "task_chains_system_source_uq" ON "task_chains" ("source_type", "source_id")
  WHERE "kind" = 'system' AND "deleted_at" IS NULL;
```

Влияние на данные: 0 изменённых строк, 0 удалённых. `ADD CONSTRAINT` проверяет существующие строки: у них `manual` и NULL, проверка проходит. Откатить можно: колонки, ограничение и индекс снимаются без потери ручных цепочек. Внешнего ключа у `source_id` нет: источник полиморфный, группы и реестры удаляются только мягко.

### 4.2. Название

★ Название вычисляется при чтении из источника: «Уязвимости · <группа>», «Реестр · <название реестра>». В `title` хранится снимок, его обновляет переименование группы или реестра в той же транзакции. Снимок нужен для поиска по названию и для 1.13.12 после отката. `title_key` — `titleKey(title)`, как у ручных.

### 4.3. Служебная учётная запись «Портал»

- Seed `system.portal_user.v1_14_0`, один раз (`seed_markers`): логин `portal-system`, ФИО «Портал», отключена (`is_active = false`), без ролей. Пароль — argon2id от случайных 64 байт, которые сразу забываются: войти нельзя.
- Если такой логин уже занят не ею (нет маркера), seed останавливается с просьбой переименовать пользователя. Так же сделано для ролей.
- В 1.14.0 её нет в «Пользователях и ролях» и в выборе сотрудников. Изменить, включить, сбросить пароль или назначить роль нельзя: 409 `SYSTEM_USER` «Служебную учётную запись портала не меняют». Вход отклоняется как неверный пароль.
- В 1.13.12 после отката она видна как отключённый пользователь. Права она не даёт.
- Новая строка в `users` появляется только из seed. Миграция строк не меняет.

### 4.4. Проверка отката

- Тест `rollback-1.13.12`: схема 1.14.0 с системной цепочкой. Запросы 1.13.12 к `task_chains` через Prisma-клиент со схемой 1.13.12 и разбор ответа его zod-схемой `Chain`: `createdBy` — «Портал», ошибок нет.
- На ibportal-v19check: образ 1.13.12 на базе после migrate 1.14.0 открывает доску, «Цепочки» и панель системной цепочки.
- После отката 1.13.12 может закрыть или удалить системную цепочку. При возврате на 1.14.0 удалённая создастся заново (уникальный индекс только по неудалённым), а закрытая откроется при следующей привязке и до того показывается как открытая.

## 5. Поведение

- **Привязка при создании** (`from-events.ts`): перед вставкой пачки — источник каждой новой задачи и `ensureSystemChain(tx, type, id)`. Это `INSERT … ON CONFLICT ("source_type", "source_id") WHERE kind = 'system' AND deleted_at IS NULL DO NOTHING RETURNING id`, а при конфликте повторное чтение. Если два создания идут одновременно, второе ждёт первое и читает его строку. `chain_id` пишется в той же вставке задачи. В `audit_log` — `task.chain_linked`, «Задача #N добавлена в цепочку «…» автоматически», `user_id = NULL`. При создании цепочки — `task_chain.created`, «Системная цепочка #N «…» создана». Комментарий в открытую задачу цепочку не трогает.
- Напоминания, уведомления и эскалации одного источника попадают в одну цепочку (по умолчанию задания). Эскалацию от напоминания отличает приоритет «Высокий» на карточке.
- **API.** Привязать к системной цепочке, перенести в неё, создать задачу в ней, править, закрыть, открыть и удалить её — 409 `SYSTEM_CHAIN` «Системную цепочку ведёт портал». Отвязать задачу и перенести её в ручную цепочку можно: это любой с `ib.work`, как у ручных.
- **Статус** системной цепочки — всегда «открыта» (в DTO принудительно). В списке у неё `counts.active` и отметка «Нет активных задач». На доске она не видна, если активных задач нет: доска строится из задач.
- **Перенос записи** (`vulns/transfer.service.ts`, «Перенести» и «Перенести выбранные»). В той же транзакции незавершённые задачи перенесённых записей (`completed_at IS NULL`, в том числе архивные), которые лежат в системной цепочке другой группы, переходят в цепочку новой группы. В `audit_log` — `task.chain_moved`, «…перенесена в цепочку «…» автоматически: запись перенесена в группу «…»». Выполненные остаются. Задачи без цепочки и в ручных цепочках не трогаются.
- **Видимость** — `visibleTasksWhere`, как в 1.7.0.
- Процесс, проверка, уведомления и `/me/attention` не меняются.

## 6. Интерфейс

- **Доска.** При включённой группировке системная цепочка в колонке — всегда карточка цепочки. На ней: название, «N задач», «не назначено: K», ближайший срок, «просрочено: M» красным, метки «Реестр» и «авто». В колонке сортируется по ближайшему сроку, вместе с задачами. Раскрытие показывает задачи колонки по сроку, с подзаголовками дат от 8 задач. У каждой — «Взять себе» и переход в карточку. «Взять себе все (K)» → подтверждение «Взять K задач?» → `POST /tasks/take-many`.
- **`POST /tasks/take-many`** `{ tasks: [{id, version}] }` (до 200, `ib.work`): одна транзакция, для каждой задачи тот же `runAction('take')` — те же проверки, переход и запись в журнале. Ошибка на любой задаче — ничего не применяется, в тексте номер задачи.
- **Ручные цепочки** — как сейчас.
- **Панель цепочки** для системной: источник со ссылкой (`/vulns/group/<id>` или `/registers/<id>`), фильтр «Активные / Выполненные / Все», задачи по сроку. Кнопок правки, закрытия и удаления нет.
- **Карточка задачи**, блок «Цепочка»: системная цепочка со ссылкой на источник, «Отвязать» и перенос в ручную цепочку.
- **Страница группы «Уязвимостей» и страница реестра**: «Задачи: N активных» открывает `/tasks?chain=<id>`. Данные — `GET /task-chains/by-source?type=&id=`, без цепочки или без видимых задач ссылки нет.
- **Список «Цепочки»** (`/tasks/chains`): системные с меткой «Системная» и «Нет активных задач».

## 7. Сборка старых автозадач

«Найти цепочки среди старых задач» → блок «Системные цепочки реестров»:
- `POST /task-chains/discover-system/preview`. Берёт задачи `source = 'automation'` без цепочки, в том числе выполненные и архивные, неудалённые и без записей `task.chain_*` в журнале. Показывает группы по источнику: название, есть ли уже цепочка, сколько задач, из них выполненных и архивных. Отдельно — «Источник не определён»: список задач с причиной.
- `POST /task-chains/discover-system/apply` `{ expected: [{ sourceType, sourceId, taskIds }] }`. Одна транзакция, план строится заново. Если не совпал с `expected` — 409 `BULK_CHANGED`. Привязка пачками, в журнале на каждую задачу «добавлена в цепочку «…» автоматически (сборка старых задач)», итог — `task_chain.discovered_system`.
- Повторный запуск ничего не находит: задачи уже с цепочкой.
- Право — как у кнопки 1.7.0: `tasks.assign` или `settings.manage`.
- Миграция и seed задачи не трогают. На проде шаг выполняет владелец после выкладки. Он описан в руководстве, в инструкции DevOps его нет.
