# Портал ИБ: сборка релиза

Для DevOps. Релиз собирается на машине сборки с доступом в интернет, на сервер переносится только готовый архив (раздел 11 `CLAUDE.md`). Установка и обновление на сервере — `docs/runbook/deploy.md` и `RELEASE.md` внутри архива.

Пример — для версии 1.1.0; для другой версии подставить её номер.

## 1. Требования к машине сборки

- Linux x86_64 или Mac (Intel или Apple Silicon). Образы всегда собираются под `linux/amd64`; на Apple Silicon — через эмуляцию buildx, сборка дольше.
- Docker 24+ с `docker buildx` (в Docker Desktop есть). Проверка: `docker version`, `docker buildx version`.
- `git`, `bash`, `gzip`, `tar`, `shasum` (на Linux — из пакета `perl`).
- Доступ к GitHub (репозиторий), реестру npm (`registry.npmjs.org`) и Docker Hub (базовые образы `node`, `nginx`, `postgres`).
- Около 20 ГБ свободного места: кэш сборки Docker, три образа и архив. В Docker Desktop место берётся из его диска (Settings → Resources).
- Node.js на машине сборки не нужен: всё собирается внутри Docker.

## 2. Сборка

```bash
git clone https://github.com/theDaemon-o13/ib-portal.git
cd ib-portal
git checkout v1.1.0                       # тег релиза; HEAD отсоединён — так и должно быть
cat VERSION                               # ожидается: 1.1.0
./deploy/scripts/make-release.sh
```

Скрипт:

1. Проверяет, что рабочее дерево чистое и тег `v<VERSION>` стоит на текущем коммите (иначе — предупреждение; для настоящего релиза его быть не должно).
2. Собирает `ibportal-db`, `ibportal-backend`, `ibportal-frontend` под `linux/amd64` и проверяет: архитектуру, что процессы не от root, что в образах нет лишнего, что в подпись интерфейса попали версия и коммит.
3. Сохраняет образы, копирует файлы эксплуатации, создаёт `RELEASE.md` (изменения, миграции с «Влияние на данные», новые переменные `.env`, команды обновления и отката), считает контрольные суммы.

Любая ошибка (`ОШИБКА: …`) останавливает сборку — архив не передавать, сообщить разработчику текст ошибки. Повторная сборка той же версии — с `--force`.

Предыдущий тег (`v1.0.1`) нужен для раздела миграций в `RELEASE.md`; `git clone` получает теги сам. Если клон неполный (`--depth`), сначала `git fetch --tags --unshallow`.

## 3. Что получится в `dist/`

| Файл | Назначение |
|---|---|
| `dist/ibportal-1.1.0.tar.gz` | Архив релиза — **передаётся администратору сервера** |
| `dist/ibportal-1.1.0.tar.gz.sha256` | Контрольная сумма архива — **передаётся вместе с ним** |
| `dist/ibportal-1.1.0/` | Та же папка в распакованном виде, для проверки |

Внутри архива: `ibportal-images-1.1.0.tar.gz` (три образа), `docker-compose.yml`, `docker-compose.restoretest.yml`, `.env.example`, `scripts/` (backup, restore, restore-test, smoke), `docs/deploy.md`, `docs/user-guide.md`, `CHANGELOG.md`, `RELEASE.md`, `SHA256SUMS`. Исходников и секретов в архиве нет.

Проверка на машине сборки:

```bash
cd dist
shasum -a 256 -c ibportal-1.1.0.tar.gz.sha256              # на Linux можно sha256sum -c; ожидается: OK
(cd ibportal-1.1.0 && shasum -a 256 -c SHA256SUMS)          # все файлы: OK
less ibportal-1.1.0/RELEASE.md
```

В `RELEASE.md` проверить: «Предыдущая версия» — 1.0.1; у каждой миграции есть «Влияние на данные» и ни одна не удаляет данные; «Новые переменные .env» — нет. Если что-то не так — архив не передавать (раздел 11A `CLAUDE.md`).

## 4. Проверка на тестовом стенде до прода

Стенд — отдельный хост или ВМ с Docker, не продуктивный сервер. Установка — по `docs/deploy.md` из архива, теми же командами, что на проде.

**Обновление 1.0.1 → 1.1.0** (главная проверка — так будет на проде):

1. Установить 1.0.1 из архива `ibportal-1.0.1.tar.gz` (тот, что стоит на проде) по его `docs/deploy.md`, разделы 2–5.
2. Завести данные: войти, загрузить отчёт сканера в «Реестр уязвимостей», создать пару задач, документ, доказательство с PDF. Если регламент банка позволяет — вместо этого восстановить копию прода (`./scripts/restore.sh`).
3. Обновить по `RELEASE.md` из архива 1.1.0 по шагам: `smoke.sh --before`, `backup.sh`, новые `docker-compose.yml` и `scripts/`, `VERSION=1.1.0` в `.env`, `migrate`, `up -d backend frontend`, `smoke.sh --after`.
4. Проверить:
   - [ ] `migrate` завершился без ошибок: применены 6 миграций 1.1.0, в конце — «Seed выполнен: …».
   - [ ] `./scripts/smoke.sh --after` — «Smoke-проверка пройдена», число записей не уменьшилось.
   - [ ] **Подпись версии:** на странице входа, внизу меню слева и в окне «О портале» (щелчок по подписи) — «Портал ИБ 1.1.0», **без «dev»**; в окне «О портале» коммит совпадает с `git rev-parse --short v1.1.0^{commit}`.
   - [ ] Данные из шага 2 на месте; у записей уязвимостей из отчёта заполнен «Отдел».
   - [ ] Экран мониторинга показывает слайды; «Настройки → Экран мониторинга» открывается.
   - [ ] `docker compose logs --since 10m backend migrate` — без ошибок и попыток обратиться в интернет.
5. Откат: по разделу «Откат» `RELEASE.md` вернуть `VERSION=1.0.1`, `docker compose up -d backend frontend`, `./scripts/smoke.sh` — пройдена, подпись «1.0.1».

**Установка с нуля** (по желанию, если на стенде есть место): чистые тома, разделы 2–5 и 9 `docs/deploy.md` с архивом 1.1.0, подпись «1.1.0» без «dev», `smoke.sh` пройдена.

Результаты стенда (что проверено, имя копии, замечания) передать разработчику вместе с подтверждением, что архив можно ставить на прод. Выкладка на прод — по `RELEASE.md`, запись в `docs/runbook/deploy-log.md` — по данным администратора.
