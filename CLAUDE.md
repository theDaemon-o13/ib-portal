# Портал ИБ — инструкция для Claude Code

Этот файл читается в начале каждой сессии. Он задаёт архитектуру, правила безопасности данных и порядок работы. Если задача противоречит правилам из разделов 3 и 9, остановись и спроси.

Сопутствующие документы:
- `docs/concept.md` — функциональная концепция: модули, бизнес-правила, открытые вопросы.
- `docs/prototype/portal-demo.html` — интерактивный прототип интерфейса. Это эталон внешнего вида и пользовательских сценариев, а не код для переноса.

**Про прототип.** Всё, что в нём есть «для демо», в продукт не переносится:
- переключатель «Демо: войти как» в меню слева нужен только для показа ролей; в продукте текущий пользователь определяется входом в систему (логин и пароль);
- список пользователей, задачи, документы, уязвимости и доказательства в прототипе — примерные данные;
- данные прототипа живут в памяти вкладки; в продукте всё хранится в базе данных.

Список пользователей в «Настройки → Пользователи и роли» — это реальная функция продукта: там администратор заводит учётные записи и назначает роли.

## 1. Что строим

Внутренний портал отдела информационной безопасности ЗАО «Хумо». Работает в закрытом контуре банка, без доступа в интернет. Ядро — конструктор реестров. Поверх него работают дашборд, экран мониторинга, задачи, документы с согласованием, риски ИБ и доказательная база.

С RISK CONSOLE портал не интегрируется. С AD и FreeIPA тоже: доступ строится по собственной модели RBAC внутри портала (раздел 5).

**Внешних интеграций нет** (решение владельца проекта 27.10.2026). Портал работает на закрытом хосте сам по себе: не отправляет и не читает почту (MDaemon), не интегрируется с PT AF и API OnlyOffice, не обращается к внешним сервисам и интернету во время работы — ни CDN, ни обновлений, ни телеметрии, ни проверок лицензий. E-mail в справочниках хранится только для справки.

## 2. Архитектура: три изолированные зоны

```
 браузер ──HTTPS──▶ [frontend]  nginx: статика SPA + прокси /api
                        │  сеть "front"
                        ▼
                    [backend]   Node.js API: вся логика, права, файлы
                        │  сеть "back" (internal, без выхода наружу)
                        ▼
                    [db]        PostgreSQL
 тома:  ibportal_pgdata ──▶ db       ibportal_files ──▶ backend
```

| Зона | Что внутри | Что ей запрещено |
|---|---|---|
| **frontend** | React SPA, собранная в статику; nginx | Ходить в БД и файловое хранилище. Хранить бизнес-данные (только UI-состояние в localStorage). Проверка прав в UI только прячет кнопки, решает всегда backend |
| **backend** | REST API `/api/v1`, проверка прав, бизнес-правила, импорт и экспорт Excel, файлы | Отдавать файлы мимо проверки прав. Подключаться к БД под владельцем схемы (кроме команды миграции) |
| **db** | PostgreSQL, схема и данные | Публиковать порт наружу. Быть доступной из сети `front` |

Зоны связаны только контрактами: frontend ↔ backend через OpenAPI, backend ↔ db через миграции. Изменение в одной зоне не должно требовать одновременного изменения другой. Если требует, сначала меняется backend с обратной совместимостью, потом frontend.

### Стек по умолчанию

Отступать от стека можно только после согласования с владельцем проекта.

- **Backend:** Node.js 24 LTS (ADR-0004; Node 20 снят с поддержки 30.04.2026), TypeScript (strict), Fastify, Prisma 7 (ADR-0014; клиент через `@prisma/adapter-pg`, адрес БД — в `prisma.config.ts`), zod для валидации, `@fastify/swagger` для OpenAPI, exceljs для Excel, argon2 для паролей, pino для логов.
- **Frontend:** React 18, Vite, TypeScript (strict), React Router, TanStack Query. Типы API генерируются из OpenAPI (`openapi-typescript`) и вручную не правятся. pdf.js для просмотра PDF.
- **БД:** PostgreSQL 16.
- **Контейнеры:** Docker и Docker Compose v2.

**Закрытый контур.** Никаких внешних CDN, Google Fonts и внешних API во время работы. Шрифты (Inter как замена SF Pro на Windows), pdf.js и иконки входят в сборку. Новые npm-зависимости добавляются только после согласования, потому что их нужно будет собрать на машине с доступом к реестру.

## 3. Сохранность данных — обязательные правила

Данные банка важнее скорости разработки. Эти правила действуют в любой задаче.

### 3.1. Запрещено без явного письменного подтверждения в чате

- `docker compose down -v`, `docker volume rm`, `docker volume prune`, `docker system prune --volumes`;
- `prisma migrate reset`, `prisma db push`, любой флаг `--accept-data-loss`;
- `DROP`, `TRUNCATE`, `DELETE` или `UPDATE` без `WHERE` на любой базе, кроме одноразовой тестовой (`*_test`) и одноразовой теневой (`*_shadow`);
- теневая база Prisma (`shadowDatabaseUrl`, `--shadow-database-url`), указывающая на существующую базу: Prisma очищает теневую базу целиком. Теневая база — только отдельная одноразовая с именем на `_shadow`, которую скрипт сам создаёт и удаляет (`npm run check:schema`; при другом имени скрипт отказывается работать);
- правка уже применённых файлов в `backend/prisma/migrations/`;
- удаление файлов в хранилище и в каталоге резервных копий;
- любые действия с `deploy/.env`, сертификатами и продуктивным сервером.

Если задачу нельзя решить без такого действия, опиши, что именно будет удалено, и предложи сначала сделать резервную копию.

### 3.2. Тома не управляются Compose

Тома `ibportal_pgdata`, `ibportal_files` и `ibportal_backups` создаются один раз вручную (раздел 10) и объявлены в compose как `external: true`. Поэтому `docker compose down` и даже `down -v` их не удаляют. Не меняй это объявление.

### 3.3. Миграции только вперёд, по схеме «расширить → перенести → сузить»

1. Схема меняется только миграциями Prisma. Сначала `prisma migrate dev --create-only --name <что_меняем>` на dev-базе, затем чтение и проверка SQL, затем применение.
   - `prisma migrate dev --create-only` перед созданием новой миграции применяет все неприменённые, в том числе пустые. Поэтому миграции создаются по одной: следующую — только после того, как SQL предыдущей окончательно написан и проверен. Пустых заготовок в `migrations/` не оставлять.
2. Каждая миграция совместима с предыдущей версией backend. Тогда откат приложения не требует отката базы.
3. Переименование или удаление колонки разбивается на релизы. Сначала новая колонка и перенос данных. Только в следующем релизе, после подтверждения, удаляется старая.
4. В описании PR и в `CHANGELOG.md` у каждой миграции есть строка «Влияние на данные»: что меняется, сколько строк затронет, можно ли откатить.

### 3.4. Удаление в бизнес-сущностях — мягкое

- Задачи, записи реестров, документы, доказательства и значения справочников архивируются (`archived_at`) или помечаются удалёнными (`deleted_at`).
- Физическое удаление выполняется только по праву `*.delete`, только для записей без зависимостей, и всегда пишется в журнал аудита. Оценки самооценки не удаляются никогда — только архив.
- Удаление реестров, групп и узлов уязвимостей, записей (1.6.1, ADR-0033) — мягкое, событием в `deletions` (кто, когда, причина, сколько скрыто): всё скрытое получает `deletion_id` и восстанавливается вместе с ним из «Настройки → Корзина» (только супер-администратор). Событие не меняется (триггер), кроме однократного восстановления.
- Значения справочников, которые уже используются, не удаляются, а уходят в архив.

### 3.5. Журнал аудита

- Таблица `audit_log` только пополняется: `at`, `user_id`, `action`, `entity`, `entity_id`, `diff` (jsonb), `ip`.
- У роли приложения в БД нет прав `UPDATE` и `DELETE` на эту таблицу.
- История изменений в карточках (задача, запись реестра, документ, доказательство) строится из этого журнала или из отдельных таблиц истории, но никогда не перезаписывается.
- Журнал читается в разделе «Журнал» по праву `audit.view`, история в карточках — по `history.view` (ADR-0021). Раздел только читает `audit_log`.

### 3.6. Две роли в PostgreSQL

| Роль | Права | Где используется |
|---|---|---|
| `ibportal_owner` | Владелец схемы, DDL | Только команда миграции (сервис `migrate`) |
| `ibportal_app` | `SELECT`, `INSERT`, `UPDATE`, `DELETE` на таблицы данных; на `audit_log` только `INSERT` и `SELECT` | Работающий backend |

Права выдаются скриптом `db/init/01-app-role.sh` при первой инициализации и закрепляются через `ALTER DEFAULT PRIVILEGES`. Права приложения выдаются групповой роли `ibportal_app` (NOLOGIN); логин backend (`DB_APP_USER`) — её член. Запрет `UPDATE`, `DELETE`, `TRUNCATE` на `audit_log` выдаётся первой миграцией и дублируется триггером (ADR-0002).

### 3.7. Файлы

- Файлы хранятся в томе `ibportal_files` по пути `/data/files/<yyyy>/<mm>/<uuid>`. Исходное имя файла в пути не используется.
- Метаданные лежат в БД: исходное имя, MIME, размер, sha256, кто и когда загрузил, к чему привязан.
- Выдача файлов идёт только через backend, с проверкой прав и `Content-Disposition`.
- Действуют ограничения: размер (по умолчанию 25 МБ) и список разрешённых типов (pdf, png, jpg, txt, csv, xlsx, docx).
- Файл не удаляется физически, пока на него ссылается хоть одна запись.

### 3.8. Dev никогда не трогает prod

- Dev-окружение запускается отдельным compose-проектом `ibportal-dev` со своими томами `ibportal_dev_*`.
- Скрипт демо-данных `npm run seed:demo` отказывается работать, если `NODE_ENV=production` или имя базы не оканчивается на `_dev`.
- `npm run test:db` пересоздаёт только базу, имя которой оканчивается на `_test`, и отказывается работать при `NODE_ENV=production`.

## 5. Доступ: RBAC

Аутентификация своя: логин и пароль портала. Интеграции с AD и FreeIPA нет.

### Модель

- Таблицы: `users`, `roles`, `permissions`, `role_permissions`, `user_roles`, `sessions`.
- Пользователь получает сумму прав всех своих ролей.
- Иерархия (ADR-0020): у пользователя поле «Руководитель» (`users.manager_id`); «старшие» — вся цепочка руководителей выше. Руководители и подчинённые — только пользователи с `ib.work`; цикл запрещён в backend и триггером в БД.
- Права — фиксированный список кодов в seed. Роли и их состав настраиваются в интерфейсе.
- Права, добавленные в обновлении, системным ролям выдаёт один раз шаг seed (`PERMISSION_GRANTS` в `lib/permissions.ts`): снятое администратором при следующем обновлении не возвращается.

| Код права | Что разрешает |
|---|---|
| `ib.work` | Разделы ИБ: дашборд, мониторинг, реестры, задачи, доказательства. Без этого права пользователь видит только «Документы» |
| `records.edit` | Добавление и правка записей реестров, импорт Excel |
| `records.delete` | Удаление записей реестров (мягкое, раздел 3.4) |
| `registers.manage` | Конструктор реестров: создание и архив реестров, поля, значения списков, смена типа поля. Раздел «Уязвимости»: создание и переименование группы, «Добавить тип» (1.5.0) |
| `tasks.delete` | Удаление задач (архивировать может любой с `ib.work`) |
| `tasks.assign` | Назначать исполнителем любого сотрудника ИБ; без права — только себя (релиз 1.2.0) |
| `tasks.review` | Не используется с 1.4.0 (ADR-0028): принимает проверяющий — руководитель исполнителя. Действует только для задач, отправленных до 1.4.0 без проверяющего. Код и строки в БД остаются ради отката на 1.3.0; убрать из матрицы — следующим релизом после согласия владельца |
| `tasks.status.override` | Перетаскивание карточек и смена статуса в обход процесса (1.2.0); «Заменить проверяющего». Из «На проверке» — только проверяющий; в «Выполнено» из других колонок — только без руководителя у исполнителя (1.4.0) |
| `tasks.report` | Отчёт по задачам в Excel (1.2.0); страница «Задачи → Отчёт» — выполненные задачи с иллюстрациями и списком (1.6.4) |
| `vulns.deadlines` | «Уязвимости: изменение сроков» (1.5.0, ADR-0030): продление сроков по обоснованию ОИКТ и отмена продления. Никому не выдаётся автоматически (ни одной системной роли, в том числе «Супер-администратору»), назначается в матрице |
| `data.delete` | «Удаление данных» (1.6.1, ADR-0033): удаление реестров, групп и типов систем в «Уязвимостях» и записей уязвимостей — мягко, в корзину. Никому не выдаётся автоматически, назначается в матрице. Записи остальных реестров — `records.delete` |
| `evidence.review` | Принять или отклонить доказательство |
| `docs.manage` | Создание документов, запуск пересмотра, отправка на согласование за автора |
| `docs.delete` | Мягкое удаление неподписанного документа; подписанный — только в архив (1.2.0) |
| `docs.approve.head` | Не используется с 1.4.0 (ADR-0027): этапы начальника ИБ — по отметке «Является начальником ИБ». Код и строки в БД остаются ради отката на 1.3.0; убрать из матрицы — следующим релизом после согласия владельца |
| `settings.manage` | Справочники и шаблоны форм |
| `users.manage` | Пользователи, роли и права |
| `history.view` | История изменений в карточках задач, записей реестров, документов и доказательств (1.2.0) |
| `audit.view` | Раздел «Журнал»: все действия пользователей из `audit_log`, выгрузка в Excel (1.2.0) |
| `monitor.kiosk` | Настенный монитор: только `/monitor`. Не сочетается с другими правами и ролями; вход только с `MONITOR_ALLOWED_IPS`; без завершения по бездействию, абсолютный срок 7 суток — только у этой роли и только с `MONITOR_ALLOWED_IPS`; сессии закрываются при смене пароля и при снятии роли или права (ADR-0012, изменение 1.2.0). У остальных — 12 часов |
| `assessment.manage` | Раздел «Самооценка» целиком (этап Д, ADR-0026). Только в системной роли «Самооценка»: другой роли не выдаётся (409, ячейка матрицы заблокирована), с этой роли не снимается; не входит в «Супер-администратора»; открывает раздел без `ib.work`. Роль seed никому не назначает |

Системные роли из seed: «Супер-администратор», «Сотрудник ИБ», «Начальник ИБ», «Читатель документов» (без прав: видит подписанные документы и их файлы), «Настенный монитор», «Самооценка» (только `assessment.manage`, никому не назначена; «Обычно назначается одному сотруднику»), «SOC» (релиз 1.4.0: права «Сотрудника ИБ» — `ib.work`, `records.edit`, `evidence.review`; никому не назначена). Если до обновления уже заведена своя роль с названием новой системной, seed останавливается с просьбой переименовать её.

Роли «Юрист» и «Правление» и коды `docs.approve.legal`, `docs.approve.board` выведены из обращения в 1.2.0 (ADR-0024): их пользователей seed переводит в «Читатель документов» при каждом `migrate`; в интерфейсе и коде их нет, назначить нельзя; строки в БД остаются до 1.3.0 ради отката на 1.1.0.

### Правила

- Права проверяются только на backend, хуком `requirePerm('<код>')` у каждого маршрута. Маршрут без явного права не проходит ревью.
- Нельзя снять `users.manage` с последнего активного пользователя, у которого оно есть, и нельзя снять его с себя.
- У системной роли «Супер-администратор» права `settings.manage` и `users.manage` не снимаются.
- Права согласования этапов (`docs.approve.*`) не входят в роль супер-администратора. Он не согласует за других: так сохраняется разделение полномочий.
- **Начальник ИБ — отметка у пользователя** (`users.is_ib_head`, релиз 1.4.0, ADR-0027), а не право: не больше одного пользователя (уникальный индекс в БД); только активный, с `ib.work`, без роли «Супер-администратор» (409 в обе стороны). Ставит `users.manage`, себе — нельзя (409), снять свою или передать — можно; у другого — «Передать от <ФИО>?», передача одной транзакцией с записью в журнал; отключение снимает отметку. Seed отметку никому не ставит.
- Пароли:
  - хранятся как argon2id;
  - длина не менее 12 символов, не менее 3 классов символов;
  - после 5 неудачных попыток вход блокируется на 15 минут;
  - нельзя повторять последние 5 паролей;
  - срок действия пароля — 90 дней, после него смена обязательна (`users.password_changed_at`);
  - при первом входе и после сброса пароль обязательно меняется;
  - временный пароль при создании пользователя и сбросе генерирует портал по этой политике; он показывается администратору один раз и нигде не хранится в открытом виде (ни в БД, ни в журнале аудита, ни в логах).
- Портал должен соответствовать инструкции по парольной защите (шаблон формы «Парольная защита» в доказательной базе). MFA для привилегированных учётных записей не делается (ADR-0006 отклонён 28.10.2026: портал работает только во внутренней сети). Компенсирующая мера (ADR-0015): пользователь с `settings.manage` или `users.manage` входит только с адресов `ADMIN_ALLOWED_IPS` — проверка при входе и на каждом запросе, отказ во входе целиком, ответ как на неверный пароль; пусто — без ограничения. `create-admin` из консоли сервера работает без ограничения.
- Сессия хранится на сервере, в таблице `sessions`. Cookie: `HttpOnly`, `Secure`, `SameSite=Strict`. Неактивная сессия завершается через 30 минут. Сессию продлевают только действия пользователя: фоновые запросы страницы (опрос по таймеру) идут с `X-Background: 1` и её не продлевают; за 2 минуты до завершения — предупреждение «Продолжить работу», после — вход с объяснением и возврат на ту же страницу (ADR-0023). Настенный монитор по бездействию не завершается (ADR-0012).
- «Настройки → Параметры портала» (1.6.0) — не право, а системная роль «Супер-администратор» (`requireSuperAdmin`): право `settings.manage` доступа не даёт.
- Первый администратор создаётся командой из раздела 10, а не миграцией.
- Вход, выход, неудачные попытки и изменения прав пишутся в журнал аудита.

## 6. Предметная модель (кратко)

- **Справочники:** `catalogs` и `catalog_items` (значение, цвет-тон, системное, `archived_at`, `deleted_at`, `version`). Сущности ссылаются на значения справочников по `id`, а не по тексту, поэтому переименование ничего не ломает (ADR-0005).
  - Состав: категории задач, статусы задач — колонки доски (пять системных колонок процесса только переименовываются; свои колонки добавляются; признаки «комментарий при переходе вперёд / при возврате», ADR-0022), приоритеты, правила разбора почты (ключевые слова и ответственный), системы (владелец системы), типы систем (узлы раздела «Уязвимости», 1.5.0), типы документов, получатели уведомлений (метка → участники `catalog_item_users` — только пользователи с `ib.work` — и e-mail).
  - Производственный календарь РТ — отдельная таблица `work_calendar_days` (праздники и переносы); выходные дни недели — настройка `app_settings.work_week`, по умолчанию пятидневка. Расчёт — `backend/src/lib/working-days.ts`.
  - Стартовые значения seed создаёт один раз (отметки в `seed_markers`): удалённое или архивированное администратором не восстанавливается.
  - «Используется ли значение» модули сообщают через `modules/settings/usage.ts`; используемое значение только архивируется.
- **Конструктор реестров** (ADR-0007):
  - `registers` (`next_number` — номер записи, он же колонка ID в Excel; `archived_at`);
  - `register_fields`: тип, порядок, роль для аналитики, `is_title` (заголовок записи), `is_status` (статус), правило вычисления `calc_rule`, `archived_at`, `deleted_at`;
  - `register_field_options`: значения списков и решений, `is_closed` (закрытый статус), архив;
  - `register_records`: `values jsonb` — `{ id поля: значение }`, списки — по `id` значения; `search_text`, `version`, `archived_at`, `deleted_at`;
  - `register_decisions`: решения другого отдела с документом-основанием, только пополняется (как `audit_log`); файл документа — этап 7;
  - `register_imports`: предпросмотр импорта Excel до применения;
  - `register_automations` и `automation_events`: автоматизации «условие → действие» (этап 4); событие превращается в задачи получателям (`automation_event_tasks`, этап 5).
  - Типы полей: текст, список, число, дата, сотрудник, вычисляемое, решение другого отдела, значение справочника (`catalog_code`; в `values` — id значения справочника). Вычисляемое поле и решение в `values` не хранятся: форма и импорт их не перезаписывают.
  - Поле с данными не удаляется, только архивируется. Смена типа поля с данными — только «в текст» и «из текста в число, дату или список, если все значения распознаются», всегда с предпросмотром и записью в журнал.
- **Карточка записи** строится на frontend из описания полей, отдельный код под каждый реестр не нужен.
- **Уязвимости** (1.5.0, ADR-0029, ADR-0030; `docs/specs/vulnerabilities.md`): одна структура полей — системный реестр конструктора `vulns`; записи и сканы принадлежат узлу «группа × тип систем».
  - `vuln_groups` (вид «Сервис» / «Подразделение»; системная «Без группы» — «Временная»), `vuln_nodes` (группа × значение справочника `system_types`; в «Без группы» — узел «Из прежнего реестра»);
  - `vuln_records` (запись узла: `key_norm` «пакет + идентификатор» уникален в узле, скан срока, первый и последний скан, цикл), `vuln_record_scans` (в каких сканах встречалась; только пополняется);
  - `vuln_scans` (дата, файл, охват, снимок строк, сравнение, передача ИКТ — один раз; не меняется, триггер); отчёты 1.1.0–1.4.0 (`scan_reports`, `scan_hosts`) — сканы «Без группы» через `legacy_report_id`;
  - `vuln_extensions`, `vuln_extension_items` — продления по обоснованию ОИКТ; только пополняются, отмена — один раз;
  - служебные поля реестра: «Уведомлено ДИКТ» (дата передачи ИКТ), «Срок из прежнего реестра», «Продлено, дн.» — их ставит только портал (форма, обратный импорт и массовые действия — 409 `VULN_SERVICE_FIELD`).
- **Активы** (1.6.0, ADR-0031, ADR-0032; `docs/specs/assets.md`): системные реестры конструктора «Сервисы» (продукты), «Компоненты» и «Хосты», без своих таблиц. Служебные поля «Ключ компонента», «ОС / ПО в источнике», «Покрытие защиты» ставят только адаптеры импорта (409 вручную). Адаптеры (`?adapter=services|ksc`) готовят лист для общего конвейера импорта; сведения об источнике — `register_imports.summary.source`. Разбор XML — `saxes`, DTD и сущности отклоняются. Сверка считается при запросе; параметры — `app_settings.assets*` («Параметры портала»).
- **Задачи:** `tasks` (статус, приоритет и категория — по `id` значений справочников; `archived_at`, `deleted_at`, `completed_at`; `reviewer_id` — проверяющий задачи «На проверке», ADR-0028; у задач автоматизаций — запись, правило и метка получателя; у задач документа — `document_reason` `review` / `returned` / `stage` и `document_state` — состояние маршрута задачи этапа, 1.6.3, ADR-0034; `task_candidates` — кто может взять общую задачу, 1.6.4), `task_comments` (`transition_id` — комментарий перехода), `task_transitions` (переходы между колонками: кто, когда, откуда, куда, комментарий, `reviewer_id` — зафиксированный проверяющий; только пополняется, ADR-0022), исходное письмо (`task_mail_sources`), история — из `audit_log`. Колонка открытой задачи согласована с исполнителем: без исполнителя — Backlog, с исполнителем в начале процесса — «Поставленные».
- **Документы** (ADR-0010, маршрут — ADR-0024): `documents` (тип, владелец, цикл, `review_due`, ссылки на подписанную и рабочую версии, `deleted_at`), `document_versions` (номер, редакция, ссылка OnlyOffice, этап 11–16 (до 1.2.0 — 0–3), круг, `signed_on`, `cancelled_at`; утверждённая не меняется — триггер), `document_approvals` (кто, когда, этап, `to_stage`, решение, комментарий, версия, `self_approved`; только пополняется), `document_files` (файлы драфта, зафиксированные файлы версии по кругам и ответы лиц; не удаляются), `document_comments` (комментарии сотрудников на этапе 12), `document_parties` (ответственные лица этапа 14), `document_translations` (языки этапа 15: переводчик — текстом `translator_name`, 1.4.0), `document_deadline_changes` (история сроков лиц и переводов, только пополняется), `document_blockers` (блокеры; снятие — один раз). Пересмотр — через `automation_events.document_id` → задачи (`tasks.document_id`, `document_reason`).
- **Риски ИБ:** отдельно от рисков банка, связь с реестром ОУР по номеру. Решение ОУР сохраняется только с документом-основанием.
- **Доказательства:**
  - `evidence`;
  - `evidence_files` (ссылка на `files`);
  - `form_templates` и `form_template_fields` (тип проверки: «не менее», «не более», «да/нет», «текст»);
  - снимок полей и значений формы в `evidence.checks jsonb`, чтобы правка шаблона не меняла старые формы.
- **Файлы:** `files` (раздел 3.7).
- **Уведомления:** `notifications` (адресат, вид, снимок текста, задача или документ, кто сделал, `dedupe_key`, `read_at`) — видит только адресат; служебные строки: прочитанные старше 90 дней и непрочитанные старше 180 удаляет фоновая очистка (ADR-0023).

## 7. Бизнес-правила, которые обязательно покрыты тестами

Тесты лежат рядом с кодом (`*.test.ts`, vitest). Изменение правила без изменения теста не принимается.

1. **Оценка уязвимости (п. 7.1).**
   - Формула: `Оценка = CVSS × Кэ × Ки`, округление вверх до 0,1.
   - Кэ = 1,00, если эксплойт «есть, эксплуатируется»; 0,94, если «есть»; 0,91 в остальных случаях.
   - Ки = 0,95, если исправление выпущено; 1,00, если нет.
   - Нет CVSS — Оценка пустая, Критичность «Высокая».
2. **Критичность по Оценке:**
   - ≥ 9,0 — «Критическая»;
   - ≥ 7,0 — «Высокая»;
   - ≥ 4,0 — «Средняя»;
   - иначе — «Низкая».
   - Сотрудник ИБ может поправить её вручную с учётом критичности системы и доступности из интернета; ручное значение не перетирается пересчётом.
3. **Сроки устранения (п. 7.2, ADR-0030).** Считаются в календарных днях от даты передачи отчёта ИКТ (действие у скана, не импорт): Критическая — 14, Высокая — 30, Средняя — 90, Низкая — 180; окончание на выходном переносится на ближайший рабочий день по производственному календарю. До передачи срока нет — статус «Не передано ИКТ».
   - Итоговый срок = решение п. 7.3, если оно есть; иначе перенос((срок из прежнего реестра ?? передача ИКТ + дни) + сумма действующих продлений). Ручная Критичность пересчитывает базу.
   - Срок идёт от первого переданного ИКТ скана (по времени передачи), в котором запись встречалась после последнего открытия; поздняя передача более раннего скана и повторные сканы его не сдвигают.
   - Повторное обнаружение устранённой записи: открывается заново (новый цикл), передача ИКТ, срок из прежнего реестра, продления и решение п. 7.3 снимаются с записью в истории. «Риск принят» при новом скане не открывается.
   - Просрочка, уведомления и эскалации п. 7.4, дашборд, монитор, фильтры и Excel — по итоговому сроку, по всем узлам (одна функция `calcValue`).
4. **П. 7.3.** Если заполнены «Компенсирующие меры» и «Срок после пересмотра ИБ», срок берётся из решения ИБ; оно главнее продлений.
5. **П. 7.4.** По истечении срока уведомляются руководитель отдела ИКТ и владелец системы. Если мер нет 10 рабочих дней (по производственному календарю), запись эскалируется руководству и попадает в отчётность.
6. **Импорт отчёта сканера (1.5.0, ADR-0029).** Только в узел, не в «Без группы»; разбор по содержимому: лист хостов — где в первых 12 строках есть «Имя хоста», строка над заголовком — охват; листы находок — все с «Пакет» и «CVE» / «Идентификатор», объединяются. «Оценка» из файла не используется. Дата скана — из имени файла (`ГГГГ_ММ_ДД`, `-`, `.`), правится в предпросмотре.
   - Ключ записи — «Пакет + Идентификатор» (без регистра и лишних пробелов), одна запись на ключ в узле. Повтор ключа в файле объединяется, «Обнаружений» — по максимуму. Без пакета или идентификатора — строка пропускается; CVSS не число — пустой; обе — с сообщением.
   - Предпросмотр сравнивает с узлом: новые (выбраны), повторно обнаружены — были «Устранена» (выбраны), изменились — Уровень, CVSS, Эксплойт, Сетевой вектор, Обновить до версии, Обнаружений (выбраны), без изменений, пропали — открытые записи узла не в файле (не выбраны; выбранные — «Устранена» со ссылкой на скан); плюс охват — новые и выбывшие хосты против прошлого скана узла. Применение — выбранное, одной транзакцией; если записи или поля изменились после предпросмотра — ничего.
   - Скан хранит файл, охват, снимок строк и сравнение; не удаляется и не редактируется. «Система» в окне импорта необязательна, предзаполняется из прошлого импорта узла.
   - Профиль (1.6.0, `docs/specs/vulnerabilities.md`, 2а): значение «Типов систем» в имени файла отдельным словом, два — профиля нет. Не совпал с типом узла — применение только с подтверждением (409 `PROFILE_NOT_CONFIRMED`), факт — в `comparison.profileMismatch` и журнале.
   - Поле «Отдел» новые импорты заполняют охватом скана (для отката на 1.1.0); дубли по отделу больше не ищутся.
7. **Excel.** Выгруженный реестр после заполнения в ДИКТ импортируется обратно и обновляет записи по колонке ID. Вычисляемые поля и решения ОУР при импорте не перезаписываются.
   - Импорт всегда в два шага: предпросмотр (добавится, изменится, по полям, строки с ошибками), затем применение одной транзакцией. Если после предпросмотра запись или поля изменились — не применяется ничего.
   - Пустой ID — новая запись; неизвестный ID — ошибка строки, запись не создаётся. Пустая ячейка не меняет значение.
   - Сотрудник выгружается как «ФИО (логин)», при импорте ищется по логину в скобках; по одному ФИО — только если такое имя единственное.
   - Колонки сопоставляются с полями по `id` (скрытый лист `_поля`), поэтому переименование поля после выгрузки не мешает импорту.
8. **Документы (маршрут 1.2.0, ADR-0024).**
   - Маршрут: 11 Драфт → 12 Проверка сотрудниками → 13 Согласование начальника ИБ → 14 Согласование с ответственными лицами → 15 Перевод → 16 Подписание. Номера 11–16 — чтобы backend 1.1.0 после отката не двигал документ; старая история (этапы 0–3) — со старыми подписями.
   - 11 → 12 — автор (владелец или `docs.manage`), файл не обязателен; 12 → 13 — автор или старший над автором, только с файлом автора (pdf или docx; файлы автор добавляет и заменяет на 11 и 12; та же проверка для документов из старого маршрута); 13 → 14 — начальник ИБ (отметка, ADR-0027) без загрузки: фиксирует один из файлов автора (по умолчанию последний) как «версию при согласовании начальником ИБ» (привязка `head_approved` на тот же файл, sha256 — в решении); без файла автора на 13 — только возврат; 14 → 15 — начальник ИБ, с загрузкой финальной версии (pdf или docx); 15 → 16 — начальник ИБ или старший над автором; 16 — подписанный PDF и дата подписания (автор или `docs.approve.head`).
   - Свой документ начальник ИБ на этапе 13 согласует сам (отметка одна, другого начальника ИБ нет), с отметкой `self_approved` («без независимого согласования»).
   - 14 → 15 — только когда все ответственные лица (хотя бы одно) отмечены «согласовал(а)». Лица внешние (ФИО, подразделение или должность, срок; ответ-файл — при «Отметить согласование»; с 1.4.0 e-mail и пользователь портала не вводятся, старые значения — текстом), их ведут автор и начальник ИБ на этапах 11–14. Срок меняется только с комментарием; история сроков только пополняется.
   - 15 → 16 — только когда у каждого добавленного языка есть файл (языков нет — этап проходится без файлов). Строка перевода — язык, переводчик текстом (`translator_name`, необязательно), срок, файл; строки ведут автор, старшие над автором и начальник ИБ на этапах 11–15, снять строку можно до прохождения этапа 15 (и с файлом). Файл перевода прикладывает автор (владелец или `docs.manage`) на этапе 15. С 1.4.0 переводчик — не пользователь портала: не видит документ, не получает уведомлений, не входит в «Сейчас у» и «ждёт вас»; `translator_id` новых строк — кто добавил (ради отката на 1.3.0).
   - Открытый блокер останавливает любой шаг вперёд и подписание (возврат — нет). Блокеры открывают и снимают автор, старшие над автором и начальник ИБ; снятие — с комментарием.
   - Возврат — начальник ИБ с этапов 13–15 на 11, только с комментарием, файл-записка по желанию (pdf или docx, `document_approvals.file_id` — не вид `document_files`: backend 1.3.0 ломался бы на карточке): новый круг, задача автору.
   - После подписания запускается цикл пересмотра от даты подписания (по умолчанию 12 месяцев); за 30 дней до срока создаётся задача. «Отменить пересмотр» — автор или начальник ИБ, с комментарием; версия остаётся в истории.
   - «Сейчас у» и «ждёт вас» (1.4.0) — одна функция `stageHolders`: 11, 12, 16 — автор; 13, 14 — начальник ИБ (нет отметки — «Начальник ИБ не назначен»); 15 — есть язык без файла — автор, иначе начальник ИБ и старшие над автором. Видимость документа не считается.
   - Удаление (`docs.delete`) — мягкое, только без подписанной версии, вместе с архивом.
   - Задачи по этапам (1.6.3, общая задача — 1.6.4, ADR-0034): получатели — `stageHolders`; несколько человек — одна общая задача без исполнителя со списком `task_candidates`; на 12 ещё одна общая «Проверить документ» — роль из `app_settings` `documents.reviewRole` (нет — все активные сотрудники ИБ), кроме владельца; на 11 — только первый драфт, заведённый за другого владельца. Взять общую задачу себе — только из списка (403 `NOT_CANDIDATE`), назначить другого — `tasks.assign`. Одна задача на человека (или общая) и состояние (`document_state`, у общей — с `#group`); смена состояния закрывает прежние системой, смена ответственного — закрывает и отправляет в архив (`syncStageTasks` в транзакции действия); закрытую вручную по тому же состоянию не создавать. Срок — рабочие дни из `documents.stageDays`, этап 14 — ближайший срок несогласовавшего лица, 15 «переводы» — языка без файла. Уведомления «назначена задача» нет; списку общей задачи проверки — уведомление при создании.
9. **Почта → задача.**
   - Разбираются строки «От», «Тема», «Отправлено».
   - Срок: «до ДД.ММ», «сегодня», «завтра», «в течение N (рабочих) дней»; по умолчанию 3 рабочих дня; «срочно» означает 1 рабочий день и высокий приоритет.
   - Категория и ответственный определяются по правилам из справочника.
10. **Справочники.** Используемое значение не удаляется, только архивируется. Системные значения не удаляются и не переименовываются.
11. **Процесс задач (ADR-0022).**
   - Колонки: Backlog (без исполнителя) → Поставленные → В работе → На проверке → Выполнено. Исполнитель определяет начало: назначили — «Поставленные», сняли — Backlog, сменили у задачи «В работе» / «На проверке» — «Поставленные».
   - Кнопки: «Взять себе» (Backlog, любой с `ib.work`), «Взять в работу» (только исполнитель), «Отправить на проверку» (исполнитель с проверяющим) или «Завершить» (исполнитель без проверяющего, сразу в «Выполнено»), «Принять» и «Вернуть в работу» — только проверяющий. Исполнитель никогда не принимает и не возвращает свою задачу (409).
   - Проверяющий (1.4.0, ADR-0028) — ближний активный руководитель исполнителя с `ib.work`, фиксируется при отправке (`tasks.reviewer_id`, `task_transitions.reviewer_id`). Задачи, отправленные до 1.4.0 без проверяющего, — по старым правилам (`tasks.review` и автор, или старший, или исполнитель без руководителя). Отключили проверяющего — следующий по цепочке («проверяющий заменён»); никого — без проверяющего.
   - Смена статуса в обход кнопок (перетаскивание, свои колонки, переоткрыть выполненную) — только `tasks.status.override`, иначе 403; из «На проверке» — только проверяющий (403), в «Выполнено» из любой другой колонки при проверяющем — 409 (отменить — архив или удаление), в «На проверке» — с вычислением проверяющего, некому — 409. «Заменить проверяющего» — `tasks.status.override`, с записью в журнал.
   - Другого исполнителя ставит только `tasks.assign`; без права — себя на задачу без исполнителя и снять себя, пока задача в «Поставленные».
   - Комментарий обязателен по признакам колонки (вперёд — `comment_forward`, возврат — `comment_return`), и для кнопок, и для свободной смены. Каждый переход — строка `task_transitions`.
12. **Уведомления (ADR-0023).**
   - О собственных действиях пользователь уведомлений не получает; отключённым не пишем; уведомление — в той же транзакции, что и событие.
   - Индикаторы (1.4.0): `GET /me/attention` — задачи на вашей проверке (у «Задачи»), документы «ждут вас» (у «Документы»), сумма — на колокольчике и в заголовке вкладки; непрочитанные — только в открытом списке; уведомления о сроках цифру не меняют. Уведомления и индикаторы — любому вошедшему, только свои (id из сессии); без прав — нули.
   - Назначили — новому исполнителю, сменили — и прежнему; «ждёт вашей проверки» — только проверяющему (отправка, перенос, замена; ADR-0028), исполнителю — никогда; «вернули», «принята», свободная смена статуса — исполнителю; «выполнена» («Завершить») — автору; комментарий человека — исполнителю и автору (комментарии автоматизации — нет).
   - «Срок завтра» — исполнителю (нет — автору), «просрочено» — исполнителю и автору; по одному на задачу и срок (`dedupe_key`).
   - Первый прогон после обновления: по задачам, просроченным уже на этот момент, — одно сводное «У вас N просроченных задач» каждому получателю со ссылкой на доску с фильтром «просрочено»; дальше — по задаче (опорная дата `app_settings.notifications.overdue_since`).
   - Документы (Г5, ADR-0024): «ждёт вас» — этап 13 начальнику ИБ (отметка; о своих действиях — нет), этап 14 «все лица согласовали» — начальнику ИБ, этап 15 — автору «ждёт файлов перевода», «переводы готовы» — начальнику ИБ и старшим над автором, этап 16 — автору (получатели — `stageHolders`, одно на состояние); вернули на доработку, комментарий сотрудника на этапе 12 — автору; сменили срок — автору; «срок ответственного лица завтра» и «просрочен» — автору, по одному на лицо и срок.

13. **Самооценка (этап Д, `docs/self-assessment.md`, раздел 5).**
   - Балл раздела — выбранный уровень 1–4; домен — сумма баллов, средний — сумма / число отвеченных; итог — сумма 24 разделов (24–96).
   - Уровень по итогу: до 43 — «Цифровая гигиена», 44–66 — «Классическая ИБ», 67–85 — «Трансформируемая КБ», 86 и выше — «Результативная КБ», только если 1.2, 4.2 и 10.1 оценены на 4, иначе «Трансформируемая КБ». Эталон `backend/test/fixtures/cyber-checklist-2025.xlsx`: 34 балла, «Цифровая гигиена», домены 5 / 4 / 5 / 2 / 3 / 5 / 1 / 2 / 6 / 1.
   - Пока заполнено меньше 24 разделов — итог «предварительно», зафиксировать нельзя; при фиксации итог замораживается. Ответы меняются только в черновике (409 и триггер); черновик один.
   - Разрыв = цель − текущий, если цель выше; динамика — с предыдущей зафиксированной оценкой.
   - Задачи по разрывам ставит `assessment.manage` (без `tasks.assign`), исполнитель — сотрудник с `ib.work`, источник `manual`; в карточке и журнале задачи нет следа самооценки.
   - Напоминание о переоценке — за 30 дней до годовщины последней зафиксированной оценки всем держателям `assessment.manage`, без повторов, не при открытом черновике.
   - Удаления оценки нет, только архив.

14. **Продления сроков уязвимостей (1.5.0, ADR-0030).**
   - Право `vulns.deadlines`; область — узел или все узлы группы. Дни 0–365 по Уровню сканера (и «Без уровня»), только продление.
   - Участвуют открытые записи с идущим сроком; не участвуют (показывается число) записи с решением п. 7.3 и из сканов, не переданных ИКТ. Фильтры «Только просроченные», «Только со сроком до <дата>».
   - Обоснование ОИКТ обязательно: номер обращения, дата, файл; комментарий по желанию. Предпросмотр «было → станет», применение с `expected` (409 `BULK_CHANGED`) одной транзакцией; в истории записи — «Срок продлён на N дн. (было → стало) по обоснованию ОИКТ № … от …».
   - Отмена — только целиком, с подтверждением: сроки возвращаются (только у записей в том же цикле), событие остаётся с отметкой «Отменено <дата>».
   - «Продлено, дн.» = сумма действующих продлений текущего цикла; `check-integrity` перечисляет расхождения.

## 8. API и frontend

### API
- Префикс `/api/v1`, JSON, даты в ISO 8601, деньги и проценты числами.
- Ошибки в одном формате: `{ "error": { "code": "...", "message": "понятный текст на русском" } }`.
- Списки отдаются с пагинацией `?limit=&cursor=`.
- Правка записи требует `version`. Если запись успела измениться, backend отвечает 409, и frontend предлагает перечитать запись.
- `GET /api/health` возвращает состояние backend и БД, без авторизации, без данных.

### Frontend
- Внешний вид берётся из прототипа:
  - стиль Apple Liquid Glass: стеклянные панели с размытием;
  - акцент — синий Apple: `#007AFF` в светлой теме, `#0A84FF` в тёмной;
  - заливка главной кнопки (`.btn.primary`) — `#0071E3` в обеих темах (токен `--accent-btn`, белый текст 4,7:1, решение владельца 04.11.2026); `#007AFF` / `#0A84FF` — фокус, индикаторы и прочие акценты;
  - светлая тема и чёрная (`#000`) тёмная, переключатель «Авто / Светлая / Чёрная».
- Токены цвета переносятся из `:root` прототипа в `frontend/src/styles/tokens.css`. UI-библиотеки, которые навязывают свой вид, не подключаем.
- Экраны «список + детали» — только через `components/DetailPanel.tsx` (1.6.5, `docs/ui-audit-1.6.5.md`): `inline` — колонка справа, прилипает к верху окна, на ≤1180 px выезжает справа; `sheet` — всегда выезжает. Главные действия — в `footer` (подвал панели), открытая запись — в адресе (`?doc=`, `?task=`, `?record=`, `?ev=`) шагом истории, выбранная строка подсвечена. Ряды фильтров-чипов — `components/ChipScroller.tsx`.
- Текст цветом акцента — `--accent-ink` (AA в обеих темах); `--accent` — заливки, фокус, индикаторы. Flex- и grid-дети с текстом — `min-width: 0`, сетки — `minmax(0, 1fr)`: длинные ФИО, хосты, sha256 не растягивают контейнер.
- Тексты интерфейса на русском: короткие, конкретные, без канцелярита. Кнопка называет действие, уведомление подтверждает результат. Имена в коде — на английском.
- Экран мониторинга `/monitor`:
  - один экран без прокрутки, автолистание каждые 12 секунд;
  - панель «назад / пауза / вперёд / на весь экран / закрыть» прячется без движения мыши;
  - клавиши ← → и пробел; экран не гаснет (Wake Lock).

## 9. Как работать в этом репозитории

1. **Сначала план.** Для задачи больше одного файла кратко опиши: что меняется, в какой зоне, затрагивает ли схему БД и существующие данные. Затем работай.
2. **Одна зона за изменение**, где это возможно. Изменение API — сначала backend с обратной совместимостью, перегенерация типов, потом frontend.
3. **Схема БД.** Перед любой миграцией покажи SQL и строку «Влияние на данные». Миграции, которые удаляют или переписывают данные, — только после подтверждения.
4. **Проверки перед завершением** в затронутом пакете: `npm run typecheck`, `npm run lint`, `npm test`. Для изменений интерфейса — ещё `npm run test:e2e` во frontend: сквозной тест в Chrome через прокси Vite настоящими щелчками и вводом (нужно запущенное dev-окружение). В backend ещё `npm run test:db` — тесты с настоящим PostgreSQL на одноразовой базе `ibportal_test` в dev-контейнере (пересоздаётся при каждом запуске, подключение под ролью приложения, каждый тест в транзакции с откатом). Для изменений схемы ещё и `prisma migrate dev` на dev-базе с последующим `npm run check:schema` (миграции и живая dev-база против `schema.prisma`, теневая база — одноразовая `ibportal_dev_shadow`) и `npm run check:integrity`.
5. **Документация.** Изменил поведение — обнови `docs/concept.md`. Принял архитектурное решение — добавь ADR в `docs/decisions/`. Каждое изменение для пользователя записывается в `CHANGELOG.md` в раздел «Не выпущено».
6. **Секреты.** Пароли, ключи и `.env` в git не попадают. В коде и тестах только заглушки.
7. **Спроси, прежде чем:**
   - добавлять зависимость;
   - менять коды прав RBAC;
   - менять формат хранения файлов;
   - трогать `deploy/docker-compose.yml`, тома или сети;
   - выполнять что-либо из раздела 3.1.
8. **Ты не выкладываешь на сервер.** Claude готовит релиз: версию, CHANGELOG, проверенные миграции, заметки для выкладки. Саму выкладку выполняет человек по разделу 11.

## 10. Docker

### Сервисы и сети

- Сеть `back` объявлена с `internal: true`, у неё нет выхода наружу. Порт наружу публикует только `frontend`.
- Образы приложения (`ibportal-db`, `ibportal-backend`, `ibportal-frontend`) тегируются версией из `VERSION` и собираются под `linux/amd64`. Базовые образы закреплены по точной версии.
- Процессы в контейнерах работают не от root.
- Серверный `deploy/docker-compose.yml` не содержит `build:` и путей к исходникам: на сервере есть только образы. Сборка описана в `deploy/docker-compose.build.yml` и выполняется на машине разработчика (раздел 11).
- Init-скрипт ролей БД входит в образ `ibportal-db` (`db/Dockerfile`: `postgres:16.15-alpine3.24` + `db/init/`), а не монтируется с диска.

Каркас `deploy/docker-compose.yml`:

```yaml
name: ibportal

services:
  db:
    image: ibportal-db:${VERSION}
    restart: unless-stopped
    environment:
      POSTGRES_DB: ibportal
      POSTGRES_USER: ${DB_OWNER_USER}
      POSTGRES_PASSWORD: ${DB_OWNER_PASSWORD}
      DB_APP_USER: ${DB_APP_USER}
      DB_APP_PASSWORD: ${DB_APP_PASSWORD}
    volumes:
      - pgdata:/var/lib/postgresql/data
    networks: [back]
    healthcheck:
      test: ["CMD-SHELL", "pg_isready -U $${POSTGRES_USER} -d ibportal"]
      interval: 10s
      retries: 5

  backend:
    image: ibportal-backend:${VERSION}
    restart: unless-stopped
    environment:
      NODE_ENV: production
      DATABASE_URL: postgresql://${DB_APP_USER}:${DB_APP_PASSWORD}@db:5432/ibportal
      FILES_DIR: /data/files
      SESSION_SECRET: ${SESSION_SECRET}
      TRUSTED_PROXY_IPS: ${TRUSTED_PROXY_IPS:-172.31.250.6}   # кому верить в X-Forwarded-For: nginx (ADR-0012)
      MONITOR_ALLOWED_IPS: ${MONITOR_ALLOWED_IPS:-}           # адреса настенных мониторов; пусто — вход монитора запрещён
      ADMIN_ALLOWED_IPS: ${ADMIN_ALLOWED_IPS:-}               # рабочие места администраторов; пусто — без ограничения (ADR-0015)
      ONLYOFFICE_URL_PREFIX: ${ONLYOFFICE_URL_PREFIX:-}       # сервер OnlyOffice банка; пусто — любая ссылка http(s) (ADR-0010)
      PORTAL_URL: ${PORTAL_URL:-}                             # адрес портала для проверки Origin; пусто — backend не стартует
    volumes:
      - files:/data/files
    depends_on:
      db: { condition: service_healthy }
    networks: [back, front]
    healthcheck:
      test: ["CMD", "node", "dist/scripts/healthcheck.js"]
      interval: 15s

  frontend:
    image: ibportal-frontend:${VERSION}
    restart: unless-stopped
    ports: ["443:8443"]
    environment:
      PORTAL_URL: ${PORTAL_URL:-}                             # страницы по другому адресу — 301 на PORTAL_URL
    volumes:
      - ./certs:/etc/nginx/certs:ro
    depends_on: [backend]
    networks:
      front: { ipv4_address: "${FRONTEND_IP:-172.31.250.6}" }   # постоянный адрес nginx (TRUSTED_PROXY_IPS)

  migrate:                          # разовый запуск: docker compose --profile tools run --rm migrate
    image: ibportal-backend:${VERSION}
    profiles: [tools]
    command: ["sh", "-c", "npx prisma migrate deploy && node dist/prisma/seed/index.js"]
    environment:
      DATABASE_URL: postgresql://${DB_OWNER_USER}:${DB_OWNER_PASSWORD}@db:5432/ibportal
    depends_on:
      db: { condition: service_healthy }
    networks: [back]

volumes:
  pgdata: { external: true, name: ibportal_pgdata }
  files:  { external: true, name: ibportal_files }

networks:
  front:
    ipam:
      config:
        - subnet: ${FRONT_SUBNET:-172.31.250.0/29}
  back:
    internal: true
    ipam:
      config:
        - subnet: ${BACK_SUBNET:-172.31.249.0/24}
```

Сервис `migrate` после миграций выполняет идемпотентный seed прав и системных ролей (ADR-0003).

`deploy/docker-compose.dev.yml` запускается как проект `ibportal-dev`:
- использует свои тома `ibportal_dev_pgdata` и `ibportal_dev_files` (тоже `external: true`, создаются вручную);
- база называется `ibportal_dev`, публикуется только на `127.0.0.1:5433`. Для этого db в dev подключена ещё к обычной сети `dbhost`: Docker не публикует порты контейнера, у которого только internal-сети. В серверном compose этого нет;
- dev-сервисы `backend` и `migrate` перед запуском выполняют `prisma generate`: схема монтируется с хоста, а клиент в образе собран по схеме на момент сборки;
- запускает backend и frontend в режиме разработки (стадии `dev` в Dockerfile, исходники монтируются с хоста);
- переменные — из `deploy/.env.dev` (образец `deploy/.env.dev.example`).

Cookie сессии всегда `Secure`. На `http://localhost` её принимают Chrome и Firefox, Safari — нет: dev проверяется в Chrome или Firefox.

### Первичная настройка сервера (один раз)

Полная последовательность — в `RELEASE.md` каждого релиза и в `docs/runbook/deploy.md`. Коротко:

```bash
docker volume create ibportal_pgdata
docker volume create ibportal_files
docker volume create ibportal_backups
# распаковать релиз, проверить sha256, docker load, скопировать docker-compose.yml, .env.example и scripts/ в /srv/ibportal/deploy
cd /srv/ibportal/deploy
cp .env.example .env && chmod 600 .env      # заполнить пароли и VERSION
# положить сертификат и ключ в ./certs (portal.crt, portal.key)

docker compose --profile tools run --rm migrate
docker compose run --rm backend node dist/scripts/create-admin.js   # спросит логин и пароль
docker compose up -d
./scripts/smoke.sh
```

## 11. Ручная выкладка (CI/CD нет)

На сервере нет Claude Code, git и Node — только Docker. Разработчик собирает готовый релиз на своей машине, администратор выкладывает его по `RELEASE.md` из релиза.

**На сервер никогда не передаются исходники и отдельные файлы кода** (`.ts`, `.js`, `.sql`, `Dockerfile`, `package.json`, каталоги `backend/`, `frontend/`, `db/`). Код приезжает только внутри образов. Кроме образов в релиз входят лишь файлы эксплуатации: `docker-compose.yml`, `docker-compose.restoretest.yml`, `scripts/` (backup, restore, restore-test, smoke), `.env.example`, `docs/` (инструкция по установке и руководство пользователя), `CHANGELOG.md`, `RELEASE.md`, `SHA256SUMS`. Если для выкладки понадобился какой-то ещё файл, его место — в образе, а не рядом с ним.

Каждая выкладка записывается в `docs/runbook/deploy-log.md`: дата, версия, кто выкладывал, имя резервной копии, результат. Администратор передаёт эти данные разработчику.

### A. Сборка релиза (машина разработчика)

```bash
# CHANGELOG: перенести «Не выпущено» в раздел [0.3.0]; VERSION = 0.3.0; закоммитить
git tag v0.3.0
./deploy/scripts/make-release.sh
```

`make-release.sh`:
1. Проверяет, что дерево git чистое, и предупреждает, если тег `v<VERSION>` не стоит на текущем коммите.
2. Собирает `ibportal-db`, `ibportal-backend`, `ibportal-frontend` командой `docker buildx build --platform linux/amd64 --load` и проверяет архитектуру образов.
3. Сохраняет образы: `docker save | gzip` → `ibportal-images-<VERSION>.tar.gz`.
4. Копирует `docker-compose.yml`, `scripts/`, `CHANGELOG.md`, `.env.example`.
5. Создаёт `RELEASE.md` из `deploy/RELEASE.template.md`: изменения, миграции и их «Влияние на данные», новые переменные `.env`, команды выкладки и отката, проверки после.
6. Считает `SHA256SUMS` и упаковывает всё в `dist/ibportal-<VERSION>.tar.gz` с файлом `.sha256`.

Перед передачей прочитать `RELEASE.md`. Если у миграции нет строки «Влияние на данные» или она удаляет данные, релиз не передаётся.

Администратору передаются только `dist/ibportal-<VERSION>.tar.gz` и `dist/ibportal-<VERSION>.tar.gz.sha256`.

### B. Выкладка на сервере

```bash
cd /srv/ibportal/releases
sha256sum -c ibportal-0.3.0.tar.gz.sha256
tar -xzf ibportal-0.3.0.tar.gz && cd ibportal-0.3.0 && sha256sum -c SHA256SUMS
docker load -i ibportal-images-0.3.0.tar.gz
cd /srv/ibportal/deploy
./scripts/smoke.sh --before
./scripts/backup.sh                     # ОБЯЗАТЕЛЬНО. Если копия не создалась — стоп
cp /srv/ibportal/releases/ibportal-0.3.0/docker-compose.yml .
cp /srv/ibportal/releases/ibportal-0.3.0/scripts/*.sh scripts/
# новые переменные из RELEASE.md — в .env
sed -i 's/^VERSION=.*/VERSION=0.3.0/' .env
docker compose --profile tools run --rm migrate
docker compose up -d backend frontend   # db уже перезапущена с новым образом на шаге migrate
./scripts/smoke.sh --after              # health, вход, количество записей до и после
```

### C. Откат

1. Если миграции в релизе совместимы с прошлой версией (так должно быть всегда, раздел 3.3): вернуть прежний `VERSION` в `.env` и выполнить `docker compose up -d backend frontend`. Образы прошлой версии остаются на сервере после `docker load`; не удалять их, пока новая версия не проработала хотя бы неделю.
2. Если релиз всё же испортил данные: вернуть прежний `VERSION` (`restore.sh` сверяет его с версией копии), выполнить `./scripts/restore.sh <имя копии>`, поднять сервисы. Восстановление проверяет контрольные суммы, спрашивает подтверждение вводом имени копии, само делает копию текущего состояния и останавливает backend и frontend перед заменой. База восстанавливается одной транзакцией с сохранением прав ролей (запрет правки `audit_log`), после чего запускается `check-integrity`.

### Резервные копии

- `backup.sh` пишет в том `ibportal_backups`:
  - `pg_dump -Fc` базы (и проверяет, что дамп читается `pg_restore` целиком);
  - архив тома файлов;
  - `manifest.txt` с версией и `SHA256SUMS`.
  - Имя копии: `<дата>_<время>_<версия>`.
- Для работы с томами скрипты используют одноразовый контейнер из образа `ibportal-backend` текущей версии, без сети. Сторонние образы на сервер не нужны.
- Копия делается автоматически перед каждой выкладкой и ежедневно по cron на сервере (`./scripts/backup.sh --rotate`). Хранятся 14 последних и по одной за каждый из 6 последних месяцев. Без `--rotate` скрипт ничего не удаляет.
- Копии регулярно выносятся за пределы сервера по регламенту банка.
- Раз в месяц восстановление проверяется в отдельном compose-проекте `ibportal-restoretest` (`scripts/restore-test.sh <копия>`, `docs/runbook/deploy.md`, раздел 8), проверка отмечается в `deploy-log.md`.
