Все запросы раздела «До выкладки» написаны для схемы 1.1.0 (запросы из предпроверок 1.2.0–1.4.0, которые ссылаются на появившиеся позже таблицы и колонки, здесь заменены равнозначными). ### Что сделает шаг `migrate`

Сначала все миграции 1.2.0, 1.3.0 и 1.4.0 (список и «Влияние на данные» — в разделе «Миграции базы данных»), затем одной транзакцией шаги seed, в таком порядке:

1. **Коды прав** — 19 кодов; новые с 1.1.0: `tasks.assign`, `tasks.review`, `tasks.status.override`, `tasks.report`, `docs.delete`, `history.view`, `audit.view` (1.2.0), `assessment.manage` (1.3.0). Коды `docs.approve.legal` и `docs.approve.board` выведены из обращения (строки в базе остаются).
2. **Системные роли** — создаются без пользователей: «Читатель документов» (1.2.0, без прав), «Самооценка» (1.3.0, только `assessment.manage`), «SOC» (1.4.0, права «Сотрудника ИБ»). Если своя роль с таким названием уже есть — `migrate` останавливается, ничего не применяется (пункт 1 «До выкладки»). Существующие роли не перезаписываются; «Юрист» и «Правление» остаются строками без пользователей.
3. **Права ролям, один раз** (`rbac.permissions.v1_2`): «Начальник ИБ» ← `tasks.assign`, `tasks.review`, `tasks.status.override`, `tasks.report`, `docs.delete`, `history.view`, `audit.view`; «Супер-администратор» ← `history.view`, `audit.view`. Право «Документы: начальник ИБ» у роли остаётся, но с 1.4.0 не используется (этапы начальника ИБ — по отметке у пользователя, п. 3 «После `migrate`»).
4. **«Юрист» и «Правление» → «Читатель документов»** (при каждом `migrate`): все их пользователи переходят в новую роль, прежняя снимается, учётные записи не отключаются.
5. **Справочники**: колонка доски «Поставленные» и признаки комментария у колонок.
6. **Задачи, один раз** (`tasks.process.v1_2`): колонки Backlog → Поставленные → В работе → На проверке → Выполнено; «Новые» → «Backlog», «Готово» → «Выполнено» (если администратор их не переименовывал); задачи «Новые» с исполнителем (и архивные) → «Поставленные». При каждом `migrate` — выравнивание открытых задач по исполнителю.
7. **Проверяющие задач, один раз** (`tasks.reviewer.v1_4`): задачам «На проверке» ставится проверяющий — ближний руководитель исполнителя. На 1.1.0 руководителей у пользователей нет (колонка появляется этим же `migrate` пустой), поэтому **проверяющего не получит ни одна задача**: все задачи «На проверке» остаются на правилах до 1.4.0 — принимает держатель «Задачи: проверка» (роль «Начальник ИБ» после шага 3). Новым задачам проверяющий назначается при отправке, когда у исполнителей заведён руководитель (п. 3 «После `migrate`»).
8. **Документы** (при каждом `migrate`): рабочие версии переходят на маршрут 1.2.0 — этап 0 «Автор» → 11 «Драфт», 1 «Начальник ИБ» → 13 «Согласование начальника ИБ», 2 и 3 → 14 «Согласование с ответственными лицами». В истории — решение «Система». Утверждённые версии не меняются.
9. **Самооценка, один раз**: методика `cyber-express-v1` версии 1 и подпись презентации.
10. Таблица переводов создаётся этим же `migrate` пустой — заполнение имени переводчика (миграция `…_translation_translator_name`) затрагивает 0 строк.

После первого часового прогона по задачам, уже просроченным к этому моменту, каждый получатель получит одно сводное уведомление «У вас N просроченных задач» (пункт 4 «До выкладки»).

### До выкладки (на работающей 1.1.0, до `backup.sh`)

**1. Нет ли своих ролей с названиями новых системных (стоп-условие).**

```bash
docker compose exec -T db sh -c 'psql -U "$POSTGRES_USER" -d ibportal -c "
SELECT name AS роль, code AS код, (SELECT count(*) FROM user_roles ur WHERE ur.role_id = r.id) AS пользователей
FROM roles r
WHERE name IN (\$\$Читатель документов\$\$, \$\$Самооценка\$\$, \$\$SOC\$\$) OR code IN (\$\$doc_reader\$\$, \$\$assessment\$\$, \$\$soc\$\$);"'
```

Ожидается **0 строк**. Есть строка — до `migrate` переименуйте эту роль в «Настройки → Роли и права» (например, «SOC (старая)») и запишите в журнал выкладок.

**2. Задачи, которые перейдут в «Поставленные».**

```bash
docker compose exec -T db sh -c 'psql -U "$POSTGRES_USER" -d ibportal -c "
SELECT s.value AS колонка, s.system_key AS ключ, t.assignee_id IS NOT NULL AS есть_исполнитель,
       t.archived_at IS NOT NULL AS в_архиве, count(*) AS задач
FROM tasks t JOIN catalog_items s ON s.id = t.status_id
WHERE t.deleted_at IS NULL
GROUP BY 1, 2, 3, 4 ORDER BY 2, 3, 4;"'
```

- Сумма строк с ключом `new` и `есть_исполнитель = t` (в архиве и нет) — **N₂**: столько задач перейдёт в «Поставленные».
- Сумма открытых строк с ключом `review` — **M₂**: задачи «На проверке», которые останутся на правилах до 1.4.0 (шаг seed 7).

**3. Документы на маршруте.**

```bash
docker compose exec -T db sh -c 'psql -U "$POSTGRES_USER" -d ibportal -c "
SELECT CASE WHEN d.working_version_id IS NULL THEN \$\$утверждён, без рабочей версии\$\$
            WHEN d.approved_version_id IS NULL THEN \$\$первая версия\$\$ ELSE \$\$новая версия утверждённого\$\$ END AS вид,
       wv.stage AS этап, d.archived_at IS NOT NULL AS в_архиве, count(*) AS документов
FROM documents d LEFT JOIN document_versions wv ON wv.id = d.working_version_id
GROUP BY 1, 2, 3 ORDER BY 1, 2, 3;"'
```

- Сумма строк с непустым этапом — **N₃**: столько рабочих версий перейдёт на маршрут 1.2.0.
- Строки с **этапом 1** — документы, которые окажутся на «Согласовании начальника ИБ» **без файла автора** (в 1.1.0 файлов версии ещё нет). Их можно будет только вернуть на доработку: автор приложит файл (pdf или docx) на «Драфте» (п. 3 «После `migrate`»). Номера этих документов:

```bash
docker compose exec -T db sh -c 'psql -U "$POSTGRES_USER" -d ibportal -c "
SELECT d.number AS документ, wv.title AS название, wv.no AS версия
FROM documents d JOIN document_versions wv ON wv.id = d.working_version_id
WHERE wv.stage = 1 ORDER BY d.number;"'
```

**4. Сводное уведомление о просроченных задачах.**

```bash
docker compose exec -T db sh -c 'psql -U "$POSTGRES_USER" -d ibportal -c "
WITH late AS (
  SELECT id, assignee_id, created_by FROM tasks
  WHERE deleted_at IS NULL AND archived_at IS NULL AND completed_at IS NULL AND due_date < current_date
), who AS (
  SELECT assignee_id AS user_id, id FROM late WHERE assignee_id IS NOT NULL
  UNION SELECT created_by, id FROM late WHERE created_by IS NOT NULL
)
SELECT (SELECT count(*) FROM late) AS просроченных_задач, count(DISTINCT w.user_id) AS получат_сводное
FROM who w JOIN users u ON u.id = w.user_id AND u.is_active;"'
```

**5. Пользователи «Юриста» и «Правления» — перейдут в «Читатель документов».**

```bash
docker compose exec -T db sh -c 'psql -U "$POSTGRES_USER" -d ibportal -c "
SELECT r.name AS роль, u.login, u.full_name AS фио, u.is_active AS активен,
       (SELECT string_agg(r2.name, \$\$, \$\$) FROM user_roles x JOIN roles r2 ON r2.id = x.role_id
        WHERE x.user_id = u.id AND r2.id <> r.id) AS другие_роли
FROM roles r JOIN user_roles ur ON ur.role_id = r.id JOIN users u ON u.id = ur.user_id
WHERE r.code IN (\$\$legal\$\$, \$\$board\$\$) ORDER BY 1, 2;"'
```

Число разных логинов — **N₅**.

**6. Кандидаты в «начальника ИБ» и руководителей групп** (для п. 3 «После `migrate`»): кто сейчас в роли «Начальник ИБ».

```bash
docker compose exec -T db sh -c 'psql -U "$POSTGRES_USER" -d ibportal -c "
SELECT u.login, u.full_name AS фио, u.is_active AS активен,
       bool_or(r.code = \$\$super_admin\$\$) AS супер_администратор
FROM users u JOIN user_roles ur ON ur.user_id = u.id JOIN roles r ON r.id = ur.role_id
WHERE u.id IN (SELECT user_id FROM user_roles x JOIN roles y ON y.id = x.role_id WHERE y.code = \$\$ib_head\$\$)
GROUP BY 1, 2, 3 ORDER BY 1;"'
```

Все числа и списки — в журнал выкладок.

### После `migrate` (шаг 5 инструкции)

**1. Вывод seed** (`docker compose --profile tools run --rm migrate`) — сверить с числами «До выкладки»:

- «Создана роль «Читатель документов»», «… «Самооценка»», «… «SOC»» — по строке на роль.
- «Задачи 1.2.0: колонки Backlog → … ; в «Поставленные» перенесено N» — **N = N₂**.
- «Задачи 1.4.0: проверяющий назначен 0 задачам на проверке (—); без цепочки руководителей, по правилам до 1.4.0 — M (…)» — **M = M₂**.
- «Документы 1.2.0: на новый маршрут перенесено N (…)» — **N = N₃** (нет рабочих версий — строки нет).
- «Читатель документов: перенесено пользователей — N» — **N = N₅** (никого — строки нет).
- «Самооценка: методика cyber-express-v1 v1 загружена».

**2. Проверка целостности** (шаг 6): «Целостность в порядке»; среди строк — «отметка «Начальник ИБ» не поставлена (этап документов без исполнителя)», «· задач на проверке без проверяющего (правила до 1.4.0, tasks.review): M — #номера» (M = M₂), «право „Самооценка“ есть только у системной роли „Самооценка“», «методика самооценки загружена».

**3. Действия администратора портала — сразу после выкладки** («Настройки → Пользователи и роли»), результат — в журнал выкладок:

1. **Отметка «Является начальником ИБ»** — одному пользователю из пункта 6 «До выкладки» (активный, с доступом к разделам ИБ, не «Супер-администратор»; себе поставить нельзя — ставит другой администратор). Без отметки этапы «Согласование начальника ИБ» и «Согласование с ответственными лицами» никто не выполнит.
2. **«Руководитель»** у сотрудников ИБ. Проверяющий задачи — руководитель исполнителя; у исполнителя без руководителя проверки нет — он завершает задачу сам («Завершить»).
3. **Кто ставит задачи другим** — права есть только у роли «Начальник ИБ» (шаг seed 3). Список (только чтение):

   ```bash
   docker compose exec -T db sh -c 'psql -U "$POSTGRES_USER" -d ibportal -c "
   SELECT u.login, u.full_name AS фио, string_agg(DISTINCT r.name, \$\$, \$\$) AS роли,
          bool_or(rp.permission_code = \$\$tasks.assign\$\$) AS ставит_другим
   FROM users u JOIN user_roles ur ON ur.user_id = u.id JOIN roles r ON r.id = ur.role_id
   LEFT JOIN role_permissions rp ON rp.role_id = r.id
   WHERE u.is_active GROUP BY 1, 2 ORDER BY 4 DESC, 1;"'
   ```

4. **Документы на этапе 13 без файла автора** (из пункта 3 «До выкладки», этап 1) — начальник ИБ возвращает их на доработку с замечанием «приложите файл документа (pdf или docx)». Проверка, что таких не осталось:

   ```bash
   docker compose exec -T db sh -c 'psql -U "$POSTGRES_USER" -d ibportal -c "
   SELECT d.number AS документ, v.title AS название, v.stage AS этап
   FROM documents d JOIN document_versions v ON v.id = d.working_version_id
   WHERE d.deleted_at IS NULL AND d.archived_at IS NULL AND v.cancelled_at IS NULL AND v.stage IN (12, 13)
     AND NOT EXISTS (SELECT 1 FROM document_files f WHERE f.version_id = v.id AND f.kind = \$\$draft\$\$ AND f.removed_at IS NULL)
   ORDER BY v.stage DESC, d.number;"'
   ```

5. **Роль «Самооценка»** — одному сотруднику по решению владельца проекта; проверка раздела — как в «Самооценка: проверка владельцем после выкладки» ниже. Роль «SOC» — по необходимости.

**4. Самооценка: проверка владельцем после выкладки.** Под пользователем с ролью «Самооценка»: пункт меню «Самооценка» → «Новая оценка» → «Импорт Excel» исходного чек-листа — предпросмотр «Найдено разделов: 24 из 24», после применения 34 из 96, «Цифровая гигиена». Под другими пользователями пункта нет.

**5. Просмотр файлов документа.** Документ с PDF → щелчок по имени файла → окно на весь экран, страница нарисована, ← → листают, Esc закрывает; в консоли браузера (F12) нет сообщений `Refused to …` (Content-Security-Policy). Файл .docx → сообщение «Для просмотра в портале приложите PDF; .docx открывается в OnlyOffice» и «Скачать».

### Откат на 1.1.0

Без отката базы: `VERSION=1.1.0` в `.env`, `docker compose up -d backend frontend`, `./scripts/smoke.sh`. Проверено запуском: код 1.1.0 на базе, прошедшей путь прода (миграции и seed 1.1.0, затем миграции и seed 1.4.0), — 191 из 194 тестов 1.1.0 с базой проходят; 3 отличия — названия и число колонок доски. После отката пользователи 1.1.0 увидят:

- колонки доски «Backlog», «Поставленные», «Выполнено» (5 колонок вместо 4) — задачи на месте;
- документы на этапах 11–16 1.1.0 не двигает: согласование документов стоит до повторной выкладки 1.4.0;
- бывшие «Юристы» и «Правление» — в роли «Читатель документов» (для 1.1.0 — роль без прав);
- журнала, уведомлений, самооценки, отметки начальника ИБ, проверяющих нет; данные этих разделов остаются в базе.

Если релиз испортил данные — `./scripts/restore.sh <копия из шага 3>` (раздел «Откат» ниже).

**Повторная выкладка 1.4.0 после отката**: тем же порядком. Однократные шаги seed (права ролям, перенос задач, проверяющие, методика) второй раз не выполняются; перенос документов и «Юристов» и выравнивание задач — при каждом `migrate`. Задачи, отправленные на проверку под 1.1.0, остаются на правилах до 1.4.0 — проверка целостности называет их номера; проверяющего им назначает держатель «Задачи: свободная смена статуса» («Заменить проверяющего» в карточке задачи).
