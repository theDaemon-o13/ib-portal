Сервер работает на **1.8.0**. Если там версия старше, сначала выложите 1.8.0 по его RELEASE.md, затем 1.9.0.

**Выкладка — обязательно с `migrate`** (шаг 5 инструкции ниже). Без него у 1.9.0 нет таблиц учебных писем, реестра «Рассылки» и «Подписи ИБ»: раздел «Осведомлённость» и расписание не заработают, `smoke.sh` и `check-integrity` покажут ошибку. `migrate` — одна команда: сначала миграция, затем seed одной транзакцией. Если команда завершилась ошибкой, seed не применён целиком: backend не поднимайте, устраните причину из сообщения и повторите `migrate`. Повторный запуск безопасен: однократные шаги отмечены и второй раз не выполняются.

### Что сделает шаг `migrate`

1. **Миграция `20261105045141_awareness_letters`.** Семь новых таблиц учебных писем и расписания, их ограничения и триггеры. Существующие строки не меняются; существующие таблицы получают только входящие внешние ключи.
2. **Seed, один раз (`awareness.v2`):**
    - пустой системный реестр «Рассылки» (9 полей). Если уже есть свой реестр «Рассылки», системный получит название «Рассылки (системный)»;
    - «Подпись ИБ» — заглушка «Отдел информационной безопасности» / «Шуъбаи амнияти иттилоотӣ»: замените её после выкладки;
    - лимиты писем `awareness.letters`: изображение 1 МБ, письмо 2 МБ, предупреждение от 1 МБ;
    - категория задач «Осведомлённость» — системное значение. Если такое значение уже завели вручную, оно станет системным (запись в журнале), задачи в нём останутся.

   В выводе: «Учебные письма: реестр «Рассылки» (полей 9), «Подпись ИБ» (заглушка), лимиты размера писем» и «Seed выполнен: …».

### До выкладки (на работающей 1.8.0, до `backup.sh`)

Запросы только читают базу. Результаты запишите в журнал выкладок. Считаются только свои объекты (без системного кода): при повторной выкладке после отката системные объекты 1.9.0 уже есть и сюда не попадают.

```bash
docker compose exec -T db sh -c 'psql -U "$POSTGRES_USER" -d ibportal -c "
SELECT \$\$свой реестр «Рассылки»\$\$ AS что, count(*) FROM registers
  WHERE system_key IS NULL AND archived_at IS NULL AND deleted_at IS NULL AND lower(name) = lower(\$\$Рассылки\$\$)
UNION ALL SELECT \$\$категория задач «Осведомлённость»\$\$, count(*) FROM catalog_items
  WHERE catalog_code = \$\$task_categories\$\$ AND system_key IS NULL AND deleted_at IS NULL AND lower(value) = lower(\$\$Осведомлённость\$\$)
UNION ALL SELECT \$\$держатель отметки «Является начальником ИБ»\$\$, count(*) FROM users WHERE is_ib_head AND is_active;"'
```

- **Реестр: больше 0 — не стоп.** Свой реестр не трогается, системный получит «Рассылки (системный)». Переименовать любой из них можно после выкладки.
- **Категория: больше 0 — не стоп.** Значение станет системным: его нельзя будет удалить, переименовать можно.
- **Держатель отметки: 0 — не стоп, а предупреждение.** Утверждает учебные письма пользователь с отметкой «Является начальником ИБ». Без неё письма некому утверждать (плановые не уйдут дальше «На согласовании»), а уведомления «рассылку никто не взял» получат держатели роли «Начальник ИБ». Поставьте отметку до первой рассылки: «Настройки → Пользователи и роли» → строка пользователя → «Изменить» → «Является начальником ИБ» → «Отметить». Отметку ставит пользователь с правом «Пользователи и роли»; самому себе — нельзя; супер-администратору — нельзя.

Кто держит отметку и кто может взять задачи рассылки (роли с правом «Работа в разделах ИБ» и число их активных участников):

```bash
docker compose exec -T db sh -c 'psql -U "$POSTGRES_USER" -d ibportal -c "
SELECT login, full_name FROM users WHERE is_ib_head AND is_active;
SELECT r.name AS роль, count(u.id) AS участников FROM roles r
  JOIN role_permissions rp ON rp.role_id = r.id AND rp.permission_code = \$\$ib.work\$\$
  LEFT JOIN user_roles ur ON ur.role_id = r.id LEFT JOIN users u ON u.id = ur.user_id AND u.is_active
  WHERE coalesce(r.code, \$\$\$\$) <> \$\$portal_admin\$\$ GROUP BY r.name ORDER BY r.name;"'
```

Роль-исполнитель правил расписания выбирается из этого списка. Роль без участников — задачи без кандидатов и сразу уведомление начальнику ИБ.

### После `migrate`

1. **Вывод `migrate`.** Миграция `..._awareness_letters` применена, есть строки из пункта 2 выше, команда завершилась без ошибки.
2. **`./scripts/smoke.sh --after`.** Строки «✓ реестр «Рассылки» …», «✓ системные поля реестра «Рассылки» (9)», «✓ категория задач «Осведомлённость» …», «✓ «Подпись ИБ» …», «✓ лимиты писем …», «✓ таблицы учебных писем (7)», «✓ триггеры учебных писем (4)», затем «Smoke-проверка пройдена». «✗ … найдено 0» — `migrate` не выполнен или прерван: повторите шаг 5.
3. **Проверка целостности.** `docker compose run --rm -T --no-deps backend node dist/scripts/check-integrity.js` → «Целостность в порядке», в том числе строки «учебные письма» и «расписание». Строка с «!» о роли правила — предупреждение, не ошибка.
4. **В интерфейсе:** в меню — «Осведомлённость» («Письма», «Шаблоны», «Расписание»); в «Реестрах» — «Рассылки»; в «Настройках» — вкладка «Подпись ИБ»; на дашборде — виджет «Ближайшая рассылка» («Запланированных рассылок нет»).

### После выкладки: до первой рассылки сотрудникам

1. **«Подпись ИБ»** — «Настройки → Подпись ИБ»: подпись отдела и контакт для сообщений о подозрительных письмах, **на русском и на таджикском**. В seed — заглушка. Вкладка видна пользователю с правом «Настройки» и доступом к разделам ИБ.
2. **Отметка «Является начальником ИБ»** — если запрос «до выкладки» показал 0 (см. выше, где её поставить).
3. **Проверка экспорта на одном тестовом письме самому себе** — в Outlook и в WorldClient, по чек-листу руководства пользователя (`docs/user-guide.md`, «Учебные письма → Экспорт и проверка в почтовом клиенте»): письмо с заголовком, списком, таблицей, ссылкой, изображением и «Подписью ИБ» на двух языках; «Скопировать с оформлением» и «.eml»; открыть полученные письма в обоих клиентах и на телефоне. Результат — в журнал выкладок и разработчику. **Сотрудникам — только после этой проверки.**
4. **Показатели рассылок на мониторе** — раздел ниже.

### После выкладки: показатели рассылок на мониторе

Необязательный шаг. В 1.9.0 у слайда «Ключевые показатели» появились два показателя учебных писем. В набор по умолчанию они не входят: слайд должен помещаться на один экран без прокрутки.

- **«Ближайшая рассылка»** — сколько дней до отправки ближайшей плановой рассылки, под числом — правило и дата. Число красное, если этап рассылки (черновик, согласование, отправка) просрочен.
- **«Рассылки с просрочкой»** — сколько рассылок по расписанию с невыполненным этапом, дата которого уже прошла.

Чтобы показать их на настенном мониторе, пользователь с правом «Настройки» и доступом к разделам ИБ:

1. Открывает «Настройки → Экран мониторинга», слайд «Ключевые показатели», «Изменить».
2. Отмечает «Ближайшая рассылка» и «Рассылки с просрочкой».
3. Снимает два других, чтобы на слайде осталось **не больше 8 показателей**. Удобнее всего убрать те, у которых есть свой слайд:
    - «Срок устранения в ближайшие 7 дней» — есть на слайде «Уязвимости по срокам»;
    - «Доказательства истекают» — есть на слайде «Доказательства».
4. Нажимает «Предпросмотр» и проверяет, что слайд помещается на экран без прокрутки. Мониторы подхватят изменение сами в течение 1–2 минут.

Если слайда «Ключевые показатели» нет — добавьте его и выберите не больше 8 показателей.

### Откат на 1.8.0

**Способ 2 (только код)** — `sed -i 's/^VERSION=.*/VERSION=1.8.0/' .env` и `docker compose up -d backend frontend`. Ничего отключать не нужно, база остаётся от 1.9.0:
- 1.8.0 новые таблицы не читает: раздела учебных писем нет, письма и правила ждут повторной выкладки;
- задачи рассылок для 1.8.0 — обычные задачи «поставлена вручную», этапы видны в описании;
- реестр «Рассылки» — обычный реестр; категория «Осведомлённость» — обычное значение;
- неизвестные показатели монитора и виджет дашборда 1.8.0 отбрасывает;
- 1.8.0 может удалить (мягко) задачу или запись «Рассылок», связанную с письмом; после возврата на 1.9.0 письмо покажет ссылку на удалённую;
- `smoke.sh` при `VERSION=1.8.0` объекты 1.9.0 не проверяет.

При повторной выкладке 1.9.0 seed заново ничего не создаёт: отметка `awareness.v2` уже стоит, «Подпись ИБ» и лимиты сохраняются.

**Способ 1** (резервная копия перед `migrate`, образы 1.8.0) возвращает состояние до обновления полностью. Письма, шаблоны и правила, созданные после обновления, теряются.
