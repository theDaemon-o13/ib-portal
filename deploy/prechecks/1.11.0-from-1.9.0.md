Сервер работает на **1.9.0**; 1.10.0 туда не выкладывалась. Один `migrate` применяет миграции 1.10.0 и 1.11.0 по порядку, затем шаги seed. Если на сервере версия старше 1.9.0 — сначала 1.9.0 по его RELEASE.md.

**Выкладка — обязательно с `backup.sh` и `migrate`** (шаги 3 и 5 инструкции ниже). Миграций три:
- `20261105103617_sessions_remember` (1.10.0) — две колонки в `sessions`;
- `20261105160000_documents_route_v3` (1.11.0) — маршрут из 4 этапов: новые колонки и таблица;
- `20261106053127_document_controls` (1.11.0) — механизмы контроля и автоматизации: новые пустые таблицы.

Существующие строки миграции не меняют. Документы в работе переносит на новый маршрут шаг seed `docs.route.v3` внутри того же `migrate`. Без `migrate` backend 1.11.0 не открывает сессии и не работает с документами — `smoke.sh --after` покажет «✗». Повторный запуск `migrate` безопасен.

### Что меняется для пользователей

- **Сессии (1.10.0).**
    - По бездействию портал больше не выходит. На форме входа — «Запомнить меня» (включено по умолчанию).
    - Администраторы — сессия 12 часов от входа, «Запомнить меня» для них не действует.
    - «Профиль → Мои сессии» и «Пользователи и роли» → «Сессии»: завершить сессии.
    - Сессии, открытые до выкладки, доживают прежний срок.
- **Маршрут документа (1.11.0)** — 4 этапа: «Драфт» (с проверкой начальника ИБ) → «Согласование» (с повторной проверкой после доработки) → «Перевод» (ссылки на переводы в OnlyOffice) → «Утверждение». Файлы (подписанный PDF, исходный Word, Word переводов) прикладываются только на «Утверждении».
- **Документы в работе после выкладки** — на новых этапах:
    - «Драфт» и «Проверка сотрудниками» → «Драфт»;
    - «Согласование начальника ИБ» → «Драфт — на проверке у начальника ИБ», его задача сохраняется;
    - «Ответственные лица» → «Согласование»; если все лица согласовали — «на повторной проверке»;
    - «Перевод» → «Перевод»: ссылки на переводы автор добавит заново, прежние файлы — в «Файлах прежнего маршрута»;
    - «Подписание» → «Утверждение».

  Утверждённые документы не меняются.
- **Подменю «Документы»** — «В работе» и «Утверждённые» (реестр действующих документов с выгрузкой в Excel). У утверждённого документа — вкладки «Механизмы контроля» и «Автоматизации».

### До выкладки (на работающей 1.9.0, до `backup.sh`)

Запросы только читают базу. Результаты запишите в журнал выкладок.

**Сессии (1.10.0):**

```bash
docker compose exec -T db sh -c 'psql -U "$POSTGRES_USER" -d ibportal -c "
SELECT count(*) FILTER (WHERE revoked_at IS NULL AND expires_at > now()) AS открытых_сессий,
       count(*) AS строк_в_sessions
FROM sessions;
SELECT count(DISTINCT u.id) AS администраторов_12_часов FROM users u
  JOIN user_roles ur ON ur.user_id = u.id JOIN roles r ON r.id = ur.role_id
  LEFT JOIN role_permissions rp ON rp.role_id = r.id AND rp.permission_code = \$\$users.manage\$\$
  WHERE u.is_active AND (rp.role_id IS NOT NULL OR r.code = \$\$portal_admin\$\$);"'
```

**Документы (1.11.0):**

```bash
docker compose exec -T db sh -c 'psql -U "$POSTGRES_USER" -d ibportal -c "
SELECT v.stage AS этап,
       CASE WHEN v.stage = 14 AND p.cnt > 0 AND p.pending = 0 THEN \$\$все лица согласовали\$\$ WHEN v.stage = 14 THEN \$\$лица не все\$\$ ELSE \$\$\$\$ END AS уточнение,
       count(*) FILTER (WHERE d.deleted_at IS NULL AND d.archived_at IS NULL) AS активных,
       count(*) FILTER (WHERE d.deleted_at IS NULL AND d.archived_at IS NOT NULL) AS в_архиве,
       count(*) FILTER (WHERE d.deleted_at IS NOT NULL) AS удалённых
FROM documents d JOIN document_versions v ON v.id = d.working_version_id AND v.cancelled_at IS NULL
LEFT JOIN LATERAL (SELECT count(*) cnt, count(*) FILTER (WHERE approved_at IS NULL) pending
                   FROM document_parties WHERE version_id = v.id AND removed_at IS NULL) p ON true
GROUP BY 1, 2 ORDER BY 1, 2;
SELECT count(*) FILTER (WHERE approved_version_id IS NOT NULL) AS утверждённых,
       count(*) FILTER (WHERE approved_version_id IS NOT NULL AND working_version_id IS NOT NULL) AS на_пересмотре
FROM documents WHERE deleted_at IS NULL;
SELECT count(*) AS открытых_этапных, count(*) FILTER (WHERE document_state LIKE \$\$%:13\$\$) AS начальника_ИБ_на_13
FROM tasks WHERE document_reason = \$\$stage\$\$ AND completed_at IS NULL AND archived_at IS NULL AND deleted_at IS NULL;
SELECT count(*) AS категория_уже_есть FROM catalog_items
WHERE catalog_code = \$\$task_categories\$\$ AND deleted_at IS NULL AND lower(value) = \$\$контроль по документу\$\$;"'
```

- **Строк в `sessions`** получат две новые колонки. Ни одна сессия не закроется. Не стоп.
- **Администраторов** — у них после выкладки сессия 12 часов от входа. Не стоп.
- **Рабочие версии по этапам** — столько документов перейдут на новые этапы (таблица соответствия — выше). Не стоп.
- **Утверждённых и на пересмотре** — не меняются. Не стоп.
- **Открытых этапных задач** — задачи прежних этапов закроются системой при переносе. Задачи начальника ИБ на этапе 13 (их число — во втором столбце) сохраняются. Не стоп.
- **Категория «Контроль по документу» уже есть** (1) — она станет системной (запись в журнале). Не стоп.

### Откат на 1.9.0

Только код: `sed -i 's/^VERSION=.*/VERSION=1.9.0/' .env` и `docker compose up -d backend frontend`. База не восстанавливается: 1.9.0 новые колонки и таблицы не читает.
- Сессии снова завершаются через 30 минут без действий и через 12 часов — пользователи войдут заново.
- Утверждённые документы работают как прежде.
- Документы в работе (этапы 21–24) в 1.9.0 только показываются. Задачи контроля видны как задачи с неизвестным источником.
- Если документы в работе нужно двигать в 1.9.0 — **после** смены версии выполнить ручной обратный перенос (по желанию; одна транзакция, повторный запуск ничего не меняет). Перенос: 21 «Драфт» → 11, «на проверке у начальника ИБ» → 13, 22 → 14, 23 → 15, 24 → 16. При повторной выкладке 1.11.0 seed перенесёт их обратно.

```bash
docker compose exec -T db sh -c 'psql -U "$POSTGRES_USER" -d ibportal -v ON_ERROR_STOP=1' <<'SQL'
BEGIN;
CREATE TEMP TABLE rollback_1110 ON COMMIT DROP AS
SELECT v.id, v.document_id, v.no, v.round, v.stage, v.route_state, d.owner_id,
       CASE WHEN v.stage = 21 AND v.route_state = 'head_review' THEN 13
            WHEN v.stage = 21 THEN 11 WHEN v.stage = 22 THEN 14 WHEN v.stage = 23 THEN 15 ELSE 16 END AS to_stage
FROM document_versions v JOIN documents d ON d.working_version_id = v.id
WHERE v.stage BETWEEN 21 AND 24 AND v.approved_at IS NULL AND v.cancelled_at IS NULL;
INSERT INTO document_approvals (document_id, version_id, version_no, round, stage, to_stage, decision, comment, actor_id)
SELECT r.document_id, r.id, r.no, r.round, r.stage, r.to_stage, 'migrated',
       'Возвращён на маршрут 1.2.0 при откате: «' || CASE r.stage WHEN 21 THEN CASE WHEN r.route_state = 'head_review' THEN 'Драфт — На проверке у начальника ИБ' ELSE 'Драфт' END
         WHEN 22 THEN CASE WHEN r.route_state = 'head_recheck' THEN 'Согласование — На повторной проверке у начальника ИБ' ELSE 'Согласование' END
         WHEN 23 THEN 'Перевод' ELSE 'Утверждение' END || '» → «' || CASE r.to_stage WHEN 11 THEN 'Драфт' WHEN 13 THEN 'Согласование начальника ИБ'
         WHEN 14 THEN 'Согласование с ответственными лицами' WHEN 15 THEN 'Перевод' ELSE 'Подписание' END || '»', r.owner_id
FROM rollback_1110 r;
UPDATE document_versions v SET stage = r.to_stage, updated_at = now() FROM rollback_1110 r WHERE v.id = r.id;
UPDATE documents d SET version = d.version + 1, updated_at = now() FROM rollback_1110 r WHERE d.id = r.document_id;
INSERT INTO audit_log (user_id, action, entity, entity_id, diff)
SELECT NULL, 'document.route_rollback', 'document', NULL, jsonb_build_object('summary', 'Документы: возвращены на маршрут 1.2.0 при откате 1.11.0 → 1.10.0 — ' || count(*), 'moved', count(*))
FROM rollback_1110 HAVING count(*) > 0;
SELECT to_stage AS "на этап", count(*) AS "версий" FROM rollback_1110 GROUP BY to_stage ORDER BY to_stage;
COMMIT;
SQL
```

То же содержимое — `docs/rollback/1.11.0-documents-stages.sql` в репозитории. Проверено на репетиции 1.9.0 → 1.11.0 (`deploy/verification/1.11.0.md`, раздел «Путь 1.9.0 → 1.11.0»).
