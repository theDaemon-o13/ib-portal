### Уязвимости: что сделает шаг `migrate` (ADR-0029, ADR-0030)

- Миграция `20261030172054_vuln_groups_scans`: пять новых пустых таблиц раздела «Уязвимости». Существующие строки не меняются.
- Seed, один раз: справочник «Типы систем» (5 значений), группа «Без группы» с узлом «Из прежнего реестра», поля реестра уязвимостей «Срок из прежнего реестра» и «Продлено, дн.», правило «Срок устранения» с ними.
- Seed, **при каждом** `migrate`: записи реестра уязвимостей и отчёты сканера, у которых ещё нет узла, переносятся в «Без группы / Из прежнего реестра». При первом обновлении — весь реестр. Записям со сроком в новое поле «Срок из прежнего реестра» пишется их текущий срок по процедуре («Уведомлено ДИКТ» + дни по Критичности, с переносом на рабочий день, без решения п. 7.3). Остальные значения, номера записей и история не меняются; итоговый срок каждой записи остаётся прежним. Каждая запись — строка в журнале, плюс сводная строка `vuln.legacy.moved`. Отчёты становятся сканами «Без группы», переданными ИКТ в дату «Уведомлено ДИКТ».

### Уязвимости: сколько записей и отчётов перенесётся (до выкладки)

Запросы только читают базу (`BEGIN TRANSACTION READ ONLY`). Проверены на схеме 1.1.0 (миграции тега `v1.1.0`) с данными, загруженными кодом 1.1.0.

```bash
docker compose exec -T db sh -c 'psql -v ON_ERROR_STOP=1 -U "$POSTGRES_USER" -d ibportal' <<'SQL'
BEGIN TRANSACTION READ ONLY;
WITH reg AS (SELECT id FROM registers WHERE system_key = 'vulns'),
fld AS (SELECT system_key, id::text AS id FROM register_fields WHERE register_id = (SELECT id FROM reg) AND deleted_at IS NULL),
st AS (SELECT o.id::text AS id, o.is_closed FROM register_field_options o JOIN register_fields f ON f.id = o.field_id
       WHERE f.register_id = (SELECT id FROM reg) AND f.system_key = 'status'),
rec AS (
  SELECT r.deleted_at, r.archived_at,
         r."values" ->> (SELECT id FROM fld WHERE system_key = 'status') AS status_id,
         (r."values" ? (SELECT id FROM fld WHERE system_key = 'notified')
          AND r."values" ? (SELECT id FROM fld WHERE system_key = 'crit')) AS has_base,
         (r."values" ? (SELECT id FROM fld WHERE system_key = 'measures')
          AND r."values" ? (SELECT id FROM fld WHERE system_key = 'newDue')) AS has_73
  FROM register_records r WHERE r.register_id = (SELECT id FROM reg))
SELECT
  count(*)                                                                     AS records_total,
  count(*) FILTER (WHERE deleted_at IS NOT NULL)                               AS deleted,
  count(*) FILTER (WHERE deleted_at IS NULL AND archived_at IS NOT NULL)       AS archived,
  count(*) FILTER (WHERE deleted_at IS NULL AND archived_at IS NULL
                   AND NOT coalesce((SELECT is_closed FROM st WHERE st.id = status_id), false)) AS open,
  count(*) FILTER (WHERE deleted_at IS NULL AND has_base)                      AS legacy_due_to_write,
  count(*) FILTER (WHERE deleted_at IS NULL AND NOT has_base)                  AS without_deadline,
  count(*) FILTER (WHERE deleted_at IS NULL AND has_73)                        AS with_decision_7_3,
  (SELECT count(*) FROM scan_reports WHERE register_id = (SELECT id FROM reg))                              AS scan_reports,
  (SELECT count(*) FROM scan_reports WHERE register_id = (SELECT id FROM reg) AND archived_at IS NOT NULL)  AS scan_reports_archived,
  (SELECT count(*) FROM scan_hosts h JOIN scan_reports s ON s.id = h.report_id
    WHERE s.register_id = (SELECT id FROM reg))                                                             AS scan_hosts,
  (SELECT count(*) FROM register_imports WHERE register_id = (SELECT id FROM reg) AND file_id IS NOT NULL)  AS compare_files
FROM rec;

WITH reg AS (SELECT id FROM registers WHERE system_key = 'vulns'),
fld AS (SELECT system_key, id FROM register_fields WHERE register_id = (SELECT id FROM reg) AND deleted_at IS NULL),
k AS (
  SELECT r.number,
         lower(regexp_replace(btrim(o.label), '\s+', ' ', 'g')) || ' · '
           || lower(regexp_replace(btrim(r."values" ->> (SELECT id::text FROM fld WHERE system_key = 'cve')), '\s+', ' ', 'g')) AS key
  FROM register_records r
  JOIN register_field_options o ON o.id::text = r."values" ->> (SELECT id::text FROM fld WHERE system_key = 'pkg')
  WHERE r.register_id = (SELECT id FROM reg) AND r.deleted_at IS NULL
    AND r."values" ? (SELECT id::text FROM fld WHERE system_key = 'cve'))
SELECT key, count(*) AS records, string_agg(number::text, ', ' ORDER BY number) AS numbers
FROM k GROUP BY key HAVING count(*) > 1 ORDER BY count(*) DESC, key;
ROLLBACK;
SQL
```

Первый запрос — одна строка: `records_total` (всего записей, вместе с удалёнными и архивными), `deleted`, `archived`, `open` (не закрыты статусом и не в архиве), `legacy_due_to_write` (сколько записей получат «Срок из прежнего реестра»), `without_deadline` (без даты «Уведомлено ДИКТ» — срока нет и не будет), `with_decision_7_3`, `scan_reports`, `scan_reports_archived`, `scan_hosts`, `compare_files`. Второй — повторы ключа «пакет · идентификатор» среди неудалённых записей с номерами: такие записи остаются в «Без группы»; если перенести пару в один узел, вторая получит отказ «В узле уже есть …».

Числа запишите в журнал выкладок. В выводе `migrate` должна быть строка с теми же числами:
`Без группы: записей <records_total> (открытых <open>, со сроком <legacy_due_to_write>, без срока <without_deadline>, удалённых <deleted>), отчётов прежнего реестра <scan_reports> (хостов <scan_hosts>, в архиве <scan_reports_archived>), повторов ключа <строк во втором запросе>`.

Проверено (данные кодом 1.1.0: два отчёта образца, повторный импорт после «Устранена», удалённая и архивная записи, решение п. 7.3, ручные записи): 95 / 1 / 1 / 92 / 93 / 1 / 1 / 3 / 0 / 36 / 0, два повтора ключа; строка `migrate` — «записей 95 (открытых 92, со сроком 93, без срока 1, удалённых 1), отчётов прежнего реестра 3 (хостов 36, в архиве 0), повторов ключа 2»; итоговый срок всех 95 записей до и после обновления совпал. На dev-базе с 10 050 записями (из них 4541 удалённая) и 118 отчётами весь `migrate` с переносом занял около 16 с.

### Уязвимости: после `migrate`

```bash
docker compose exec -T db sh -c 'psql -v ON_ERROR_STOP=1 -U "$POSTGRES_USER" -d ibportal' <<'SQL'
BEGIN TRANSACTION READ ONLY;
SELECT (SELECT count(*) FROM vuln_records v JOIN vuln_nodes n ON n.id = v.node_id WHERE n.system_key = 'legacy') AS в_без_группы,
       (SELECT count(*) FROM vuln_scans WHERE legacy_report_id IS NOT NULL) AS сканов_прежнего_реестра,
       (SELECT count(*) FROM register_records r JOIN registers g ON g.id = r.register_id
          JOIN register_fields f ON f.register_id = g.id AND f.system_key = 'legacyDue'
         WHERE g.system_key = 'vulns' AND r.deleted_at IS NULL AND r."values" ? f.id::text) AS со_сроком_из_прежнего_реестра;
ROLLBACK;
SQL
```

Ожидается: `в_без_группы` = `records_total`, `сканов_прежнего_реестра` = `scan_reports`, `со_сроком_из_прежнего_реестра` = `legacy_due_to_write`. В проверке целостности — строки «у каждой записи реестра уязвимостей есть узел» и «есть «Без группы / Из прежнего реестра»».

### Уязвимости: повторная выкладка после отката

Перенос в «Без группы» выполняется при каждом `migrate`: записи и отчёты, которые 1.1.0–1.4.0 создадут после отката, при повторной выкладке 1.5.0 попадут в «Без группы» (их число — в той же строке вывода `migrate`; при выкладке без отката там нули). Записи, уже разложенные по узлам, не меняются.

### Откат

Два способа. **Правило выбора:** проблема найдена при проверке после выкладки, пользователи ещё не начали работу — способ 1. Проблема всплыла после начала работы — способ 2: данные пользователей важнее.

**Способ 1. Полный откат: резервная копия, сделанная перед `migrate` (шаг 3), и образы 1.1.0.** Состояние 1.1.0 полностью, ограничений нет. Данные, внесённые после обновления, теряются.

```bash
cd /srv/ibportal/deploy
sed -i 's/^VERSION=.*/VERSION=1.1.0/' .env      # сначала версия: restore.sh проверяет её по копии
./scripts/restore.sh <копия из шага 3>
docker compose up -d backend frontend
./scripts/smoke.sh
```

**Способ 2. Откат только кода на 1.1.0 при новой базе.** Данные сохраняются, всё восстанавливается повторной выкладкой 1.5.0.

```bash
cd /srv/ibportal/deploy
sed -i 's/^VERSION=.*/VERSION=1.1.0/' .env
docker compose up -d backend frontend
./scripts/smoke.sh
```

Ограничения способа 2 до повторной выкладки:

- **карточка документа, перенесённого на маршрут 11–16, отвечает 500** (дефект с 1.2.0: решения `migrated`, `moved`, `signed` вне схемы ответа 1.1.0). Это все документы с рабочей версией на момент обновления и все, что двигали после него. Список документов работает. Подписанные документы без рабочей версии seed не трогает; запуском это не проверялось;
- **согласование документов не работает**: документы на этапах 11–16 код 1.1.0 не двигает;
- **продления сроков не учитываются** (`vuln_extensions`, `vuln_extension_items`, «Продлено, дн.»): продлённые записи показаны по сроку без продления. Проверено: 29.10.2026 вместо 30.11.2026, после повторной выкладки снова 30.11.2026. Просрочка в таблице, на дашборде и мониторе считается по короткому сроку, правила п. 7.4 могут поставить задачи «просрочено» по таким записям;
- **группы, узлы и сканы не видны**, данные не теряются: записи видны одним реестром, в списке отчётов — только отчёты прежнего реестра;
- записи из сканов, не переданных ИКТ, остаются без срока: «Уведомлено ДИКТ» у них пусто, правила п. 7.4 по ним молчат;
- «Срок из прежнего реестра» не действует: срок считается от «Уведомлено ДИКТ», значение совпадает, пока не менялась Критичность;
- служебные поля «Уведомлено ДИКТ», «Срок из прежнего реестра», «Продлено, дн.» редактируемы в карточке и в обратном импорте Excel; правка «Продлено, дн.» после повторной выкладки станет расхождением в `check-integrity`;
- отчёт, загруженный на 1.1.0, ищет дубли по «CVE + пакет + отдел» среди всех записей: если один охват загружен в два узла, «Обнаружений» обновится только у первой записи. Новые записи и отчёты этого периода после повторной выкладки попадут в «Без группы»;
- файлы сканов и обоснований скачать может только загрузивший: код 1.1.0 не знает этих ссылок;
- колонки доски «Backlog», «Поставленные», «Выполнено» (5 колонок вместо 4) — задачи на месте;
- бывшие «Юристы» и «Правление» — в роли «Читатель документов» (для 1.1.0 — роль без прав);
- журнала, уведомлений, самооценки, отметки начальника ИБ, проверяющих нет; данные этих разделов остаются в базе.
