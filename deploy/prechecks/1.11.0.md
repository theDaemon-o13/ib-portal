Сервер работает на **1.10.0**. Если там версия старше, сначала выложите 1.10.0 по его RELEASE.md, затем 1.11.0.

**Выкладка — обязательно с `migrate`** (шаг 5 инструкции ниже). Миграций две: `documents_route_v3` (маршрут из 4 этапов — новые колонки и таблица) и `document_controls` (механизмы контроля и автоматизации — новые пустые таблицы). Существующие строки миграции не меняют. Документы в работе переносит на новый маршрут шаг seed `docs.route.v3` внутри того же `migrate`. Без `migrate` backend 1.11.0 не работает с документами — `smoke.sh --after` покажет «✗ … маршрут 1.11.0». Повторный запуск `migrate` безопасен.

### Что меняется для пользователей

- Маршрут документа — 4 этапа: «Драфт» (с проверкой начальника ИБ) → «Согласование» (с повторной проверкой после доработки) → «Перевод» (ссылки на переводы в OnlyOffice) → «Утверждение». Файлы (подписанный PDF, исходный Word, Word переводов) прикладываются только на «Утверждении».
- Документы в работе после выкладки — на новых этапах: «Драфт» и «Проверка сотрудниками» → «Драфт»; «Согласование начальника ИБ» → «Драфт — на проверке у начальника ИБ» (его задача сохраняется); «Ответственные лица» → «Согласование» (если все согласовали — «на повторной проверке»); «Перевод» → «Перевод» (ссылки на переводы автор добавит заново, прежние файлы — в «Файлах прежнего маршрута»); «Подписание» → «Утверждение». Утверждённые документы не меняются.
- «Документы» — подменю «В работе» и «Утверждённые» (реестр действующих документов с выгрузкой в Excel).
- У утверждённого документа — вкладки «Механизмы контроля» и «Автоматизации» (периодические задачи по механизмам, категория задач «Контроль по документу»).

### До выкладки (на работающей 1.10.0, до `backup.sh`)

Запросы только читают базу. Результаты запишите в журнал выкладок.

```bash
docker compose exec -T db sh -c 'psql -U "$POSTGRES_USER" -d ibportal -c "
SELECT v.stage AS этап,
       CASE WHEN v.stage = 14 AND p.cnt > 0 AND p.pending = 0 THEN \$\$все лица согласовали\$\$ WHEN v.stage = 14 THEN \$\$лица не все\$\$ ELSE \$\$\$\$ END AS уточнение,
       count(*) FILTER (WHERE d.deleted_at IS NULL AND d.archived_at IS NULL) AS активных,
       count(*) FILTER (WHERE d.deleted_at IS NULL AND d.archived_at IS NOT NULL) AS в_архиве,
       count(*) FILTER (WHERE d.deleted_at IS NOT NULL) AS удалённых
FROM documents d JOIN document_versions v ON v.id = d.working_version_id AND v.cancelled_at IS NULL
LEFT JOIN LATERAL (SELECT count(*) cnt, count(*) FILTER (WHERE approved_at IS NULL) pending
                   FROM document_parties WHERE version_id = v.id AND removed_at IS NULL) p ON true
GROUP BY 1, 2 ORDER BY 1, 2;
SELECT count(*) FILTER (WHERE approved_version_id IS NOT NULL) AS утверждённых,
       count(*) FILTER (WHERE approved_version_id IS NOT NULL AND working_version_id IS NOT NULL) AS на_пересмотре
FROM documents WHERE deleted_at IS NULL;
SELECT count(*) AS открытых_этапных, count(*) FILTER (WHERE document_state LIKE \$\$%:13\$\$) AS начальника_ИБ_на_13
FROM tasks WHERE document_reason = \$\$stage\$\$ AND completed_at IS NULL AND archived_at IS NULL AND deleted_at IS NULL;
SELECT count(*) AS категория_уже_есть FROM catalog_items
WHERE catalog_code = \$\$task_categories\$\$ AND deleted_at IS NULL AND lower(value) = \$\$контроль по документу\$\$;"'
```

- **Рабочие версии по этапам** — столько документов перейдут на новые этапы (таблица соответствия — выше). Не стоп.
- **Утверждённых и на пересмотре** — не меняются. Не стоп.
- **Открытых этапных задач** — задачи прежних этапов закроются системой при переносе, кроме задач начальника ИБ на этапе 13 (их число — во втором столбце): они сохраняются. Не стоп.
- **Категория «Контроль по документу» уже есть** (1) — она станет системной (запись в журнале). Не стоп.

### После `migrate`

1. **Вывод `migrate`.** Применены миграции `20261105160000_documents_route_v3` и `20261106053127_document_controls`; строка «Документы 1.11.0: на маршрут из 4 этапов перенесено N (…); задач начальника ИБ сохранено M» (N — сумма активных, архивных и удалённых рабочих версий из первого запроса; если рабочих версий не было — строки нет); «Создано системное значение «Контроль по документу»» (или «…стало системным»); «Seed выполнен: …».
2. **`./scripts/smoke.sh --after`.** Строки «✓ … маршрут 1.11.0 …», «✓ механизмы контроля …», «✓ категория задач «Контроль по документу»», «✓ рабочих версий на этапах 11–16 нет», затем «Smoke-проверка пройдена».
3. **Проверка целостности.** `docker compose run --rm -T --no-deps backend node dist/scripts/check-integrity.js` → «Целостность в порядке» (строки «триггеры маршрута 1.11.0», «механизмов контроля», «запуски контроля»).
4. **Вручную:** «Документы» → «Утверждённые» — реестр открывается, «Выгрузить в Excel» скачивает файл; карточка утверждённого документа — вкладки «Механизмы контроля» и «Автоматизации». «Настройки → Параметры портала → Документы: сроки этапов» — пять полей (драфт, проверка, повторная проверка, перевод, утверждение).

### После выкладки — сообщить сотрудникам ИБ

- Авторам документов, которые были на «Переводе»: добавить ссылки на переводы в OnlyOffice (прежние файлы перевода остались в карточке).
- Документы, которые были на «Подписании», — на «Утверждении»: подписанный PDF и исходный Word загружаются в блок «Файлы утверждения».

### Откат на 1.10.0

Только код: `sed -i 's/^VERSION=.*/VERSION=1.10.0/' .env` и `docker compose up -d backend frontend`. База не восстанавливается: 1.10.0 новые колонки и таблицы не читает.
- Утверждённые документы работают как прежде (пересмотр, задачи за 30 дней).
- Документы в работе (этапы 21–24) в 1.10.0 только показываются: этап — «этап 21» … «этап 24», «Сейчас у» пусто, действий нет. Задачи контроля видны как задачи с источником «другое».
- Если документы в работе нужно двигать в 1.10.0 — по желанию, **после** смены версии выполнить ручной обратный перенос (одна транзакция; повторный запуск ничего не меняет; новые колонки не трогает): 21 «Драфт» → 11, «на проверке у начальника ИБ» → 13, 22 → 14, 23 → 15, 24 → 16. При повторной выкладке 1.11.0 seed перенесёт их обратно.

```bash
docker compose exec -T db sh -c 'psql -U "$POSTGRES_USER" -d ibportal -v ON_ERROR_STOP=1' <<'SQL'
BEGIN;
CREATE TEMP TABLE rollback_1110 ON COMMIT DROP AS
SELECT v.id, v.document_id, v.no, v.round, v.stage, v.route_state, d.owner_id,
       CASE WHEN v.stage = 21 AND v.route_state = 'head_review' THEN 13
            WHEN v.stage = 21 THEN 11 WHEN v.stage = 22 THEN 14 WHEN v.stage = 23 THEN 15 ELSE 16 END AS to_stage
FROM document_versions v JOIN documents d ON d.working_version_id = v.id
WHERE v.stage BETWEEN 21 AND 24 AND v.approved_at IS NULL AND v.cancelled_at IS NULL;
INSERT INTO document_approvals (document_id, version_id, version_no, round, stage, to_stage, decision, comment, actor_id)
SELECT r.document_id, r.id, r.no, r.round, r.stage, r.to_stage, 'migrated',
       'Возвращён на маршрут 1.2.0 при откате: «' || CASE r.stage WHEN 21 THEN CASE WHEN r.route_state = 'head_review' THEN 'Драфт — На проверке у начальника ИБ' ELSE 'Драфт' END
         WHEN 22 THEN CASE WHEN r.route_state = 'head_recheck' THEN 'Согласование — На повторной проверке у начальника ИБ' ELSE 'Согласование' END
         WHEN 23 THEN 'Перевод' ELSE 'Утверждение' END || '» → «' || CASE r.to_stage WHEN 11 THEN 'Драфт' WHEN 13 THEN 'Согласование начальника ИБ'
         WHEN 14 THEN 'Согласование с ответственными лицами' WHEN 15 THEN 'Перевод' ELSE 'Подписание' END || '»', r.owner_id
FROM rollback_1110 r;
UPDATE document_versions v SET stage = r.to_stage, updated_at = now() FROM rollback_1110 r WHERE v.id = r.id;
UPDATE documents d SET version = d.version + 1, updated_at = now() FROM rollback_1110 r WHERE d.id = r.document_id;
INSERT INTO audit_log (user_id, action, entity, entity_id, diff)
SELECT NULL, 'document.route_rollback', 'document', NULL, jsonb_build_object('summary', 'Документы: возвращены на маршрут 1.2.0 при откате 1.11.0 → 1.10.0 — ' || count(*), 'moved', count(*))
FROM rollback_1110 HAVING count(*) > 0;
SELECT to_stage AS "на этап", count(*) AS "версий" FROM rollback_1110 GROUP BY to_stage ORDER BY to_stage;
COMMIT;
SQL
```
