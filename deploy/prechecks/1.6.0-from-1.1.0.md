### Что сделает шаг `migrate`

Сначала все миграции 1.2.0, 1.3.0, 1.4.0 и 1.5.0 (в 1.6.0 миграций нет; список и «Влияние на данные» — в разделе «Миграции базы данных»), затем одной транзакцией шаги seed, в таком порядке:

1. **Коды прав** — 20 кодов; новые с 1.1.0: `tasks.assign`, `tasks.review`, `tasks.status.override`, `tasks.report`, `docs.delete`, `history.view`, `audit.view` (1.2.0), `assessment.manage` (1.3.0), `vulns.deadlines` (1.5.0: ни одной роли не выдаётся). Коды `docs.approve.legal` и `docs.approve.board` выведены из обращения (строки в базе остаются).
2. **Системные роли** — создаются без пользователей: «Читатель документов» (1.2.0, без прав), «Самооценка» (1.3.0, только `assessment.manage`), «SOC» (1.4.0, права «Сотрудника ИБ»). Если своя роль с таким названием уже есть — `migrate` останавливается, ничего не применяется (пункт 1 «До выкладки»). Существующие роли не перезаписываются; «Юрист» и «Правление» остаются строками без пользователей.
3. **Права ролям, один раз** (`rbac.permissions.v1_2`): «Начальник ИБ» ← `tasks.assign`, `tasks.review`, `tasks.status.override`, `tasks.report`, `docs.delete`, `history.view`, `audit.view`; «Супер-администратор» ← `history.view`, `audit.view`. Право «Документы: начальник ИБ» у роли остаётся, но с 1.4.0 не используется (этапы начальника ИБ — по отметке у пользователя, п. 3 «После `migrate`»).
4. **«Юрист» и «Правление» → «Читатель документов»** (при каждом `migrate`): все их пользователи переходят в новую роль, прежняя снимается, учётные записи не отключаются.
5. **Справочники**: колонка доски «Поставленные» и признаки комментария у колонок.
6. **Задачи, один раз** (`tasks.process.v1_2`): колонки Backlog → Поставленные → В работе → На проверке → Выполнено; «Новые» → «Backlog», «Готово» → «Выполнено» (если администратор их не переименовывал); задачи «Новые» с исполнителем (и архивные) → «Поставленные». При каждом `migrate` — выравнивание открытых задач по исполнителю.
7. **Проверяющие задач, один раз** (`tasks.reviewer.v1_4`): задачам «На проверке» ставится проверяющий — ближний руководитель исполнителя. На 1.1.0 руководителей у пользователей нет (колонка появляется этим же `migrate` пустой), поэтому **проверяющего не получит ни одна задача**: все задачи «На проверке» остаются на правилах до 1.4.0 — принимает держатель «Задачи: проверка» (роль «Начальник ИБ» после шага 3). Новым задачам проверяющий назначается при отправке, когда у исполнителей заведён руководитель (п. 3 «После `migrate`»).
8. **Документы** (при каждом `migrate`): рабочие версии переходят на маршрут 1.2.0 — этап 0 «Автор» → 11 «Драфт», 1 «Начальник ИБ» → 13 «Согласование начальника ИБ», 2 и 3 → 14 «Согласование с ответственными лицами». В истории — решение «Система». Утверждённые версии не меняются.
9. **Самооценка, один раз**: методика `cyber-express-v1` версии 1 и подпись презентации.
10. **Уязвимости, один раз** (1.5.0): поля реестра «Срок из прежнего реестра» и «Продлено, дн.» и правило «Срок устранения» с ними; справочник «Типы систем» (5 значений; удалённое администратором не восстанавливается); группа «Без группы» с узлом «Из прежнего реестра».
11. **Уязвимости, при каждом `migrate`** (1.5.0): записи реестра уязвимостей (с архивными и удалёнными) и отчёты сканера без узла — в «Без группы / Из прежнего реестра». При этом обновлении — весь реестр. Записям со сроком в новое поле пишется текущий срок по процедуре («Уведомлено ДИКТ» + дни по Критичности, с переносом на рабочий день, без решения п. 7.3). Остальные значения, номера и история не меняются, итоговый срок каждой записи остаётся прежним. По записи — строка журнала, плюс сводная `vuln.legacy.moved`. Отчёты становятся сканами, переданными ИКТ в дату «Уведомлено ДИКТ».

12. **Реестр активов, один раз** (1.6.0): реестры «Сервисы», «Компоненты» и «Хосты» без записей, метка «Активы», напоминание о пересмотре, поле «Сервис» у реестра инцидентов. В выводе: «Системные реестры «Сервисы», «Компоненты», «Хосты», метка «Активы»…».
13. **«Типы систем», один раз** (1.6.0): профили Windows, Linux, PostgreSQL, Website, Docker. Данные не меняются.

Таблица переводов создаётся этим же `migrate` пустой — заполнение имени переводчика (миграция `…_translation_translator_name`) затрагивает 0 строк. Таблицы раздела «Уязвимости» создаются пустыми.

После первого часового прогона по задачам, уже просроченным к этому моменту, каждый получатель получит одно сводное уведомление «У вас N просроченных задач» (пункт 4 «До выкладки»).

SELECT key, count(*) AS records, string_agg(number::text, ', ' ORDER BY number) AS numbers
FROM k GROUP BY key HAVING count(*) > 1 ORDER BY count(*) DESC, key;

7. **Группы и разнесение «Без группы»**, раздел «Уязвимости»: при необходимости поправить справочник «Типы систем»; создать группы — сервисы и подразделения с типами систем (право «Реестры: создание и настройка полей»); открыть «Без группы / Из прежнего реестра» и «Перенести» или «Перенести выбранные» записи по узлам (право «Записи реестров: добавление и правка»). Срок сохраняется. Повторы ключа из пункта 7 «До выкладки» в один узел не перенесутся. Новые сканы загружаются только в узел группы; срок новых записей пойдёт от «Передать ИКТ» на экране скана. Не перенесённые записи продолжают работать: срок и уведомления идут.

**4. Самооценка: проверка владельцем после выкладки.** Под пользователем с ролью «Самооценка»: пункт меню «Самооценка» → «Новая оценка» → «Импорт Excel» исходного чек-листа — предпросмотр «Найдено разделов: 24 из 24», после применения 34 из 96, «Цифровая гигиена». Под другими пользователями пункта нет.

**5. Просмотр файлов документа.** Документ с PDF → щелчок по имени файла → окно на весь экран, страница нарисована, ← → листают, Esc закрывает; в консоли браузера (F12) нет сообщений `Refused to …` (Content-Security-Policy). ### После выкладки: до создания первой группы

Обязательный шаг. На сервере узлов с прежними типами нет, поэтому прежние типы сразу убираем из выбора: иначе группа, созданная с типом «Серверы», будет требовать подтверждение на каждом скане Windows и Linux.

В «Настройки → Справочники → Типы систем» отправьте в архив: **Рабочие станции, Серверы, БД, Сетевое оборудование, Веб-приложения**. Останутся Windows, Linux, PostgreSQL, Website, Docker. Если узел всё же создан с прежним типом, откройте его и нажмите «Сменить тип»: реестр и сканы останутся у узла, значение освободится для архива.
