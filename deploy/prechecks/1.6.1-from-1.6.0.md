Сервер работает на **1.6.0**. Если на сервере ещё 1.1.0 — сначала выложите 1.6.0 по его RELEASE.md (предпроверки 1.6.0 — для схемы 1.1.0), затем 1.6.1. Каждый запрос ниже только читает базу.

### Что сделает шаг `migrate`

1. **Миграция `20261102120130_soft_delete_trash`**: пустая таблица `deletions` (корзина), новые колонки `deleted_at`/`deletion_id` — NULL у всех строк, частичные уникальные индексы названий реестров и групп и «тип в группе». Существующие строки не меняются.
2. **Коды прав** — 21 код: новый `data.delete` «Удаление данных». Ни одной роли, в том числе «Супер-администратору», не выдаётся.
3. **«Компоненты», один раз** (`system.register.assets.components_instance.v1`): поле «Экземпляр» становится заголовком; ключ и заголовок существующих записей пересчитываются по правилу «Компонент / Продукт / Среда / IP:порт» (запись в журнал на каждую). Если новые ключи двух неудалённых записей совпадут — `migrate` остановится со списком «ключ — номера записей». Seed — одна транзакция: **ни один его шаг не применится**. Миграция к этому моменту уже применена; она только добавляет пустую таблицу и колонки, 1.6.0 с ней работает. Портал не запускайте новой версией, пока `migrate` не пройдёт. В выводе: «Компоненты»: заголовок «Экземпляр», ключ … — пересчитано записей N из M».

### До выкладки (на работающей 1.6.0, до `backup.sh`)

**1. Сколько записей «Компонентов» пересчитает seed.**

```bash
docker compose exec -T db sh -c 'psql -U "$POSTGRES_USER" -d ibportal -c "
SELECT count(*) FILTER (WHERE r.deleted_at IS NULL) AS действующих, count(*) AS всего
FROM register_records r JOIN registers g ON g.id = r.register_id WHERE g.system_key = \$\$asset_components\$\$;"'
```

Ожидается **0 / 0** (реестр сервисов на проде ещё не загружали). Не ноль — seed пересчитает ключи; совпадения, если будут, `migrate` покажет списком: удалите повтор в реестре «Компоненты» (или в файле реестра сервисов) и повторите `migrate`.

**2. Нет ли своей роли с правом, похожим на новое** — не нужно: код `data.delete` новый, роли не меняются.

### После `migrate`

**1. Вывод seed**: «Seed выполнен: прав 21, …» и строка «Компоненты» (п. 3 выше; при 0 записей — «пересчитано записей 0 из 0»).

**2. Проверка целостности**: «Целостность в порядке»; среди строк — «у удалённой группы уязвимостей нет действующих типов систем», «восстановленные удаления ничего не скрывают (корзина)».

**3. Действие владельца — назначить право «Удаление данных»** нужным ролям: «Настройки → Пользователи и роли» → матрица → строка «Удаление данных». Право удаляет реестры, группы и типы систем в «Уязвимостях» и записи уязвимостей (мягко, в корзину). Без него кнопок удаления в «Уязвимостях» нет. Восстанавливает из корзины только «Супер-администратор». Результат — в журнал выкладок.

**4. Проверка в интерфейсе**: «Настройки → Корзина» открывается (пусто). Если в «Без группы» записей не осталось, её нет в дереве, а на «Все группы» есть «Архив сканов прежнего реестра».

### Откат на 1.6.0

**Способ 2 (только код, база 1.6.1)** — совместим: 1.6.0 не читает новые колонки и таблицу. Ограничения (приняты владельцем):
- реестры, группы и типы систем, удалённые в 1.6.1, после отката **видны снова, пустые** (их записи у 1.6.0 тоже скрыты);
- поле «Экземпляр» остаётся заголовком «Компонентов», ключи — нового вида: **реестр сервисов после отката не загружать** (1.6.0 посчитает ключ по-старому и заведёт дубли);
- код права `data.delete` остаётся строкой в матрице, 1.6.0 его не проверяет.

Повторная выкладка 1.6.1 после отката: однократный шаг «Компонентов» второй раз не выполняется.

**Способ 1 (резервная копия перед `migrate` и образы 1.6.0)** — состояние 1.6.0 полностью; данные после обновления теряются.
